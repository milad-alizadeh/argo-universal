# Storybook

Read [Testing seams](testing-seams.md) for fixture boundaries, wrapper scope and what each test proves. [ADR-0021](../adr/0021-storybook-renders-views-from-props.md) owns Storybook's data boundary. App E2E, not Storybook, proves that a screen is wired.

- Presentation: `*.stories.tsx` renders the actual component for people to inspect and use. Name stories for visible states or experiences, not a prop inventory. A file with one story names it after the component (`name: 'Button'`) so the sidebar shows one entry.
- Views, not screens: a connected screen is a thin shell that passes tRPC data to its view, and stories render the view. Every connected screen's view has a `<view-name>.stories.tsx` file, titled `Screens/<ScreenName>` so story ids stay, showing the complete normal view at the full available viewport. Its loading, empty, error and disconnected states are props stories too. Child stories do not replace it. `parameters.screenPreview` fills the viewport; use it for views, shells and interactive lists. A section that embeds a connected screen takes it as a slot, and its story passes a view.
- Fixtures are props: a story passes plain typed props fixtures and callback spies. No story imports tRPC, TanStack Query, the Connection's tRPC client or a data hook; lint blocks them. A fixture used by one story lives beside that story; `@repo/client/mocks` holds only shared fixtures, and the harness comes from `@repo/client/storybook` (ADR-0021). Feed props come from recordings through the real converter.
- Uniqueness: present each distinct result once. Identical appearance and behavior make stories duplicates even when props differ; loading, empty or error stories must visibly differ from the normal one.
- Ownership: child states belong in child stories. A parent may contain them but gets no story or variation for a covered child state: selected SessionRow coverage rules out selected-row SessionsList and SessionsScreen showcases.
- Callbacks: a view's callbacks are spies. Function-only cases such as `onSearch`, `onSelect`, and `onProjectSettings` belong in functionality tests. Passing a function or logging an action does not earn a presentation story.
- Comparisons: use shared `Variation` and `Variations` helpers for distinct component states. Use viewport and theme controls for phone, desktop, light, and dark instead of multiplying presentation stories.
- Interaction: use existing product controls and visibly update the UI. Search filters; Project + inserts a Session. Pagination starts with enough rows to scroll, shows temporary loading, appends rows, and stops at the limit. Use valid product states.
- Wrappers: provide required context and realistic layout constraints, with no padding, surface or sizing that distorts the component's product appearance or scrolling.
- Isolation: a story's result never depends on which story ran before it. Reset story state between visits; clean up timers, subscriptions and mocks. `apps/storybook/vitest.setup.ts` restores the viewport before each test.
- Data: stable mock IDs, dates and ordering, so interactive changes are reproducible.
- Platforms: share presentation stories and mock data across web and iOS. Check both previews when changing shared UI; keep intentional platform differences.
- Native drawings: there is no native CI (ADR-0011), so a primitive's iOS and Android drawings are checked in the iOS and Android Storybook previews, or, where no Android preview exists, by the PR evidence table of the parent spec's decision 14 (the PR says which). Each primitive has one `Variations` presentation story, not one story per platform.
- Native headers: a phone page's header comes from its section Stack or Drawer options, which no story renders. A view built on the kit `Page` needs nothing: with no navigator, Page draws its own heading, search and Actions. Other views that need the narrow web header pass `ScreenHeaderMock` (or `mockHeader`) into their `renderHeader` slot. Check iOS and Android headers in the real App on a simulator or emulator, not in the on-device Storybook, whose pages sit under its own hidden route.
- Discovery: Storybook previews load presentation stories only. Vitest also loads test-only stories, whose static browser imports need its runner.
- Titles: the folder decides the group, and `node tools/check-story-titles.mts` (in `pnpm quality`) enforces it. `lib/generic/primitives` → `Design System/Primitives/<Name>`; other `lib/generic` → `Design System/<Name>`; `lib/product` → `Shared/<Name>`; a feature's components → `<Feature>/<Name>`; screen views → `Screens/<Section>/<visible page title>`; `*.test.stories.tsx` → `Tests/…`. Only a `*-view` or `*-page` story or a story in `screens/` may use `Screens/`. Never start a new top-level group: the check fails a story in any other folder. It checks the group only, not the `<Section>/<visible page title>` shape.
- Tests: `*.test.stories.tsx`, titled `Tests/<ComponentName>`, uses browser play functions for behaviour, content and accessibility assertions; tests never assert appearance ([testing seams](testing-seams.md#review-each-tests-claim)). Await observable asynchronous states. Plain Vitest tests non-UI code only.
  - A play function that clicks, types or selects runs at one viewport for one Agent. Make one story per viewport and Agent with a file-local factory, as `conflict(width)` in `permission-request.test.stories.tsx` does, reusing `settleViewport` and `layoutWidths` from the Storybook harness.
  - Take expected facts from the story's own recorded catalog, independently of the production calculation under test. State what a catalog must contain in one module-level check that throws "Recorded catalog needs …".
  - Assert absence as well as presence; never guard an assertion with `if (found)`.
- SettingsList: keep one interactive `Settings` presentation story; clicking its rows demonstrates selection.
- SF Symbols on a Mac: a browser Storybook draws Material Symbols, since only macOS can draw SF Symbols. Run `pnpm storybook:mac [port]` (port 6006 by default) to see the icons the macOS desktop app draws: it attaches to the Storybook on that port, or starts one, and opens it in an Electron window with the desktop app's preload, whose bridge the preview iframe reads through `window.parent` (`apps/desktop/scripts/storybook-mac.mts`). It is a local development tool only: Apple's licence keeps SF Symbols to Apple platforms (ADR-0019), so macOS draws each symbol at runtime, and no SF image reaches the web build, a static Storybook build or any packaged app.
