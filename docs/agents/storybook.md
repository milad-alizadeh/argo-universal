# Storybook

Storybook is the source of truth for built UI: a component's states, its platforms and its appearance are whatever its stories show. A design in Paper leads up to that story and is deleted once the component ships (`paper.md`).

[ADR-0021](../adr/0021-storybook-renders-views-from-props.md) owns Storybook's data boundary. App E2E, not Storybook, proves that a screen is wired.

For side-by-side previews, run `pnpm dev:storybook:all`. It starts web Storybook, opens it in the browser, then starts Expo and opens `/storybook` in the iOS Simulator and Android Emulator apps. Selecting a story in the browser selects the same shared story on the devices. The web addon serves a local WebSocket on port 7007; the launcher supplies Android Emulator's host address while iOS Simulator uses loopback. Interactions are exercised separately on each platform. A native development build must already be installed; rebuild it after native dependency changes. To run one platform manually, start `pnpm dev:storybook` first, then `pnpm --filter @repo/universal-app exec expo start --ios` or `EXPO_PUBLIC_STORYBOOK_ANDROID_WS_HOST=10.0.2.2 pnpm --filter @repo/universal-app exec expo start --android`.

Concurrent native QA sessions need a separate Storybook sync channel as well as separate web and Metro ports. Set `EXPO_PUBLIC_STORYBOOK_WS_PORT` to one free local port in both the web Storybook and Expo commands for each session; the shared default remains 7007. Start Expo without a device flag so it starts Metro without selecting a booted device. For example, a session can use:

```sh
EXPO_PUBLIC_STORYBOOK_WS_PORT=7011 pnpm --filter @repo/storybook exec storybook dev -p 6007 --no-open
EXPO_PUBLIC_STORYBOOK_WS_PORT=7011 pnpm --filter @repo/universal-app exec expo start --port 8082
EXPO_PUBLIC_STORYBOOK_WS_PORT=7011 EXPO_PUBLIC_STORYBOOK_ANDROID_WS_HOST=10.0.2.2 pnpm --filter @repo/universal-app exec expo start --port 8082
```

Copy the development-client URL printed by Expo and open it on a disposable device you selected by UDID or serial. After the bundle loads, open the Storybook route on that same device:

```sh
# iOS Simulator: set OWNED_UDID and EXPO_DEV_URL to the selected device and Expo's printed URL.
xcrun simctl openurl "$OWNED_UDID" "$EXPO_DEV_URL"
xcrun simctl openurl "$OWNED_UDID" argo://storybook

# Android Emulator: set OWNED_SERIAL and EXPO_DEV_URL to the selected device and Expo's printed URL.
adb -s "$OWNED_SERIAL" shell am start -a android.intent.action.VIEW -d "$EXPO_DEV_URL" dev.argo.app
adb -s "$OWNED_SERIAL" shell am start -a android.intent.action.VIEW -d argo://storybook dev.argo.app
```

Use a different sync, web and Metro port in the other checkout, such as 7012, 6008 and 8083. Keep each native app's host pointed at its own Storybook server: iOS Simulator uses `127.0.0.1`, and Android Emulator uses `10.0.2.2` via `EXPO_PUBLIC_STORYBOOK_ANDROID_WS_HOST`. The sync port must match between that session's web addon and native app; a dedicated Metro port alone still leaves both native apps on the default shared port 7007. Devices intentionally share story selection when they connect to the same sync port. `pnpm dev:storybook:all` keeps its default web and Metro ports, so use the separate web and Expo commands above when those ports are already in use.

## Static build

`pnpm --filter @repo/storybook build-storybook` (`storybook build`) writes the static Storybook to `apps/storybook/storybook-static`. It is what Chromatic publishes and what a deployable preview serves; it also proves the production pass, which resolves modules differently from the dev server. Skia's web entry needs the `skiaAssetRegistry` resolver (`apps/storybook/.storybook/expo-web-imports.ts`, registered in `main.ts`) to build.

## Stories inside a navigation stack

`withStack(pages?)` from `#story-stack` (`packages/kit/src/story-stack/`) is a story decorator: the story is the root screen of a real expo-router `Stack`, and `pages` maps a name to a component the story can push. Inside any page, `useStackPush()` returns `push(name)`; a pushed page gets Back from the stack's header, and `useRouter().back()` serves a wide window's own Back (`onBack`). Examples: `Design System/Primitives/Scaffolds/Screen/Stack` (`screen-stack.stories.tsx`, pages in `screen-stack.mocks.tsx`), tested in `screen-stack.test.stories.tsx`.

```tsx
export const PushedScreen: Story = {
  decorators: [withStack({ detail: DetailScreen })],
  render: () => <ListScreen />, // calls useStackPush()('detail')
};
```

- Web: the stack is expo-router's own, held in memory through `ExpoRoot`'s `context`. A phone width draws the stack header with the Screen's title, header Actions and overflow menu; a wide window draws the Screen's own heading, as the App does. The router writes its path into the preview's address bar and the decorator restores the story's address when it unmounts, so a pushed page shows `/detail` there until you leave the story.
- iOS and Android (on-device Storybook): the app already runs the one expo-router store, so a second router cannot start inside it. The decorator instead draws an "Open stack" button; it pushes the dev route `(dev)/story-stack/[story]` (`apps/universal-app/src/app/(dev)/story-stack/`), a real native Stack that renders the story and its pages from a registry (`stack-registry.ts`). The native header is therefore the App's: iOS toolbar items, Android top app bar. Back from the root page returns to Storybook.
- The pages render outside Storybook's tree on a phone, so they get the App's providers, not the preview's decorators; a page that needs fixtures passes them itself.
- Not for `ListDetail` or other wide-only layouts: use a plain story.

## The shape of a story file

Run `pnpm new:story <component-path>`, then edit what it wrote to match [storybook-template.md](storybook-template.md). [ADR-0040](../adr/0040-one-shape-for-a-story.md) records the rules and why.

## Rules the template does not show

- Views, not screens: a connected screen is a thin shell that passes tRPC data to its view, and stories render the view. Every connected screen's view has a `<view-name>.stories.tsx` file, titled `Screens/<Section>/<page title>` so story ids stay, showing the complete normal view at the full available viewport. Its loading, empty, error and disconnected states are props stories too. Child stories do not replace it. `parameters.screenPreview` fills the viewport; use it for views, shells and interactive lists. A section that embeds a connected screen takes it as a slot, and its story passes a view.
- Fixtures are props: a story passes plain typed props fixtures and callback spies. No story imports tRPC, TanStack Query, the Connection's tRPC client or a data hook; lint blocks them. A fixture used by one story lives beside that story: a component's states are exported from `<component>-fixtures.ts` in its own folder, one export per story and named as the story is, and its own stories read `args: <fixture>` (ADR-0040 item 10). Callbacks stay in the story file. `@repo/client/mocks` and `@repo/kit/mocks` hold only shared fixtures, each beside the package whose stories use them, and the harness comes from `@repo/client/storybook` (ADR-0021). Feed props come from recordings through the real converter.
- Primitive copy: kit primitive stories in `@repo/kit` use placeholder text, not Sessions, Projects or Agents copy, so product copy changes never reach the kit.
- Callbacks: a view's callbacks are spies. Function-only cases such as `onSearch`, `onSelect`, and `onProjectSettings` belong in functionality tests; passing a function or logging an action does not earn a presentation story. Loading, empty or error stories must visibly differ from the normal one.
- Uniqueness: present each distinct result once. Identical appearance and behavior make stories duplicates even when props differ.
- Interaction: use existing product controls and visibly update the UI. Search filters; Project + inserts a Session. Pagination starts with enough rows to scroll, shows temporary loading, appends rows, and stops at the limit. Use valid product states.
- Wrappers: provide required context and realistic layout constraints, with no padding, surface or sizing that distorts the component's product appearance or scrolling.
- Isolation: a story's result never depends on which story ran before it. Reset story state between visits; clean up timers, subscriptions and mocks. `apps/storybook/vitest.setup.ts` restores the viewport before each test.
- Failure probe: `apps/storybook/shard-probe.ts` records what the page saw around each story and prints it only when a story fails, as a `[shard-probe]` block in the shard's log. It names the page and the stories that ran before in it, where the last trusted pointer event left the Playwright mouse (the mouse is page-level and outlives a story file's iframe), the animations and pending frames at story start, and a timeline of pointer, focus and removal events against the story's own synthetic ones. It asserts nothing and sets no wait, so read it before guessing why a story failed only in CI (#1590, #1625, #1626).
- Data: stable mock IDs, dates and ordering, so interactive changes are reproducible.
- Platforms: share presentation stories and mock data across web and iOS. Check both previews when changing shared UI; keep intentional platform differences.
- Native drawings: there is no native CI (ADR-0011), so a primitive's iOS and Android drawings are checked in the iOS and Android Storybook previews, or, where no Android preview exists, by the PR evidence table of the parent spec's decision 14 (the PR says which). Platforms share one story per state, not one story per platform.
- Native headers: a view built on the kit `Screen` with no navigator draws its own heading, search and Actions, because the preview turns the Screen's navigator off (`ScreenNavigationEnabled`). To see the header a navigator draws, or a push with Back, use `withStack` (next section). Check iOS and Android headers in the real App on a simulator or emulator when a change touches the native header code.
- Local runs: one Storybook or Playwright browser suite runs at a time on a Mac. A run waits for `@repo/browser-suite-lock`, which holds a localhost port until the suite ends or dies, and prints which checkout holds it. CI and watch runs, including Storybook's test widget, skip the lock. Locally Storybook opens fewer browser pages than in CI (`apps/storybook/vitest.config.ts`); `VITEST_MAX_WORKERS` overrides both.
- SettingsListView: keep one interactive `Settings` presentation story; clicking its rows demonstrates selection.
- Discovery: Storybook previews load presentation stories only. Vitest also loads test-only stories, whose static browser imports need its runner.
- Docs pages: autodocs is on for every story file, from `tags: ['autodocs']` in `apps/storybook/.storybook/preview.tsx`. A file's Docs page renders its stories in order above a props table, so a presentation story file sets `component:` in its meta and that page is the component's one page. A file whose subject has no props component — an imperative API such as Toast, or a view whose stories pass a wrapper arg — opts out with `tags: ['!autodocs']` and says in a comment why. Test stories need no opt-out: the preview's glob loads presentation stories only, so `Tests/` has no Docs pages.
- Kit props tables: a kit component's props come from its Contracts schema, so its story meta sets `argTypes: kitArgTypes('<Name>')` from `#kit/kit-arg-types`. The table then carries every prop with its type, its values and the schema's own description, and cannot drift from the component. `kitPropDescriptors` in Contracts reads the schema; the Storybook side only turns a descriptor into an `argTypes` entry. The table shows the schema and nothing else, so a prop a component adds beside its kit props — `testID`, and `className` on a drawn primitive — is absent from it by design: those are kit plumbing, not props a Plugin sets.
- Kit prop defaults: a default is declared once, in Contracts. The component's defaults sit as a `*Defaults` const in `packages/contracts/src/kit-tokens.ts` (`buttonDefaults`), the schema marks the prop `.meta({ default: buttonDefaults.size })`, and the component's styles use the same const (`defaultVariants: buttonDefaults`). `.meta` rather than `.default()`, so nothing is parsed or filled and the wire is unchanged. `kitPropDescriptors` reads the schema's `default`, which fills the props table's Default column. Never write a default as an inline `prop === undefined` conditional, and a story need not cover the default state separately.
- Docgen: `typescript: { reactDocgen: 'react-docgen' }` in `main.ts` reads the props of a component that declares them in its own file. It cannot read a kit component's props, which are a generic mapped type over the schemas (`KitProps<'Button'>`). A file that exports several components is fine: each definition keeps its own props. `react-docgen-typescript` is not an option here: the repo's TypeScript ships no compiler API for it to call. Being Babel-based, `react-docgen` reads only a props type spelled out in the component's own file; it cannot follow one imported from a `*-props.ts`, nor expand an intersection or a discriminated union. So a kit component takes `kitArgTypes`, and a component whose props docgen cannot read shows a table built from the args its stories pass — the names are right, the types read `string` or `object`, and there are no descriptions. Spacer's table is empty, a kit component whose schema declares no props, and ContextMenu's is the `argTypes` its meta declares, since its `component` is the story's own wrapper. Two files whose subject declares no props at all have no Docs page: Portal and ArchivedBanner opt out.
- `third-party`: `tags: ['third-party']` marks a primitive Argo wraps rather than draws, whose behaviour its own library already tests. `apps/storybook/vitest.config.ts` excludes those stories from the Vitest run; they still appear in the preview and get a Docs page.
- Titles: `node tools/check-story-titles.mts` (in `pnpm quality:lint`) derives the whole title from the file's path and compares it, from the rules in `tools/story-title-rules.mts`, which `pnpm new:story` also writes titles from. A file named after its folder draws the component (`list.stories.tsx` → `…/Lists/List`); one named `<folder>-<aspect>` **whose meta draws that folder's component** draws an aspect of it (`list-tiles.stories.tsx` sets `component: List`, so it is `…/Lists/List/Tiles`). A file that draws a component of its own keeps its own node however its name reads beside the folder's — `menu-trigger.stories.tsx` sets `component: MenuTrigger`, so it is `…/Overlays/MenuTrigger`. Never start a new top-level group, and never rename a leaf by hand: rename the folder or the file. One segment is not derived — a screen's visible page title — and the check says so when it fails. The kit has two roots and one depth each: `Design System/Primitives/<Category>/<Name>` from `primitives/<category>/<name>/`, and `Design System/Foundations/<Topic>` from `foundations/<topic>/`, for a token scale no component owns. A scale a component already draws as its own states is not a foundation: the typography roles are Text's stories and the icon scale is Icon's `Roles`.
- Gates: `node --import tsx tools/check-story-gates.mts` (in `pnpm quality:lint`) reads a story file's body, from the rules in `tools/story-gate-rules.mts`. Four rules. A meta that sets `component:` also sets `argTypes`, or opts out with `tags: ['!autodocs']` and a comment saying why. A story export is not named for the prop that drives it: `WithPoster`, `WithoutMetadata`, `FullWidthTrue` and `LoadingFalse` are refused, while `Selected` and `Disabled` pass, because they name the look rather than the prop. A file varies only props its own component declares, read from the component beside it or from the `*-props.ts` it imports; where the props type is an intersection, a union, a generic or inline on the signature, or where the meta draws through its own `render:`, the gate says nothing rather than guess. And an args entry spelling out three or more data keys inline is a state that belongs in `<component>-fixtures.ts`, spies excluded, since a spy stays in the story file.
- Drawings: a duplicate drawing inside one file, and a parent story that is a child's state in disguise, are caught by `node --import tsx tools/check-story-renders.mts`. It draws every story and holds the browser-suite lock, so it runs in its own CI job rather than in `pnpm quality:lint`; [hooks.md](hooks.md) records that. It draws at the 1440px desktop the preview pins, since at a narrower one the phone layout collapses several states into one drawing and the gate reads them as duplicates. A `play` does not take a story out of its reach: `run` plays the story before the fingerprint is read, so what is compared is what the story ends up drawing. The first story of a file is drawn once and thrown away, because a cold first paint never matches a warm one and a duplicate of it would go unreported. Both gates fingerprint the DOM and the pixels together, and both fire only on equality, so a story that moves on its own — a live clock, a running ring — hides a finding rather than inventing one.
- Paint contract: the render gate also audits `ComposerPillComparison/CompactMenuSurface` at 390px. It locates Mode by button role and label. Its inset must have visible fill, and the surrounding 12px ring must match the clear themed backdrop. The fixture isolates the real control on padded `bg-card`; no child selectors or stored screenshots define this contract. Keep geometry and overlay interactions in behavior stories.
- Tests: `*.test.stories.tsx`, titled `Tests/` + its subject's whole title, uses browser play functions for behaviour, content and accessibility assertions; tests never assert appearance or pin whole copy. Await observable asynchronous states. Plain Vitest tests non-UI code only.
  - The subject is the presentation story beside it: the one whose name the test's name extends (`composer-send.test.stories.tsx` beside `composer.stories.tsx` is `Tests/Composer/Send`), else the folder's own story (`plugin-canvas.test.stories.tsx` under `plugin-registry/` is `…/PluginRegistry/Canvas`), else, in a route folder, that route's detail view. What is left of the test's name is the aspect segment, and a segment the subject's title already says is said once. With no presentation story beside it, the test's own path derives the title through the same rules, reading its folder as its subject: a `<folder>-<aspect>` name is an aspect of the folder's component, since a test meta carries no `component:` to read.
  - A play function that clicks, types or selects runs at one viewport for one Agent. Make one story per viewport and Agent with a file-local factory, as `conflict(width)` in `permission-request.test.stories.tsx` does, reusing `settleLayout` from `@repo/kit/mocks/story-layout`, the one driver for viewport, breakpoints and settling. It is test-only: `tools/check-test-only-imports.mts` fails a shipped file that imports it or `vitest/browser`.
  - A press a real browser pointer makes, through `vitest/browser`'s `userEvent`, is aimed at the box the row had when the runner measured it. A menu, a popover and a drill zoom in from 95%, so their rows keep moving for the length of that entrance, and a nested menu moves with the row it hangs off. Await `settleOverlays()` from `@repo/kit/mocks/settle-overlays` before such a press: a pointer that lands beside a row of a nested menu focuses a row of the menu above, which closes the nested one for good, and the press is then lost rather than late (#1466).
  - Take expected facts from the story's own recorded catalog, independently of the production calculation under test. State what a catalog must contain in one module-level check that throws "Recorded catalog needs …".
  - Assert absence as well as presence; never guard an assertion with `if (found)`.
- SF Symbols on a Mac: a browser Storybook draws Material Symbols, since only macOS can draw SF Symbols. Run `pnpm storybook:mac [port]` (port 6006 by default) to see the icons the macOS desktop app draws: it attaches to the Storybook on that port, or starts one, and opens it in an Electron window with the desktop app's preload, whose bridge the preview iframe reads through `window.parent` (`apps/desktop/scripts/storybook-mac.mts`). It is a local development tool only: Apple's licence keeps SF Symbols to Apple platforms (ADR-0019), so macOS draws each symbol at runtime, and no SF image reaches the web build, a static Storybook build or any packaged app.
