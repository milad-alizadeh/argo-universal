# Storybook

Storybook is the source of truth for built UI: a component's states, its platforms and its appearance are whatever its stories show. A design in Paper leads up to that story and is deleted once the component ships (`paper.md`).

**Writing a story file: run `pnpm new:story <component-path>` and copy `storybook-template.md`.** The generator derives the title from the path and writes one story per branch it reads in the component's own source; the template is the shape, annotated, in both flavours. This page is the rules behind it.

[ADR-0040](../adr/0040-one-shape-for-a-story.md) owns the shape of a story. Its test: **a prop value earns a story when the component branches on it** — when it is a key in the component's variants map, a key in a table the prop indexes, a literal it is compared against, or a platform fork. Everything else is an arg, and Controls covers it. One story per branch, never per combination; a pair earns a story only where the component has a rule for the pair. A **child's states are exported fixtures**, and a parent earns a story for one only when it changes the parent's own composition.

[ADR-0021](../adr/0021-storybook-renders-views-from-props.md) owns Storybook's data boundary. App E2E, not Storybook, proves that a screen is wired.

For side-by-side previews, run `pnpm dev:storybook:all`. It starts web Storybook, opens it in the browser, then starts Expo and opens `/storybook` in the iOS Simulator and Android Emulator apps. Selecting a story in the browser selects the same shared story on the devices. The web addon serves a local WebSocket on port 7007; the launcher supplies Android Emulator's host address while iOS Simulator uses loopback. Interactions are exercised separately on each platform. A native development build must already be installed; rebuild it after native dependency changes. To run one platform manually, start `pnpm dev:storybook` first, then `pnpm --filter @repo/universal-app exec expo start --ios` or `EXPO_PUBLIC_STORYBOOK_ANDROID_WS_HOST=10.0.2.2 pnpm --filter @repo/universal-app exec expo start --android`.

- Presentation: `*.stories.tsx` renders the actual component for people to inspect and use.
- Views, not screens: a connected screen is a thin shell that passes tRPC data to its view, and stories render the view. Every connected screen's view has a `<view-name>.stories.tsx` file, titled `Screens/<Section>/<Page>` so story ids stay, showing the complete normal view at the full available viewport. Its loading, empty, error and disconnected states are stories of their own: each is a branch the view takes. `parameters.screenPreview` fills the viewport; use it for views, shells and interactive lists. A section that embeds a connected screen takes it as a slot, and its story passes a view.
- Fixtures are props: a story passes plain typed props fixtures and callback spies. No story imports tRPC, TanStack Query, the Connection's tRPC client or a data hook; lint blocks them. A fixture a parent needs for a child's state is exported by the child; a fixture used by one story lives beside that story; `@repo/client/mocks` holds only shared fixtures, and the harness comes from `@repo/client/storybook` (ADR-0021). Feed props come from recordings through the real converter.
- Primitive copy: kit primitive stories use placeholder text, not Sessions, Projects or Agents copy, so product copy changes never reach the kit.
- Callbacks: a view's callbacks are spies. Function-only cases such as `onSearch`, `onSelect`, and `onProjectSettings` belong in functionality tests. Passing a function or logging an action does not earn a presentation story.
- Interaction: use existing product controls and visibly update the UI. Search filters; Project + inserts a Session. Pagination starts with enough rows to scroll, shows temporary loading, appends rows, and stops at the limit. Use valid product states.
- Wrappers: provide required context and realistic layout constraints, with no padding, surface or sizing that distorts the component's product appearance or scrolling.
- Isolation: a story's result never depends on which story ran before it. Reset story state between visits; clean up timers, subscriptions and mocks. `apps/storybook/vitest.setup.ts` restores the viewport before each test.
- Data: stable mock IDs, dates and ordering, so interactive changes are reproducible.
- Platforms: one story draws on web, iOS and Android, so a platform fork earns no story of its own. Share presentation stories and mock data; check both previews when changing shared UI; keep intentional platform differences.
- Native drawings: there is no native CI (ADR-0011), so a primitive's iOS and Android drawings are checked in the iOS and Android Storybook previews, or, where no Android preview exists, by the PR evidence table of the parent spec's decision 14 (the PR says which).
- Native headers: a phone page's header comes from its section Stack or Drawer options, which no story renders. A view built on the kit `Page` needs nothing: with no navigator, Page draws its own heading, search and Actions. Other views that need the narrow web header pass `ScreenHeaderMock` (or `mockHeader`) into their `renderHeader` slot. Check iOS and Android headers in the real App on a simulator or emulator, not in the on-device Storybook, whose pages sit under its own hidden route.
- Local runs: one Storybook or Playwright browser suite runs at a time on a Mac. A run waits for `@repo/browser-suite-lock`, which holds a localhost port until the suite ends or dies, and prints which checkout holds it. CI and watch runs, including Storybook's test widget, skip the lock. Locally Storybook opens fewer browser pages than in CI (`apps/storybook/vitest.config.ts`); `VITEST_MAX_WORKERS` overrides both.
- Discovery: Storybook previews load presentation stories only. Vitest also loads test-only stories, whose static browser imports need its runner.
- Docs pages: autodocs is on for every story file, from `tags: ['autodocs']` in `apps/storybook/.storybook/preview.tsx`. A file's Docs page renders its stories in order above a props table, which is where a reader sees the whole component at once. A file whose subject has no props component — an imperative API such as Toast, or a view whose stories pass a wrapper arg — opts out with `tags: ['!autodocs']` and says in a comment why. Test stories need no opt-out: the preview's glob loads presentation stories only, so `Tests/` has no Docs pages.
- Kit props tables: a kit component's props come from its Contracts schema, so its story meta sets `argTypes: kitArgTypes('<Part>')` from `#lib/generic/kit-arg-types`. The table then carries every prop with its type, its values and the schema's own description, and cannot drift from the component. `kitPropDescriptors` in Contracts reads the schema; the Storybook side only turns a descriptor into an `argTypes` entry. The table shows the schema and nothing else, so a prop a component adds beside its kit props — `testID`, and `className` on a drawn primitive — is absent from it by design: those are kit plumbing, not props a Plugin sets.
- Docgen: `typescript: { reactDocgen: 'react-docgen' }` in `main.ts` reads the props of a component that declares them in its own file. It cannot read a kit component's props, which are a generic mapped type over the schemas (`KitProps<'Button'>`). A file that exports several components is fine: each definition keeps its own props. `react-docgen-typescript` is not an option here: the repo's TypeScript ships no compiler API for it to call. Being Babel-based, `react-docgen` reads only a props type spelled out in the component's own file; it cannot follow one imported from a `*-props.ts`, nor expand an intersection or a discriminated union. So a kit component takes `kitArgTypes`, and a component whose props docgen cannot read shows a table built from the args its stories pass — the names are right, the types read `string` or `object`, and there are no descriptions.
- `third-party`: `tags: ['third-party']` marks a primitive Argo wraps rather than draws, whose behaviour its own library already tests. `apps/storybook/vitest.config.ts` excludes those stories from the Vitest run; they still appear in the preview and get a Docs page.
- Titles: a title derives from the component's path, never written freehand, and `node tools/check-story-titles.mts` (in `pnpm quality`) enforces it. `tools/story-title.mts` holds the derivation the generator uses, so the path is the one source of a title. A kit primitive is always four segments. Never start a new top-level group: the sidebar order in `preview.tsx` names the roots, and the check fails a story in any other folder.
- Tests: `*.test.stories.tsx`, titled `Tests/<ComponentName>`, uses browser play functions for behaviour, content and accessibility assertions; tests never assert appearance or pin whole copy. Await observable asynchronous states. Plain Vitest tests non-UI code only.
  - A play function that clicks, types or selects runs at one viewport for one Agent. Make one story per viewport and Agent with a file-local factory, as `conflict(width)` in `permission-request.test.stories.tsx` does, reusing `settleViewport` and `layoutWidths` from the Storybook harness.
  - Take expected facts from the story's own recorded catalog, independently of the production calculation under test. State what a catalog must contain in one module-level check that throws "Recorded catalog needs …".
  - Assert absence as well as presence; never guard an assertion with `if (found)`.
- SettingsListView: keep one interactive `Settings` presentation story; clicking its rows demonstrates selection.
- SF Symbols on a Mac: a browser Storybook draws Material Symbols, since only macOS can draw SF Symbols. Run `pnpm storybook:mac [port]` (port 6006 by default) to see the icons the macOS desktop app draws: it attaches to the Storybook on that port, or starts one, and opens it in an Electron window with the desktop app's preload, whose bridge the preview iframe reads through `window.parent` (`apps/desktop/scripts/storybook-mac.mts`). It is a local development tool only: Apple's licence keeps SF Symbols to Apple platforms (ADR-0019), so macOS draws each symbol at runtime, and no SF image reaches the web build, a static Storybook build or any packaged app.
