# Storybook

Read [Testing seams](testing-seams.md) for fixture boundaries, wrapper scope and what each test proves. [ADR-0021](../adr/0021-storybook-renders-views-from-props.md) owns Storybook's data boundary: stories render views from props and never use tRPC fixtures. App E2E, not Storybook, proves that a screen is wired.

- Presentation: `*.stories.tsx` renders the actual component for people to inspect and use. Name stories for visible states or experiences, not a prop inventory. A file with one story names it after the component (`name: 'Button'`) so the sidebar shows a single entry.
- Views, not screens: a connected screen is a thin shell that passes tRPC data to its view, and stories render the view. Every connected screen's view has a `<view-name>.stories.tsx` file, titled `Screens/<ScreenName>` so story ids stay, showing the complete normal view at the full available viewport. Its loading, empty, error and disconnected states are props stories too. The custom Agent screen has no view; its form gets the stories. Child stories do not replace it. `parameters.screenPreview` fills the viewport; use it for views, shells and interactive lists. A section that embeds a connected screen takes it as a slot, and its story passes a view.
- Fixtures are props: a story passes plain typed props fixtures and callback spies. No story imports tRPC, TanStack Query, the Connection's tRPC client or a data hook; lint blocks them. A fixture used by one story lives beside that story; `@repo/client/mocks` holds only shared fixtures, and the harness comes from `@repo/client/storybook` (ADR-0021). Feed props come from recordings through the real converter.
- Uniqueness: present each distinct result once. Identical appearance and behavior make stories duplicates even when props differ. Keep the normal state once; additional loading, empty, or error stories must visibly differ.
- Ownership: child states belong in child stories. Parents may naturally contain them, but get no separate story or variation for an already-covered child state. Selected SessionRow coverage rules out selected-row SessionsList and SessionsScreen showcases.
- Callbacks: a view's callbacks are spies. Function-only cases such as `onSearch`, `onSelect`, and `onProjectSettings` belong in functionality tests. Passing a function or logging an action does not justify a presentation story.
- Comparisons: use shared `Variation` and `Variations` helpers for distinct component states. Use viewport and theme controls for phone, desktop, light, and dark instead of multiplying presentation stories.
- Interaction: use existing product controls and visibly update the UI. Search filters; Project + inserts a Session. Pagination starts with enough rows to scroll, shows temporary loading, appends rows, and stops at the limit. Use valid product states.
- Wrappers: provide required context and realistic layout constraints. Extra padding, surfaces, and sizing must not distort the component's product appearance or scrolling.
- Isolation: reset story state between visits; clean up timers, subscriptions, and mocks. A story's result must not depend on which story ran before it. `apps/storybook/vitest.setup.ts` restores the viewport before each test.
- Data: use stable mock IDs, dates, and ordering. Keep interactive changes predictable and reproducible.
- Primitives: each primitive in `lib/generic/primitives` has one presentation story, built with `Variations`, showing its states side by side.
- Platforms: share presentation stories and mock data across web, iOS and Android. Check every preview when changing shared UI; preserve intentional platform differences.
- Native drawings: a primitive's `.ios.tsx` and `.android.tsx` drawings (ADR-0020) never run in web Storybook or CI (ADR-0011). Check them in the on-device Storybook on iOS and Android. Where a preview cannot show one, the PR evidence proves it: screenshots beside the Paper frame in light and dark, at the largest text sizes, with menus, sheets and dialogs open, and a VoiceOver and TalkBack pass. The PR says whether an Android preview was checked.
- Discovery: normal Storybook previews load presentation stories. Vitest additionally loads test-only stories, whose static browser imports require its runner. Test-only stories are absent from the preview sidebar.
- Tests: `*.test.stories.tsx`, titled `Tests/<ComponentName>`, uses browser play functions for behaviour, content and accessibility assertions. Apply the [testing seam rule](testing-seams.md) for appearance: styling belongs in visual review; geometry checks must prove a functional outcome such as reachable controls or scroll completion. Await observable asynchronous states. Plain Vitest tests non-UI code only.
- Styling: tests never assert how things look. No font sizes, line heights, weights, colours, spacing, radii, or fixed widths and heights; Paper owns those. When a design change breaks one, delete the assertion. Layout bugs a user would see, such as overflow, clipping or a covered control, are behaviour and stay.
  - A play function that clicks, types or selects runs at one viewport for one Agent. Make one story per viewport and Agent with a file-local factory, as `conflict(width)` in `permission-request.test.stories.tsx` does, reusing `settleViewport` and `layoutWidths` from the Storybook harness.
  - Take expected facts from the story's own recorded catalog, independently of the production calculation under test. State what a catalog must contain in one module-level check that throws "Recorded catalog needs …".
  - Assert absence as well as presence; never guard an assertion with `if (found)`.
- SettingsList: keep one interactive `Settings` presentation story; clicking its rows demonstrates selection.
