# Argo's native primitives can draw plugin trees

Research date: 2026-10-14. Input to the Plugins grilling in #506; nothing here is a decision, and nothing has been run on a simulator yet.

Yes, the agreed design works on both phones, with rules attached. Argo's primitives are ordinary React components, and so are the Expo UI views under them. A registry that turns `{type, props, children}` nodes into those components is plain React. Expo UI turns React child changes into SwiftUI and Compose child changes, so adding, removing and reordering nodes is the normal path ([SwiftUIVirtualView.swift](https://github.com/expo/expo/blob/main/packages/expo-modules-core/ios/Core/Views/SwiftUI/SwiftUIVirtualView.swift); [ExpoComposeView.kt](https://github.com/expo/expo/blob/main/packages/expo-modules-core/android/src/compose/expo/modules/kotlin/views/ExpoComposeView.kt)). The risk sits in three places. The first is **Host boundaries**, where most Expo UI bugs have been. The second is **long lists**: on SDK 57, React creates every row up front. The third is **Android**, where Argo draws its own Compose groups and rows and still carries an `@expo/ui` patch. About half the vocabulary from the earlier report already exists as data-only primitives. Page, Nav, Properties, Banner, Avatar, Stack and a List node do not exist yet and must be built. A four-day throwaway spike on one iOS simulator and one Android emulator would settle the open points. Its pass/fail criteria are in section 5.

## 1. iOS is feasible; Android is feasible with more to prove

**iOS: feasible.** Each Expo UI view except `Host` is a light native object whose children are the views React has mounted. SwiftUI takes each child's identity from that native object, so a stable React key keeps a row's SwiftUI state ([AnyChild.swift](https://github.com/expo/expo/blob/main/packages/expo-modules-core/ios/Core/Views/SwiftUI/AnyChild.swift); [ListForEachView.swift](https://github.com/expo/expo/blob/main/packages/expo-ui/ios/ListForEachView.swift)). The link between keys and SwiftUI state is inferred from source; the docs do not state it. Argo already ships what plugins need, with data-only props: `FieldGroup` is a SwiftUI `Form` in one Host, `FieldSection` is a `Section`, and `ListItem`, `Picker`, `Switch` and `FieldInput` are rows ([field-group-view.ios.tsx](../../../packages/client/src/lib/generic/primitives/fields/field-group/field-group-view.ios.tsx); [field-props.ts](../../../packages/client/src/lib/generic/primitives/fields/field-props.ts)). Three iOS problems are known. An open bug makes children vanish early during animated removal ([#51263](https://github.com/expo/expo/issues/51263)). `measure()` inside `RNHostView` is wrong until SDK 58 ([#51501](https://github.com/expo/expo/issues/51501)). A Host mounted in a repeated full-screen modal loses its safe area ([#51288](https://github.com/expo/expo/issues/51288)).

**Android: feasible, with more to prove.** Argo does not use Expo's `FieldGroup` on Android. It draws its own: an RN `ScrollView` around a content-sized Host around a Compose `Column`. Expo's version matched sections by component identity and nested ListItems wrongly ([ADR-0020](../../adr/0020-argo-owns-its-primitives.md); [field-group-view.android.tsx](../../../packages/client/src/lib/generic/primitives/fields/field-group/field-group-view.android.tsx)). That choice is good for plugins, because Argo's groups already accept wrapped and conditional rows ([project-detail-view.tsx](../../../packages/client/src/features/settings/components/project-detail-view/project-detail-view.tsx)). The costs are these. Every row is composed, because nothing is lazy. RN content inside rows learns its height only after layout ([field-group-row.tsx](../../../packages/client/src/lib/generic/primitives/fields/field-group/field-group-row.tsx)). Icons in Compose rows are RN views inside `RNHostView` ([native-symbol.tsx](../../../packages/client/src/lib/generic/symbols/native-symbol.tsx)). And `RNHostView` touch bugs were still being fixed in 57.0.x and 58.0.16 ([#48131](https://github.com/expo/expo/issues/48131); [@expo/ui CHANGELOG](https://github.com/expo/expo/blob/main/packages/expo-ui/CHANGELOG.md)).

**A discrepancy to settle first.** The `@expo/ui@57.0.22` patch is still on `main` ([pnpm-workspace.yaml](../../../pnpm-workspace.yaml); [patches/@expo__ui@57.0.22.patch](../../../patches/@expo__ui@57.0.22.patch)). Its removal exists only on the unmerged branch `spec-648/remove-expo-ui-patch` (commit `3fca120d`; `git merge-base --is-ancestor` against `main` fails, re-checked for this report). Argo's memory notes say the patch was removed on 2026-10-14, but `main` does not agree. This matters because the Android ListItem row uses the patch's `clearSemantics` modifier ([list-item-android-row.tsx](../../../packages/client/src/lib/generic/primitives/lists/list-item/list-item-android-row.tsx)). The spike must run on whichever state will ship, and switching states means rebuilding the Android dev client ([patches/README.md](../../../patches/README.md)).

**Wide windows.** On iPad and in other wide windows, every primitive switches to its RN drawing inside the same file ([use-wide.ts](../../../packages/client/src/lib/generic/use-wide/use-wide.ts)). Plugins need not care, but each node type then has three drawings to check.

## 2. Primitive by primitive

"Data-only variant" means the node takes only strings, enums, booleans and arrays, and callbacks become event ids. Anything typed `ReactNode`, `ReactElement`, `style`, `className`, `ref`, `onHover*` or `aria-*` is removed or replaced by a restricted child list. All of this comes from reading props files ([field-props.ts](../../../packages/client/src/lib/generic/primitives/fields/field-props.ts); [button-props.ts](../../../packages/client/src/lib/generic/primitives/buttons/button/button-props.ts)). Proposed props are inferences.

| Primitive (plugin name) | iOS today | Android today | Verdict | What to change |
|---|---|---|---|---|
| **Page** | none; header is `Stack.Screen` options via `ScreenHeader` | same | **Missing, must be built** | Data-only `title`, `actions[{id,label,icon,href}]`, `loading`. Set the header through the existing `ScreenHeader`/`HeaderButton` path ([screen-header.tsx](../../../packages/client/src/lib/product/navigation/screen-header.tsx)); the body is a registry-inserted `FieldGroup` on phone and `SettingsPage` on wide. |
| **Nav** (Plugin's own root) | none | none | **Missing, must be built** | Compose from `FieldGroup variant="navigation"` + `ListItem href`. No new drawing. |
| Rail / drawer entry | `NavigationItem` (Paper rows) | `NavigationItem` (native M3 drawer item) | **Works as-is** | Fed from the manifest (`label`, `icon`), not from a tree. |
| **Section** → `FieldSection` | SwiftUI `Section` | Argo Compose `Column` | **Works as-is** (data props) | Add `count`. The registry infers `textFields`. Children: rows only. |
| `FieldGroup` | `Host` > `Form`/`List` | `ScrollView` > `Host` > `Column` | **Keep internal** | The registry inserts it under Page and Settings. Plugins never name it. |
| **ListItem** | `HStack`/`Button` row, no Host | `Surface`/`Button` row, no Host | **Needs a data-only variant** | Drop `leading`/`valueLeading`/`accessory`/`control`/`detail` elements. Add `meta`, `accessories[]` (Badge, Icon, Avatar only) and `control` (Switch only). |
| **Properties / Property** | none | none | **Missing, must be built** | On phone, compose from `ListItem` + `Picker` as accessory, a pattern already shipped ([project-detail-new-sessions.tsx](../../../packages/client/src/features/settings/components/project-detail-view/project-detail-new-sessions.tsx)). This revises the earlier "chips" idea: a chip row would need one `Menu` Host per chip (inferred). |
| **Banner** | none (only the Connection feature's banner) | none | **Missing, must be built** | RN view, like all Argo content ([ADR-0020](../../adr/0020-argo-owns-its-primitives.md)). Main use is slots. |

| **Stack** | none (layout is Uniwind inside each view) | none | **Missing, must be built** | RN `View` with `direction`/`gap`/`align` tokens. Allowed only outside native lists. |
| **List** (long, keyed) | `ScrollFadeList`/`FieldList` take render functions | same | **Missing, must be built** | A node with keyed items and `hasMore`. The registry supplies `renderItem`. Cap rows on SDK 57 (see risks). |
| **Text** | RN `Text` with role classes | same | **Needs a data-only variant** | `text`, `role`, `tone`; no `className`/`asChild`. Inside a native list only via `FieldRow`. |
| **Markdown** → `FeedMarkdown` | RN | RN | **Works as-is** | Already `text` + `variant` ([feed-markdown.tsx](../../../packages/client/src/lib/product/markdown/feed-markdown.tsx)). Restrict syntax. |
| **Badge** | RN `View` + `Text` | same | **Needs a data-only variant** | `label`, `tone`. |
| **Icon** | `SymbolView`; SwiftUI `Image` in native rows | `SymbolView`; RN in `RNHostView` in Compose rows | **Works as-is, with validation** | Name must be one of ~140 `IconName` keys. `Icon` crashes on unknown names ([icon.tsx](../../../packages/client/src/lib/generic/symbols/icon.tsx)). Several names in the earlier report's examples (`status-in-progress`, `cloud-rain`, `calendar`) do not exist. |
| **Button** | SwiftUI `Button`, own Host | Compose `Button` family, own Host | **Works as-is** | Expose only the `system` appearance. One Host per button. |
| IconButton | RN Pressable + icon | same | **Needs a data-only variant** | `icon`, `accessibilityLabel`, `variant`. |
| **Menu** | `Menu` + inline `Picker` | Compose `DropdownMenu` | **Works for single-select; action menu missing** | `trigger` becomes a fixed label + icon. Header overflow ("extras fold into one menu") needs action items, which Menu lacks. |
| **Select** → `Picker` | Menu picker ≤ 7 options, drill-in list above | radio dialog | **Works as-is** | Note that iOS changes control kind when the option count crosses 7 ([picker.ios.tsx](../../../packages/client/src/lib/generic/primitives/inputs/picker/picker.ios.tsx)). |
| **Toggle** → `Switch` | `Toggle` | Compose `Switch` | **Needs a data-only variant** | `checked`, `disabled`, `accessibilityLabel` only. Today's props inherit `className`/`style`. |
| Slider, SegmentedControl, Checkbox | SwiftUI | Compose | **Works as-is** | none |
| **TextField** → `FieldInput` | `TextField` with native state | Compose filled `TextField` | **Works as-is** | The App already owns the draft (`useNativeState`), which matches the earlier design. |
| Alert | `Alert`/`ConfirmationDialog` | `AlertDialog` | **Works as-is** | Confirms only. |
| Toast, Spinner, InfoPopover | | | **Works as-is** | none |

| LiquidGlass, NativeOnlyAnimatedView, RichTextarea, Collapsible, Popover, Portal, ScrollFadeView | | | **Keep internal** | Style-carrying or web-only. |

The surfaces map onto this as follows. A **plugin screen** is Page plus a registry-inserted FieldGroup inside the catch-all stack. A **Settings section** is one `FieldSection` subtree placed in the existing Settings group, which is a grouped card on phone. **Rail and drawer entries** are `NavigationItem`s built from the manifest. **`composer.above`** is RN territory, because the Composer is drawn in RN ([ADR-0020](../../adr/0020-argo-owns-its-primitives.md)), so only RN nodes and Buttons go there. **The inspector on phone** is a bottom sheet, which already nests Host > sheet > `RNHostView` > FieldGroup Host > `Form` ([bottom-sheet-viewport.tsx](../../../packages/client/src/lib/generic/primitives/overlays/bottom-sheet/bottom-sheet-viewport.tsx)). **Header actions** are `HeaderButton` data, not a tree. All of this mapping is inferred from the code.

## 3. Rules the registry must enforce

Today, app code keeps these rules by hand. A plugin tree is untrusted, so the registry must check them. The Server rejects a breaking node with a path-addressed error, and the App drops it without crashing.

| Rule | Why |
|---|---|
| **Plugins never emit a Host.** The registry places one Host per page body (through FieldGroup) and one per free-standing native control. Changing a Host's sizing mode means remounting it with a new key. | `matchContents` is mount-only. A Host directly inside a Host now triggers a dev warning. Expo UI views outside a Host log "Missing Host" ([Host docs](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/host/); [CHANGELOG](https://github.com/expo/expo/blob/main/packages/expo-ui/CHANGELOG.md)). |
| **Rows only inside Section inside the page FieldGroup.** ListItem, Property, FieldInput and Toggle rows never sit at the root or inside a Stack. | ListItem returns SwiftUI/Compose nodes with no Host of its own (inferred from [list-item-view.ios.tsx](../../../packages/client/src/lib/generic/primitives/lists/list-item/list-item-view.ios.tsx)). |
| **RN nodes enter a native list only through `FieldRow`.** These are Text, Markdown, Banner, Badge, Stack and Avatar. | This is how the repo crosses from SwiftUI/Compose to RN today ([field-row-view.ios.tsx](../../../packages/client/src/lib/generic/primitives/fields/field-row/field-row-view.ios.tsx)). |
| **Restricted slots.** ListItem `accessories` takes only Badge, Icon or Avatar. `control` takes only Toggle. Menu triggers are a label and an icon. | Free trees in these slots cross the RN/native boundary in places Argo has not tested (inferred). |
| **A stable node id is the React key.** Never use the index. The Server rejects duplicate sibling ids. | SwiftUI ties state to identity. Index ids break on insert, and duplicate ids collapse views ([Demystify SwiftUI](https://developer.apple.com/videos/play/wwdc2021/10022/)). Wide `FieldList` falls back to keying by index ([field-list-entries.ts](../../../packages/client/src/lib/product/field-list/field-list-entries.ts)). |
| **Validate icon names** against `iconNames`, on the Server and again in the App. Drop unknown icons. | Unknown names crash `Icon`. The set is closed at build time ([icon-names.ts](../../../packages/client/src/lib/generic/symbols/icon-names.ts); [ADR-0019](../../adr/0019-icons-are-native-symbols.md)). |
| **No modifiers, colours, `className`, `style` or refs from plugins.** Tones are an enum that the registry maps through `useNativeTheme`. | Modifiers are built in JS and sent across the bridge, and each primitive fixes its own ([native-theme.ts](../../../packages/client/src/lib/generic/native-theme.ts)). |
| **Lists are explicit `List` nodes** with keyed items, a row cap and `hasMore`. A Section never holds hundreds of children. | On SDK 57, React creates every row up front ([List docs](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/list/); [LazyColumn docs](https://docs.expo.dev/versions/latest/sdk/ui/jetpack-compose/lazycolumn/)). |
| **Patches never animate removals**, and a focused input is not removed until it blurs. | These match the open iOS removal bug and the earlier focused-`TextField` crash ([#51263](https://github.com/expo/expo/issues/51263); [#47682](https://github.com/expo/expo/issues/47682)). The defer rule is inferred. |
| **One memoised component per node.** Unchanged subtrees keep the same object reference after a patch. | Compose re-runs on new instances even when the values are equal ([Compose stability](https://developer.android.com/develop/ui/compose/performance/stability)). |

## 4. Risks, most serious first

| # | Risk | Mitigation |
|---|---|---|
| 1 | **Long lists.** SDK 57 mounts every row. Argo's Android group composes them all. Expo publishes no safe row count. | Cap rows per Section and List, page with `hasMore`, and measure in the spike. SDK 58 adds recycled `List.ForEach` / `LazyColumn.Items` with `data` + `keyExtractor` ([CHANGELOG](https://github.com/expo/expo/blob/main/packages/expo-ui/CHANGELOG.md)), so model `List` with `items` + `key` now and swap the drawing later. |
| 2 | **Host and `RNHostView` bugs**: touch, measure, safe area, a sheet unmounting in the same tick ([#47708](https://github.com/expo/expo/issues/47708)). | The registry owns every Host and uses only patterns already shipped in Argo screens. Pin `@expo/ui` exactly and keep a fixture regression set. |
| 3 | **Android state is unsettled.** The patch is on `main`, its removal is on a branch, and the rows are Argo's own Compose. | Merge or drop `spec-648/remove-expo-ui-patch` before the spike and test only that state. |
| 4 | **Dynamic removal edge cases**: focused inputs, animated removal, toggling a mount-only prop. | Turn each into a fixture patch in the spike and the regression set. |
| 5 | **Vocabulary gaps**: seven missing primitives and an action menu. | Build in this order: Page, Properties, Banner, List, then the rest. Each needs a Paper design first ([AGENTS.md](../../../AGENTS.md)). |
| 6 | **Three drawings per node** (iOS, Android, wide RN) and no native CI. | One Storybook story per fixture, checked on both phone previews ([docs/agents/storybook.md](../../agents/storybook.md)). |
| 7 | **Icon set closed at build time.** | Publish `iconNames` in the plugin types. A new icon ships with an Argo release. |
| 8 | **SDK churn.** 58.0.0 changes Host alignment and default stack spacing, and removes `RNHostView` `style` on Android ([CHANGELOG](https://github.com/expo/expo/blob/main/packages/expo-ui/CHANGELOG.md)). | Upgrade deliberately and rerun the fixture set on both phones. |
| 9 | **Re-render cost.** Hyperview reported cutting render time and re-renders by up to 50% after reworking its pipeline ([Hyperview blog](https://hyperview.org/blog/2025/08/01/Out-with-the-old)). | Memoise per node and reuse references (rule above). |

Two reported costs do not change the plugin decision. The **~380 ms iOS cold start** from installing `@expo/ui` is a single unconfirmed report ([#51042](https://github.com/expo/expo/issues/51042)), and Argo already pays it. The **Material 3 alpha pin** ([#50050](https://github.com/expo/expo/issues/50050)) matters only if plugins add native code, and they do not.

## 5. A four-day spike on real simulators

This is a throwaway prototype on a branch, not product code. Plugins are not decided yet (#506), and UI code needs the user's go-ahead. No Server and no reconciler are involved. The App reads JSON fixtures, and a dev timer applies scripted patches. Use one booted iOS simulator and one Android emulator, built from the `@expo/ui` state chosen in risk 3.

| Day | Work | Pass | Fail |
|---|---|---|---|
| 1 | `PluginTreeView` takes `{tree}` props (ADR-0021). A registry covers Page, Section, ListItem (data variant), Property, Toggle, TextField, Button, Banner, Text and Badge. One story per fixture. | Each fixture looks the same as the hand-written Settings screen built from the same primitives, on iOS, Android and wide. | Any primitive needs a style, modifier or child element from the tree to look right. |
| 2 | Catch-all route `(shell)/plugins/[pluginId]/[...path].tsx` with `href` push, one Settings section, a `composer.above` Banner, and an inspector bottom sheet holding a FieldGroup tree. | Each push is one native stack entry with a native header. The sheet opens and closes 20 times, and an RN modal is still tappable afterwards. | Header flashes, a lost back gesture, or dead touches after a dismiss. |
| 3 | Patch driver: add, remove and reorder rows; change values; remove a focused TextField; switch a Picker from 5 to 9 options; send an unknown type and an unknown icon. | A reorder keeps Toggle state and the TextField draft. Removing a focused field does not crash. Unknown nodes are dropped. Logs show no "Missing Host" or nested-Host warnings. | Any crash, state reset on reorder, or a warning in the log. |
| 4 | 50-, 200- and 500-row fixtures on an Android release build and on iOS. Time to first render and scroll. Events reach a stub with node id, pending state and revert. | A clear row cap that renders fast enough (target proposed, not sourced: first render under about 500 ms on the emulator), and pending/revert works on both. | 50 rows already visibly slow, which would mean SDK 58 recycled lists before v1. |

The spike's output is a short note with screenshots attached to #506. It should name the row cap, give a yes or no on each Day 3 case per platform, and list the primitives that needed changes.

## 6. Prior art: closed catalogs survive, toolkit mirrors do not

| System | What it shows for Argo |
|---|---|
| **Shopify POS UI extensions** | The closest match. Sandboxed extension JS sends JSON tree updates to native Swift and Kotlin hosts with a fixed component set, and callbacks are proxied back ([Shopify Engineering](https://shopify.engineering/remote-rendering-ui-extensibility); [POS docs](https://shopify.dev/docs/api/pos-ui-extensions/latest)). It does not say whether the hosts draw with SwiftUI/Compose or UIKit/Views. |
| **LiveView Native** | Server markup mapped straight onto SwiftUI and Compose views and modifiers. The main repo was archived on 10 Feb 2026 with no reason given, the 0.4 line stayed at release candidate, and the Compose client lagged the SwiftUI one ([live_view_native](https://github.com/liveview-native/live_view_native); [liveview-client-jetpack](https://github.com/liveview-native/liveview-client-jetpack)). Lesson (inferred): mirroring the whole toolkit is costly; a curated set is not. |
| **Nimbus** (SwiftUI + Compose SDUI) | Archived in June 2024 ([nimbus-swiftui](https://github.com/ZupIT/nimbus-swiftui), search summary only). |
| **DivKit** | Production SDUI with a closed, versioned schema and native renderers. Its pages do not say whether it uses SwiftUI or Compose ([divkit](https://github.com/divkit/divkit)). |
| **Airbnb Ghost, Nubank** | Sections from a closed catalog at scale ([Okoone on Ghost](https://www.okoone.com/spark/product-design-research/changing-user-interface-with-airbnbs-ghost-platform/), secondary). Nubank runs on Flutter, not SwiftUI/Compose ([Nubank](https://building.nubank.com/server-driven-ui-framework-at-nubank/), search summary only). |
| **Hyperview** | XML to RN components. A pipeline rework cut re-renders by up to 50% ([Hyperview blog](https://hyperview.org/blog/2025/08/01/Out-with-the-old)). |
| **Apple, Android guidance** | Stable unique ids, no type erasure, and keys on lists ([Demystify SwiftUI](https://developer.apple.com/videos/play/wwdc2021/10022/); [Compose best practices](https://developer.android.com/develop/ui/compose/performance/bestpractices)). |

No Expo-sanctioned server-driven UI pattern exists, and no public report describes a JSON-driven renderer on Expo UI ([GitHub SDUI topic](https://github.com/topics/server-driven-ui)). Argo would be early, but it would use only ordinary React on top of Expo UI.

**Confidence notes.** Section 2 and the rules come from reading Argo's code on `main` at `9ae20ba5`. Nothing has been run on a device. Expo UI internals come from `expo/expo` `main`, which is already SDK 58. Recycled lists and the `measure()` fix are not in Argo's 57.0.22, and which 57.0.x patch release carries each touch fix was not checked against 57.0.22. These rest on search summaries only: the SDK 57 changelog contents, the SDK 56 `WorkletCallback` note, Nimbus's archive date, the Nubank figures, the Callstack parity remark, and the titles-only reads of #42576, #50655 and #48834 (not used above). There is no row-count benchmark anywhere, which is why the spike's Day 4 exists.

## Conclusion

The question was never whether React can drive SwiftUI and Compose; Expo UI already does that for every Argo screen. The real question is whether Argo's primitives are disciplined enough to accept untrusted trees. Mostly they are, and the ADR-0020 rule ("data props, not children") is what makes this possible. The work left is to make implicit rules explicit: who places Hosts, which nodes nest where, and which slots accept what. That code belongs in the registry, not in each plugin.

One earlier assumption should change. The phone version of Properties should reuse the ListItem + Picker row Argo already ships, not a row of menu chips. In general, a plugin primitive on the phone should be built by composing existing native rows. Each new native drawing adds Host and parity risk on both platforms. Long lists are the one limit that needs SDK 58 to lift.
