# Copy VS Code, ship the API with its plugin

Research date: 2026-10-14. Input to the Plugins grilling in #506; nothing here is a decision.

Most of Argo's plugin plan already copies proven systems. The shared plugin host, the folder-plus-manifest Plugin, the built-in-but-toggleable first-party Plugins and the JSON tree of primitives all have a direct parent in VS Code or Raycast. Argo is inventing in six places: it exposes the whole primitives library, it names its slot without a version, it has no activation or crash rules, it lets Plugins draw their own Settings, it compiles TSX on every load, and it builds the Plugin system before the Plugin that proves it. Each has a proven replacement, listed below. The biggest lesson is about order. VS Code made its SCM API public in the same release that moved Git onto it, and the first-party extensions still lean on unstable "proposed" API today. Backstage shows the cost of the other order: retrofitting slots onto hand-built screens took years of hybrid migration. So Argo should keep its four slices but let the Issue tracker Plugin drive every slice from the first one. It should also ship all Plugin API as "proposed" (first-party only) until a second Plugin has used it.

## The runtime and manifest already follow VS Code and Raycast

Argo's runtime is VS Code's local extension host. VS Code runs all extensions of one kind in **one shared Node process**, apart from the UI, so they cannot slow startup or touch the UI ([VS Code: Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)). VS Code accepts that one bad extension can kill the others, and handles it with rules instead of more processes. The host **restarts itself up to 3 times in 5 minutes**, then asks the user and offers Extension Bisect. It marks the host unresponsive after **3 seconds** without an RPC reply and profiles it to blame one extension ([abstractExtensionService.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/extensions/common/abstractExtensionService.ts), [rpcProtocol.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/extensions/common/rpcProtocol.ts)). Argo's Supervisor already restarts the Engine; the plugin host needs the same budget, plus a log line naming the Plugins that were running. Raycast v1 is the same shape one level down: one Node child, but **each extension in its own worker thread with a capped heap**, so a crash or out-of-memory shows an error for that extension only ([Raycast: How the API works](https://www.raycast.com/blog/how-raycast-api-extensions-work)). Letting Plugins use Node directly also matches: Raycast says extensions are "not further sandboxed" ([Raycast: Security](https://developers.raycast.com/information/security)).

The manifest matches too. A folder plus `plugin.json` is Grafana's file name and VS Code's idea. Shipping first-party Plugins from the app and user Plugins from a home folder, through one loader, is how VS Code scans its "system" and "user" extensions ([extensionsScannerService.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/extensionManagement/common/extensionsScannerService.ts)). Built-in Git "can be disabled but not uninstalled" ([Git README](https://github.com/microsoft/vscode/blob/main/extensions/git/README.md)), and Obsidian ships toggleable Core plugins next to community ones ([Obsidian Help: Plugins](https://obsidian.md/help/plugins)). The JSON-tree UI is Raycast v1 almost exactly: a custom React reconciler, a JSON render tree, JSON Patch diffs, a fixed list of message types, and a view-model layer that keeps native views apart from the wire format ([Raycast blog](https://www.raycast.com/blog/how-raycast-api-extensions-work)). One caveat: Raycast 2.0 (2026) moved its frontend to WebViews, and its post does not say whether the reconciler survived ([Raycast deep dive](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)).

## Six inventions, each with a proven replacement

**Exposing the whole primitives library** is the largest invention. No system that draws plugin UI natively hands over its full component set. Raycast exposes **four views, List, Grid, Detail and Form, each with an ActionPanel** ([Raycast: User Interface](https://developers.raycast.com/api-reference/user-interface)). VS Code gives tree views and discourages webviews ([VS Code: Webview UX](https://code.visualstudio.com/api/ux-guidelines/webviews)). The reason is VS Code's first API rule: "We DO NOT want to break API" ([API guidelines](https://github.com/microsoft/vscode/wiki/Extension-API-guidelines)). Every exposed primitive becomes a promise. Start with the generic set being added (Page, Stack, Markdown, Properties, EmptyState) plus ListItem, FieldGroup, Button and TextField, and add more on request.

**The unversioned `project.details` slot** should follow Grafana. Grafana slot ids carry an owner prefix and a version, such as `grafana/user/profile/menu/v1`. A breaking change means a new `/v2`, served next to the old one for a while. Older Grafana ids lack the suffix, which shows the rule was added late ([Grafana: Versioning extensions](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/versioning-extensions), [pluginExtensions.ts](https://github.com/grafana/grafana/blob/main/packages/grafana-data/src/types/pluginExtensions.ts)). Grafana also **freezes the context object** it passes in, and requires every contribution to be listed in `plugin.json` or it is not shown ([Grafana: Create an extension point](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/create-an-extension-point)). Copy all three: `argo/project/details/v1`, a frozen `{ projectId }`, and slots declared in `contributes`.

**No activation rule.** VS Code draws the activity-bar icon, view title and settings from `contributes` before the extension runs. Since 1.74, contributing a command or view implies its activation event, so code starts on first use ([VS Code: Activation Events](https://code.visualstudio.com/api/references/activation-events)). Argo should do the same: nav items and settings come from the manifest, and a Plugin's worker starts the first time its page, slot or setting is opened.

**Plugin-drawn Settings.** If "a Settings section per Plugin" means Plugin JSX, it breaks the most consistent rule in the research. VS Code's UX guide says do not "create your own settings page/webview" ([VS Code: Settings UX](https://code.visualstudio.com/api/ux-guidelines/settings)). Settings are a JSON schema in `contributes.configuration`, with scopes from app-wide down to one folder ([Contribution Points](https://code.visualstudio.com/api/references/contribution-points)). Raycast does the same with manifest preferences, and blocks a command until required ones are filled ([Raycast: Preferences](https://developers.raycast.com/api-reference/preferences)). Obsidian started with hand-drawn settings and added a declarative API in 1.13 ([Obsidian: Settings](https://docs.obsidian.md/Plugins/User+interface/Settings)). IntelliJ is the exception: its settings pages are plugin-drawn forms ([IntelliJ: Settings](https://plugins.jetbrains.com/docs/intellij/settings-guide.html)). For Argo, a schema drawn with FieldGroup also gets the phone layout right for free.

**Compiling TSX on every load.** VS Code and Obsidian load a built file named in the manifest (`main: ./out/main`) ([Git package.json](https://github.com/microsoft/vscode/blob/main/extensions/git/package.json), [Obsidian: Build a plugin](https://docs.obsidian.md/Plugins/Getting+started/Build+a+plugin)). Building and hot reload belong to dev mode: Raycast's `npm run dev` ([Raycast: First extension](https://developers.raycast.com/basics/create-your-first-extension)) and Zed's "Install Dev Extension", which overrides the published copy ([Zed: Developing Extensions](https://zed.dev/docs/extensions/developing-extensions)). Keep esbuild for dev Plugins and first-party builds. Installed Plugins load built JS. Agent-written Plugins can go through the dev path later.

**Building the system before the Plugin.** This is about order, so it is covered in the phasing section below.

## The Issue tracker should copy IntelliJ's Tasks plugin

IntelliJ already ships what Argo wants. Its "Issue Trackers" plugin (`com.intellij.tasks`) owns one provider extension point, which its source calls "the main extension point for issue tracking integration." YouTrack, Redmine and others register there, and Jira, Trac and Bugzilla ship as **modules inside the same plugin** ([tasks-core plugin.xml](https://github.com/JetBrains/intellij-community/blob/master/plugins/tasks/tasks-core/resources/META-INF/plugin.xml), [TaskRepositoryType.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-api/src/com/intellij/tasks/TaskRepositoryType.java)). So "one Plugin, several providers inside" is a match. Keeping that interface internal in v1 is fine, as long as it has the same shape: name, icon, settings, create a connection, and states on the connection rather than on the provider type. Then promoting it to a public extension point later is a move, not a rewrite. IntelliJ's GitHub provider lives in the GitHub plugin, which already owns GitHub sign-in ([intellij.vcs.github.tracker.xml](https://github.com/JetBrains/intellij-community/blob/master/plugins/github/github-tracker/resources/intellij.vcs.github.tracker.xml)). That is the case a public extension point would later serve in Argo.

Three details are worth copying. First, IntelliJ stores each Project's configured trackers per user. Only the type and URL of trackers marked "shared" go into committed project files, and credentials go to the keychain keyed by provider, URL and user ([TaskManagerImpl.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-impl/src/com/intellij/tasks/impl/TaskManagerImpl.java), [BaseRepository.java](https://github.com/JetBrains/intellij-community/blob/master/plugins/tasks/tasks-api/src/com/intellij/tasks/impl/BaseRepository.java)). Second, it drops configs whose provider disappeared. Third, Grafana adds a "Save & Test" health check per configured instance ([Grafana: Backend plugins](https://grafana.com/developers/plugin-tools/key-concepts/backend-plugins/)), which fits the `project.details` picker. Using the `gh` CLI for GitHub has no direct precedent in this research. The proven pattern is a host-owned sign-in, like VS Code's `authentication.getSession('github')` used by GitHub Pull Requests ([credentials.ts](https://github.com/microsoft/vscode-pull-request-github/blob/main/src/github/credentials.ts)). `gh` is a fine first provider, but keep it behind the provider interface so a host sign-in can replace it.

## Ship the API and its first Plugin in the same milestone

Every system here built its plugin API and its first real plugin together. VS Code 1.11 moved Git out of core in March 2017, and the release notes say it "goes through the same extension points as third-party SCM providers" and that the SCM API "is now public" in the same release ([VS Code 1.11](https://code.visualstudio.com/updates/v1_11)). Even now, built-in Git uses about **35 proposed APIs**, which only built-in or allowlisted extensions may call ([Git package.json](https://github.com/microsoft/vscode/blob/main/extensions/git/package.json), [extensionsProposedApi.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/extensions/common/extensionsProposedApi.ts)). JetBrains moved plugins out of the IDE in waves (2019, 2022, 2023), each after the platform could carry them ([IntelliJ notable changes 2023](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2023.html)). Backstage is the warning. Its New Frontend System turns every screen into a slot. It was "adoption ready" in v1.42 and only became the default in v1.49, after a long hybrid migration that its own guide says not to stay in ([Backstage v1.49.0](https://backstage.io/docs/releases/v1.49.0/), [Backstage: Migrating apps](https://backstage.io/docs/frontend-system/building-apps/migrating)). Its lesson for Argo: name the core slots before the first Plugin ships, and move a feature out in one go.

So keep the ADR, the parent spec and the four slices, with three changes. **The Issue tracker Plugin exists from slice 1 as a skeleton.** Each slice ends with it visibly working one step further, the way Git proved the SCM API. **Static contributions come before the reconciler.** Nav items and schema-drawn settings need no JSX, so slice 2 can ship them end to end. **All Plugin API is "proposed" in v1**, like VS Code's proposals: first-party Plugins may use it, and nothing is promised to others until a second Plugin has used it.

| Slice | Delivers | Issue tracker at the end | Pattern |
|---|---|---|---|
| 0. ADR + parent spec | Manifest schema (`engines.argo`, `contributes`), slot id rules, typed API package | Manifest written | `vscode.d.ts`; Grafana `plugin.json` |
| 1. Core nav refactor + catch-all route | Rail and drawer read nav from a list; Issues and Atlas stubs deleted | Its nav item opens an empty page | VS Code `viewsContainers`; Backstage `PageBlueprint` |
| 2. Host, loader, toggles | Host with worker per Plugin, crash budget, `plugins.list`, Settings › Plugins, schema-drawn settings, dev hot reload | Nav item and settings come from its manifest; it can be turned off | VS Code host and scanner; Raycast workers; VS Code `configuration` |
| 3. Reconciler, wire, registry, slot | Small primitive catalog, snapshots and patches, `argo/project/details/v1` | Its page and slot render a static list | Raycast v1 pipeline; Grafana slots |
| 4. Providers and Start Session | GitHub provider over `gh`, per-Project choice, keychain, own SQLite, prefilled Composer | Done; Linear next | IntelliJ Tasks; Grafana health check |

For tests, the shared JSON fixtures for reconciler tests and Storybook have no published precedent. Raycast, Obsidian and Zed document little beyond dev mode and store CI. It is still a sound idea, because the tree is plain data. Add what VS Code does: integration tests that boot a real host with only the Plugin under test loaded, in VS Code's case through `@vscode/test-electron` with `--disable-extensions` ([VS Code: Testing Extensions](https://code.visualstudio.com/api/working-with-extensions/testing-extension)).

## Conclusion

The plan's architecture is not the risk; the order and the size of the promise are. Systems that lasted kept their public surface small and stable, let first-party plugins move fast on unstable API, and treated the first real plugin as the test of the API rather than its reward. If Argo exposes a small, versioned catalog and labels it all "proposed" until the Issue tracker and one more Plugin have used it, then later steps (more slots, Linear, Agent-written Plugins) become additions rather than migrations.

Two items remain open. Before Agent-written or third-party Plugins, Argo needs a permission model; Figma's manifest network allowlist and Zed's `granted_extension_capabilities` are the templates ([Figma: Plugin manifest](https://developers.figma.com/docs/plugins/manifest/), [Zed: Capabilities](https://zed.dev/docs/extensions/capabilities)). Argo also needs to decide what uninstall does to a Plugin's data folder. VS Code gives extensions an uninstall hook, and this research could not confirm that it deletes their data ([Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest)).
