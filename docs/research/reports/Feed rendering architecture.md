# Feed rendering architecture

Research snapshot, 20 November 2026.

**Start with a simpler web Feed that keeps loaded entries mounted by identity and lets the browser lay them out in normal flow.** Argo already retrieves older Session updates in pages, which is the part of ChatGPT's approach OpenAI has confirmed. Argo differs in how it renders that loaded history. Open WebUI has the closest inspectable implementation of the simpler approach. VS Code Chat and OpenCode show the cases for virtualization when a coding Session has too much content to keep mounted. [ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes#:~:text=Faster%20long%20conversations%20on%20the%20web), [Open WebUI message list](https://github.com/open-webui/open-webui/blob/0666e59d26a4d056e0bacee41742486badd71cf8/src/lib/components/chat/Messages.svelte#L523-L581), [VS Code Chat tree](https://github.com/microsoft/vscode/blob/1dedb183002b007f2bc5a2925488bb90de89f4f0/src/vs/workbench/contrib/chat/browser/widget/chatListWidget.ts#L645-L663), [OpenCode virtual rows](https://github.com/anomalyco/opencode/blob/d412042beb9821ed61c73466406f7dbfdadc04e0/packages/app/src/session/timeline/virtualizer.tsx#L1194-L1216)

The [real-Session benchmark](#real-session-benchmark) found that normal flow helped with a modest amount of loaded history. Its memory use and frame gaps grew on the largest Session. A bounded history window is the next prototype to compare with LegendList.

## ChatGPT web

- OpenAI's August 2026 release notes say long conversations retrieve messages in smaller sections. That establishes **data paging**. The release notes leave the section size, eviction, offscreen rendering and cell reuse unspecified. [August 21 release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes#:~:text=Faster%20long%20conversations%20on%20the%20web)
- In November 2024, OpenAI described bringing the start of a new conversation into view and stopping automatic bottom scrolling during generation for that interaction. Argo later chose to send the Prompt to the end and follow new content until the reader scrolls away. Changing that product behavior would also change the comparison. [November 22 release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes#:~:text=Initiating%20a%20new%20conversation%20now%20scrolls%20it%20into%20view), [Argo #1874](https://github.com/milad-alizadeh/argo-universal/issues/1874), [Feed streaming motion](Feed%20streaming%20motion.md)
- ChatGPT shows some interactive results inline and opens Canvas beside the conversation for editing. Its public Plugin guidance recommends lightweight inline cards, an expanded surface for complex interaction, and separate data and render tools to avoid repeatedly refreshing a widget. Argo already has a Workbench and Inspector for work outside the Feed. A useful product question is which Plugin output needs to stay interactive inline after its Turn settles. [ChatGPT Canvas](https://openai.com/index/introducing-canvas/), [Plugin UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines), [Plugin rendering guidance](https://developers.openai.com/plugins/build/chatgpt-ui#separate-data-processing-from-ui-rendering), [Argo Workbench and Inspector](../../adr/0039-the-workbench-summarises-sections-and-the-inspector-shows-them-in-full.md)
- The browser inspection covered a short public share in desktop Chrome. Its accessibility tree exposed four role-labeled messages. OpenAI describes public shares as snapshots. The authenticated long-conversation renderer, mounted row count during scroll, CSS containment, and recycling remain unverified. [Observed public share](https://chatgpt.com/share/6ae56d3d-ed8c-83e9-9688-427423100381), [OpenAI shared links documentation](https://help.openai.com/en/articles/7925741-sharing-conversations-and-scheduled-tasks-in-chatgpt)

A repeatable check on a long authenticated conversation would count mounted turn wrappers at the latest, middle and oldest reachable positions. Compare the same wrapper's DOM identity before and after it leaves the viewport, and read computed `position`, `content-visibility` and `contain-intrinsic-size` on its ancestors. A bounded count with changing entries would be evidence of windowing. A wrapper assigned to a different entry would be evidence of recycling. CSS containment can leave every wrapper mounted while skipping offscreen layout and paint. [CSS containment specification](https://drafts.csswg.org/css-contain-2/#using-cv-auto)

## Where Argo differs

1. **Argo already defers data.** The App requests the newest page first, 150 Session updates at a time, and pages backwards by position. Live changes resume by revision. The App translates the loaded updates into visible entries and keeps unchanged entry references. Paging and reconnect are independent of which renderer draws the resulting Feed. [History hook](../../../packages/client/src/features/feed/hooks/use-feed-history.ts), [ADR-0007](../../adr/0007-feed-sync-uses-position-and-revision.md), [view translation](../../../packages/client/src/features/feed/view/to-feed-view.ts), [view state](../../../packages/client/src/features/feed/stores/session-feed-state.ts)
2. **Each projected entry is a measurement boundary.** A Tool call group, Agent message, or Live header can have its own LegendList row. The row data carries spacing and streaming state to invalidate the right cell. Disclosures can report layout and height changes during animation. An earlier page can also grow an existing group above the reader. Those are distinct cases the scroll code handles in addition to a plain prepend. [Feed entries](../../../packages/client/src/features/feed/components/feed/feed-entry.ts), [row data](../../../packages/client/src/features/feed/components/feed/feed-row-data.ts), [row layout sync](../../../packages/client/src/features/feed/components/feed/feed-row.tsx), [disclosure motion](../../../packages/client/src/features/feed/components/feed/use-collapsible-motion.ts), [group growth](../../../packages/client/src/features/feed/components/feed/use-feed-growth.ts)
3. **Several behaviors share the same geometry.** Argo remembers an entry key and offset, seeks older pages to find it, and corrects the offset as sizes settle. Separately, the web end-follow loop watches list size while the reader follows the end, and the Composer needs clearance. These behaviors still matter with simpler layout. A normal-flow prototype could let the browser place neighboring rows and leave the App responsible for restoring the reading place, following the end and preserving a prepend anchor where browser anchoring falls short. Give each change one scroll owner. [Reading place](../../../packages/client/src/features/feed/components/feed/feed-scroll-memory.ts), [restoration](../../../packages/client/src/features/feed/components/feed/restore-feed-anchor.ts), [end following](../../../packages/client/src/features/feed/components/feed/use-feed-end-motion.web.ts), [Composer clearance](../../../packages/client/src/features/feed/components/feed/feed-scroll.tsx), [CSS Scroll Anchoring](https://drafts.csswg.org/css-scroll-anchoring/#description)
4. **Recycling trades mounts for state handling.** The previous Feed explicitly disabled it because a reused cell would inherit another entry's expanded state. The current web experiment reuses Tool call group headers and untouched closed bodies, while other rows still key content by entry and previously opened group bodies reset on reassignment. It proved DOM reuse on a real Session, with mixed frame and scripting results across two real Sessions. The initial comparison left native recycling disabled. The later Feed change enables it on native as well. Disabling recycling retains viewport virtualization and its measurements. Keeping a keyed entry mounted in normal flow would avoid scroll-driven remounts for as long as that entry stays loaded. [Previous Feed configuration](https://github.com/milad-alizadeh/argo-universal/blob/0cffdc86b530aaa0a7595c0a88226ba6449d89a7/packages/client/src/features/feed/components/feed/feed-scroll.tsx#L69-L76), [current row identity](../../../packages/client/src/features/feed/components/feed/feed-row.tsx), [disclosure state](../../../packages/client/src/features/feed/components/feed-disclosure-state.ts), [recycling checks](../../../packages/client/src/features/feed/components/feed/feed-recycling.test.stories.tsx)

## What to test next

1. **Compare the same Feed content in normal web flow and LegendList.** Use existing paging and Feed entries, preserve their keys and interactions, and let the browser own ordinary scrolling and placement. Include LegendList with recycling disabled in the baseline so mount reuse and layout ownership can be measured independently. A production switch away from the current List backend would need agreement under ADR-0032, which specifies LegendList for the shared List. [ADR-0032](../../adr/0032-one-list-and-one-list-item-drawn-by-argo-everywhere.md), [profiling guide](../../agents/profiling.md)
2. **Add offscreen deferral only when a measurement calls for it.** If layout or paint dominates, test `content-visibility: auto` on settled Turns or bounded sections, with a remembered intrinsic block size and a fallback estimate. It can skip offscreen rendering while keeping mounted DOM and component state. It still pays for initial component construction and retained memory. If DOM or heap growth is the problem, test a bounded contiguous history window with overlapping keys and an explicit retained anchor. A single tool-heavy Turn can be large, so measure section mount cost before using one Turn as the only unit. [CSS containment](https://drafts.csswg.org/css-contain-2/#using-cv-auto), [remembered size](https://drafts.csswg.org/css-sizing-4/#last-remembered), [Zulip windowing](https://github.com/zulip/zulip/blob/d770d79da7924cc7720fa8463d13d729ad6f3753/web/src/message_list_view.ts#L1688-L1799)
3. **Use real Sessions and check reading behavior along with timing.** Compare first and repeat passes in both directions, a long tool-heavy Turn, and multiple pages of settled history. Record frame intervals, long tasks, style and layout time, mounted node count and heap growth. Test Chromium and Safari, and include Firefox before shipping a containment path. Confirm anchor drift on prepend and revisit, selection and keyboard focus, opening groups and Plugin cards, and end-follow detachment and Jump to latest during streaming. Use seeded 100, 1,000 and 10,000-row tiers to find where retained rendering stops paying off. Keep native on its measured baseline until profiling on physical devices justifies a change. [Argo profiling guide](../../agents/profiling.md), [Open WebUI browser guards](https://github.com/open-webui/open-webui/blob/0666e59d26a4d056e0bacee41742486badd71cf8/src/lib/components/chat/Messages/Message.svelte#L55-L76)

## Real-Session benchmark

The temporary web renderer drew the App's existing Feed rows in a ScrollView, using stable entry keys, the same history requests and the Feed's fade. It kept loaded entries mounted and let browser scroll anchoring handle prepends. A Session-local entry key and offset recorded on `scrollend` restored the reading place on revisit. LegendList 3.7.3 ran with recycling on and off in the same production profiling build against the same local Server.

Three settled real Sessions contained approximately 448, 394 and 2,793 stored Session updates. The App groups these into fewer rendered entries. The first round ran four passes per variant per Session. A second round repeated the smaller and largest Sessions starting at matching visible content and using the same 3,200 px synthetic Chrome wheel gesture in each direction. That comparison had a median browser frame interval of about 8.3 ms. Each row in the table totals four passes, alternating down and up. Heap is page JavaScript heap after forced garbage collection. DOM is the number of elements under the Feed's scroll container after paging back through the history.

| Session and renderer | Frame gaps over 13 ms | Frame gaps over 20 ms | Main-thread script time | JS heap | Feed DOM |
| --- | ---: | ---: | ---: | ---: | ---: |
| Smaller Session, LegendList with recycling | 24 / 660 | 1 | 835 ms | 55.9 MB | 454 |
| Smaller Session, LegendList without recycling | 32 / 652 | 1 | 923 ms | 55.2 MB | 454 |
| Smaller Session, normal flow with 82 entries | 2 / 682 | 0 | 277 ms | 58.2 MB | 1,146 |
| Largest Session, LegendList with recycling | 23 / 661 | 2 | 836 ms | 78.9 MB | 1,055 |
| Largest Session, LegendList without recycling | 8 / 674 | 0 | 807 ms | 78.4 MB | 1,055 |
| Largest Session, normal flow with 1,224 entries | 58 / 626 | 0 | 297 ms | 199.8 MB | 24,014 |

- The 394-update Session was mixed in the first round. Across four passes, normal flow had 8 gaps over 13 ms and 4 over 20 ms. LegendList with and without recycling had 10 and 13 gaps over 13 ms respectively, with zero over 20 ms. This Session had 176 mounted entries in normal flow.
- Reading place held across 15 sampled prepends and revisits. The measured prepend offset moved at most 0.1 CSS px and each revisit returned to the same sampled text and offset. The probe used visible content and did not cover content growing inside an expanded group.
- Loading history in the largest Session grew normal-flow heap from 59.4 MB at 74 mounted entries to 105.9 MB at 389 and 199.8 MB at 1,224. LegendList without recycling grew from 56.7 to 78.4 MB across the same Session. The largest normal-flow run had more late frames even though measured scripting and layout time were lower.
- The test used a separate headed Chrome 157 window on macOS at 1,440 × 900. Browser frame cadence shifted in the first round on the largest Session, so the matched repeat supplies the table. The benchmark used settled Sessions and synthetic wheel input. It leaves physical trackpad gestures, live streaming, complex disclosures, cross-browser behavior and a bounded renderer unverified.

**Decision.** Keep LegendList as the production baseline and pause recycling tuning. Compare a bounded normal-flow window that swaps older and newer pages at its edges, preserves keys in the overlap and retains a visible entry and offset. The experiments demonstrate a benefit to keeping a modest window mounted and a cost to keeping the entire loaded Feed mounted. The production change would require agreement under ADR-0032.
