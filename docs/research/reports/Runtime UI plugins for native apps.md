# Send plugin UI as data, draw it natively

Research date: 2026-10-14. Input to the Plugins grilling in #506; nothing here is a decision.

Every platform studied that wants third-party UI to look native on a phone does the same thing: the plugin's code runs somewhere other than the phone and sends a tree of names from a closed vocabulary, and the host app maps each name to a component already in its binary. Shopify's remote-dom, Raycast's render tree, Claude Code mods' element trees, Adaptive Cards, Slack Block Kit and Airbnb/Nubank server-driven UI all follow this pattern. The platforms that use web views instead (Wix's Owner app, VS Code) either give up the native look or never ship to phones. Wix, the first case, shows the limit most clearly. Its React Native Owner app shows third-party apps only as a mobile dashboard in a React Native WebView, without the Wix SDK. Its native Branded App widgets are still a Developer Preview. For Argo, the evidence favours five things. Plugin code runs on the Server in a managed worker per Plugin, as Raycast does. Plugins describe views as JSON built from Argo's own primitives (ADR-0020), and actions come back as keyed events. Contribution points are declared statically in a manifest. The web view stays an opt-in escape hatch, desktop and web first. Store policy points the same way: a JSON tree drawn by components in the binary is the lowest-risk option on both stores. A web view falls under Apple's 4.7 duties. A JS interpreter on the phone is the riskiest. Finally, Claude Code mods show how to make all of this writable by an agent: a closed vocabulary, published types, a validator with exact error messages, hot reload, headless press tests and a shipped authoring skill.

## Three ways to put someone else's UI on screen

The eight systems fall into three families, depending on where the plugin's logic lives and what crosses to the screen. **Declarative trees** (Block Kit, Adaptive Cards, Airbnb Ghost Platform, Nubank's Backend Driven Content) run no third-party code in the app at all: an author's server sends JSON, and the app renders it. Adaptive Cards states it outright: "No code is needed or allowed" ([Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards/)). Slack runs the app on the developer's server and POSTs interaction payloads to it ([Slack](https://docs.slack.dev/interactivity/handling-user-interaction)). **Sandboxed or isolated JS driving host components** (Shopify remote-dom, Raycast, Claude Code mods) lets authors write real code with closures and state, but that code only produces a tree of allow-listed element names that the host draws. **Web views** (Wix's Owner app, VS Code webviews, Wix dashboard iframes) hand the author a rectangle and accept that the result will not look native.

| System | Where plugin code runs | How UI is described | Author's control of look | Phone support |
|---|---|---|---|---|
| Wix (Owner app) | Developer's or Wix's server; UI in a hosted page | Mobile dashboard in a React Native WebView | Total (it is a web page); Wix Design System is advised, not enforced | WebView only, no Wix SDK |
| Shopify UI extensions | Web Worker (web); 2021 docs: web views on Android, JavaScriptCore on iOS | remote-dom mutation records of allow-listed `s-*` elements | Props only (`tone`, `variant`, `padding`); custom CSS has no effect | POS on iOS and Android renders the same components natively |
| Slack Block Kit | Developer's server | JSON blocks | Almost none | Not documented in the sources |
| Adaptive Cards | Author's bot/service | JSON elements + HostConfig | Semantic names only | iOS/Android renderers; React Native renderer is community-run |
| Airbnb / Nubank SDUI | First-party backend | Screens, sections, actions | None; the app owns the components | Native on every platform |
| Raycast | Node worker thread per extension | React → JSON render tree → AppKit | Closed set: List, Grid, Detail, Form | macOS/Windows only |
| VS Code | Extension host (Node or WebWorker) | Contribution points + TreeView; webviews for custom UI | Full HTML in webviews, theme CSS variables | None |
| Claude Code mods | In process, inside Claude Code | Element tree (`Box`, `Text`, `Button`, `Input`, ...) in named render sites | Flex layout, no fonts or chrome | Terminal and Desktop only |

Two lessons from the table drive the rest of this report. The first is that **native look on a phone only appears where the host owns the vocabulary**: Shopify POS, Adaptive Cards and Airbnb/Nubank. The second is that **no platform documents a sandbox strong enough to call real security**. Raycast rejected sandboxing as too costly. VS Code extensions run with the user's privileges. Claude Code says plainly that "mods aren't sandboxed" ([Raycast](https://raycast.com/blog/how-raycast-api-extensions-work); [Claude Code mods](https://code.claude.com/docs/en/plugins/mods/overview)). Isolation in these systems contains crashes; it does not protect the user.

## Wix keeps third parties out of its native apps

Wix is the most instructive case because it is a React Native shop at scale. It describes "one of the largest RN code base in the world" ([Wix Engineering](https://www.wix.engineering/post/wix-engineering-now-an-official-react-native-partner)). Its mobile architecture is an internal plugin system: an **Engine** provides native infrastructure, and roughly 30 teams ship mostly-JavaScript **Modules** into one app. But that composition happens at build and release time, not at runtime. The deep-dive post was only seen through a search summary ([Wix Engineering, Medium](https://medium.com/wix-engineering/react-native-at-wix-the-architecture-ii-deep-dive-9cfcb3c2822c)). No Wix source describes loading modules after install, and none describes server-driven UI.

For third parties, Wix's surface is almost entirely web. Dashboard pages, plugins and modals are iframes, hosted on Wix's cloud or on the developer's server. They talk to the host through a Dashboard SDK that offers navigation, modals, `showToast` and `observeState`. Calls run with the intersection of the app's scopes and the logged-in user's permissions ([Wix Dashboard API](https://dev.wix.com/docs/sdk/host-modules/dashboard/introduction.md)). Dashboard plugins use a clean contribution-point pattern. A first-party page declares a named **slot** with a "Plugin API" data contract, and the plugin reads the slot's data and fills its full width. But "not all apps built by Wix include pre-defined slots" ([Wix dashboard plugins](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/dashboard-extensions/dashboard-plugins/about-dashboard-plugin-extensions.md)). Backend **service plugins** reverse the call ("Don't call us, we'll call you"): Wix calls the app's endpoint in the middle of a flow and waits for the answer ([Wix service plugins](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/backend-extensions/service-plugins/about-service-plugin-extensions.md)). That is the right shape for an Argo Issue tracker. Consistency is a matter of advice, not enforcement: developers are told to "consider using" the Wix Design System ([Wix dashboard pages](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/dashboard-extensions/dashboard-pages/about-dashboard-page-extensions.md)).

On the phone, Wix's third-party story is deliberately thin. A beta "light App Market" in the Owner app opens an app's mobile-optimised dashboard in a **React Native WebView**. Eligible apps must be dashboard-only. "The Wix SDK does not work within the Wix Owner App". iOS must hide upgrade flows. And there is no way to test before production. Wix's own page could not be fetched, and these claims rest on two search summaries that agree ([Wix: Appear on the Owner App](https://dev.wix.com/docs/build-apps/launch-your-app/marketing/wix-owner-app)). The SDK's `page.getLayout()` returns `'mobile'`, which contradicts the "no SDK" claim, so the docs disagree with each other ([Wix getLayout](https://dev.wix.com/docs/sdk/host-modules/dashboard/page/get-layout.md)). Native third-party UI exists only as Velo `wix-mobile` custom widgets in Branded Apps. That is a mobile element set (button, repeater, picker, switch, text input) with stack navigation, and it is "not yet available to all users" and in "Developer Preview" ([Wix Mobile API](https://dev.wix.com/docs/sdk/frontend-modules/mobile/introduction.md)). Branded Apps also show the line Wix draws on its own. Layout and content changes "apply to the live app automatically", while design changes need store resubmission ([Wix Help](https://support.wix.com/en/article/building-your-own-native-mobile-app-with-wix)). This suggests, without Wix saying so, a server-held screen definition interpreted by a fixed native runtime. The takeaway for Argo is a warning: a WebView-first design produces exactly Wix's phone experience, which is a web page inside a native shell.

## Allow-lists make "looks native" and "stays safe" one mechanism

Shopify's design is the most refined version of the sandboxed-JS model. Extension code is third-party and sandboxed; host code is first-party. The two meet only by message passing over `MessageChannel`, which is why Shopify can write hosts in JavaScript, Kotlin and Swift. In production, risky globals such as `importScripts` are removed, `fetch` is limited to specific domains, and the sandbox loads from a separate domain ([Shopify Engineering](https://shopify.engineering/remote-rendering-ui-extensibility)). The current **remote-dom** gives the sandbox a real DOM API. A `RemoteMutationObserver` forwards mutation records, and the host's receiver applies them only for an allow-list of element names, each with its allowed attributes, events and methods ([remote-dom](https://github.com/Shopify/remote-dom)). The result is strict: "custom CSS has no effect". Appearance comes only through props such as `tone`, `variant` and `padding`, and components inherit the merchant's brand ([Polaris web components](https://shopify.dev/docs/api/polaris/using-polaris-web-components)). Shopify's docs say the same `s-*` components render as native UI on iOS and Android POS ([POS UI extensions](https://shopify.dev/docs/api/pos-ui-extensions)). How POS executes the JavaScript today is not documented. The 2021 article says web views on Android and JavaScriptCore on iOS.

Two details of Shopify's 2025–2026 migration matter for Argo. First, Shopify **dropped its custom React reconciler** (about 89 KB) for framework-agnostic custom elements, and bundle sizes fell 40–85% under a **64 KB gzip budget** ([Shopify Engineering, July 2026](https://shopify.engineering/upgrading-checkout-blocks-app-to-polaris-web-components)). The lasting contract turned out to be the element vocabulary, not the framework. Second, a closed vocabulary always has gaps. `textAlign` disappeared and came back as `textAlignment`, checkbox labels accepted only strings until a slot was added, and developers called the new set "incomplete" ([Shopify Engineering](https://shopify.engineering/upgrading-checkout-blocks-app-to-polaris-web-components); [InfoQ](https://www.infoq.com/news/2026/10/shopify-web-components)). Argo needs a quick path from "a plugin needs X" to "the vocabulary has X".

Raycast reaches the same place from the desktop. A custom React reconciler emits a JSON **render tree**. Each render is diffed with **JSON Patch**, so nothing is sent when nothing changed. Swift turns the tree into view models and applies them to custom AppKit components, and the view-model layer keeps native code insulated from changes to the tree format ([Raycast](https://raycast.com/blog/how-raycast-api-extensions-work)). The vocabulary is coarse on purpose: four top-level views (`List`, `Grid`, `Detail`, `Form`), each with an `ActionPanel` of keyboard-bindable actions, and no layout primitives ([Raycast UI](https://developers.raycast.com/api-reference/user-interface)). Claude Code mods choose a finer vocabulary: `Box` with flex layout, `Text`, `Button`, `Input`, `Select`, `Markdown`, `Code`, and an `Svg` element on Desktop only. A tree that uses an unknown element or a disallowed prop is refused. Claude Code then draws its own version of that render site and logs a precise reason such as `Text prop "bogusProp" is not allowed` ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)).

Theming follows the same rule everywhere: **the author names a meaning, the host picks the pixels**. Adaptive Cards states it as a principle, "Card Authors own the content, Host App owns the look and feel". Its **HostConfig** is a JSON object that maps semantic sizes, colours (`good`, `warning`, `attention`), spacing and container styles to each renderer ([HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)). Block Kit leaves contrast to Slack and only asks authors to test light and dark ([Designing with Block Kit](https://docs.slack.dev/block-kit/designing-with-block-kit)). Even VS Code's escape hatch keeps theming host-side: webviews get `vscode-light`/`vscode-dark` body classes and `--vscode-*` CSS variables ([VS Code webviews](https://code.visualstudio.com/api/extension-guides/webview)). Server-driven UI at scale works the same way. Airbnb's Ghost Platform sends **Sections**, **Screens** (with `LayoutsPerFormFactor`) and **Actions**, drawn by native frameworks on each platform ([InfoQ on Airbnb](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)). Nubank builds over half its app from server-sent "building blocks" that comply with its design system, more than 1,000 screens in all ([Nubank](https://building.nu.com/server-driven-ui-framework-at-nubank/); [QCon London 2025](https://qconlondon.com/presentation/apr2025/mobile-server-driven-ui-scale)).

## Actions return as closures or verbs, and version skew is the hard part

There are two proven ways for actions to travel back. In the **stateless verb** model, used by Slack and Adaptive Cards, the app sends an interaction payload to the author's server, and the server answers with a replacement. Adaptive Cards' `Action.Execute` carries a `verb` and `data`, and the bot can return a new card shown in place of the old one ([Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)). Slack requires an acknowledgement within 3 seconds, and its `trigger_id` is single-use and expires in 3 seconds ([Slack](https://docs.slack.dev/interactivity/handling-user-interaction)). In the **closure** model, used by Raycast and Claude Code mods, handlers live inside the plugin. Raycast's worker talks to the native app over **JSON-RPC** on file-descriptor streams. Extensions "can only send registered messages, such as render or set-clipboard" and "cannot call arbitrary Raycast code" ([Raycast](https://raycast.com/blog/how-raycast-api-extensions-work)). In mods, a press calls `onPress` inside the mod; the callback changes state and calls `$.ui.invalidate`, and the host re-renders. "Every interactive drawing uses that render cycle". Controls need stable `key`s, redraws are throttled to 10 per second, and hooks have a 10-second budget ([Mods interface](https://code.claude.com/docs/en/plugins/mods/interface); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). Shopify adds the host-capability side: a global `shopify` object for data, queries, navigation, toast and modals. `fetch` to the app's own domain carries an ID token automatically, and "credentials must stay on the app server" ([Admin extensions](https://shopify.dev/docs/api/admin-extensions); [POS](https://shopify.dev/docs/api/pos-ui-extensions)).

The closure model fits an interactive Rail page: the Plugin owns its state and the App owns the pixels. The verb model is easier to generate and to test from fixtures. Argo can have both. Closures inside the Plugin work over the wire because the App sends only `{key, event, value}`, never code.

Versioning is where the open schemas suffer. Adaptive Cards puts a `version` on every card and lets elements carry `requires` and `fallback` (another element, or `"drop"`). In practice the Teams mobile app is reported to support only schema 1.2, so authors write `Action.Execute` with an `Action.Submit` fallback inside an `ActionSet`. That gives a "degraded experience", because Submit cannot return a new card ([Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model); the 1.2 figure comes only from a search snippet of the [Teams cards reference](https://learn.microsoft.com/microsoftteams/platform/concepts/cards/cards-reference)). Shopify uses dated API versions, supports each for at least 12 months, and blocks deploys that target old ones ([Checkout UI extensions](https://shopify.dev/docs/api/checkout-ui-extensions)). Nubank names "users who do not update and multiple app versions running at once" as the core problem but publishes no recipe ([QCon London 2025](https://qconlondon.com/presentation/apr2025/mobile-server-driven-ui-scale)). Claude Code falls back at the level of the whole render site, not per element ([Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)). Argo has one structural advantage: the Server sits between every Plugin and every App. It can learn what each Connection supports and adapt the tree before sending it. Neither Teams nor Shopify can do that.

## Store policy rewards data and punishes downloaded behaviour

Apple's text pulls in two directions. Guideline **2.5.2** says apps "may not download, install, or execute code which introduces or changes features or functionality of the app" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). **DPLA 3.3.1(B)** is more permissive: "Interpreted code may be downloaded", but only if it does not change the app's "primary purpose", does not bypass OS security, and does not create "a store or storefront for other Applications" ([DPLA](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)). The old exception for code run by WebKit or JavaScriptCore is no longer in the current text ([Apple Developer Forums](https://developer.apple.com/forums/thread/52161)). Guideline **4.7** explicitly permits non-embedded "HTML5 and JavaScript mini apps and mini games, streaming games, chatbots, and plug-ins". The conditions are moderation, reporting and blocking (4.7.1); no exposure of native APIs without Apple's permission (4.7.2); per-use consent for data (4.7.3); an index with universal links to all software (4.7.4); and age gating (4.7.5). Apple's November 2025 update confirmed that HTML5/JS mini apps are in scope ([Apple Developer News](https://developer.apple.com/news/?id=ey6d8onl)). Claims that 4.7 requires WebKit/JavaScriptCore and bans Hermes come only from third-party blogs; Apple's text does not say so ([UK PDF](https://developer.apple.com/support/downloads/terms/app-review-guidelines/App-Review-Guidelines-English-UK.pdf)). Google Play is simpler. Downloading dex, JAR or .so files is forbidden, but the ban "does not apply to code that runs in a virtual machine or an interpreter" with indirect API access, "such as JavaScript in a webview". A WebView "with an added JavaScript Interface that loads untrusted web content" is a listed violation ([Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/9888379?hl=en); [alt copy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en)).

No Apple ruling covers server-driven UI. The argument that it is safe comes from vendors: DockYard argues that SDUI sends "UI representations, events, and data, not executable code", mapped one-to-one onto views already in the binary ([DockYard](https://dockyard.com/blog/2024/12/20/are-liveview-native-apps-accepted-by-apple)). Rejections under 2.5.2 have hit hot-code-push SDKs, apparently because of native-calling code ([Meteor forum](https://forums.meteor.com/t/apple-starts-rejecting-apps-with-hot-code-push-features/34597), search summary only). The table below is this report's reading, not a store statement.

| Option for the phone | Apple | Google Play | Main obligation |
|---|---|---|---|
| (a) JSON tree drawn by components in the binary; logic on the Server | Lowest. Data, not code, as long as actions are an enumerated set the App already implements and the tree has no expression language | Lowest; no code is downloaded | Keep the vocabulary and host actions in the binary; explain them in review notes |
| (b) Plugin HTML/JS in a WKWebView / Android WebView | Explicit lane under 4.7, with 4.7.1–4.7.5 duties; must not become the whole app (4.2) | The exception Google itself names | No `addJavascriptInterface` for content you don't trust; message bridge only; per-use consent |
| (c) JS interpreter in the App (Hermes/JSC) running Plugin code | Highest. Allowed in text by 3.3.1(B), but weakest precedent; any native binding conflicts with 4.7.2 | Allowed if API access stays indirect | Effectively requires Apple's permission for anything useful |

Argo's situation raises two Argo-specific points, both of them inference. First, with (a), the Plugin runs on the user's own Mac and only data reaches the phone. That resembles 4.2.7's remote-desktop carve-out (logic "fully executed on the host device", which must be "user-owned", on a LAN), but nobody has tested whether Argo qualifies. Second, the policy text never treats the source of downloaded code (the user's Server or a vendor) as relevant: with (b) or (c), Plugin code is still code "not embedded in the binary", and "you are responsible for all such software offered in your app" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). The storefront clause also bears on product design. A phone screen for browsing and installing outside Plugins comes close to 3.3.1(B)(c) and 4.2.7(d). Installs started from the user's own Server are safer than a catalogue.

## What Argo could copy: input for the #506 grilling

The recommendations below take the #506 starting proposal (Plugins run on the Server, contribute only through named places, and send data rather than UI code) and fill in the mechanics from the evidence above. They also mark where the evidence pushes back.

### Plugin code runs in one managed worker per Plugin on the Server

Copy Raycast. The Engine starts one isolated worker per enabled Plugin, either a Node worker thread or a child process (an open choice). Workers talk to the Engine only through a registered message set, such as `render`, `toast`, `navigate`, `storage.get/set`, `issues.*` and `fetch`. Raycast showed that this gives a per-extension heap cap and a per-extension error screen while the app keeps running ([Raycast](https://raycast.com/blog/how-raycast-api-extensions-work)). Add the Claude Code budgets: a timeout per handler (10 s for actions, much shorter for render), a fault event, and a fallback drawing when a tree fails ([Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). Load Plugins lazily, the way VS Code uses activation events and Raycast unloads a command when its view closes ([Raycast lifecycle](https://developers.raycast.com/information/lifecycle)). Be honest about trust: a Plugin on the user's Mac is trusted local code, like Raycast, VS Code and Claude Code plugins. The worker contains crashes, not attackers. Plugin secrets stay on the Server, as Shopify insists ([POS](https://shopify.dev/docs/api/pos-ui-extensions)), and no App ever runs Plugin code. This keeps ADR-0002's equal abilities across Devices and option (a)'s store position. When a Plugin faults, the surface shows its fallback and Argo raises one error toast through the existing wrapper; there is no centred error screen.

### The UI format is a JSON view tree over Argo's primitives, not a layout language

Define a closed, versioned vocabulary that maps one-to-one onto the primitives ADR-0020 already owns. Each element is drawn by SwiftUI or Compose on the phone and by Argo's Uniwind components on web and desktop. A starting set: page templates in Raycast's style (`List`, `Detail`, `Form`); `ListItem`, `FieldGroup`/`FieldSection`, `Menu`, `SelectMenu`, `TextField`, `Toggle`, `Button` (semantic variants only); `Text` with a typography role (title, heading, body, secondary); `Icon` by **Argo icon name**, never by SF or Material name, so ADR-0019's map stays the only place those names live; `Badge`/chip with a tone; `Markdown`; `Code`; and a `Stack` limited to semantic gaps. Props are data, as ADR-0020 already requires ("data props, not children"). There is no `className`, no pixel values and no colour values, only tones and roles, so HostConfig's guarantee holds by construction ([HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)). Prefer Raycast's coarse templates over Claude Code's free `Box`. A free flex box lets a Plugin hand-build rows, which is exactly what Argo forbids in its own screens. A `Form` template lets the App draw iOS grouped cards and Android plain stacked M3 fields from the same tree.

Plugins write JSX that compiles to plain JSON objects, as `.tsx` mod trees do. There is no reconciler in the Plugin, which avoids the dead weight Shopify had to remove. The Engine diffs successive trees with JSON Patch, as Raycast does, and pushes patches over the existing tRPC subscription on the one WebSocket (ADR-0002). The tree is validated with Zod at the Server boundary. Following ADR-0015, anything unrecognised is rejected, reported and counted, with a message as exact as Claude Code's refusal lines. Do not add an expression language like json-render's `$cond`/`$computed` ([json-render](https://github.com/vercel-labs/json-render)). Logic in the tree is what moves SDUI from "data" towards "code" in a reviewer's eyes, and the Server can compute anything the tree would have computed.

Actions use the closure model. Each control has a stable `key`. The App sends `{plugin, surface, key, event, value}` as a tRPC mutation, the worker runs the handler, the handler changes state and invalidates, and the Engine re-renders with coalescing (mods throttle at 10/s). Host-side effects go through an enumerated set of host actions in the tree: `navigate` (to a Plugin page or an Argo route), `openSession`, `insertIntoComposer`, `toast`, `openUrl` and `copy`. The App already implements all of them, which keeps option (a) in its lowest-risk form. Text inputs should keep their value locally and send on submit or after a debounce, because a paired phone may be on a relay rather than localhost. This last point is an inference; none of the sources faced that latency.

### Contribution points are declared in a manifest and filled at runtime

Follow VS Code's split. The manifest declares each contribution statically (id, title, Argo icon name, order, the Rail or Inspector placement), so the App can draw a Rail icon, a Settings row or a Plugin page's "What it adds" section before any Plugin code runs. Content arrives later through `render` ([VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)). Claude Code's `Pane` and `AbovePrompt` are the direct analogues of a Rail page and a Composer band ([Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)).

| Contribution point | Shape | Desktop / web | Phone | Precedent |
|---|---|---|---|---|
| Rail item + page | Manifest: id, title, icon, order. Runtime: a page tree (`List`/`Detail`/`Form`) plus header actions | Rail tile → page in the main pane; the page draws its own header | Drawer row → pushed native screen; header title from the manifest; header actions as `headerRight` | VS Code `viewsContainers` + `views`; Raycast view commands |
| Composer band | Runtime tree, height-capped, per Session; receives Session context | Band above the Composer, inside the one Session column | Same; Permission/Elicitation cards stay closest to the Composer and never displaced | Claude Code `AbovePrompt` (shared, ordered) |
| Inspector panel | Manifest: id, title, icon. Runtime tree with the selected Session/Issue/file as input | Inspector section | Bottom sheet | Wix dashboard slots + `observeState`; VS Code views |
| Issue tracker | **No UI.** A typed provider: list/search/get, status catalogue + mapping to Argo statuses, transitions, link to Sessions | Argo's own Issues UI | Argo's own Issues UI | Wix service plugins; Shopify runnable targets |
| Settings section | Manifest: a typed settings schema (string, secret, toggle, select); secrets to the OS credential store on the Server Device | FieldGroup rows under Settings › Plugins › <Plugin> | Grouped card (iOS), stacked M3 fields (Android) | Raycast `preferences`; Claude Code `userConfig` with `sensitive` |

The Issue tracker point matters most. Argo should draw the Issues UI itself and let trackers supply only data, so Linear, Jira and GitHub Issues look identical and status mapping lives in one place. If the built-in trackers go through the same provider interface, the Plugin API is used from day one. Atlas is the natural test case for the vocabulary's limit. A code map needs a graph canvas that no list-and-form vocabulary contains, which leaves two choices. Argo can add a first-party `Graph` element (as Claude Code added `Svg` for Desktop), or Atlas can use the web-view escape hatch. Grilling Atlas first will show whether the vocabulary is big enough.

### The web view is an escape hatch, desktop and web first

Offer a `WebView` element whose content the Server serves from the Plugin's folder. Copy VS Code's rules: scripts only when declared, CSP `default-src 'none'` plus explicit allowances, local resources limited to the Plugin's root, theme passed as CSS variables matching Argo's tokens, and a JSON-only `postMessage` bridge carrying the same enumerated host actions ([VS Code webviews](https://code.visualstudio.com/api/extension-guides/webview)). On **web and Electron**, it is a sandboxed iframe with an opaque origin, as Wix sandboxes site widgets ([Wix sandboxing](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/site-extensions/handle-sandboxing-in-the-editor.md)). On **iOS** it would be a WKWebView, which puts the Plugin under 4.7: Argo would need 4.7.1 reporting/blocking, an index (4.7.4) and per-use consent for any data (4.7.3), and must not expose native APIs (4.7.2). On **Android** it would be a WebView with message ports and **no** `addJavascriptInterface`, since the content is not reviewed by Argo. Ship web views on desktop and web only at first. On the phone, a web-view surface draws a native fallback the Plugin declares (for example a `Detail` with a summary and an "Open on desktop" action). This is the one place where the evidence argues against ADR-0002's "same abilities everywhere", and it needs an owner ruling.

### Plugin storage lives in the Server database, code stays in files

Plugin code lives as files under `~/.argo/plugins/<id>/`, the equivalent of `${CLAUDE_PLUGIN_ROOT}`. A separate data directory survives updates, like `${CLAUDE_PLUGIN_DATA}` ([Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)). The SQLite database (ADR-0002) holds the rest. A `plugins` table stores id, source (built-in, folder, git, npm), version, the declared API version, the validated manifest JSON, enabled state, last load status, and fault counts for ADR-0015 reporting. A per-Project enablement table answers #506's question 7, and a non-secret settings table holds Settings values. A `plugin_kv` store is scoped by Server, Project or Session. Unlike Claude Code's `$.store`, which is 4 MiB and race-prone because get-then-set is not atomic ([Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)), every `plugin_kv` write goes through the existing Writer, so updates are transactional and Writer commit notifications invalidate App queries as they already do. Secrets go to the OS credential store, never into SQLite.

### Versioning: one integer API, Connection capabilities, two fallback layers

Every manifest declares `argoApi: <n>`. Each Connection tells the Server which API version and elements its App supports, an Argo version of HostConfig's per-property versioning ([HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)). This matters because ADR-0022 lets one App talk to several Servers, and a phone from the App Store will often be older than the Server. Before sending, the Server checks the tree against that Connection's capabilities and resolves per-element `fallback`s, as in Adaptive Cards. If a surface still cannot be drawn, the App shows a whole-surface fallback such as "Update Argo to see this", as in Claude Code. Shopify's discipline is worth copying: support each API version for a fixed period, and have the validator refuse Plugins that target versions Argo has dropped ([Checkout UI extensions](https://shopify.dev/docs/api/checkout-ui-extensions)).

### Store risk depends on keeping the phone a renderer

If Argo picks the JSON tree on the Server, the phone downloads no code, every element and host action is in the binary, and the App Store description and review notes can truthfully say "extend Argo with plugins that run on your Mac". This is option (a), the lowest risk on both stores. Phone web views are option (b): manageable, but they bring Argo under 4.7 with its moderation and index duties, so keep them out of the first phone release. A JS engine in the App is option (c). It adds nothing that running the code on the Server does not already provide, and it carries the most review risk, so drop it. Separately, keep Plugin browsing and installing off the phone, or limit the phone to enabling what the user's Server already has (3.3.1(B)(c), 4.2.7(d)). Give App Review a demo Server and a sample Plugin, because a phone App that needs a desktop Server already invites 4.2.3 questions.

### The agent-authoring loop copies Claude Code mods

Claude Code shows the ingredients that make UI plugins writable by an LLM. "Describe what you want in a Claude Code session, and Claude writes the mod". A built-in `plugin-authoring` skill and published `claude-code.d.ts` types serve as the spec. `claude plugin validate` lists every event handled and API called, with `--json` for machines. `claude plugin test` presses controls by `key` without a UI. `--plugin-dir` reloads on save. Refusals name the offending prop ([Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)). Argo's version of the loop has six steps. (1) A user asks the Agent in a Session for a Plugin. (2) The Agent loads an Argo `plugin-authoring` skill. The skill points at the vocabulary types, generated from the same Zod schemas the Server validates with, so they cannot drift, plus an `llms.txt`-style reference. (3) The Agent writes into a dev folder the Server watches. (4) It calls `validate` and `test`, which the Server exposes to Sessions as tools, for example over MCP, so any ACP Agent can use them. Both return structured errors. (5) The Server hot-reloads the Plugin, and its Rail item or band appears live in the user's App. (6) The user enables it after seeing the validator's list of what the Plugin touches (network hosts, Project files, Sessions). Storybook (ADR-0021) can render the same fixture trees through the real renderer, giving Argo a visual check that Block Kit Builder and the Adaptive Cards Designer provide for their formats ([Block Kit](https://docs.slack.dev/block-kit/); [Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards/)).

### Open questions for the grilling

Several questions remain open. Does ADR-0002's equal-abilities rule allow a surface that is native on the phone but a web view on desktop, or a desktop-only Plugin at all? Is the vocabulary Raycast-coarse (templates only) or does it include a constrained `Stack`, and who decides when a Plugin needs a new element? Is each Plugin a worker thread (cheap, shared process) or a child process (stronger containment, Raycast's rejected cost)? Do the built-in Linear, Jira and GitHub Issues Plugins use the public provider interface, and how does one Project use two trackers? Can a Plugin call the Agent, start Sessions or edit the Composer, which is the reach Claude Code's `$.agent` and `$.prompt` give mods, and how does a person grant that? Can a phone install Plugins, given the storefront clause? Does Atlas get a first-party graph element or a web view? Should Argo send App Review a pre-submission question before relying on 4.2.7-style reasoning? Finally, the sources leave several things unknown: how Shopify POS runs extension JS today, how Slack's phone apps draw Block Kit, and how Airbnb handles unknown sections.

## Conclusion

The research changes the framing of #506's question 4. The choice is not really "native data versus web views". The real question is who owns the vocabulary, and how fast it can grow. Every system that looks native on a phone gets there because the host owns a closed set of components and the plugin only names them. Every complaint in those systems is about a component the host has not built yet. Argo already owns its primitives (ADR-0020) and already validates outside data at the Server (ADR-0015). A Plugin vocabulary is therefore the same primitives, given a schema and a version number. The store analysis also produces an unexpected result: running Plugins on the Server, chosen for architecture reasons in ADR-0002, is the same decision that keeps the iOS App on the safest side of 2.5.2 and 4.7.

The second insight is that agent authoring and safety need the same thing. A closed vocabulary, typed schemas, a strict validator with exact refusals, and a per-surface fallback are what let Claude Code's agent write mods reliably. They are also what keep a bad Plugin from blanking a screen, and what lets a reviewer see that the phone only draws data. Built for the agent loop first, Argo's Plugin system gets its native look and its store position from the same design.
