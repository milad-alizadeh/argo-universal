# Plugin system patterns to copy: JetBrains IntelliJ Platform, Grafana, Backstage, Figma

Researched 2026-10-14 for Argo (Expo app + local Node Server; plugins run on the Server; UI places = plugin pages, a Settings section, nav items, slots in core pages such as `project.details`; plugins keep their own storage and point at core entities by id; first plugin = Issue tracker with several providers chosen per Project). Sources are official docs and the projects' own source code, read on GitHub at `main` on the date above.

## JetBrains IntelliJ Platform: plugin.xml, extension points, services, dynamic plugins, settings, secrets, and the Tasks plugin (many issue-tracker providers in one plugin)

### Takeaway
IntelliJ is the closest match to Argo's Issue tracker. A host plugin ("Issue Trackers", id `com.intellij.tasks`) owns one provider extension point (`com.intellij.tasks.repositoryType`). Each provider (YouTrack, GitHub, Jira, Redmine, ...) is one class registered against that point, and some ship as separate modules or plugins. The host keeps a per-project list of configured "servers" (provider type + URL + settings). Passwords live in the OS keychain (PasswordSafe), never in project files. Only the type and URL of servers marked "shared" go into the project files that teams commit.

### Cited Findings
**Declaring and using extension points**
- An extension point (EP) is declared in `plugin.xml` under `<extensionPoints>` with `name` or `qualifiedName`, plus either `interface` (other plugins supply classes that implement it) or `beanClass` (other plugins supply data that becomes bean instances). — [Extension Points](https://plugins.jetbrains.com/docs/intellij/plugin-extension-points.html)
- Consumers register under `<extensions defaultExtensionNs="my.plugin">` with one element per EP, e.g. `<myExtensionPoint1 key="..." implementationClass="..."/>`. At runtime the host reads them with `ExtensionPointName.create("my.plugin.myExtensionPoint1").getExtensionList()`. — [Extension Points](https://plugins.jetbrains.com/docs/intellij/plugin-extension-points.html)
- For dynamic plugins, the host must list extensions again on every use and must not store the instances. Otherwise it registers an `ExtensionPointListener` to react to adds and removes. EPs that follow these rules are marked `dynamic="true"`, and the DevKit inspection flags EPs that are not. — [Extension Points](https://plugins.jetbrains.com/docs/intellij/plugin-extension-points.html)
- Errors should be logged with `PluginException` so they are blamed on the right plugin. — [Extension Points](https://plugins.jetbrains.com/docs/intellij/plugin-extension-points.html)

**Services (application-level and project-level)**
- Services exist at application level (one global instance) and project level. Module-level services are discouraged because they use more memory. A service is created lazily on the first `getService()` call, and only one instance ever exists. — [Services](https://plugins.jetbrains.com/docs/intellij/plugin-services.html)
- A "light service" is a `final` class annotated `@Service`, with no `plugin.xml` entry. A declared service uses `applicationService`/`projectService` with a required `serviceImplementation` and an optional `serviceInterface`. Constructor injection of other services is deprecated. A coroutine service gets its own `CoroutineScope`, which is cancelled when the project closes or the plugin unloads. — [Services](https://plugins.jetbrains.com/docs/intellij/plugin-services.html)
- Pitfalls: don't cache service instances in fields or statics, avoid initialization cycles (they throw), and keep constructors light for startup speed. Put cleanup in `Disposable.dispose()`. — [Services](https://plugins.jetbrains.com/docs/intellij/plugin-services.html)

**Dynamic plugins (install, update, uninstall without a restart)**
- Requirements: no legacy "components" (use services, extensions and listeners), unique action group ids, only dynamic EPs used, own EPs declared dynamic, any `Configurable` that depends on dynamic EPs implements `Configurable.WithEpDependencies`, and no `overrides="true"` services. Paid third-party plugins are excluded. A plugin can opt out with `require-restart="true"`. — [Dynamic Plugins](https://plugins.jetbrains.com/docs/intellij/dynamic-plugins.html)
- Load and unload run under a write action on the EDT. Plugins hold `SmartPsiElementPointer` rather than raw PSI references, key maps by string ids rather than `FileType`/`Language` objects, and listen to `DynamicPluginListener` to cancel work and clear data. — [Dynamic Plugins](https://plugins.jetbrains.com/docs/intellij/dynamic-plugins.html)
- Failure mode: the IDE waits for unload to finish, and if unload fails (usually because something still references the plugin's classloader) it asks the user to restart. A registry key, `ide.plugins.snapshot.on.unload.fail`, writes an `.hprof` heap dump so authors can find the `PluginClassLoader` leak. Marketplace runs the Plugin Verifier on every upload. — [Dynamic Plugins](https://plugins.jetbrains.com/docs/intellij/dynamic-plugins.html)

**Compatibility ranges and descriptor**
- `since-build` is required. `until-build` is optional, and the docs strongly recommend leaving it unset so the plugin stays compatible going forward. `strict-until-build` (since 2025.3) sets a hard upper limit, for publishers who release one version per major IDE release. — [Plugin Configuration File](https://plugins.jetbrains.com/docs/intellij/plugin-configuration-file.html)
- `<depends optional="true" config-file="x.xml">` loads extra registrations only when the other plugin is present. `<incompatible-with>` blocks loading when a named plugin is installed. — [Plugin Configuration File](https://plugins.jetbrains.com/docs/intellij/plugin-configuration-file.html)
- Deprecated: `application-components`/`project-components` (since 2020.1) and the `IDEA_MODULE` EP area. — [Plugin Configuration File](https://plugins.jetbrains.com/docs/intellij/plugin-configuration-file.html)
- The current descriptor format splits a plugin into `<content><module name=.../></content>` modules with a `<dependencies>` block. The Tasks plugin's own `plugin.xml` uses this to ship `intellij.tasks.jira`, `intellij.tasks.trac` and `intellij.tasks.bugzilla` as content modules of one plugin. — [tasks-core plugin.xml](https://github.com/JetBrains/intellij-community/blob/master/plugins/tasks/tasks-core/resources/META-INF/plugin.xml)

**Settings (Configurable)**
- Settings pages are registered as `applicationConfigurable` (IDE-wide) or `projectConfigurable` (per project) in `<extensions defaultExtensionNs="com.intellij">`. Attributes: `instance` or `provider`, `id`, `displayName` or `key`+`bundle`, `parentId` (group, e.g. `tools`; `groupId` is deprecated), `groupWeight`, and `nonDefaultProject`. — [Settings Guide](https://plugins.jetbrains.com/docs/intellij/settings-guide.html)
- Allowed groups: `appearance`, `build`, `build.tools`, `editor`, `language`, `tools`. `root`, `other` and `project` must not be used. A `ConfigurableProvider.canCreateConfigurable()` hides the page when it does not apply. Project configurables take a single `Project` constructor argument. — [Settings Guide](https://plugins.jetbrains.com/docs/intellij/settings-guide.html)

**Persisted state**
- `PersistentStateComponent` with `@State(name=...)` and `@Storage(file, roamingType)`. Project-level components default to the project file (in `.idea/`, shared via VCS). Per-user, per-machine project values go in `StoragePathMacros.WORKSPACE_FILE` (`workspace.xml`, not shared). App-level state should use a custom file; `other.xml` is deprecated. — [Persisting State](https://plugins.jetbrains.com/docs/intellij/persisting-state-of-components.html)
- `RoamingType` takes `DEFAULT`, `PER_OS` or `DISABLED`. A component holding both shareable and machine-specific data should be split into two components. `loadState()` can fire after an external file change, so the UI must refresh. `SerializablePersistentStateComponent` (immutable data class plus `updateState`) has been recommended since 2022.2. — [Persisting State](https://plugins.jetbrains.com/docs/intellij/persisting-state-of-components.html)

**Secrets (PasswordSafe)**
- `PasswordSafe` stores passwords, API keys and private keys under `CredentialAttributes(serviceName, userName?)`, with `generateServiceName(subsystem, key)` → "IntelliJ Platform <subsystem> - <key>". Backends: macOS Keychain, Linux Secret Service (libsecret), and a KeePass-format file on Windows; the user can change this in Settings. — [Persisting Sensitive Data](https://plugins.jetbrains.com/docs/intellij/persisting-sensitive-data.html)
- Calls block, so they must run off the EDT (Kotlin: `Dispatchers.IO`). PasswordSafe cannot list stored credentials, so the username/identity has to be persisted separately in normal state. Since 2025.3, Remote Development stores credentials on the frontend; before that they were plain text on the backend. — [Persisting Sensitive Data](https://plugins.jetbrains.com/docs/intellij/persisting-sensitive-data.html)

**The Tasks & Contexts plugin, step by step (source code)**
- The platform API module declares two EPs: `com.intellij.tasks.repositoryType` (interface `TaskRepositoryType`, `dynamic="true"`) and `com.intellij.tasks.contextProvider`. — [intellij.platform.tasks.xml](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-api/resources/intellij.platform.tasks.xml)
- `TaskRepositoryType<T extends TaskRepository>` is documented in source as "The main extension point for issue tracking integration". Each provider implements `getName()`, `getIcon()`, `createEditor(repository, project, changeListener)` (its own settings form), `createRepository()`, `getRepositoryClass()`, optional `getAvailableSubtypes()` (variants of one provider) and `getSortOrder()`. Task states moved from the type (`getPossibleTaskStates`, deprecated for removal) to the configured repository (`TaskRepository#getAvailableTaskStates(Task)`). — [TaskRepositoryType.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-api/src/com/intellij/tasks/TaskRepositoryType.java)
- The host plugin is named "Issue Trackers", id `com.intellij.tasks`. It registers YouTrack, Lighthouse, Pivotal Tracker, Redmine, FogBugz and others as `<tasks.repositoryType implementation="..."/>`. Its source tree also has gitlab, mantis, trello and a "generic" (configurable REST) provider. Settings are one `projectConfigurable` (`groupId="tools"`, id `tasks`) with a child configurable `TaskRepositoriesConfigurable`, which is the "Servers" page under Tools › Tasks. — [tasks-core plugin.xml](https://github.com/JetBrains/intellij-community/blob/master/plugins/tasks/tasks-core/resources/META-INF/plugin.xml), [tasks-core sources](https://github.com/JetBrains/intellij-community/tree/master/plugins/tasks/tasks-core/src/com/intellij/tasks)
- The GitHub provider is not in the Tasks plugin. It lives in the GitHub plugin as a small module (`intellij.vcs.github.tracker`) that depends on plugin `com.intellij.tasks` and contributes one `tasks.repositoryType` (`GithubRepositoryType`). So a provider can ship from another plugin that already owns that vendor's auth. — [intellij.vcs.github.tracker.xml](https://github.com/JetBrains/intellij-community/blob/master/plugins/github/github-tracker/resources/intellij.vcs.github.tracker.xml)
- The configured servers per project are held by `TaskManagerImpl`, annotated `@State(name="TaskManager", storages=@Storage(StoragePathMacros.WORKSPACE_FILE))`, i.e. per user and machine, not shared. On load it loops over every registered `TaskRepositoryType`, deserializes the XML elements named after each type into that type's repository class, and skips types with no settings so their EPs are not loaded early. — [TaskManagerImpl.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-impl/src/com/intellij/tasks/impl/TaskManagerImpl.java)
- Team sharing is a second project service, `TaskProjectConfiguration` (`@State(name="TaskProjectConfiguration")`, default project file, i.e. committed). It stores only `<server type="..." url="..."/>` for repositories marked `isShared()`. On project open, `TaskManagerImpl.projectOpened()` creates a local repository for each shared server that has no local one yet, so a teammate gets the tracker set up automatically and only adds their own credentials. — [TaskProjectConfiguration.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-impl/src/com/intellij/tasks/impl/TaskProjectConfiguration.java), [TaskManagerImpl.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-impl/src/com/intellij/tasks/impl/TaskManagerImpl.java)
- When a provider is uninstalled, `TaskManagerImpl` listens for EP changes and drops configured repositories whose type no longer exists (`removeIf` on repository classes). — [TaskManagerImpl.java](https://github.com/JetBrains/intellij-community/blob/master/platform/tasks-platform-impl/src/com/intellij/tasks/impl/TaskManagerImpl.java)
- Credentials: `BaseRepository.getPassword()` is `@Transient` (never serialized to XML) and loads lazily from `PasswordSafe`. The key is `CredentialAttributes(generateServiceName("Tasks", repositoryType.getName() + " " + url), username)`. — [BaseRepository.java](https://github.com/JetBrains/intellij-community/blob/master/plugins/tasks/tasks-api/src/com/intellij/tasks/impl/BaseRepository.java)

**Bundled plugins vs Marketplace**
- JetBrains has moved plugins out of the IDE bundle in several waves: J2ME, JsTestDriver and Struts 1.x in 2019.2; Haml, Vaadin, Tapestry and others in 2022; Android, Ant, GlassFish and Plugin DevKit in 2023. Unbundled plugins move to Marketplace with their own release cycle, and the IDE suggests installing them when a project uses the related framework. — [Notable changes 2019](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2019.html), [2022](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2022.html), [2023](https://plugins.jetbrains.com/docs/intellij/api-notable-list-2023.html)
- Old, retired plugins are archived in a public repo. — [intellij-obsolete-plugins](https://github.com/JetBrains/intellij-obsolete-plugins)

### Inferences
- Argo's Issue tracker can follow Tasks almost exactly. Use one "provider" extension point with name, icon, settings schema/form, `createConnection(config)` and capabilities. Keep one list of configured connections per Project. Providers can be bundled with the Issue tracker plugin or contributed by other plugins (as GitHub does).
- Copy the shared/local split. Shareable connection info (provider + URL/workspace) goes on the Project, so it can travel with the repo or to other Devices. Credentials go in the OS keychain, keyed by `provider + url + user`. Per-user state stays local.
- Copy "drop configs whose provider vanished" and "don't load providers with no config".
- IntelliJ's dynamic-unload pain comes from in-process classloaders and leaked references. Argo's choice to run plugins on the Server, ideally in their own process or worker, avoids most of it.

### Gaps
- Linear and Jira Cloud as `TaskRepositoryType`s: Jira ships as a content module of the Tasks plugin. Whether a Linear provider exists in-repo or only on Marketplace was not checked.
- No official write-up found of the history or pitfalls of the Tasks plugin itself.
- 2024–2026 unbundling waves were not found in search results.

## Grafana: plugin.json, core vs external plugins, backend plugins as processes, UI extensions (slots), per-instance data source config and secrets

### Takeaway
Grafana has three plugin types (app, panel, datasource), each described by `plugin.json`. Backend parts run as separate processes over gRPC (hashicorp/go-plugin), so a crash stays inside the plugin. UI extension is a typed slot system: core and app plugins declare string-id extension points (`grafana/dashboard/panel/menu`, versioned with a `/vN` suffix). Plugins push links, components or functions into those slots, or expose components for others to pull. Each slot passes a frozen context object, and contributions must be declared in `plugin.json`. Data sources are multi-instance: one plugin type, many configured instances, each with `jsonData` (public) and `secureJsonData` (encrypted, never sent back to the browser). That instance model fits Argo's "several providers, chosen per Project".

### Cited Findings
**plugin.json**
- `type` takes `app`, `datasource`, `panel` or `renderer`. `includes[]` lists pages, dashboards and panels, with `type`, `path`, `role` (minimum role to see it in navigation), `action` (RBAC), `addToNav` and `defaultNav`. `dependencies.grafanaDependency` is a required semver range; `grafanaVersion` is deprecated. `dependencies.plugins[]` lists required external plugins. — [plugin.json reference](https://grafana.com/developers/plugin-tools/reference/plugin-json)
- `backend: true` plus `executable` gives the binary name prefix; Grafana looks for `<executable>_<GOOS>_<GOARCH>`. `preload` (app plugins only) loads the plugin at startup instead of on first use. `autoEnabled` enables an app in every org and pins it to the nav. `roles[]` (9.4+) lets plugins define RBAC roles, with action names prefixed by the plugin id. `iam` (10.3+) gives the backend a service account token. — [plugin.json reference](https://grafana.com/developers/plugin-tools/reference/plugin-json)
- `extensions` in plugin.json: `addedLinks[]`, `addedComponents[]` and `addedFunctions[]` (each with `targets`, `title`, `description`), `exposedComponents[]` (with `id` in the form `{PLUGIN_ID}/name/vN`), and `extensionPoints[]` (`id`, `title`, `description`). — [plugin.json reference](https://grafana.com/developers/plugin-tools/reference/plugin-json)

**Backend plugins (process isolation)**
- Each plugin backend runs as a subprocess and talks to Grafana over gRPC (HashiCorp go-plugin). "A panic in a plugin doesn't panic the server", and a plugin only sees the arguments passed to it. — [Backend plugins](https://grafana.com/developers/plugin-tools/key-concepts/backend-plugins/)
- Capabilities: query data, resources (custom HTTP endpoints under the Grafana API), health checks (run on "Save & Test"), metrics (Prometheus format) and streaming. Instance management is opt-in: the SDK caches one instance per configured data source or app and recreates it when that configuration changes, which also gives per-instance connection pools. — [Backend plugins](https://grafana.com/developers/plugin-tools/key-concepts/backend-plugins/)

**UI extensions: the slot model**
- Roles: content providers (app plugins), content consumers (core or plugins), and extension points (UI locations owned by core or by a plugin). Two ways to share: **add** (push, one-to-many: a plugin registers content into a named extension point) and **expose** (pull, one-to-one: a plugin publishes a component under an id, and another chooses to render it). — [UI extensions key concepts](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/ui-extensions-concepts)
- Registration (in `module.tsx` on `AppPlugin`): `addLink({targets, title, description, path|onClick, icon, group, openInNewTab, configure})`, `addComponent({targets, title, description, component})` (11.1+), `addFunction({targets, title, description, fn})` (11.6+) and `exposeComponent({id, title, description, component})` (11.1+). Link `category` is deprecated in favor of `group`. — [UI extensions reference](https://grafana.com/developers/plugin-tools/reference/ui-extensions-reference/ui-extensions)
- Consumption hooks: `usePluginLinks({extensionPointId, context, limitPerPlugin})`, `usePluginComponents({extensionPointId, limitPerPlugin})`, `usePluginFunctions(...)` and `usePluginComponent(id)`. Each returns its items plus `isLoading`. — [UI extensions reference](https://grafana.com/developers/plugin-tools/reference/ui-extensions-reference/ui-extensions)
- Link `configure(context)` can hide the link (return `undefined`) or change its title, path, icon or group based on the slot's context. A component gets the context as props, renders outside the plugin's React tree (so it must wrap its own providers), and can return `null` to hide itself. Plugins "must update your plugin.json metadata to list any registered extensions". Missing or wrong entries show up as console validation errors and the extension is not shown. — [Register an extension](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/register-an-extension)
- Declaring a slot: the id must be prefixed `grafana/` (core) or `{plugin-id}/`, e.g. `myorg-foo-app/toolbar/v1`, and must be listed under `extensions.extensionPoints`. The context object is **frozen** before it reaches extensions; dynamic contexts should be wrapped in `useMemo`. Slots should cope with zero to many items, and `limitPerPlugin` caps how many each plugin contributes. — [Create an extension point](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/create-an-extension-point)
- Versioning: breaking changes "must introduce a new version suffix" (`/v2`). Serve old and new side by side for a transition, mark the old one `@deprecated`, and publish versioned types (`@grafana/plugin-types`, Grafana-org only for now). — [Versioning extensions](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/versioning-extensions)
- Protecting the host UI: hide the section or show a fallback when nothing renders, wrap each extension in a container with controlled layout, share only the minimum data, and filter by `pluginId` against an allow list when needed. — [Protect your UI](https://grafana.com/developers/plugin-tools/how-to-guides/ui-extensions/degregate-ui)
- Current core slot ids (`PluginExtensionPoints` enum in source) include `grafana/dashboard/panel/menu`, `grafana/explore/toolbar/action`, `grafana/commandpalette/action`, `grafana/user/profile/tab`, `grafana/user/profile/menu/v1`, `grafana/datasources/config`, `grafana/datasources/config/actions`, `grafana/datasources/config/status`, `grafana/alerting/home`, `grafana/alerting/instance/action`, `grafana/dashboard/sidebar/v1`, `grafana/app/chrome/v1`, `grafana/extension-sidebar/v0-alpha`, `grafana/megamenu/action`, `grafana/homepage/tabs/v1` and `grafana/admin/user-list/tab/v1`. Core also exposes components such as `grafana/add-to-dashboard-form/v1` and `grafana/alerting/create-alert-from-panel/v1`. Older ids have no `/vN` suffix and newer ones do, so the convention was added later. — [pluginExtensions.ts](https://github.com/grafana/grafana/blob/main/packages/grafana-data/src/types/pluginExtensions.ts); the docs page lists only 8 of these: [Extension points reference](https://grafana.com/developers/plugin-tools/reference/ui-extensions-reference/extension-points)

**Per-instance configuration and secrets**
- Each data source instance has its own `jsonData` (readable by Viewers, and by anyone if anonymous access is on, so never secrets) and `secureJsonData`, which is encrypted on save and can never be read back by the browser. The ConfigEditor uses `secureJsonFields` to show "configured" and to support reset. — [Add authentication for data source plugins](https://grafana.com/developers/plugin-tools/how-to-guides/data-source-plugins/add-authentication-for-data-source-plugins)
- Secrets are used in two places. One is server-side proxy routes in plugin.json templated with `{{ .SecureJsonData.apiKey }}`, which Grafana fills in on the server. The other is the backend's `DecryptedSecureJSONData` on `PluginContext.DataSourceInstanceSettings`. A pitfall in the docs' own example: replacing the whole `secureJsonData` object drops other secrets, so spread the existing values. — [Add authentication for data source plugins](https://grafana.com/developers/plugin-tools/how-to-guides/data-source-plugins/add-authentication-for-data-source-plugins)

**Core vs external**
- Grafana ships "core" data sources (Prometheus, Loki, MySQL, ...) and hundreds more in the catalog. — [Grafana data source concepts](https://grafana.com/docs/grafana/v13.2/datasources/concepts.md)
- In the repo on `main` today, `public/app/plugins/datasource` holds only alertmanager, azuremonitor, cloudwatch, dashboard, grafana-testdata-datasource, grafana, graphite and mixed; Prometheus and Loki are no longer there. `grafana-testdata-datasource` has its own `package.json`, `webpack.config.ts` and `CHANGELOG.md`, so it is built like an external plugin while living in the repo. Core panels (timeseries, table, stat, ...) are still in `public/app/plugins/panel`. — [public/app/plugins/datasource](https://github.com/grafana/grafana/tree/main/public/app/plugins/datasource), [public/app/plugins/panel](https://github.com/grafana/grafana/tree/main/public/app/plugins/panel)
- A commit to the TestData README states that the bundled core TestData takes precedence over an installed external copy of the same plugin while the related feature toggle is off. — [TestData README commit (mirror)](https://forger.sitiv.fr/apitech/grafana/commit/f7361a27553acbba399e00e948a4241873c0cff9)

### Inferences
- Grafana's slot ids map directly onto Argo's slots: `argo/project/details/v1`, `argo/settings/section/v1`, `argo/nav/item/v1`. Use namespaced string ids with a major-version suffix from day one, a frozen and minimal context object (e.g. `{ projectId }`), and "declare in the manifest or be ignored" so the host knows a plugin's contributions without running its code. That matters for lazy loading and for showing plugin capabilities before install.
- The data-source pattern (plugin type → many configured instances, each with public `jsonData` and write-only `secureJsonData`, plus a "test connection" health check) fits "Issue tracker providers chosen per Project". A Project references a configured connection by id.
- Separate process plus gRPC is the proven way to keep a plugin crash out of the host. For Argo's Node Server the equivalent would be a child process or worker per plugin.

### Gaps
- Where Prometheus and Loki moved (separate repos or an external-but-bundled build) was not confirmed. Grafana's official rationale and pitfalls for "decoupling" core plugins were not found.
- What exactly happens to undeclared extensions at runtime (the docs say "required" and list validation errors) and which Grafana version made the plugin.json declaration mandatory were not found.
- App plugin settings (org-level `jsonData`/`secureJsonData` on the app's config page) were not checked against the docs.

## Backstage: frontend and backend plugins, the New Frontend System (extensions, blueprints, attachTo, app-config), backend extension points and services, migration

### Takeaway
In Backstage's New Frontend System (NFS), the whole app, including core pieces like nav, routes and the catalog's entity page, is a tree of **extensions**. Each extension has an id (`kind:namespace/name`), attaches to a named **input** on a parent (`attachTo: {id, input}`), outputs typed data, can be disabled by default, and has a config schema. Integrators enable, disable, reconfigure or re-parent any extension in `app-config.yaml` without code. Plugins mostly create extensions through **blueprints** (`PageBlueprint`, `NavContentBlueprint`, `EntityContentBlueprint`, `EntityCardBlueprint`, ...). The backend mirrors this: `createBackendPlugin`, plugin-owned extension points that **modules** fill in, and per-plugin scoped services such as the database. The NFS became the default for new apps in v1.49.0 (1.0 release candidate) after a multi-year hybrid migration.

### Cited Findings
**Extensions and the extension tree**
- An extension has an id, output, inputs, an attachment point, a disabled flag, optional conditions, a config schema and a factory. Id format: `[<kind>:][<namespace>][/][<name>]`; the namespace defaults to the plugin id, e.g. `app/nav` or `page:catalog`. — [Extensions](https://backstage.io/docs/frontend-system/architecture/extensions)
- `attachTo` is a parent id plus an input name (e.g. `{ id: 'app/nav', input: 'items' }`). An extension attaches to exactly one parent input, so the tree has no cycles, and integrators can override the attachment. Outputs use typed data refs (`createExtensionDataRef<T>().with({id})`, plus `coreExtensionData.reactElement`, `path`, `routeRef`). Inputs are declared with `createExtensionInput([refs], {singleton, optional, internal})`. `internal` inputs accept only the same plugin's extensions; others are ignored with a warning. — [Extensions](https://backstage.io/docs/frontend-system/architecture/extensions)
- Each extension's config is validated by a schema (zod v4 in the docs). Several configs for the same extension replace each other rather than merge. Extensions can be **disabled by default**. Re-enabling one via config moves it to the end of its list, so for ordered slots everything is disabled by default and config enables them in order. `if` conditions (feature flags, permissions with `$all/$any/$not`) are evaluated only when the tree is built, so changes need a reload. — [Extensions](https://backstage.io/docs/frontend-system/architecture/extensions)
- Every extension is wrapped in an "extension boundary": Suspense, an error boundary that isolates crashes, and analytics context (`extensionId`, `pluginId`). Factories should be light and synchronous; expensive work goes behind a callback. — [Extensions](https://backstage.io/docs/frontend-system/architecture/extensions)
- `app-config.yaml` syntax: `app.extensions` is an array. Items look like `- page:catalog: false` (disable), `- page:catalog` (enable), or `- <id>: { attachTo: {id, input}, disabled, config: {...} }`. Values like `${SOME_EXTENSION_ENABLED}` allow env-driven toggles. — [Configuring extensions](https://backstage.io/docs/frontend-system/building-apps/configuring-extensions)
- Architecture: the App "has no functionality of its own" and wires extensions into one tree. Plugins communicate by composing extensions, sharing Utility APIs (interface + ref, implementations provided by extensions and overridable) and through route refs: indirection so plugins link to each other without knowing paths, with bindings set by the integrator. — [Architecture overview](https://backstage.io/docs/frontend-system/architecture/index)

**Blueprints and plugins**
- Blueprints wrap `createExtension`. They are made with `createExtensionBlueprint({kind, attachTo, output, configSchema, factory})` and used via `XBlueprint.make({params, name?, attachTo?, disabled?, if?})` or `makeWithOverrides({factory, inputs, configSchema})`. — [Extension blueprints](https://backstage.io/docs/frontend-system/architecture/extension-blueprints)
- Common blueprints: `PageBlueprint` (attaches to app routes), `SubPageBlueprint` (a parent page's `pages` input), `ApiBlueprint`, `PluginHeaderActionBlueprint`, `SignInPageBlueprint`, `ThemeBlueprint`, `IconBundleBlueprint`, `TranslationBlueprint`, `NavContentBlueprint` (app nav; `items` prop deprecated for `navItems` with `take(id)`/`rest()`), `RouterBlueprint`; catalog: `EntityCardBlueprint`, `EntityContentBlueprint` (`group`, `icon`), `EntityContextMenuItemBlueprint`; search: `SearchResultListItemBlueprint`. — [Common extension blueprints](https://backstage.io/docs/frontend-system/building-plugins/common-extension-blueprints)
- `EntityContentBlueprint` and `EntityCardBlueprint` are blueprints owned by the catalog plugin (in `@backstage/plugin-catalog-react/alpha`). The catalog's entity page is therefore itself a slot owner that other plugins fill: the same pattern as Argo's `project.details`. — [Common extension blueprints](https://backstage.io/docs/frontend-system/building-plugins/common-extension-blueprints)
- `createFrontendPlugin({pluginId, extensions, routes, externalRoutes, featureFlags})`. Plugin ids are unique per app, and two plugins with the same id can't be installed. `plugin.withOverrides` makes a modified copy (via `getExtension`). Plugin-wide `if` is ANDed with extension-level conditions. — [Frontend plugins](https://backstage.io/docs/frontend-system/architecture/plugins)
- Feature discovery: adding a compatible package to the app's `package.json` installs it with no import code (requires `@backstage/cli`). — [App](https://backstage.io/docs/frontend-system/architecture/app)

**Backend system**
- `createBackendPlugin({pluginId, register(env){ env.registerInit({deps:{logger: coreServices.logger,...}, init}) }})`, installed with `backend.add(import('pkg'))`. Static config goes under a top-level key matching the plugin id. Rules: plugins must be horizontally scalable (stateless or external state) and "must not call each other through code"; they talk over the network, and each is described as "a separate microservice". — [Backend plugins](https://backstage.io/docs/backend-system/architecture/plugins)
- Extension points are created with `createExtensionPoint<T>({id})` and registered by the owning plugin in `register`. **Modules** (separately installable) use them, and only modules extending that same plugin can see them. Modules are fully initialized before the plugin's `init`. Guidance: many small extension points rather than one big one; design for additions only, since uninstalling a module removes its contribution; for breaking changes, add a new point (e.g. `V2`); for single-owner slots, use a setter that throws on a second registration; the factory variant enables `reportModuleStartupFailure`. Example: `scaffolderActionsExtensionPoint` with `addAction`. — [Backend extension points](https://backstage.io/docs/backend-system/architecture/extension-points)
- The database service is "scoped per plugin too, so that table names do not conflict across plugins". Each plugin gets a knex client and runs its own migrations; with no config it falls back to in-memory SQLite. — [Database service](https://backstage.io/docs/backend-system/core-services/database)

**Migration and status**
- v1.42.0 declared the NFS "adoption ready". — [v1.42.0 release notes](https://backstage.io/docs/releases/v1.42.0/)
- v1.49.0 is the NFS 1.0 release candidate. "Newly created Backstage apps now use the New Frontend System by default", the `create-app` `--next` flag became `--legacy`, the old "Plugins" docs section is marked legacy, `ToastApi` replaces the deprecated `AlertApi`, and the catalog bumped a major version moving entity cards from MUI to BUI. — [v1.49.0 release notes](https://backstage.io/docs/releases/v1.49.0/); secondary: [Backstage Weekly #126](https://roadie.io/backstage-weekly/126-new-frontend-system-default-ai-context-idp-architecture/)
- Migration is two phases. Phase 1 is a hybrid: `convertLegacyAppOptions` and `convertLegacyAppRoot` from `@backstage/core-compat-api`. Phase 2 removes legacy code, preferring extension config first, then blueprints and modules, then overrides. "Staying in hybrid mode for too long is not recommended", and compat helpers will be removed. Pitfalls: all routes of one plugin must move at once (otherwise legacy routes override the new plugin with the same id), only one version of a plugin can be installed, duplicate entity cards appear if cards remain in the legacy entity page, and `FlatRoutes` accepts only `Route` children. — [Migrating apps](https://backstage.io/docs/frontend-system/building-apps/migrating)

### Inferences
- Backstage gives Argo the cleanest "core is plugins too" model. Core screens (Project details, Settings, nav) declare named inputs, and plugins attach to them by id. Config (in Argo's case, per Server or per Project settings) can disable or reorder contributions without code. "Disabled by default + config enables in order" is a useful answer to slot ordering.
- The backend split (plugin owns extension point → modules add providers) is a good shape for "Issue tracker plugin + provider modules", equivalent to IntelliJ's `TaskRepositoryType`.
- The multi-year hybrid migration is the main warning. Retrofitting a slot system onto hand-wired screens is expensive, so declare core slots before the first plugin ships.

## Figma: manifest.json, sandbox + iframe split, network allowlist, documentAccess, clientStorage, relaunch data, widgets (declarative UI with synced state)

### Takeaway
Figma splits each plugin in two. A main-thread sandbox (now QuickJS compiled to WebAssembly) has the document API but no browser APIs. An optional UI iframe has browser APIs but no document access, and the two talk by message passing. Capabilities are declared in `manifest.json`: editor types, a required `networkAccess.allowedDomains` allowlist enforced by CSP, `permissions`, and `documentAccess: "dynamic-page"`. Widgets are a declarative model: a pure, synchronous JSX render function of synced state (`useSyncedState`, or `useSyncedMap` for per-key last-writer-wins). That is close to "the server describes UI, clients render it". The security lesson from Figma: the risky part is the APIs, not JavaScript itself, and a swappable sandbox let them switch from Realms to QuickJS quickly after Realms escapes were found.

### Cited Findings
**Manifest**
- Fields: `name`, `id`, `api`, `main`, `ui` (an HTML file or a map of files), `editorType` (`figma`, `figjam`, `dev`, `slides`, `buzz`; `figjam`+`dev` cannot be combined), `documentAccess` ("must be `dynamic-page`", required for new plugins; without it, existing plugins load all pages on first run), `networkAccess` (`allowedDomains` required, `["none"]` blocks all, `reasoning` required for `*` or localhost, `devAllowedDomains` for development), `parameters`/`parameterOnly`, `menu`, `relaunchButtons`, `permissions` (`currentuser`, `activeusers`, `fileusers`, `payments`, `teamlibrary`), `capabilities` (`textreview`, `codegen`, `inspect`, `vscode`), `enableProposedApi` (development only), `enablePrivatePluginApi`, and an experimental `build` command. — [Plugin manifest](https://developers.figma.com/docs/plugins/manifest/)
- The domain allowlist is shown on the plugin's Community page. It covers only the plugin's own requests, not resources loaded by a site framed in the UI. — [Plugin manifest](https://developers.figma.com/docs/plugins/manifest/)
- `relaunchButtons` declare `command`/`name`/`multipleSelection`. Nodes get buttons via `setRelaunchData`, and removing a command from the manifest hides its buttons. — [Plugin manifest](https://developers.figma.com/docs/plugins/manifest/)

**How plugins run**
- Main thread: a minimal sandbox with ES2020+ but no `fetch`, XHR, `setTimeout` or DOM; it has scene access. UI: `figma.showUI()` iframe with full browser APIs and no scene access. The two talk via message passing. Requests to undeclared domains fail with a CSP error. A plugin must call `figma.closePlugin()`, otherwise it keeps running with a "Running [plugin]" toast; users can cancel it. — [How plugins run](https://developers.figma.com/docs/plugins/how-plugins-run/)
- Design history. A pure iframe was rejected: every scene call became async, which confused designers, and serializing a large document took about 14 s. Duktape compiled to WebAssembly was ES5-only and slow. A Realms shim was chosen (main thread, JIT speed, devtools). Every API goes through an audited, roughly 500-line, VM-style handle interface (a "membrane"), so the sandbox can be swapped. Lessons: "the dangerous part is the APIs, not JavaScript"; allow lists are safer than block lists; hiding globals is not enough (`({}).constructor`); passing outside functions into the sandbox lets code escape. Plugins run only on explicit user action, so a hang is attributable. — [How we built the Figma plugin system](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/)
- Follow-up. Realms shim escapes were found. Figma paused approvals and updates, patched with Agoric, then switched to **QuickJS compiled to WebAssembly**, which is "somewhat slower for certain plugins, but intrinsically more secure". The swappable architecture made the switch fast. Manual review exists for user experience, not security; the sandbox is the security boundary. — [An update on plugin security](https://www.figma.com/blog/an-update-on-plugin-security/)

**Storage**
- `figma.clientStorage`: async key/value (`getAsync`, `setAsync`, `deleteAsync`, `keysAsync`) on the user's machine, scoped to the plugin id, 5 MB per plugin, values are JSON types or `Uint8Array`. It is not synced and not secure ("don't store secrets"), changing the plugin id orphans the data, and clearing the browser cache can wipe it. Document-scoped data (`setPluginData`) is saved with the file and synced to collaborators. — [figma.clientStorage](https://developers.figma.com/docs/plugins/api/figma-clientStorage/)

**Widgets (declarative, synced-state UI)**
- Widgets run in the plugin sandbox, but only in response to a user action and only on that user's client; others see the result via multiplayer file sync. Rendering code is synchronous and should depend only on widget state ("will be enforced at the API level"). State-updating code is async, can call the Plugin API and the network (through iframes), and triggers a re-render. — [How widgets run](https://developers.figma.com/docs/widgets/how-widgets-run/)
- `useSyncedState(key, default)` holds JSON-serializable per-instance state, synced to all clients. Keys must be unique, there is no local-only state, and any update re-renders. — [Widget state](https://developers.figma.com/docs/widgets/widget-state/)
- `useSyncedMap(name)`: "each value within the map is updated last-writer-wins" per key, so concurrent writes to different keys don't clobber each other. With `useSyncedState`, the last writer overwrites the whole value. Example: per-session votes stored as `voteMap.set(sessionId, 1)`. — [useSyncedMap](https://developers.figma.com/docs/widgets/api/properties/widget-usesyncedmap/)

### Inferences
- The manifest-declared capability model (network allowlist with a stated reason, permissions, editor types) is a direct template for Argo's plugin manifest. Declare the provider hosts (`api.github.com`, `*.atlassian.net`, `api.linear.app`) and permissions up front, enforce them on the Server, and show them before install.
- The widget model (pure render from synced state, async handlers, per-key last-writer-wins maps) is a working example of server-owned declarative UI. Argo could do the same if plugins on the Server must contribute UI to native phone clients that can't load arbitrary JS.
- Figma's main lesson for Argo: put a narrow, audited API layer between plugin code and the host, and keep the runtime swappable (in-process, worker, child process). Don't hand host objects to plugins.
