# Declarative and contribution-point plugin systems: Slack Block Kit, Adaptive Cards, Raycast, VS Code, Claude Code plugins and mods

Research date: 2026-10-14. Primary docs fetched via WebFetch (summarised by a small model, so wording is paraphrase, not verbatim) unless marked "search snippet". Claude Code docs are at v2.1.290-ish ("mods" docs state "as of v2.1.290").

## 1. Where does plugin code run (host, isolation, crash handling)?

### Takeaway
Only the declarative systems (Block Kit, Adaptive Cards) run no third-party code in the client; the code lives on the vendor's own server and the client only receives JSON. Every "code plugin" system here (Raycast, VS Code, Claude Code mods) runs author code on the user's machine with essentially full user privileges. Isolation is by process/worker for crash containment, not for security. Raycast is the most relevant model: a managed Node worker thread per extension that talks JSON-RPC to the native app.

### Cited Findings
- **Slack Block Kit**: the app is a server on the developer's side. Slack POSTs interaction payloads (form-encoded `payload` JSON, types `block_actions`, `view_submission`, `view_closed`, shortcuts) to the app's Request URL; the app must return HTTP 200 within 3 seconds. Slack runs no app code. — [Slack: handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction)
- **Adaptive Cards**: a "card author" (a bot/service) produces JSON; a "host application" renders it. "Purely declarative - No code is needed or allowed". Host apps get "safe payloads" so they "don't have to open up your UI framework to raw markup and scripting". — [Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/)
- **Raycast**: Raycast first tried JavaScriptCore (one engine per extension in an XPC process) and abandoned it because of endless polyfills and no npm compatibility. It now downloads and integrity-checks a Node runtime (not bundled in the app) and runs it as a separate managed process. Each extension runs in a **Node worker thread** (own V8 instance and event loop), so Raycast can cap heap per extension and create/destroy workers on demand. — [How the Raycast API and extensions work](https://raycast.com/blog/how-raycast-api-extensions-work)
- **Raycast crash handling**: if a worker crashes or runs out of memory, Raycast catches it and shows an error screen for that extension while Raycast itself is largely unaffected; stack traces are forwarded to a native overlay with jump-to-line in the editor. Extensions exceeding memory limits are stopped (and the lifecycle docs say the user sees an error). Limitation: a buggy *native API method* called by an extension can still crash Raycast. — [Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work); [Raycast lifecycle](https://developers.raycast.com/information/lifecycle)
- **Raycast lifecycle**: a view command's code runs on launch and is unloaded (whole command removed from memory) when the user returns to root search; a no-view command unloads when its script finishes. — [Raycast lifecycle](https://developers.raycast.com/information/lifecycle)
- **Raycast sandboxing was considered and rejected**: process-level sandboxing would need one Node process per extension (expensive), `sandbox-exec` not available to third parties, Node permission model experimental; engine-level sandboxing slows execution with limited protection. Extensions inherit the parent app's macOS permissions. — [Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work)
- **VS Code**: extensions run in an "Extension Host". Three kinds: local (Node.js, same machine as UI), web (browser WebWorker, needs a `browser` entry), remote (Node.js in container/SSH/WSL/Codespaces). Placement depends on `extensionKind` (`ui`, `workspace`). The host "prevents extensions from" slowing UI operations, impacting startup or modifying the UI. Docs page does not describe crash handling. — [VS Code extension host](https://code.visualstudio.com/api/advanced-topics/extension-host)
- **VS Code isolation is not a security boundary**: community/academic sources state VS Code extensions are not sandboxed and run with the user's privileges; one extension (e.g. out-of-memory) can take down the shared host and all extensions in it ("Extension host terminated unexpectedly"). These are secondary sources (forums, an NDSS paper, security blogs), not VS Code docs. — [NDSS 2024 paper](https://www.ndss-symposium.org/wp-content/uploads/2024-73-paper.pdf); [search results on host termination](https://github.com/anthropics/claude-code/issues/11178)
- **VS Code webviews** are isolated like an `iframe`: cannot access local resources or the VS Code API directly; scripts off unless `enableScripts: true`. — [VS Code webview guide](https://code.visualstudio.com/api/extension-guides/webview)
- **Claude Code mods**: "A mod's handlers are functions that run inside Claude Code" (in-process), unlike settings hooks (shell/HTTP). "Mods aren't sandboxed"; a mod runs with the user's permissions, can read/write files, spawn processes, read env vars, see every prompt and tool call, approve tool calls, and spend usage. A process a mod starts runs outside Claude Code's Bash sandbox. — [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- **Claude Code mods crash/limit handling**: each hook has a time budget (10 s; 50 ms for `prompt.edit`; `.catch` handler 1 s), Claude Code skips a hook that exceeds it, and each hook can register a `.catch(handler)` error handler. A tree that fails validation makes Claude Code "draw its own version of the site" and logs the reason. A `Client` element failing in the terminal is replaced by a dim error line while the rest of the drawing still shows, and a `ui.fault` event fires. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)
- **Claude Code other plugin components** run as separate processes: MCP servers (stdio command/args/env, or http/sse/ws URL), LSP servers (`restartOnCrash` default `true`, `maxRestarts`, `startupTimeout`, `requestTimeout` 60 s), and monitors (persistent background shell commands). — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)

### Inferences
- A useful spectrum for Argo: (a) vendor-server + JSON UI (Slack, Adaptive Cards, no client trust needed); (b) managed worker with a narrow message protocol to a native renderer (Raycast, best fit: the local Node Server hosts a worker/process per plugin, UI crosses as JSON); (c) in-process full-trust code (VS Code host, Claude Code mods).
- Because Argo's plugin code runs on a local Node Server the user owns, the realistic security stance (as in Raycast, VS Code, Claude Code) is "trusted code with crash containment", not a sandbox. Raycast explicitly judged real sandboxing too costly and relies on review plus an allow-listed message set.
- Crash containment pattern worth copying: per-plugin worker, host shows a per-plugin error surface (not a global crash), UI falls back to a default when a plugin returns an invalid tree (Claude Code), and per-hook time budgets.

### Gaps
- VS Code docs do not document extension host crash/restart behaviour on the fetched page; only secondary sources describe it.
- Raycast's published memory cap value was not found.

## 2. How is UI described (blocks, React-reconciled native, webviews, mixed), what components exist, and how are layout, styling and theming constrained?

### Takeaway
Two clean models exist. Declarative-JSON (Block Kit, Adaptive Cards) gives the host total control of look and feel via semantic values; React-with-custom-reconciler (Raycast, and Claude Code mods' element trees) lets authors write components but only from a closed vocabulary that the host maps to native views. VS Code uses native contribution points for chrome (tree views, commands) and webviews (an iframe-like HTML escape hatch) for custom UI, with theming exposed as CSS variables.

### Cited Findings
- **Block Kit**: three layers: blocks (visual components), block elements (interactive parts), composition objects (text, options). Surfaces: messages (max 50 blocks), modals and Home tabs (max 100). Examples: `section` (text/fields + accessory), `header`, `button`; menus and text inputs are elements. Authors only supply JSON; no layout or CSS control. — [Block Kit overview](https://docs.slack.dev/block-kit/)
- **Block Kit theming**: Slack handles most text contrast; developers are told to test in both light and dark mode, not to rely on color alone, and to expect users/orgs to disable animated GIFs and emoji. — [Designing with Block Kit](https://docs.slack.dev/block-kit/designing-with-block-kit)
- **Block Kit tooling**: Block Kit Builder is a visual prototyping sandbox (choose, configure, drag/drop, preview blocks); JSON can also be hand-written from the reference. — [Block Kit overview](https://docs.slack.dev/block-kit/)
- **Adaptive Cards design principles**: "Semantic instead of pixel-perfect" (colors, sizes, FactSet, ImageSet); "Card Authors own the content, Host App owns the look and feel"; "Keep it simple, but expressive" (explicitly "we don't want to build a UI framework", "expressive enough" like Markdown); "When in doubt, keep it out". — [Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/)
- **Adaptive Cards HostConfig** is a cross-platform JSON object telling any renderer how to generate UI. Sections: `fontFamily`, `fontSizes` (small 10 / default 12 / medium 14 / large 17 / extraLarge 20), `fontWeights`, `foregroundColors` (default, accent, dark, light, good, warning, attention, each with default/subtle), `containerStyles` (default, emphasis), `spacing` (small 3 / default 8 / medium 20 / large 30 / extraLarge 40 / padding 20), `imageSizes`, `separator`, `actions` (`maxActions` default 5, orientation, `iconPlacement`), `inputs` (label/error message, v1.3), `media` (v1.1), plus `supportsInteractivity` and `allowCustomStyle`. Because it is shared JSON, tooling can preview "the look and feel that card would have for a given environment". — [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- **Adaptive Cards renderers**: Android, iOS, JavaScript, ASP.NET, .NET WPF, Windows (UWP), React Native. Claim: "Adaptive Cards render native UI on any platform." — [Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/)
- **Adaptive Cards React Native renderer is community-maintained**, not by Microsoft: npm `adaptivecards-reactnative`, props `payload`, `hostConfig`, `themeConfig`, `onExecuteAction`, `onParseError`; docs say "no SLA can be guaranteed", maintainer listed as BigThinkCode; originally built by Imaginea (released at Build, May 2019). Source lives under `source/community/reactnative/` in the AdaptiveCards monorepo. — [search snippet of RN docs/README](https://github.com/Microsoft/AdaptiveCards/blob/master/source/community/reactnative/README.md); [Microsoft Learn RN getting started](https://learn.microsoft.com/lt-lt/adaptive-cards/sdk/rendering-cards/react-native/getting-started)
- **Adaptive Cards newer elements** (responsive layout, Icon, Badge, Carousel, Charts) are documented on a separate hub, not the old Learn docs. — [Adaptive Cards overview note](https://learn.microsoft.com/en-us/adaptive-cards/)
- **Raycast UI**: four top-level view components: `List`, `Grid`, `Detail`, `Form`, each with an `ActionPanel` of `Action`s bindable to keyboard shortcuts. A view command exports a React component; slow data uses `isLoading`. Other fetched manifest page lists `menu-bar` command mode (Menu Bar Extra). — [Raycast user interface](https://developers.raycast.com/api-reference/user-interface); [Raycast manifest](https://developers.raycast.com/information/manifest)
- **Raycast native rendering mechanism**: not react-dom. A custom React reconciler outputs a JSON "render tree" instead of DOM. After each render the full tree is diffed against the previous with **JSON Patch**; no patches means nothing is sent; large payloads gzipped above a size threshold; the Swift side converts the tree into lightweight view models and applies patches (bitset types) to **custom AppKit components**. The view-model layer insulates native components from render-tree format changes. They chose AppKit over SwiftUI for crash-rate/performance confidence. Goal: native feel, no webviews/Electron-style. — [How the Raycast API and extensions work](https://raycast.com/blog/how-raycast-api-extensions-work); FAQ confirming "similar to how React Native works": [Raycast FAQ](https://developers.raycast.com/misc/faq)
- **Raycast theming**: icon manifest field is a 512x512 PNG with an `@dark` variant; store requires icons that look good in light and dark. (Color/Icon theming API page not fetched.) — [Raycast manifest](https://developers.raycast.com/information/manifest); [Prepare for store](https://developers.raycast.com/basics/prepare-an-extension-for-store)
- **VS Code contribution points for chrome**: `viewsContainers` (`id`, `title`, `icon`; locations `activitybar` and `panel`); `views` (`id`, `name`, `when`, `icon`, `contextualTitle`; containers `explorer`/`scm`/`debug`/`test` or custom; populated by a TreeView or a WebviewView; emits `onView:${viewId}`); `viewsWelcome` (empty-state content with command links); `commands`; `menus` (locations such as `editor/context`, `view/title`, `view/item/context`, `commandPalette`; `group` ordering, `when` clauses); `walkthroughs`. The fetched page did not list a `statusBar` contribution (status bar items are created via API). — [VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)
- **VS Code webviews**: HTML in an isolated frame; recommended CSP `default-src 'none'`; `localResourceRoots` narrows readable local paths; theme exposed as `body` classes `vscode-light`/`vscode-dark`/`vscode-high-contrast` and CSS variables `--vscode-*` (e.g. `--vscode-editor-foreground`, font family/size variables). `retainContextWhenHidden` has "high memory overhead", `getState`/`setState` preferred; serialization needs `onWebviewPanel:<viewType>` activation. — [VS Code webview guide](https://code.visualstudio.com/api/extension-guides/webview)
- **Claude Code mods element tree**: a `ui.render` hook returns a tree built from elements obtained from `$.ui.resolve(e)`: `Box` (flex layout, gap, padding, borderStyle, width), `Text`, `Button`, `Link`, `Code`, `Markdown`, `Input`, `Select`, `Svg` (Desktop only, up to 131,072 chars), `Client`, plus terminal-only `Raster` and `Image`. A tree can be written as JSX in `.tsx`. If a tree uses an element the app lacks, a prop an element doesn't take, or a child where none goes, Claude Code draws its own version of the site, and logs a message such as `ui.render (Pane) refused: Text prop "bogusProp" is not allowed`. Text is capped at 100,000 chars per tree; redraw is throttled (10/s). — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)
- **Claude Code mods render sites = contribution points for UI**: `Pane` (sidebar beside transcript in wide terminal or framed region above the prompt, opened by `$.ui.open({id,title,focus,...})`), `AbovePrompt` (the shared band directly above the prompt, "always there, and every mod shares it"; a returned tree replaces what later mods draw unless the author nests `await next(e)` in it), and replaceable built-in sites (`UserMessage`, `AssistantMessage`, `ToolUse`, `Spinner`, `PromptHint`, ...). The same element tree is drawn by the terminal and by the Desktop app (Desktop skips terminal-only elements). A `ui.render` hook can edit props of the host's own drawing (`next({...e, props})`), replace it, or leave it. The permission prompt is not a render site. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)
- **Claude Code `Client` element**: "A region drawn by a second file of yours, for animation and pointer input. That file gets no mods API"; it talks back only by posting data, arriving as `ui.message`. This is the escape hatch for richer drawing, analogous to a webview but with no API access. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)

### Inferences
- Comparison of "how bespoke can plugin UI be":

| System | UI model | Author control of look | Escape hatch |
|---|---|---|---|
| Block Kit | Fixed JSON blocks | Almost none (text, fields, accessories) | None; modals/home are still blocks |
| Adaptive Cards | Fixed JSON elements + HostConfig | Semantic only (size/color names), host owns theme | Custom elements via open schema (host must implement), `fallback` |
| Raycast | React → render-tree JSON → native AppKit | Closed component set (List/Grid/Detail/Form/Action), no layout primitives | None (explicitly no webviews) |
| VS Code | Contribution points + TreeView; webviews for custom | Full HTML in webview, host provides theme CSS vars | Webview (iframe-like) |
| Claude Code mods | Element tree (Box/Text/Button/Input/...) in named render sites | Flex layout and colors, not fonts/chrome; Box is a general layout primitive | `Client` module, `Svg`, `Raster` |

- Raycast and Claude Code mods are the two real precedents for "React-ish authoring, host draws natively": both serialise a tree and let the host choose the real widgets. Raycast's closed set guarantees native look; Claude Code's `Box`/`Text` set offers general layout but keeps theming host-side via theme keys. For Argo (Expo/RN across iOS/Android/web/macOS) the host is itself React, so the "reconciler" can be replaced by a tree-to-component mapping in the app; the plugin only ever sends JSON.
- Both Raycast and Claude Code diff and validate on the host: Raycast via JSON Patch, Claude Code via tree validation with a safe default fallback. A schema-validated tree with a defined fallback is also exactly what an LLM-authoring loop needs (see question 6).
- Rail item with page and a band above the Composer map directly onto VS Code `viewsContainers`/`views` and Claude Code's `Pane`/`AbovePrompt` render sites: a contribution point name plus a render function.

### Gaps
- Slack Block Kit's full block/element list (section, actions, context, divider, image, input, rich_text, table, etc.) was not extracted; the fetched page only confirmed `section`, `header`, `button`, menus, text inputs.
- Raycast `Color`/`Icon` theming and `MenuBarExtra` pages not fetched; exact light/dark behaviour of Raycast components is undocumented in my sources.
- Adaptive Cards element list (TextBlock, Container, ColumnSet, Input.*, Action.*) was not extracted from the schema explorer (the Learn card-schema page only redirects to adaptivecards.io/explorer).

## 3. How do actions, events and data round-trip?

### Takeaway
Declarative systems use stateless request/response over HTTP: the client sends an interaction payload to the author's server, which answers with a new card or view. Code-plugin systems use a command registry (VS Code, Claude Code) or a handler closure inside the plugin (Raycast, mods) with a message channel to the host. Claude Code mods and Raycast are closest to Argo's shape: plugin process owns state and re-renders, the host owns pixels.

### Cited Findings
- **Slack**: interactions POST to the Request URL with `payload` JSON; must ack with 200 in 3 seconds; `response_url` (up to 5 responses in 30 minutes; ephemeral by default; options `in_channel`, `replace_original`, `delete_original`) lets the app respond later; `trigger_id` opens a modal, expires in 3 s and is single-use (errors `trigger_expired`, `trigger_exchanged`). — [Slack: handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction). (The page did not cover `views.update` or Socket Mode.)
- **Adaptive Cards (legacy)**: `Action.Submit` posts input values to the bot (which cannot return a new card), `Action.Http` used by Outlook Actionable Messages. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- **Adaptive Cards (Universal Action Model, schema 1.4)**: `Action.Execute` replaces both; has `verb`, `data` (merged with input values), `fallback`, `requires`. The client sends an `adaptiveCard/action` Invoke to the bot with `value.action` and `value.trigger` (`automatic` or `manual`); the bot replies `{statusCode, type, value}` where `type: application/vnd.microsoft.card.adaptive` returns a replacement card shown in place of the current one. Card `refresh` (an `Action.Execute` plus `userIds`, max 60) re-fetches a card when displayed; without `userIds` Teams shows a manual refresh button. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- **Adaptive Cards in RN host**: the host receives actions through an `onExecuteAction` callback and parse failures via `onParseError`; `hostConfig` controls `supportsInteractivity`. — [RN renderer docs](https://learn.microsoft.com/lt-lt/adaptive-cards/sdk/rendering-cards/react-native/getting-started); [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- **Raycast**: the extension worker talks to the native app over standard file-descriptor streams using **JSON-RPC**; extensions "can only send registered messages, such as render or set-clipboard"; "they cannot call arbitrary Raycast code". Per-instance temporary session IDs route messages; Swift uses serial queues for ordering. Action handlers are closures in the React component; the tree carries action definitions, native sends events back. — [How the Raycast API and extensions work](https://raycast.com/blog/how-raycast-api-extensions-work)
- **VS Code commands**: `contributes.commands` declares id/title/icon/category; `menus` places commands in named locations with `when` clauses; invoking a command emits `onCommand:${command}` for lazy activation. Webview messaging: extension→webview `webview.postMessage()` (JSON-serialisable, received as `window` `message` event); webview→extension via `acquireVsCodeApi().postMessage` and `webview.onDidReceiveMessage`. — [Contribution points](https://code.visualstudio.com/api/references/contribution-points); [Webview guide](https://code.visualstudio.com/api/extension-guides/webview)
- **Claude Code mods**: pressing a `Button`, typing in an `Input` or picking a `Select` calls the control's callback (`onPress`, `onSubmit`/`onInput`, `onSelect`) inside the mod; the callback mutates state and calls `$.ui.invalidate('ui.render')`, then the host re-runs the `ui.render` hook "Every interactive drawing uses that render cycle: a callback changes state, and the hook renders again from the new state." Each use also fires `ui.press`/`ui.input`/`ui.select` events that other mods can intercept first. Reactive `$.state` values (`atom`, `read`, `update` from `claude-code`) re-render automatically; `$.store` is a JSON key-value store shared by all sessions (4 MiB, race-prone: get-then-set not atomic). Controls need a stable `key`. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Claude Code mods commands/tools**: `$.command.register({name, description})` and a `command.run` hook; `$.tool.register` adds tools for the model; mods can also call models (`$.model.complete`), HTTP, processes, MCP. Names limited to letters, digits, `_`, `-`, up to 64 chars. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Claude Code UI presses are plain callbacks, not network**: `Client` modules post data into the mod as `ui.message`. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)

### Inferences
- Two proven round-trip shapes for Argo: (1) Raycast/mods "plugin owns closures; host sends element key + event; plugin returns new tree" (best for an interactive Rail page); (2) Adaptive Cards "verb + data payload → server returns replacement card" (stateless, easy for an LLM to author and to test with fixtures).
- Stable element keys, an `invalidate` primitive with host-side throttling/coalescing (10/s in mods) and a reactive state helper are the three details Claude Code needed to make closures-in-plugin work; a Raycast-style JSON Patch diff keeps the wire small.
- Slack's 3-second ack and expiring `trigger_id` are lessons for latency budgets: with a local Server, the budget can be much looser, but a per-handler timeout (mods: 10 s) is still worth copying.

### Gaps
- Slack `views.update`, `views.push` and Socket Mode details not confirmed from fetched sources.
- Raycast's exact action/event message schema (beyond "JSON-RPC, registered messages only") is not public in what I fetched.
- VS Code `commands.executeCommand` cross-extension semantics not fetched.

## 4. Mobile support, native rendering, theming, schema versioning and fallback

### Takeaway
Adaptive Cards is the only system here with a documented multi-platform renderer model (Android, iOS, JS, .NET, community React Native), HostConfig theming, and explicit schema-version plus `fallback`/`requires` mechanics; in practice Teams mobile lags the desktop schema (up to 1.2 per Microsoft's snippet). Slack's docs I could fetch say nothing about how mobile clients render Block Kit. VS Code, Raycast and Claude Code mods are desktop (and Claude Code's mods only draw in terminal and Desktop app).

### Cited Findings
- **Adaptive Cards native rendering**: renderers are listed for Android, iOS, JavaScript, ASP.NET, .NET WPF, UWP, ReactNative; the pitch is that the same payload "will look and feel like Skype card" in Skype and "like Microsoft Teams" in Teams. — [Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/)
- **Adaptive Cards React Native renderer status**: community-supported, "no SLA can be guaranteed", maintained by BigThinkCode. It takes `payload`, `hostConfig`, `themeConfig`. — [RN getting started (Microsoft Learn)](https://learn.microsoft.com/lt-lt/adaptive-cards/sdk/rendering-cards/react-native/getting-started) (via search summary)
- **Teams mobile schema level**: Microsoft's cards reference is reported (search snippet) to say the Teams mobile app supports Adaptive Cards up to schema version 1.2, and later features may render incorrectly; Teams bot-sent cards otherwise support v1.5 or earlier. Third-party guides advise defaulting to 1.2 with fallback text. No documented minimum iOS/Android client build was found. — [Teams cards reference](https://learn.microsoft.com/microsoftteams/platform/concepts/cards/cards-reference) (search snippet only, not directly fetched)
- **Versioning and fallback mechanics**: card `version` property; elements/actions can carry `requires` (feature to minimum version) and `fallback` (an alternative element/action, or `"drop"`). Using `Action.Execute` or `refresh` with a card version < 1.4 breaks in Outlook ("WILL NOT work", card may be rejected) and may fail in Teams; recommended pattern is card `version: "1.2"` with `Action.Execute` whose `fallback` is `Action.Submit`, wrapped in an `ActionSet` because some older Teams clients don't support `fallback` outside an `ActionSet`. Falling back to `Action.Submit` gives a "degraded experience" because Submit cannot return a new card. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model); schema-explorer search summary: [Schema Explorer](https://adaptivecards.io/explorer/ActionSet.html)
- **HostConfig is versioned per property** (each field annotated with the schema version that introduced it, e.g. `media` 1.1, `inputs.label` 1.3), which lets a host declare what it supports. — [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- **Slack mobile rendering**: the fetched Block Kit pages never mention mobile clients; only that Slack handles contrast and authors must test light/dark. The claim that Slack mobile renders Block Kit natively is **not substantiated** in the sources I fetched. — [Designing with Block Kit](https://docs.slack.dev/block-kit/designing-with-block-kit); [Block Kit overview](https://docs.slack.dev/block-kit/)
- **Block Kit surface compatibility**: "Some blocks work only on certain surfaces, so check the block reference"; there is no schema version number or fallback property in the overview. — [Block Kit overview](https://docs.slack.dev/block-kit/)
- **Raycast platforms**: manifest field `platforms` (`macOS`, `Windows`) restricts an extension when it uses platform-specific APIs; `preferences.default` can be per-platform. — [Raycast manifest](https://developers.raycast.com/information/manifest)
- **VS Code**: web extension host runs in a WebWorker for VS Code for the Web; extension runs where `extensionKind`/capabilities allow. Webview UI Toolkit status not confirmed. — [VS Code extension host](https://code.visualstudio.com/api/advanced-topics/extension-host)
- **Claude Code mods surface support**: mods' hooks run in terminal, Desktop app, VS Code extension, `claude -p`/SDK and cloud sessions, but **drawing** appears only in the terminal and the Desktop app's Code tab (elements marked terminal-only, e.g. `Raster`/`Image`, are not drawn in Desktop; `Svg` is Desktop only). Mods "can check which app they're running in" (`e.surface`) "and fall back to a line in the transcript". Remote Control from the mobile app: hooks run on the user's machine, drawing happens in the terminal there, i.e. no mobile drawing. — [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Claude Code mods unsupported element behaviour**: an element not present in the app causes the host to draw its own default for the site (whole-tree fallback, not per-element), plus a debug-log line. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)

### Inferences
- Adaptive Cards shows the cost of an open, versioned schema: hosts lag (Teams mobile ≈ 1.2), so authors target the lowest common denominator and write explicit `fallback`s. Argo controls both the host and the schema and ships plugins to a local Server, so it can instead publish one `schemaVersion`, let the Server (not each client) negotiate/downgrade, and declare per-client capabilities in a HostConfig-like object.
- Claude Code's "unknown element → host default for the whole site" is simple but coarse; Adaptive Cards' per-element `requires`/`fallback` is finer but lets authors write brittle trees. A middle option: per-element `fallback` plus host-side whole-site fallback.
- HostConfig-style theming (semantic sizes/colors/spacing as JSON, per-platform renderer maps them to native tokens) is the strongest documented guarantee of "looks native everywhere"; the Raycast closed component set gives the same guarantee by construction.
- Using the community Adaptive Cards RN renderer in a production Expo app would mean depending on an unmaintained-feeling package; the format (not the library) is the useful reference.

### Gaps
- No official statement found on how Slack iOS/Android render Block Kit (native vs webview).
- Teams mobile version limit (1.2) came via a search-result summary of the Teams cards reference rather than a direct fetch; verify before relying on it.
- Adaptive Cards iOS/Android renderer implementation details (UIKit/View-based) not fetched.
- No data on how Raycast would handle an unsupported component in a newer API version (API versioning/compat story not fetched).

## 5. Registration and manifest (VS Code, Raycast, Claude Code) and any UI-extension surfaces ("mods")

### Takeaway
All three code-plugin systems register static, declarative metadata up front (manifest) and load code lazily on a trigger. Claude Code's plugin directory + marketplace model is the most relevant to an "agent can write the plugin" workflow, and its official "mods" feature is a documented UI-extension surface, contrary to the expectation that this documentation might be thin. It is dated v2.1.28x-290, so quite new.

### Cited Findings
- **VS Code `package.json`**: `contributes` holds `viewsContainers`, `views`, `viewsWelcome`, `commands`, `menus`, `walkthroughs`, etc.; `views` contained in `explorer`/`scm`/`debug`/`test` or custom container. — [Contribution points](https://code.visualstudio.com/api/references/contribution-points)
- **VS Code activation events** (`activationEvents`): `onCommand:<id>`, `onView:<id>`, `onWebviewPanel:<viewType>`, `onStartupFinished`, `*`, `onLanguage`, `workspaceContains`, `onUri`, `onChatParticipant`, `onLanguageModelTool`, etc. Since 1.74 contributed commands/views/languages no longer need explicit activation events; `*` is discouraged; `activate()` runs once. — [Activation events](https://code.visualstudio.com/api/references/activation-events)
- **VS Code AI surfaces**: `contributes.mcpServerDefinitionProviders` (register MCP servers; implementation via `vscode.lm.registerMcpServerDefinitionProvider`); chat participants and language-model tools have activation events. — [VS Code MCP guide](https://code.visualstudio.com/api/extension-guides/ai/mcp); [Activation events](https://code.visualstudio.com/api/references/activation-events)
- **VS Code Workspace Trust**: extensions declare `capabilities.untrustedWorkspaces.supported` as `true`, `false` (default; disabled until trust is granted) or `'limited'` (with `restrictedConfigurations`); responsibility for gating dangerous code paths sits with extension authors, and the page doesn't claim sandboxing. — [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust)
- **Raycast manifest** (superset of npm `package.json`): `name`, `title`, `icon`, `author`, `platforms`, `categories`, `commands[]` each with `name` (maps to `src/<name>.tsx`), `title`, `mode` (`view`, `no-view`, `menu-bar`), optional `interval` (background refresh, minimum `1m`), `arguments` (`text`/`password`/`dropdown`), `preferences` (`textfield`, `password`, `checkbox`, `dropdown`, `appPicker`, `file`, `directory`; command prefs override extension prefs; values read via Preferences API), `external` (unbundled deps), `tools`/`ai` for AI tools, skills and MCP config. **No permissions field**; `access` (`public`/`private`) and `owner` control who can download. — [Raycast manifest](https://developers.raycast.com/information/manifest)
- **Raycast launch triggers**: root search, alias, `launchCommand` from another command, background launch, saved Form draft, fallback commands, deeplinks. — [Raycast lifecycle](https://developers.raycast.com/information/lifecycle)
- **Claude Code plugin = directory + optional `.claude-plugin/plugin.json`**; only `name` is required; without a manifest, components are auto-discovered from the standard layout. Standard layout: `skills/<name>/SKILL.md`, `commands/*.md`, `agents/*.md`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `workflows/*.js`, `themes/`, `monitors/monitors.json`, `bin/` (put on Bash PATH), `settings.json` (only `agent` and `subagentStatusLine` defaults take effect). Everything is namespaced under the plugin name (e.g. `deploy-tools:reviewer`). Manifest fields include `displayName`, `version`, `dependencies`, `userConfig` (typed prompts; `sensitive` values go to the OS credential store), `channels`, `types` (a `.d.ts` for mod state), and `experimental.{themes,monitors,evals}`. Path rules: relative to plugin root, must start with `./`, must stay inside the root, must exist. Env vars `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` (persistent across updates), `${CLAUDE_PROJECT_DIR}`. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Claude Code settings-level UI surface**: manifest `settings.subagentStatusLine`, plus a user-configurable status line elsewhere in Claude Code (status line page not fetched). Monitors surface in the "task panel". — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Claude Code mods (the UI-extension feature) are documented**, with Overview, Create, Interface, Events, API, Test, Troubleshoot, Admin and Reference pages. A mod = a plugin with: `.claude-plugin/plugin.json` (no extra required fields), `hooks/hooks.json` containing `"modules": ["./register.js"]`, and a hooks module that exports `register(on, options)`; optional `types/index.d.ts` named by manifest `types`; optional `*.test.ts(x)`. Handlers are registered as `on('event', matcher?, async ($, e, next) => ...)` in a middleware chain; `$` is the "mods API" namespaced: `$.ui` (`resolve`, `invalidate`, `open`, `close`, `toast`, `status`, `notice`, `ask`, ...), `$.command`, `$.tool`, `$.agent`, `$.model`, `$.prompt`, `$.session`, `$.fs`, `$.store`, `$.state`, `$.clock`, `$.http`, `$.process`, `$.mcp`. Events include `tool.call`, `tool.check`, `prompt.submit`, `command.run`, `turn.*`, `session.*`, `agent.spawn`, and the interface events `ui.render`, `ui.press`, `ui.input`, `ui.select`, `ui.message`, `ui.fault`. Hooks run in a defined order: mod tiers `prepend`, `user`, `append`, `builtin`, then core. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- **Mods UI surfaces named in docs**: `Pane`, `AbovePrompt` (band), `Spinner`, `PromptHint`, message and tool-call rows, `SessionMode`, toasts (`$.ui.toast`, 4 s default), status line/`$.ui.status`, and a screen map showing a pane as a right sidebar, toast top-right, log line in transcript, band above the prompt and status line under the prompt. — [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Mods are lazy/event driven rather than activation-event driven**: `session.start` fires "once for each loaded mod, before the first prompt, and again after a reload of that mod". Plugin components such as monitors can start `on-skill-invoke:<skill>`. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Claude Code marketplaces**: a marketplace is a repo/directory with `.claude-plugin/marketplace.json` (`name`, `owner`, `plugins[]`, each with `name`, `source`, `description`). Sources: relative path, `github`, `git-subdir`, `url`, `archive` (zip over HTTPS), `npm`, `command`. Installed with `claude plugin marketplace add <owner/repo>` then `claude plugin install name@marketplace`; `strict` field controls whether an entry may add components to a plugin with its own `plugin.json`; reserved marketplace/plugin names for Anthropic. — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces); [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)

### Inferences
- A Argo plugin manifest could be a trimmed version of the Claude Code layout: one manifest, with convention-over-configuration directories and a `contributes`-style block for Rail items and composer bands. VS Code's `contributes` (`viewsContainers` + `views`) is the closest analogue of "add a Rail item with its own page"; Claude Code's `Pane` and `AbovePrompt` are the closest analogue of "page" and "widget band above the Composer".
- Two registration styles: **static manifest** (VS Code, Raycast) lets the host render the Rail item and icon before running any plugin code, giving lazy-load and trust review for free; **runtime registration** (`$.ui.open`, `$.command.register` in mods) is more flexible but requires running code first. A hybrid (static Rail item declaration, runtime page content) mirrors VS Code `views` + `TreeDataProvider`.
- Claude Code's explicit `types` file and `claude plugin validate` listing of each hook and API call a mod uses is a ready-made model for "what permissions does this plugin need" without a sandbox.

### Gaps
- Claude Code's "status line" feature docs (settings-level, not plugin) were not fetched; only the plugin `settings.subagentStatusLine` was seen.
- Mods "Create", "Events", "API", "Admin" and "Test" pages were not fetched individually; some content (e.g. `claude plugin test` semantics, `plugin.register` refusal policy) comes from the reference page.
- VS Code `statusBar` is not a contribution point on the fetched page (status items are API-created); `contributes.statusBar` not confirmed either way.
- Whether "Claude Code mods" is a stable GA feature: docs call out versions ≥ 2.1.286/2.1.287 and mention "early access" env var `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS`, so the API may still be moving; no explicit stability statement was found.

## 6. Permissions, trust model and distribution

### Takeaway
Vendor-server systems (Slack) rely on OAuth scopes plus manual Marketplace review. Local-code systems here mostly rely on review and user trust rather than technical sandboxes: Raycast reviews open-source submissions, VS Code adds Workspace Trust, and Claude Code treats mods as fully trusted with an admin policy layer (managed settings, a built-in guard mod).

### Cited Findings
- **Slack**: manual review by the Slack Marketplace team; apps must be finished and bug-free; rejected categories include scope over-requesting, data export/backup, replicating the Slack client; Dec 2024 policy bans using Slack data to train LLMs; commercial distribution at scale is expected to go through Marketplace; unlisted apps are fine for pilots. — [Slack Marketplace guidelines and review (search summary)](https://docs.slack.dev/slack-marketplace/slack-marketplace-app-guidelines-and-requirements/); [Slack Marketplace review guide](https://docs.slack.dev/slack-marketplace/slack-marketplace-review-guide)
- **Adaptive Cards**: no store; trust is in the card's channel (e.g. Outlook requires an `originator` GUID registered when the bot subscribes to the Outlook Actionable Messages channel, otherwise the card won't render; ignored in Teams). The host owns safety by restricting to declarative payloads and `supportsInteractivity`. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model); [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- **Raycast Store**: submissions are pull requests to the extensions repository, with automated checks (lint) and manual review that may take several days; requirements: `license` MIT, `author` = Raycast username, `package-lock.json`, 512x512 icon that works in light and dark, README/`help.md` where setup is needed, 2000x1250 PNG screenshots (up to 6), `CHANGELOG.md`, no Keychain access, no external analytics, binaries only downloaded with hash verification, use the Preferences API for config. Raycast says all extensions are open source and reviewed, considered a kill list like VS Code's, and is investigating enterprise controls. No manifest permissions field. — [Prepare an extension for the Store](https://developers.raycast.com/basics/prepare-an-extension-for-store); [Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work); [Raycast manifest](https://developers.raycast.com/information/manifest)
- **VS Code**: Workspace Trust restricts extensions in untrusted folders (declarations `true`/`false`/`limited`); webviews restricted by CSP and `localResourceRoots`; overall extensions run with user privileges (secondary sources). — [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust); [Webview guide](https://code.visualstudio.com/api/extension-guides/webview)
- **Claude Code**: mods and plugins are not sandboxed; "Install mods only from authors and marketplaces you trust". Before installing, `claude plugin validate ./some-mod` lists the events a mod handles and the mods API calls it makes (the `hooks:` and `calls:` lines), because "a hook has no other way" to touch the outside world than through the `$` API. A `plugin.register` event lets another mod refuse a hooks module based on its declared `uses`. Admin controls (managed settings): `allowManagedModsOnly`, `allowManagedHooksOnly`, `disableAllHooks`, `disableSideloadFlags`, `prependPlugins`/`appendPlugins`, plus a built-in guard mod `sec-default`. Users can disable via `/plugin`, `--safe-mode`, or `disableAllHooks`. Mods cannot change the permission prompt. — [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Claude Code distribution**: git-hosted marketplaces (private repos allowed), submission to Anthropic's directory (listing fields `icon`, `documentationUrl`, `supportUrl`, `privacyPolicyUrl`, `termsOfServiceUrl` in `plugin.json`), org-wide required marketplaces via managed settings, sharing a directory or zip without a marketplace. Reserved names (`claude-*`, `anthropic-*`, `official` next to claude/anthropic). Versions: setting `version` pins users until changed; local-path marketplaces reload without a version bump. Sensitive `userConfig` values stored in the OS credential store. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)

### Inferences
- A pragmatic trust model for Argo (user-owned local Server, plugins as trusted local code): static declaration of capabilities in the manifest, an automated `validate` that statically lists API calls used (Claude Code approach), user confirmation on install, and no promise of sandboxing. Raycast's "closed message set" (plugin can only issue registered host messages) gives a real policy choke point at the Server-to-App boundary even without OS sandboxing.
- If plugins are only agent-written for the user's own use, store review is moot; distribution can start as "a git-hosted directory the Server loads", like Claude Code `--plugin-dir`.

### Gaps
- Slack review was gathered through a search summary of multiple Slack doc pages, not a full fetch of any one; confirm before quoting.
- Code-signing for extensions (VS Code Marketplace signature verification, Raycast signing) was not researched.
- No data on Anthropic directory review criteria beyond field list.

## 7. Developer and agent authoring experience (dev loop, validators, designers, LLM-friendliness)

### Takeaway
Claude Code is the only system here with first-class, documented AI authoring for UI plugins (a built-in `plugin-authoring` skill, `claude plugin validate`/`test`, shipped `.d.ts` types, hot reload on save). Slack and Adaptive Cards offer visual designers and JSON schemas that suit LLM generation well. VS Code and Raycast give strong human dev loops but nothing agent-specific for UI.

### Cited Findings
- **Block Kit Builder**: visual sandbox to choose, configure, drag-drop and preview blocks; JSON can be hand-authored from the reference. Messages max 50 blocks, modals/home 100. — [Block Kit overview](https://docs.slack.dev/block-kit/)
- **Adaptive Cards tooling**: online Designer, a Designer SDK that can be embedded in your toolchain, Schema Explorer, templating (data separated from layout, sample data preview in the designer). Hosts can be previewed using HostConfig. Renders on the same JSON everywhere, which is easy to validate and to generate. — [Adaptive Cards overview](https://learn.microsoft.com/en-us/adaptive-cards/); [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- **Adaptive Cards RN API surface for hosts**: `onParseError` callback, so malformed card JSON is reported to the host rather than crashing. — [RN getting started](https://learn.microsoft.com/lt-lt/adaptive-cards/sdk/rendering-cards/react-native/getting-started) (via search summary)
- **Raycast dev loop**: TypeScript + React + Node, built-in component library; local dev and `npm run build`/`npm run lint` for store checks; errors and stack traces surfaced in a native overlay with jump-to-editor-line. Raycast also lists AI-oriented manifest fields (`tools`, `ai` with `instructions`, `evals`). — [Prepare for Store](https://developers.raycast.com/basics/prepare-an-extension-for-store); [Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work); [Raycast manifest](https://developers.raycast.com/information/manifest)
- **VS Code dev loop**: manifest-driven; webview theming through CSS variables; `contributes.mcpServerDefinitionProviders` for agent tooling. Docs fetched did not describe an agent-authoring workflow for extension UI. — [Contribution points](https://code.visualstudio.com/api/references/contribution-points); [VS Code MCP guide](https://code.visualstudio.com/api/extension-guides/ai/mcp)
- **Claude Code mods dev loop**: `claude --plugin-dir ./my-mod` loads a directory for one session and "reloads its hooks module when you save"; `/reload-plugins`; `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` reloads in long-running non-interactive sessions; module-level variables reset on each save, `$.state`/`$.store` persist. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)
- **Claude Code validators/tests**: `claude plugin validate <dir>` (checks manifest, hooks module, reports events handled and API calls; `--strict` and `--json` for CI), `claude plugin test` (runs `*.test.ts(x)`; tests press/type into controls by `key`, multi-surface; 5 s default timeout), debug log lines for refused trees. Static scan requires literal `plugin`/`key` for `atom(...)` and a `types/index.d.ts` declaration file. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)
- **Claude Code agent authoring is a first-class path**: "Make one: describe what you want in a Claude Code session, and Claude writes the mod." A built-in plugin `cc-plugin-plugin-authoring` ships the `plugin-authoring` skill "for writing mods"; the full API typings are published as `claude-code.d.ts` (on GitHub, and a per-build copy that Claude Code writes locally, "trust the copy Claude Code writes for your version"). Sample mods (`token-weather` forecasts context above the prompt, `blast-radius`, `replay-theater`) are public. — [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference)
- **Claude Code docs are agent-readable**: every docs page advertises `https://code.claude.com/docs/llms.txt` as a documentation index for agents. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- **Guard rails that help LLM authors**: strict objects reject unknown keys in `userConfig`, `channels`, `lspServers`, `monitors`; unknown top-level manifest keys are stripped with a validator warning; hook errors get `.catch`; invalid UI trees fall back with a precise reason message (e.g. naming the bad prop). — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference); [Mods interface](https://code.claude.com/docs/en/plugins/mods/interface)

### Inferences
- What makes Claude Code mods LLM-writable: (1) a small, closed element vocabulary with an exact prop allow-list, (2) published TypeScript types as the spec, (3) a static validator that returns specific errors the agent can act on, (4) hot reload on save, (5) tests that press controls by key without a running UI, (6) precise refusal messages and a safe fallback so a bad tree never blanks the app.
- Declarative JSON (Block Kit/Adaptive Cards) is the easiest format to generate and diff, and designers/schema validators provide a feedback loop; but the lack of event handlers means the agent also writes a backend. Raycast/mods trees bundle UI and logic in one file, which is better for "write me a plugin" requests.
- For Argo, the most transferable authoring stack: JSON-schema or `.d.ts` for the element vocabulary exported by the app, a `validate` CLI/Server endpoint with structured errors, file-watch hot reload on the local Server, `key`-based press tests, and `llms.txt`-style docs that the in-app agent reads.

### Gaps
- Claude Code mods "Create" page (how Claude is guided to write mods) and the `plugin-authoring` skill content were not fetched directly; a skill by that name appears in this environment's skill list but its contents were not read.
- Slack/Adaptive Cards LLM-generation quality (e.g. hallucinated fields) was not researched; no independent source evaluated it.
- Raycast `ray develop` hot-reload specifics were not fetched.
