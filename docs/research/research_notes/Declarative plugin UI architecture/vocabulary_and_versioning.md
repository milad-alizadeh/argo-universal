# Declarative / server-driven UI: vocabulary, styling limits, composition, versioning

Research date: 2026-10-14. Fetched with WebFetch (a small model summarises each page, so quotes are short and paraphrased; JSON examples marked "official" were returned from the cited page, those marked "illustrative" were written by the fetch summariser or by me and are NOT from the page). Items I could not source are in the Gaps sections.

## 1. Vocabulary shape: templates vs low-level layout primitives; layout elements; spacing/size/alignment; styling constraints

### Takeaway
Systems split into two families. Template-per-screen systems (Raycast List/Detail/Form, Slack Block Kit, Airbnb sections) give the author few, high-level building blocks, with no free layout. Primitive-based systems (DivKit, Adaptive Cards, A2UI, Hyperview, rfw) expose stack/row/grid-like containers. Even the primitive systems constrain styling to enumerated tokens or host-owned config, except Hyperview and DivKit, which allow raw numbers and colours.

### Cited Findings

**High-level / template families**
- Raycast `List.Item` has fixed props: `title`, `subtitle`, `icon`, `accessories` (right-aligned array of `text`/`icon`/`date`/`tag`/`tooltip`), `actions` (an ActionPanel) and `detail`. List-level behaviour is flags such as `isShowingDetail`, `pagination`, `filtering`, `searchBarAccessory`. There is no layout control at all. — [Raycast List](https://developers.raycast.com/api-reference/user-interface/list)
- Raycast colours are typed `Color.ColorLike` and icons `Image.ImageLike`; examples use the `Icon.*` enum and `Color.Orange`. The built-in `Icon` enum is described as a list of built-in icons, each with light and dark SVG variants. — [Raycast List](https://developers.raycast.com/api-reference/user-interface/list), [Raycast icons](https://developers.raycast.com/api-reference/user-interface/icons-and-images)
- Raycast example (official shape, from the fetch; the summariser says it is a short TSX example): `<List.Item id="camden" title="Camden Hells" icon={Icon.Star} accessories={[{ tag: { value: "Fave", color: Color.Orange } }]} detail={<List.Item.Detail markdown="..."/>} actions={<ActionPanel>...</ActionPanel>} />` — [Raycast List](https://developers.raycast.com/api-reference/user-interface/list)
- Slack Block Kit block vocabulary: Actions, Alert, Card, Carousel, Container, Context, Context actions, Data table, Data visualization, Divider, File, Header, Image, Input, Markdown, Plan, Rich text, Section, Table, Task card, Video. Limit: 50 blocks per message, 100 in modals or Home tabs. — [Slack blocks reference](https://docs.slack.dev/reference/block-kit/blocks)
- Slack `section`: `text` (1-3000 chars) or `fields` (up to 10 text objects, 2000 chars each, shown in two columns), plus one optional `accessory` (button, date picker, image, select menu, overflow, etc.). The "one accessory slot" pattern is how Block Kit gives a row a trailing control. — [Slack section block](https://docs.slack.dev/reference/block-kit/blocks/section-block)
- Slack official example: `{"type":"section","text":{"type":"mrkdwn","text":"*Deploy finished* ..."},"accessory":{"type":"button","action_id":"view_logs","text":{"type":"plain_text","text":"View logs"}}}` — [Slack section block](https://docs.slack.dev/reference/block-kit/blocks/section-block)
- Airbnb Ghost Platform: the backend sends a single response for web/iOS/Android. Core concepts are Sections (independent groups of related UI), Screens (where and how sections appear; a screen can be a popup or sheet) and Actions. A `SectionContainer` carries an id, a `sectionComponentType` enum (e.g. HERO, TITLE), the data and logging metadata; clients use the type enum to choose the rendering. A `SingleColumnLayout` places sections into `nav`, `main` and `floatingFooter` slots. — [InfoQ on Airbnb](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/); original post [Medium/Airbnb Eng](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5) (returned 403 to my fetcher, so only InfoQ and a search snippet were read)
- Airbnb sections arrive already translated, localised and formatted, so clients only map data to UI. — [search snippet summarising the Medium post](https://medium.com/p/842244c5f5) (secondary; verify against the original)
- Nubank BDC ("Backend Driven Content") is described as a "Lego manual" of building blocks that comply with Nu's Design System; Flutter components under the hood, Clojure on the authoring side. No schema is published on that page. — [Nubank blog](https://building.nu.com/server-driven-ui-framework-at-nubank/). QCon London 2025 abstract claims it powers more than half of the app and over 1000 screens — [QCon London](https://qconlondon.com/presentation/apr2025/mobile-server-driven-ui-scale) (seen only as a search result title/snippet)

**Low-level layout primitives**
- DivKit `container`: `orientation` (`vertical` default, `horizontal`, `overlap`), `layout_mode` (`no_wrap`/`wrap`), `content_alignment_horizontal` (left/center/right/start/end/space-between/space-around/space-evenly), `content_alignment_vertical` (top/center/bottom/baseline/space-*), `paddings`, `margins` (div-edge-insets), `item_spacing` (int >= 0), optional `separator` drawable, `items`, `aspect.ratio`. Children may override with `alignment_horizontal`/`alignment_vertical`. — [DivKit container](https://divkit.tech/docs/en/concepts/divs/2/div-container.md)
- DivKit has three size types: `div-fixed-size`, `div-match-parent-size`, `div-wrap-content-size` (details not retrieved). Other documented elements include text, image, gallery. The repo splits into client renderers (Android, iOS, Web), a JSON-builder (TypeScript, Kotlin, Python) and a JSON Schema from which a cross-platform API is generated. — [DivKit docs index](https://divkit.tech/docs/en/llms.txt), [DivKit README](https://raw.githubusercontent.com/divkit/divkit/main/README.md)
- DivKit's JSON uses raw numbers for spacing (`item_spacing`, `paddings`), i.e. not token-based. — [DivKit container](https://divkit.tech/docs/en/concepts/divs/2/div-container.md)
- Adaptive Cards HostConfig makes spacing/typography host-owned. `spacing` is a named scale (small 3, default 8, medium 20, large 30, extraLarge 40, plus `padding` 20); `fontSizes` small 10 … extraLarge 20; `fontWeights` lighter/default/bolder; `foregroundColors` per tone (default, accent, dark, light, good, warning, attention) each with default/subtle; `containerStyles` has default and emphasis; `imageSizes` small/medium/large. The card names `"spacing":"medium"` and the host decides pixels. `allowCustomStyle` and `supportsInteractivity` toggle capabilities. — [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- Adaptive Cards templating example shows tone as an enumerated string: `"color": "${if(priceChange >= 0, 'good', 'attention')}"`. — [AC template language](https://learn.microsoft.com/en-us/adaptive-cards/templating/language)
- Adaptive Cards action buttons configured by host: `actionsOrientation`, `actionAlignment`, `buttonSpacing`, `maxActions` (default 5), `iconPlacement`, `iconSize`. — [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- A2UI basic catalog: layout Row, Column, List; display Text, Image, Icon, Divider; interactive Button, TextField, CheckBox, Slider, DateTimeInput, ChoicePicker; containers Card, Modal, Tabs. Row/Column take `children`, `justify`, `align` (values like spaceBetween/start/center/stretch) and a common `weight` (flex-grow). Text uses `variant` h1-h5, caption, body; Button `variant: "primary"`; Icon limited to the catalog's set. "Fixed property sets" and enumerated values are the styling limit. — [A2UI components reference](https://a2ui.org/reference/components/)
- A2UI v0.9 theme is passed at surface creation and the basic catalog defines only `primaryColor`, `iconUrl`, `agentDisplayName`. — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/)
- A2UI component format (official): `{"id":"root","component":"Column","children":["title","btn"]}`; `{"id":"btn","component":"Button","child":"btn_label","action":{"event":{"name":"continue"}}}`. A flat adjacency list keyed by `id`, so an LLM can stream it incrementally. — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/)
- json-render spec is the same flat shape: `{"root":"card-1","elements":{"card-1":{"type":"Card","props":{"title":"Hello"},"children":["button-1"]}}}`; vocabulary is whatever the app defines in its catalog (no built-in layout set found on the page). — [json-render](https://github.com/vercel-labs/json-render)
- Hyperview (XML): elements `<view>`, `<text>`, `<list>`, `<section-list>`, `<form>`, `<text-field>`, `<select-single>`, `<select-multiple>`, `<switch>`, `<date-field>`, `<image>`, `<screen>`, `<body>`. Style rules are raw layout (flex, width, margin, padding), view/image (backgroundColor, borderRadius, opacity, shadows), text (color, fontSize, fontWeight). Styles are declared in `<styles><style id="Card" padding="16" backgroundColor="white" borderRadius="8"/></styles>` and applied via `style="Card"`; the docs mention no tokens or inheritance. — [Hyperview styles](https://hyperview.org/docs/reference_style)
- rfw: remote widgets are built from local widget libraries compiled into the app (`createCoreWidgets` such as Text/Row; `createMaterialWidgets`); the vocabulary is therefore "the Flutter widgets the host registered", with the full Flutter props surface (`Padding`, `SizedBox`, `Spacer`, `ListView`...). It "suits prebuilt components, not new widgets with custom gestures, animations, or painters". — [rfw on pub.dev](https://pub.dev/packages/rfw), [rfw README](https://raw.githubusercontent.com/flutter/packages/main/packages/rfw/README.md)

### Inferences
- A tokens-only requirement matches the Adaptive Cards model best: the author names `spacing: "medium"`, `color: "good"`, `style: "emphasis"`; the host owns pixel values. A2UI does the same with `variant` enums. DivKit, Hyperview and rfw leak raw px/colour values, which is the opposite of what Argo wants.
- Block Kit and Raycast prove that a vocabulary of ~10 high-level rows (section, header, context, divider, accessory slot) covers a lot of plugin UI without any layout primitive. A hybrid fits Argo: ListItem/FieldGroup/Menu as "template" nodes plus a small set of layout nodes (Stack with direction/gap token, Spacer, Divider) for composition.
- A single "accessory" / "trailing" slot with a closed set of allowed element types (Block Kit) maps directly to Argo's ListItem trailing control.
- Counting the primitives: the systems that expose layout all converge on stack-with-direction (Container/Column/Row, DivKit container, A2UI Row/Column) plus gap/padding scales plus alignment enums (start/center/end/space-between/stretch) plus a flex weight; none needs absolute positioning except DivKit `overlap`.

### Gaps
- Adaptive Cards `Container`/`ColumnSet`/`Column` property details (width, bleed, minHeight, separator) did not load (explorer pages returned 404); I cannot cite them. HostConfig above is the verified part.
- DivKit size-type semantics (fixed/match_parent/wrap_content values, weight) and DivKit styling beyond raw properties were not retrieved.
- Hyperview: no source retrieved on inheritance, modifiers in detail, or whether styles can reference tokens. The page I read said it does not describe tokens.
- Airbnb's Medium post itself and Nubank's component schema are not available to me; no data on their component vocabulary beyond the above.
- Raycast `Color`/`Image.Mask` details (second half of the icons page) not read.

## 2. Composition and reuse: templates, variables, library imports, author-defined components

### Takeaway
Reuse comes in three forms: (a) type-inheritance templates with `$param` slots (DivKit), (b) data-binding templates where the same card JSON is expanded against data with loops and conditions (Adaptive Cards, json-render, A2UI), and (c) named widgets in a library language with imports, args, state and events (rfw). Only DivKit and rfw let authors define new reusable "components" from primitives; Adaptive Cards explicitly says it cannot compose template parts.

### Cited Findings
- DivKit: templates live in a `templates` object; each needs a `type`; an instance sets `"type": "labeled-icon", "label_text": "Hello"`; inside the template a `$` prefix marks an overridable field (`"$text": "label_text"`). Templates can inherit from other templates, values passed at the top override defaults at lower nesting levels. Template and variable names cannot be system names (e.g. you cannot name a template `container`), and templates can only be built from basic visual elements. Purpose stated: remove code duplication, JSON size and typos. — [DivKit templates](https://divkit.tech/docs/en/concepts/templates)
- DivKit official example: `{"templates":{"labeled-icon":{"type":"container","items":[{"type":"text","$text":"label_text"}]}},"states":[{"state_id":0,"div":{"type":"labeled-icon","label_text":"Hello"}}]}` — [DivKit templates](https://divkit.tech/docs/en/concepts/templates)
- Adaptive Cards templating separates data from layout: `${firstName}` binding, `$data` to set context, `$root`, `$index`, an element whose `$data` is an array repeats once per item, `$when` drops an element when false, built on Adaptive Expression Language (functions like `if`, `json`), and custom functions via the SDK. — [AC template language](https://learn.microsoft.com/en-us/adaptive-cards/templating/language)
- Adaptive Cards docs state of composing: "Currently there is no support for composing template 'parts' together" (page dated for the May 2020 RC; last updated Dec 2025 per metadata). — [AC template language](https://learn.microsoft.com/en-us/adaptive-cards/templating/language)
- Adaptive Cards templating expansion runs in the SDK (`template.expand({$root: data})`) before rendering, so the renderer only ever sees a plain card. — [AC template language](https://learn.microsoft.com/en-us/adaptive-cards/templating/language)
- json-render: `defineCatalog` (Zod prop schemas + descriptions + allowed actions) → `defineRegistry` (maps each catalog entry to a real component) → `<Renderer spec registry/>`. State binding expressions in props: `{ "$state": "/path" }`, `{ "$bindState": "/path" }`, `{ "$cond","$then","$else" }`, `{ "$template": "Hello, ${/user/name}!" }`, `{ "$computed": "fn", "args": {...} }`; element `visible` conditions; `watch` fires an action on state change. A "Jev" composition feature is marked unreleased. — [json-render](https://github.com/vercel-labs/json-render)
- A2UI: data binding via JSON Pointer paths (`{"path":"/form/email"}`), relative paths inside list templates, named functions with `call`/`args` (`formatString`, `regex`, `length`, `and`/`or`/`not`, `formatDate`), no executable code. "Smart Wrappers" register existing client components against A2UI's binding/event system. Out-of-order arrival: client buffers and skips references to IDs that do not exist yet. — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/), [A2UI README](https://github.com/google/A2UI)
- rfw: `import core.widgets;` declares dependencies; remote widgets are declared as `widget Button { down: false } = ...` with local state, `args.name`, `data.server.games`, `switch` with `default`, loops `...for item in list:`, `set state.down = true`, and events `event "digit" { arguments: [7] }` delivered to `RemoteWidget.onEvent`. Remote libraries are text (`.rfwtxt`) or binary (`.rfw`, recommended for servers). "Since remote widget libraries are declarative and not code, they cannot represent executable closures." — [rfw on pub.dev](https://pub.dev/packages/rfw), [rfw README](https://raw.githubusercontent.com/flutter/packages/main/packages/rfw/README.md)
- Hyperview reuses via shared `<styles>`/ids per screen; behaviours are declarative XML. (Beyond style ids, no composition mechanism was retrieved.) — [Hyperview styles](https://hyperview.org/docs/reference_style)

### Inferences
- For Argo: plugin authors on a Node Server already have JavaScript/TypeScript. Adaptive Cards' "expand a template against data" step can simply be the plugin's own code (a function returning a tree), so the wire format does not need `$data`/`$when`/loops. json-render's and A2UI's data-binding is only needed if the App must update bound values without a round trip (input fields, toggles).
- If authors need "their own components", DivKit-style `templates` (named subtree + parameters) is the smallest mechanism and is declarative (no code). rfw shows the next step (local state + events in the library language), which is heavy; json-render's `$state` binding gives the same effect more cheaply.
- DivKit's restriction "templates only from basic elements" and rfw's "libraries bottom out in compiled-in widgets" both guarantee that composition can never add visual capability, which is the property Argo needs for tokens-only styling.
- Flat adjacency list (A2UI, json-render) vs nested tree (DivKit, Adaptive Cards, Hyperview): flat helps streaming and patching by id, nested is easier for humans to write and type-check.

### Gaps
- DivKit template inheritance details beyond "templates can inherit" and DivKit variables/expressions (`@{}` syntax) were not retrieved.
- No source retrieved for Hyperview partials/`<behavior>` reuse.
- json-render's built-in layout components and how its React Native renderer maps to native widgets: not read in detail (README only).
- How Airbnb/Nubank let teams define new section types: no public source retrieved.

## 3. Text/markdown, icons, images, lists (virtualisation hints), charts/SVG

### Takeaway
Text is plain strings with a fixed set of semantic variants/sizes/tones; rich text is either a restricted markup string (Block Kit mrkdwn, Raycast `markdown`) or a structured block. Icons are a closed enum or catalog, never arbitrary SVG, in the strict systems. Lists are a distinct element with templated items (A2UI, DivKit gallery, Raycast pagination) and the host decides virtualisation. Charts are rarely first-class; Block Kit has a recent "Data visualization" block.

### Cited Findings
- Raycast detail pane takes `markdown` (`<List.Item.Detail markdown=...>`); lists support `pagination` (`onLoadMore`, `hasMore`, `pageSize`; Raycast calls `onLoadMore` at end of list; memory limits can block further loading) and built-in fuzzy filtering (`filtering`, switched off by `onSearchTextChange`). — [Raycast List](https://developers.raycast.com/api-reference/user-interface/list)
- Slack text objects have two types, `plain_text` and `mrkdwn`; Block Kit also has a `Markdown` and `Rich text` block and a `Data visualization` block (names only seen on the blocks page). — [Slack blocks](https://docs.slack.dev/reference/block-kit/blocks), [Slack section](https://docs.slack.dev/reference/block-kit/blocks/section-block)
- A2UI: Text `variant` h1-h5/caption/body; Image `fit` enum; Icon limited to the catalog icon set; List takes `children` as an array or a template bound to data, `direction`. — [A2UI components](https://a2ui.org/reference/components/), [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/)
- Adaptive Cards: icon on actions via `iconUrl` (data URI supported from 1.2); HostConfig sets `imageSizes` (small 80, medium 120, large 180), `imageSet.maxImageHeight`, `fontSizes`, `FactSet` (title/value styling, spacing), `media`. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model), [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- DivKit has dedicated `text`, `image`, `gallery` elements with their own property pages ("Text properties", "Image properties"). — [DivKit docs index](https://divkit.tech/docs/en/llms.txt)
- Hyperview list elements are `<list>` and `<section-list>` (separate from `<view>`); image rules `objectFit`, `resizeMode`, `tintColor`. — [Hyperview styles](https://hyperview.org/docs/reference_style)
- rfw core widgets include `Text`, `ListView`, `Image`, `Spacer`; because widgets are the real Flutter widgets, list virtualisation is Flutter's own (`ListView`). — [rfw README](https://raw.githubusercontent.com/flutter/packages/main/packages/rfw/README.md)
- json-render ships renderers for React Native, PDF, email, Ink, Remotion, Three.js (same spec, different registry), i.e. the registry is what makes one JSON render natively. — [json-render](https://github.com/vercel-labs/json-render)

### Inferences
- For Argo: a closed `Icon` name set (Phosphor/SF symbol names the App already maps) matches Raycast's `Icon.*` enum and A2UI's catalog icons; do not accept arbitrary SVG or URLs unless explicitly a separate `Image` node with restricted sources.
- Virtualisation: no system makes the author pass hints beyond a list-type element plus optional `pagination`/`hasMore`; the renderer picks FlatList/LegendList. A `List` node with `items` + `itemTemplate` (A2UI style) or a plain `children` array plus `loadMore` action (Raycast style) is enough.
- Charts: none of the primary sources defines a chart vocabulary beyond Block Kit's `Data visualization` block name. For Argo a chart/graph would be a new registered primitive (`Chart` with series data and token colours), not SVG passthrough.
- Markdown: a deliberately restricted subset (bold/italic/code/link) passed as a string prop is the common compromise; full CommonMark appears only in dedicated detail panes (Raycast `markdown`).

### Gaps
- Block Kit mrkdwn syntax limits, Raycast `Image.Mask`/`Color` dynamic light/dark details, and the structure of Block Kit's `Data visualization` block were not read.
- No primary source retrieved on SVG/chart vocabularies in DivKit, Hyperview, A2UI (the basic catalog lists none).
- No source on explicit virtualisation hints in any system other than Raycast pagination.

## 4. Versioning: schema versions, `requires`/`fallback`, unknown-element handling, capability negotiation

### Takeaway
Adaptive Cards has the most complete in-document mechanism (card `version`, per-element `requires` + `fallback` with `"drop"`). A2UI negotiates by catalog id (client advertises `supportedCatalogIds`). rfw promises best-effort backward compatibility. DivKit, Hyperview, Airbnb and Nubank have no versioning/unknown-element behaviour documented in any page I could retrieve.

### Cited Findings
- Adaptive Cards: card-level `version` string (e.g. `"version": "1.4"`). `Action.Execute` and `refresh` need 1.4; with a lower card version Outlook "WILL NOT" work and Teams "MAY NOT". — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Adaptive Cards `fallback`: "what to do when Action.Execute is unsupported by the client"; value is another action/element or `"drop"`. `requires` is a dictionary of feature → minimum version, "When a feature is missing or of insufficient version, fallback is triggered". — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Official fallback example: card `"version":"1.2"` with `{"type":"Action.Execute","verb":"...","fallback":{"type":"Action.Submit","title":"Submit"}}`; clients that support 1.4 render Execute, older ones render the fallback Submit, with degraded behaviour (Submit cannot return a new card). Older Teams clients ignore `fallback` when the action is not wrapped in an `ActionSet`, so wrapping is recommended. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Per the Schema Explorer snippets: `fallback` and `requires` were added in 1.2; `fallback` "describes what to do when an unknown element is encountered or the requires of this or any children can't be met"; `"drop"` removes the element immediately and "the unknown element doesn't bubble up any higher". — [search results into Schema Explorer pages (FactSet, ActionSet)](https://adaptivecards.io/explorer/ActionSet.html) (search-result snippets; the explorer pages themselves were not fetched)
- Adaptive Cards: the host reports supported versions/features; HostConfig `supportsInteractivity: false` turns interactive actions off. HostConfig itself carries per-property "Version" columns (1.0, 1.1, 1.3), i.e. the host config is versioned alongside the schema. — [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- A2UI: every message has `"version": "v0.9"` and one of `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface`. `createSurface` carries a `catalogId` (URI-style string) that cannot change without deleting and recreating the surface. The client advertises `a2uiClientCapabilities: {"supportedCatalogIds":[...],"inlineCatalogs":[...]}` in metadata; the server advertises via transport (Agent Card or MCP init). The page does not specify the matching algorithm. Status: v0.9.1 current, v1.0 release candidate, v0.8 legacy; the project says "early stage public preview". Between v0.8 and v0.9 property names changed (`distribution`/`alignment` → `justify`/`align`, `usageHint` → `variant`, `MultipleChoice` → `ChoicePicker`, `primary` boolean → `variant`). — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/), [A2UI README](https://github.com/google/A2UI), [A2UI components](https://a2ui.org/reference/components/)
- A2UI security boundary: the client keeps a catalog of pre-approved components and the agent can only request those. — [A2UI README](https://github.com/google/A2UI)
- A2UI errors go back to the generator: `error` with `code: "VALIDATION_FAILED"`, `surfaceId`, `path`, `message`. — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/)
- rfw: "once a file works, it will keep working" is a best-effort goal; golden tests are recommended; no library versioning scheme is documented. The `child` accessor returns an `ErrorWidget` when an argument is not a widget (and `optionalChild` returns null). Unknown-widget handling is not described. — [rfw README](https://raw.githubusercontent.com/flutter/packages/main/packages/rfw/README.md), [rfw on pub.dev](https://pub.dev/packages/rfw)
- DivKit: element docs live under a `/divs/2/` path (suggesting a v2 element schema); no versioning or unknown-type page exists in the docs index. — [DivKit docs index](https://divkit.tech/docs/en/llms.txt)
- Airbnb GP: clients pick rendering from a `sectionComponentType` enum; the InfoQ article does not discuss versioning or rollout across client versions. — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)
- Nubank BDC: page does not address versioning or unknown components; says the server controls rollout pace and A/B tests without a store release. — [Nubank blog](https://building.nu.com/server-driven-ui-framework-at-nubank/)

### Inferences
- Pattern worth copying from Adaptive Cards: put the fallback on the node, not in a global rule, so the plugin author decides whether an unknown node is dropped or replaced by a simpler one (e.g. a `Chart` with `fallback: {type:"Text",...}`). The `"drop"` non-bubbling rule is a good default for unknown leaf nodes.
- Pattern from A2UI: negotiate once per surface/session with a catalog id (e.g. `argo.ui/1`), not per element. This works well for Argo because App and plugin Server are separate processes: the App can report its catalog id(s) on connect and the Server can adapt.
- Adaptive Cards shows the cost of per-card version numbers (1.2 vs 1.4 compatibility tables, degraded behaviour, wrapping workaround for old hosts). A coarse catalog version plus per-node `fallback` is simpler to reason about.
- A2UI's own renames between v0.8 and v0.9 show that early catalogs break; an Argo vocabulary should expect to ship additive-only changes after 1.0 and keep enum values stable.
- Since the Server and App are installed together on the user's machines (Argo-owned), the dangerous skew is a new Server plugin on an old phone App; this matches Adaptive Cards' Teams/Outlook version-mismatch problem.

### Gaps
- DivKit, Hyperview, rfw and Airbnb/Nubank: no retrievable primary-source statement on unknown-element behaviour or schema versioning. I did not find (and will not assert) what each does.
- Adaptive Cards Schema Explorer pages (the authoritative `requires` / `fallback` property tables) did not load; the `drop` semantics above come from search snippets of those pages plus the Learn page.
- A2UI catalog negotiation matching rules are explicitly not specified on the page I read.
- Hyperview version handling: pages for custom behaviours/extensions returned 404.

## 5. Validation: schemas published for authors; errors on invalid trees

### Takeaway
Validation is usually JSON Schema for the wire format (DivKit, Adaptive Cards) or Zod/TypeScript for catalogs (json-render), with builders in the author's language (DivKit json-builder for TypeScript, Kotlin, Python). A2UI feeds validation errors back to the generating model with a structured code. Runtime behaviour for invalid trees is largely undocumented.

### Cited Findings
- DivKit publishes a JSON Schema in the repo (`schema` folder) from which an API generator emits the cross-platform API; type-safe JSON builders exist in TypeScript, Kotlin and Python. — [DivKit README](https://raw.githubusercontent.com/divkit/divkit/main/README.md)
- Adaptive Cards cards declare `"$schema": "http://adaptivecards.io/schemas/adaptive-card.json"`, i.e. JSON-Schema-validatable; HostConfig is itself a JSON object with a published sample and tooling that previews a card for a given host. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model), [HostConfig](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/host-config)
- Adaptive Cards ships a Designer with sample data editor and preview mode for templates. — [AC template language](https://learn.microsoft.com/en-us/adaptive-cards/templating/language)
- json-render: catalog is Zod (`props: z.object({...})` with `z.enum` for constrained values); `catalog.prompt()` generates a system prompt from the same definitions; `createSpecStreamCompiler` handles partial specs while streaming. The README does not detail runtime validation mechanics. — [json-render](https://github.com/vercel-labs/json-render)
- A2UI: input components accept `checks` (`call`, `args`, `message`); a Button with failing checks is disabled; format-level failures return `{error: {code: "VALIDATION_FAILED", surfaceId, path, message}}` to the generator. The spec describes itself as "a declarative data format, not executable code". — [A2UI v0.9 spec](https://a2ui.org/specification/v0.9-a2ui/), [A2UI README](https://github.com/google/A2UI)
- rfw: strict typed data format (int vs double, no null); declarative libraries "cannot represent executable closures"; `child` returns `ErrorWidget` if the arg is not a widget. — [rfw on pub.dev](https://pub.dev/packages/rfw), [rfw README](https://raw.githubusercontent.com/flutter/packages/main/packages/rfw/README.md)
- Slack enforces hard limits at the API (50 blocks per message, 100 in modals/Home; text 3000 chars; 10 fields at 2000 chars; `block_id` 255 chars). — [Slack blocks](https://docs.slack.dev/reference/block-kit/blocks), [Slack section](https://docs.slack.dev/reference/block-kit/blocks/section-block)
- Adaptive Cards action/refresh responses use an explicit result envelope with `statusCode`, `type`, `value` (200 success; 400/401/412/500 errors), and warn that HTTP 200 does not mean success. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)

### Inferences
- With a TypeScript server, Argo can define the vocabulary once as Zod schemas (as json-render does) and publish: the TypeScript types (`z.infer`), a generated JSON Schema, and a `ui.*` builder helper package for plugin authors. This mirrors DivKit's schema-first generation but with Zod as source of truth.
- Validate on the Server before sending (plugin gets errors with path + message, A2UI style), and again on the App with a tolerant renderer that applies per-node `fallback`/drop rather than failing the whole tree. Both sides need limits like Block Kit's (max node count, string lengths) to bound plugin abuse.
- Apply Block Kit-style hard numeric limits at the schema level; they are the only primary-sourced example of enforced size limits found.

### Gaps
- What DivKit, Hyperview and Adaptive Cards renderers do at runtime with an invalid tree (skip node, error card, log): not documented in retrievable pages.
- json-render's validation mechanics (schema failure behaviour, repair loops) not documented on the README page; would need the docs site or source.
- No retrievable source on JSON Schema for Hyperview (it is XML; an XSD exists in the repo per my recollection, unverified).

## Cross-cutting note on source quality
- Pages were fetched through a summarising fetch tool; where the tool stated "page does not say X", I recorded X as a gap rather than assuming. The A2UI README example in the fetch result was labelled by the summariser as its own illustration; the A2UI spec page examples are the official ones.
- Deprecations seen: A2UI v0.8 is legacy; Adaptive Cards `Action.Submit`/`Action.Http` are superseded by `Action.Execute` (1.4) per the Universal Action Model page; the Adaptive Cards template binding syntax changed from `{...}` to `${...}` in May 2020 (old form obsolete); `adaptivecards.io` explorer now redirects to `adaptivecards.microsoft.com`; Slack docs moved from `api.slack.com` to `docs.slack.dev`; Nubank blog moved to `building.nu.com`.
