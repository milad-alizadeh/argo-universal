# Agent-generated and agent-authored UI systems, and what makes a declarative UI format reliable for an AI agent to write

Research date: 2026-10-14. Primary sources fetched where possible; search-snippet-only claims are flagged. Note a distinction the report writer should keep: most systems below are about an agent emitting UI at *runtime* (per response). Argo's case is an agent *writing plugin code once* that later emits JSON trees. Claude Code mods is the closest precedent for the latter.

## 1. What exists (as of Oct 2026): declarative host components vs HTML in an iframe, native mobile rendering, actions, validation

### Takeaway
The field splits into two camps. Declarative-data camp: A2UI, json-render, Thesys C1, AG-UI's "declarative" tier, Claude Code mods. Here the agent emits a tree of host-owned components and the host renders natively. HTML-in-iframe camp: MCP Apps (and MCP-UI, OpenAI Apps SDK, which now both ride on MCP Apps). Here the agent ships a web page that the host sandboxes. Only the declarative camp renders natively on mobile (json-render has a React Native renderer today; A2UI native iOS/Android renderers are still roadmap). MCP Apps is web/iframe-centric.

### Cited Findings

**Google A2UI (declarative, catalog-based)**
- A2UI is "a declarative data format, not executable code." The client keeps a catalog of pre-approved components and the agent can only request components from it. UI is a flat list of components that reference each other by ID, described as "easy for LLMs to generate incrementally." — [Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)
- Google contrasts it with the iframe approach (HTML/JS in iframes), which it calls heavy and visually mismatched with the host app. The client maps descriptions to its own native widgets, inheriting styling and accessibility. — [Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)
- Status: README says "early-stage public preview" and "Expect changes." Versions: v0.9.1 current production release, v1.0 release candidate, v0.8 legacy. — [github.com/google/A2UI](https://github.com/google/A2UI); [a2ui.org](https://a2ui.org)
- Renderers: web and Flutter (via GenUI SDK) are the supported hosts. React, Jetpack Compose and SwiftUI are listed as *planned* official renderers. Angular and Lit renderers listed on the site. So native iOS/Android renderers were not shipped per the README at fetch time. — [github.com/google/A2UI](https://github.com/google/A2UI); [a2ui.org](https://a2ui.org)
- Message types (v0.9): `createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface`; every message has a `version` field. v1.0 candidate adds `actionResponse` (synchronous client-to-server RPC). Data binding uses JSON Pointer paths into a per-surface data model. — [a2ui.org concepts](https://a2ui.org/concepts/overview/)
- Catalog = a JSON Schema file listing components, functions, themes. "All A2UI JSON sent from the agent is validated against the chosen catalog." Catalogs must be standalone (no external refs) at the end. Client sends `supportedCatalogIds` in preference order; catalog choice is locked for the surface lifetime. A "Basic Catalog" is "intentionally sparse." — [a2ui.org catalogs](https://a2ui.org/concepts/catalogs/)
- Validation loop: agent-side validation before sending, with option to "attempt to fix or regenerate"; client-side validation on receipt; on failure the client sends a `VALIDATION_FAILED` error with `surfaceId`, `path` and `message` so the agent can correct and re-send. Clients should degrade gracefully (unknown components skipped or shown as safe fallback). — [a2ui.org catalogs](https://a2ui.org/concepts/catalogs/); [a2ui.org actions](https://a2ui.org/concepts/actions/)
- Actions: a component's action is either an `event` (sent to the agent) or a `functionCall` (runs locally in the renderer; agent not told). Payload has top-level `action` key with `name`, `surfaceId`, `sourceComponentId`, `timestamp`, `context`; context is a hand-picked map of literals or data-model paths. v0.8 used `userAction` as the key. Buttons can have renderer-side `checks` (UX only, not a substitute for agent-side data integrity checks). — [a2ui.org actions](https://a2ui.org/concepts/actions/)
- A2UI is transport-agnostic; A2A is a named transport; MIME type `application/a2ui+json` being standardised in v0.9.1. Escape hatch: custom "Smart Wrappers" including sandboxed iframe containers. — [a2ui.org](https://a2ui.org); [github.com/google/A2UI](https://github.com/google/A2UI)

**MCP Apps (SEP-1865) and MCP-UI (HTML in iframe)**
- Tools declare `_meta.ui.resourceUri` pointing to a `ui://` resource containing an HTML page; host fetches it (can preload) and "typically" renders it in a sandboxed iframe. Extension id `io.modelcontextprotocol/ui`; MIME type `text/html;profile=mcp-app`. — [modelcontextprotocol.io MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview); [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- Status: the spec page labels it Stable (2026-01-26), Extensions track; it is an optional extension negotiated via capabilities. Supported by Claude, Claude Desktop, VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman and others. Co-authored by Anthropic, OpenAI and MCP-UI maintainers (per search summary of the SEP, secondary). — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview); [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)
- Communication: JSON-RPC over `postMessage`. Methods include `ui/initialize`, `ui/message`, `ui/open-link`, `ui/update-model-context`, `ui/request-display-mode`; host-to-view notifications `ui/notifications/tool-input-partial`, `tool-input`, `tool-result`, `host-context-changed`; the view can also call `tools/call` on the server via the host. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- Mobile: spec "has no dedicated mobile or native section"; `HostContext` includes `platform` (`web`/`desktop`/`mobile`), `deviceCapabilities` and `safeAreaInsets`. Web hosts must use a double-iframe sandbox proxy with different origins; desktop/native hosts render the View directly in an iframe. So on a phone the host must embed a web view; there is no native-component rendering. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- MCP-UI: "now standardized into MCP Apps"; its packages (`@mcp-ui/client` `AppRenderer`) implement MCP Apps and add a legacy adapter. The fetched page did not mention React Native/native support. — [mcpui.dev](https://mcpui.dev/)
- Validation is host-side message/CSP checks, not UI-tree validation: hosts "must validate incoming UI messages, reject malformed ones"; default CSP `default-src 'none'`, `connect-src 'none'`. The HTML itself is arbitrary code. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)

**OpenAI Apps SDK**
- ChatGPT renders component UIs in an iframe and "implements the open MCP Apps standard"; build on the standard first and add `window.openai` extensions only where needed. Tool linked via `_meta.ui.resourceUri` (alias `openai/outputTemplate` accepted); MIME `text/html;profile=mcp-app`. Compatibility aliases: `window.openai.toolOutput`, `callTool`, `sendFollowUpMessage`. Presentation modes: inline card, carousel, fullscreen, PiP. CSP declared (`connectDomains`, `resourceDomains`, `frameDomains`) and checked in app review. — [OpenAI Apps SDK: Build a ChatGPT UI](https://developers.openai.com/apps-sdk/build/chatgpt-ui)
- Gap: the page did not describe sandbox attributes or mobile behaviour. Earlier (secondary) guides cited a `text/html+skybridge` MIME type; the primary page now says `text/html;profile=mcp-app`, so the older name appears superseded. — [OpenAI docs](https://developers.openai.com/apps-sdk/build/chatgpt-ui)

**Vercel json-render (declarative, catalog + Zod)**
- Vercel Labs project (Apache-2.0). Developer declares allowed components/actions via `defineCatalog` with Zod props schemas and a description each; AI emits a flat JSON spec (`root` + `elements` map, each element `type`/`props`/`children`; dynamic props via `$state`, `$cond`, `$template`, `$computed`; `visible` conditions). Also YAML. — [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render)
- `catalog.prompt()` generates a system prompt from component descriptions, props schemas and actions. Streaming via JSONL patches (`createSpecStreamCompiler`, `push()` returns partial result). — [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render); [json-render.dev](https://json-render.dev/docs)
- Renderers: React, Vue, Svelte, Solid, and `@json-render/react-native` (25+ standard components: Container, Row, Column, ScrollContainer, SafeArea, Pressable, Heading, Button, TextInput, Switch, Slider, SearchBar, Card, ListItem, Modal as bottom sheet, etc.). You register native implementations with `defineRegistry`; the `Renderer` needs StateProvider/VisibilityProvider/ActionProvider/ValidationProvider; `useUIStream` streams specs. — [json-render react-native package](https://github.com/vercel-labs/json-render/tree/main/packages/react-native)
- Actions: declared in the catalog with typed params; components trigger them via `emit`; built-in `setState`; `watch` fires actions on state change. — [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render)
- Status: Vercel Labs, launched January 2026 (per secondary press); The New Stack called it an early research prototype; README shows ~18.7k stars; fast-moving versions (0.14 to 0.19 in sources). Documentation fetched did not describe a dedicated validate/repair API; the claim that malformed output "fails loudly" comes from a secondary write-up. — [The New Stack](https://thenewstack.io/vercels-json-render-a-step-toward-generative-ui/); [InfoQ](https://www.infoq.com/news/2026/03/vercel-json-render); [pyshine write-up](https://pyshine.com/json-render-Generative-UI-Framework-Keeps-AI-on-a-Leash/)

**Vercel AI SDK generative UI**
- AI SDK RSC (`streamUI`) "is currently experimental"; Vercel recommends AI SDK UI for production, with a migration guide. — [ai-sdk.dev AI SDK RSC](https://ai-sdk.dev/docs/ai-sdk-rsc/overview)
- AI SDK UI approach: each tool gets a typed message part `tool-${toolName}`; client switches on `part.state` (`input-available`, `output-available`, `output-error`) and spreads `part.output` into an app-owned React component. This is the "static" tier: the model picks a tool, the app owns the component. — [ai-sdk.dev generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)
- AI SDK 5 adds typed data parts, tools streaming input by default, `inputSchema`/`outputSchema`, dynamic tools. — [Vercel AI SDK 5 post](https://vercel.com/blog/ai-sdk-5)

**CopilotKit / AG-UI**
- AG-UI is an open, event-based protocol connecting agents to user-facing apps; it is the agent-to-user connection layer, not a UI format. A2UI is "a generative UI specification" that works with it; MCP Apps listed as supported generative UI. Born from CopilotKit with LangChain and CrewAI; CopilotKit is first-party client. — [docs.ag-ui.com](https://docs.ag-ui.com/introduction)
- AG-UI docs name three generative UI tiers: Static ("stable, typed components under app control"), Declarative ("a small declarative language for constrained yet open-ended agent UIs", app validates and mounts trees), and open-ended (the page did not clearly define the third). — [docs.ag-ui.com](https://docs.ag-ui.com/introduction)

**Thesys C1**
- Generative UI API with an OpenAI-compatible endpoint plus a React runtime (`<C1Component />`); outputs a declarative DSL "similar to JSX or JSON" describing components, streamed progressively. No public schema/OpenAPI for the DSL found in search results. React-only runtime per sources; native mobile not confirmed. Search-summary only (not fetched in full). — [docs.thesys.dev](https://docs.thesys.dev/guides/how-c1-works.md); [what is C1](https://docs.thesys.dev/guides/what-is-thesys-c1)

**Claude Code mods (agent-authored code that emits element trees)**
- A mod is a plugin with a hooks module (JS/TS). A `ui.render` hook runs when Claude Code is about to draw a "render site" (Pane, AbovePrompt, Spinner, ToolUse, etc.) and returns an element tree built with `$.ui.resolve(e)` → `Box`, `Text`, `Button`, `Link`, `Code`, `Markdown`, `Input`, `Select`, `Svg`, `Client`, `Raster`, `Image`. Some elements are surface-specific (terminal vs Desktop). — [Draw in the interface with a mod](https://code.claude.com/docs/en/plugins/mods/interface)
- Event model: callbacks (`onPress`, `onSubmit`, `onSelect`) run in the mod's module; they change state and call `$.ui.invalidate('ui.render')` to re-run the hook, which rebuilds the tree from state ("Every interactive drawing uses that render cycle"). Controls need stable `key`s. Reactive `$.state` auto-redraws; `$.store` persists JSON across sessions. — [Draw in the interface with a mod](https://code.claude.com/docs/en/plugins/mods/interface)
- Redraw is throttled and coalesced; sites can use `next(e)` to defer to the built-in drawing, with props rewritten. — [Draw in the interface with a mod](https://code.claude.com/docs/en/plugins/mods/interface)
- Validation of output: "If a tree uses an element the app doesn't have, a prop an element doesn't take, or a child where none goes, Claude Code draws its own version of the site," and in a `--plugin-dir` session a transcript line gives a precise reason, e.g. `ui.render (Pane) refused: Text prop "bogusProp" is not allowed; the engine drew its own`; also logged in the debug log. — [Draw in the interface with a mod](https://code.claude.com/docs/en/plugins/mods/interface)

### Inferences
- For a native Expo/React Native host, the viable lineage is the declarative-catalog camp (A2UI, json-render, Claude Code mods), not MCP Apps. MCP Apps/Apps SDK would force a WebView on phones and bypass Argo's primitives, contradicting "JSON trees of Argo's primitives."
- Argo's design (server-side plugin code emitting JSON trees of host primitives into pages and slots) is structurally closest to Claude Code mods (code emits tree per render site; host validates; callbacks return to code) combined with json-render/A2UI (JSON tree format with a catalog). The main departure: mods' trees are built by function calls (`Box({...})`), Argo's would be plain JSON, so schema-level validation/constrained decoding is more applicable.
- A2UI's design choice of a flat ID-referenced list was made specifically for LLM generation and streaming, but a nested tree is also what json-render's `children` and mods use; the evidence found does not show which is more reliable for models (see section 2 gaps).
- The "static / declarative / open-ended" tiering (AG-UI) maps Argo to the declarative tier.

### Gaps
- No primary source found on how A2UI's React Native / SwiftUI / Compose renderers actually work (they were roadmap items at fetch time; A2UI repo README may be stale vs. late 2026).
- Did not read the A2UI message JSON schema or `client_to_server.json` directly, only concept pages.
- json-render's own docs fetched did not document validation/repair or error feedback; I could not verify a built-in repair loop.
- Thesys C1 DSL schema, native mobile support, and openness not verified from primary docs.
- MCP Apps on native mobile hosts (e.g. whether Claude mobile renders them in a WebView) not covered by the spec; unverified.
- Did not check ADRs/glossary in the Argo repo; "plugin direction" is explicitly undecided per project memory (grilling #506), so this research is input, not a decision.

## 2. What makes LLM authoring of a declarative UI format reliable

### Takeaway
Evidence from the primary sources converges on: a small closed catalog with per-component descriptions, machine-readable schemas (Zod / JSON Schema), validation with path-addressed errors fed back to the agent, generated types matching the exact host version, a static validate command, a no-network test harness, hot reload, and a fail-safe host that refuses an invalid tree without crashing. Constrained decoding makes runtime-emitted JSON schema-valid but does not apply to a plugin-authoring agent writing code, and has limits (no recursive schemas).

### Cited Findings
- Closed catalog as the contract: json-render says output is limited to developer-defined components, with the prompt auto-generated from the catalog (`catalog.prompt()`) so docs and schema cannot drift. — [github.com/vercel-labs/json-render](https://github.com/vercel-labs/json-render)
- Catalog descriptions are part of the schema: each json-render component has a props Zod object *and* a description. — [json-render catalog skill listing (secondary)](https://mcpservers.org/zh-CN/agent-skills/vercel/core); [json-render README](https://github.com/vercel-labs/json-render)
- Unsafe/underspecified types are excluded: when importing from Storybook, callbacks, raw-object props and `z.any()` are dropped; v0.19 added "directives" as an escape hatch for computed values without widening the catalog to `z.any()`. Secondary source (search summary), not verified in primary docs. — [search summary of json-render docs](https://skillselion.com/skills/yonatangross/orchestkit/json-render-catalog)
- Validation with addressable errors: A2UI's `VALIDATION_FAILED` carries `surfaceId`, `path`, `message`, designed so the agent can correct and re-send; agent-side validation before sending is also recommended. — [a2ui.org actions](https://a2ui.org/concepts/actions/); [a2ui.org catalogs](https://a2ui.org/concepts/catalogs/)
- Claude Code mods: the host names the exact bad prop in a one-line, human/LLM-readable error and falls back to a built-in drawing instead of crashing. — [Draw in the interface with a mod](https://code.claude.com/docs/en/plugins/mods/interface)
- Generated types per host version: Claude Code writes `.claude-plugin/types/claude-code/index.d.ts` (every event, API method, and the elements each surface can draw, with "a comment and an example for every mods API method"), plus a `tsconfig.json`; the docs say "trust these files over any page, this one included." — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create)
- Authoring skill: a built-in `plugin-authoring` skill "tells it where to write the mod, which events and methods your version has, and how the mod gets loaded." Claude edits, runs `claude plugin validate`, and fixes what it reports. — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create)
- Static validation with enforceable authoring rules: `claude plugin validate` runs static analysis without executing the code, prints `hooks:` and `calls:` lines, and rejects unanalyzable patterns with specific errors, e.g. `"tool.calls" is not an event`, `$.ui is used as a value`, non-literal event names, dynamic `import()`. These restrictions exist so analysis can find every hook and call. Claude Code refuses to load a mod using the API in a way the command can't read. — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create); [Manage mods](https://code.claude.com/docs/en/plugins/mods/admin)
- Test harness without a session: `claude plugin test` runs tests "with no session, sign-in, or network"; tests fire events (`$.tool.call`, `$.command.run`), stub model/store calls, and can test drawings by pressing controls by `key` ("A test presses or types into a control by its key, so give each control one"). — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create); [Draw in the interface](https://code.claude.com/docs/en/plugins/mods/interface)
- Hot reload loop: `claude --plugin-dir` reloads on every save; for Claude-written mods, files reload at the end of each turn so "you can try the change as soon as Claude finishes." — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create)
- Declarative state/redraw rule: callbacks mutate state and request a redraw; the render hook builds the tree from state only. A `ui.render` hook can read `$.state` but cannot write it (enforced by validate). This single-direction data flow is a simple pattern for an agent to follow. — [Draw in the interface](https://code.claude.com/docs/en/plugins/mods/interface)
- Streaming partial trees: json-render's JSONL patch streaming ("Each JSONL patch adds to the spec and the UI updates in real time") and A2UI's flat, incremental format both target progressive rendering; MCP Apps has `tool-input-partial` notifications for streaming tool inputs into an iframe. — [json-render docs](https://json-render.dev/docs); [Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/); [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- Constrained decoding (Anthropic structured outputs): supplying a JSON Schema yields responses that "guarantee schema-compliant responses through constrained decoding." Limits: recursive schemas not supported, no `minLength`/`maximum`/etc., `additionalProperties: false` required, max 20 strict tools and 24 optional parameters per request, 16 union-typed params; a complex schema returns 400 "Schema is too complex for compilation." Grammar compile adds first-request latency (cached 24h). Enum casing not guaranteed. — [Claude API structured outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Caveat on reliability from guardrails: a secondary write-up notes that even with guardrails, "variability is possible" and depends on prompt clarity and catalog completeness. — [SourcePulse (secondary)](https://www.sourcepulse.org/projects/25901769)

### Inferences
- A recursive tree of primitives (page → section → row → ...) cannot be expressed in Anthropic's strict-schema feature, since recursive schemas are unsupported. A flat id-referenced list (A2UI/json-render style: `root` + `elements` map) sidesteps this, and a flat list is also what the structured-output and streaming designs favour. Applies only when the model emits the tree directly; for a plugin-writing agent, the tree is produced by TypeScript code, so TypeScript types and a validator are the equivalent guard.
- Because the Argo agent writes code (not JSON directly), the Claude Code mods loop is the most applicable template: generated `.d.ts` types for the installed Argo version, a static `validate` that lists pages/slots/primitives/permissions used, a no-network `test` that renders trees and presses controls by key, and hot reload in the same Session. Precise one-line errors that name the offending prop are what the mods docs show the agent can act on.
- Giving each interactive control a required stable `key` (mods) / action id (A2UI, json-render) lets tests and the agent address controls; Argo could require it in the schema.
- Fail-safe rendering (fall back to a built-in or empty slot and surface the reason in the Session transcript) keeps a bad agent edit from breaking the app, and the error text doubles as the repair prompt.

### Gaps
- No controlled study or benchmark found comparing nested vs flat trees, or catalog size vs model error rate; reliability claims here are design rationale from the projects, not measured results.
- Did not find numbers on how often models produce invalid json-render/A2UI specs.
- json-render prompt generation details (what the generated prompt contains, whether it includes examples) not verified from primary docs.
- Anthropic docs do not describe constrained decoding applying to code generation; the structured-outputs page concerns JSON, so its direct relevance to code-writing plugin authors is an inference.
- Remaining ~3,000 characters of the structured outputs page were not read.

## 3. Security of agent-written plugins: permissions, review before enable, sandboxing

### Takeaway
Two models exist. Declarative data (A2UI, json-render) is safe by construction because there is no code on the client, only catalog-limited data. Code-bearing extensions (MCP Apps HTML, Claude Code mods) rely on sandboxing (iframe + CSP + declared permissions) or, for mods, explicitly *no* sandbox, with static capability listing and human approval before load. Argo's plugin code runs on the Server, so it falls in the second category regardless of the UI being JSON: the JSON tree is safe, the code that makes it is not.

### Cited Findings
- A2UI: because the format is declarative, agents can only request catalog components, which "reduces the risk of UI injection"; custom components or wrappers (e.g. sandboxed iframes) enforce their own trust levels. — [Google Developers Blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/); [github.com/google/A2UI](https://github.com/google/A2UI)
- MCP Apps: all View content must render in sandboxed iframes; host and sandbox must have different origins; default CSP `default-src 'none'` with `connect-src 'none'`; permissions limited to camera, microphone, geolocation, clipboard-write, requested in `_meta.ui.permissions` and not guaranteed; hosts "should warn users when a UI needs external domain access", may hash resources for allow/block-listing, and should enforce resource limits. — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- OpenAI: plugin review checks the declared CSP against the UI's actual behaviour. — [OpenAI Apps SDK](https://developers.openai.com/apps-sdk/build/chatgpt-ui)
- Claude Code mods are not sandboxed: "Mods aren't sandboxed" and "run code inside Claude Code with the permissions of the user who installed it." Capabilities like `$.fs.read/write`, `$.process.run`, `$.http.fetch`, `$.env.get`, `$.mcp.call`, `$.model.complete` are all reachable. — [Manage mods for your organization](https://code.claude.com/docs/en/plugins/mods/admin)
- Capability disclosure through static analysis: `claude plugin validate` lists the events hooked and mods-API methods called; admins/reviewers read the `calls:` line (e.g. `$.fs.write`, `$.process.run`, `$.http.fetch`) to judge risk. Code the analyser can't read is refused at load. — [Manage mods for your organization](https://code.claude.com/docs/en/plugins/mods/admin)
- Policy-as-code: a policy mod can receive `plugin.register` (with `e.uses.calls`, `e.tier`) and `{ refuse: reason }` a mod before it loads; it can intercept any API call by name (e.g. `fs.write`) to audit or deny. Fail-open by default if the check throws, with `.catch` to fail closed. — [Manage mods for your organization](https://code.claude.com/docs/en/plugins/mods/admin)
- Review before enable for agent-written mods: a mod Claude writes during a session loads only after the user approves hot reload ("Enable for this session" / "Not now"); the mod loads only in that session unless copied out; it will not load when nobody can approve (`claude -p`, `dontAsk`), in untrusted workspaces, or when mods are disabled; Claude Code asks approval per file written in `default`/`acceptEdits` modes because `~/.claude` is a protected path. — [Create a mod](https://code.claude.com/docs/en/plugins/mods/create)
- Org controls: `allowManagedModsOnly`, `disableSideloadFlags` (also blocks Claude-written mods), marketplace allowlists, `--safe-mode`. A built-in guard (`sec-default`) keeps user mods from overriding deny rules or managed hooks, but "everything else is allowed." — [Manage mods for your organization](https://code.claude.com/docs/en/plugins/mods/admin)
- General plugin trust: a plugin "can execute arbitrary code on your machine with your user privileges"; `claude plugin details` prints a component inventory; permission rules and the sandbox cover Claude's tool calls but not code a plugin runs itself; auto-update means reviewed files can change on disk. — [Plugin security and trust](https://code.claude.com/docs/en/plugins/security)

### Inferences
- Claude Code mods show the current "state of the art" for agent-authored extension code is approve-then-run with static capability listing, not real sandboxing. For Argo, if plugin code runs on the user's own Server with the user's privileges, a manifest of declared permissions (derived from or verified against static analysis, as `validate`'s `calls:` line does) plus an explicit user approval step in the Session before enabling would follow that precedent.
- The MCP Apps pattern (declared permissions/CSP in resource metadata, host enforces and warns) is the web-side precedent for manifest-declared capabilities; hosts must not assume the declaration is honest, hence "review checks declared policy against actual behaviour" at OpenAI.
- A JSON tree of a closed catalog removes UI-injection risk on the phone (the client never executes plugin code), concentrating risk in what the Server-side plugin can read, write and call. Per-plugin scoping (e.g. which Projects/files/network it can touch) has no analogue in mods (which are unscoped), so it would be new design.
- Pinning/hash of the reviewed plugin version (MCP Apps allows hashing; Claude plugins warn about auto-update changing reviewed files) suggests re-approval when a plugin's code or declared permissions change.
