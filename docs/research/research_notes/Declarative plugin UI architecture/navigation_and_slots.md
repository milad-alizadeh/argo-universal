# Declarative plugin UI: navigation and slots

Scope: how server-driven / plugin UI systems integrate with app navigation, and how host apps design slots (extension points). Aimed at Argo: Expo Router, catch-all `(shell)/plugins/[pluginId]/[...path].tsx`, and `<PluginSlot name=... context=... />`.

Research limits: about 24 tool calls. Pages that returned 404 or had no useful content are listed under Gaps. Quotes are short and taken from fetched pages. Items under Inferences are my own reasoning, not sourced.

## 1. Navigation: how server-driven UI systems map to host navigation

### Takeaway
Hyperview, the closest analogue, builds directly on React Navigation. It uses a small verb set: `push` (stack), `new` (modal), `back`, `close` (modal dismiss), `navigate` (go to or return to an existing route), and hash-target tab switches. Whether a screen is a modal is a route property in the navigation document (`modal="true"`), not a runtime choice by each link. Airbnb Ghost and LiveView Native follow the same pattern: the screen schema or router decides sheet vs push, and the client keeps the native stack. Raycast uses a plain `push`/`pop` component stack with ESC as automatic pop.

### Cited Findings

#### Hyperview
- Hyperview "builds on React Navigation": the app wraps `Hyperview` in a `NavigationContainer` and passes an `entrypointUrl` to an HXML navigation document. Hyperview builds the hierarchy from that document. — [Hyperview navigation guide](https://hyperview.org/docs/guide_navigation)
- A `<navigator>` has `id` and `type` (`stack` or `tab`). A `<nav-route>` is a screen with an `href` to a route document, or a nested `<navigator>`. Tab `selected="true"` sets the initial tab. — [Hyperview navigation guide](https://hyperview.org/docs/guide_navigation)
- Navigation actions in a behavior (`trigger` -> `href` + `verb` -> `action` at a `target`):
  - `push`: pushes a new screen onto the stack. Form data is sent as query parameters.
  - `new`: opens a screen on top of the current one (modal-style). `close` dismisses it.
  - `back`: pops the current screen. If `href` matches the previous screen's source, no request is made. Otherwise the previous screen reloads.
  - `close`: closes the current modal, with the same reload rules.
  - `navigate`: pushes or unwinds the stack to a screen loaded from the URL. In a stack it pushes the route if absent, or returns to it if it already exists, matching the exact URL. With a hash target such as `#profile` it switches tabs.
  - `reload`: re-requests the current screen.
  - `deep-link`: hands the URL to the OS. `open-settings`: opens OS settings.
  — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes); [navigation guide](https://hyperview.org/docs/guide_navigation)
- `href="#"` with `back` or `close` navigates without a reload or request. A `back` trigger on a `<view>` blocks closing the screen while visible, and "only works with internal Navigators". — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- Modals are declared on the route: `modal="true"` on a stack route. Opening is done with `new` and dismissing with `close`. — [Hyperview navigation guide](https://hyperview.org/docs/guide_navigation)
- Route documents may contain a `<header>` element for navigation UI. The example puts a text button with `action="back"` inside it. The page does not document title configuration. — [Hyperview navigation guide](https://hyperview.org/docs/guide_navigation)
- Deep links work by passing an updated navigation document to `entrypointUrl`; Hyperview re-renders the hierarchy. A changed `selected` tab moves the user there, and an added modal route shows on top. Deep links must include the full hierarchy down to the target, because intermediate hrefs are not loaded automatically. `merge="true"` on every navigator keeps the user's current state. — [Hyperview navigation guide](https://hyperview.org/docs/guide_navigation)
- Loading controls: `show-during-load` / `hide-during-load`, `delay`, `once="true"`. Update actions (`replace`, `replace-inner`, `append`, `prepend`, `show`, `hide`, `toggle`, `set-value` ...) apply to the current screen only; fetched content must be a fragment. — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)

#### Airbnb Ghost Platform (secondary source)
- Ghost Platform has three building blocks: sections (content units), screens (placement) and actions (interaction). Screens decide where and how sections appear, per device form factor. The screen-level schema covers whether a screen should appear as a popup or sheet. A single-column layout has nav, main and floating-footer slots. — summarised from [InfoQ on Airbnb server-driven UI](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/) (secondary source, 2021; the search summary cites Airbnb's Medium post as the origin)
- Section data is wrapped in a container with a component type so clients can render the same data differently. — [InfoQ](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/)

#### LiveView Native (SwiftUI client)
- Apps are generally wrapped in a `NavigationStack`, usually in a `root.swiftui.heex` template. Navigation reuses LiveView's `redirect/2`, `push_patch/2` and `push_navigate/2`. Routes are defined with the `live/4` router macro. — [LiveView Native SwiftUI native-navigation guide, v0.3.0](https://live-view-native-swiftui.hexdocs.pm/0.3.0/native-navigation.html) (via search summary; page not fetched directly)
- Two styles: one appends a history entry (system push animation and back button), the other replaces the top entry in the navigation path, so no back button. — same source (search summary, version caveat: 0.3.0 vs newer client docs)

#### Raycast
- `useNavigation` returns `push(component, onPop)` and `pop()`. The docs recommend the Push Action for most cases rather than the hook. Pressing ESC "automatically pop[s]" to the previous component. — [Raycast navigation API](https://developers.raycast.com/api-reference/user-interface/navigation)
- The page does not document `popToRoot` or when `onPop` runs. — same source

#### Expo Router specifics
- Dynamic routes use square brackets in file or directory names (`[userName].tsx`, `users/[userId].tsx`). Params are read with `useLocalSearchParams`. — [Expo Router notation](https://docs.expo.dev/router/basics/notation/)
- Catch-all: for `[...everything].tsx` and `/evanbacon/123` the result is `{ everything: ["evanbacon", "123"] }`, typed `string[]`. Search params remain individual strings. A matched route param is never nullish. — [Expo URL parameters](https://docs.expo.dev/router/reference/url-parameters/)
- `router.setParams` does not push to history. "Changing a route parameter remounts the component" (paraphrase from the fetched summary). — [Expo URL parameters](https://docs.expo.dev/router/reference/url-parameters/)
- `useLocalSearchParams` returns params for the focused route. `useGlobalSearchParams` also updates for unfocused routes. Expo's guidance is to prefer the local hook in stacks. — [Expo Router SDK reference](https://docs.expo.dev/versions/latest/sdk/router/) (via search summary)
- Runtime header options: render `<Stack.Screen options={{ title, ... }} />` inside the route component. The docs show a `title` from a route param, updated through `router.setParams`. `screenOptions` on `<Stack>` applies to all routes and is overridden per screen. — [Expo Stack](https://docs.expo.dev/router/advanced/stack/)
- `headerLeft` / `headerRight` accept a function returning an element. A composition API (alpha, SDK 55+) offers `<Stack.Title>`, `<Stack.Header>` and `<Stack.Toolbar placement="right" asChild>`. A custom title element passed as a function loses title animations. — [Expo Stack](https://docs.expo.dev/router/advanced/stack/)
- `navigation.setOptions` is not documented as a general method on that page. Its only example is `headerSearchBarOptions` inside `useLayoutEffect`. — [Expo Stack](https://docs.expo.dev/router/advanced/stack/)
- Modals: `presentation: 'modal'` on a `Stack.Screen`. `presentation: 'formSheet'` gives a bottom sheet with `sheetAllowedDetents` (fractions such as `[0.25, 0.5, 1]`, ascending, or `'fitToContents'`; Android supports at most 3), `sheetInitialDetentIndex`, `sheetGrabberVisible` (iOS), `sheetCornerRadius`, `sheetLargestUndimmedDetentIndex`. Other values: `card`, `transparentModal`, `containedModal`, `fullScreenModal`. — [Expo modals](https://docs.expo.dev/router/advanced/modals/)
- formSheet limitations: on Android, native header options (`headerShown`, `title`) do not render inside a form sheet, so put that UI in the sheet content. `flex: 1` works with numeric detents (iOS from SDK 55) but not with `'fitToContents'`. — [Expo modals](https://docs.expo.dev/router/advanced/modals/)
- Deep links: `+native-intent.tsx` exports `redirectSystemPath({ path, initial })` to rewrite incoming URLs. It is native-only, runs outside app context (no auth state or current route), and must not crash ("Do not crash inside this function!"). The page says web has no equivalent. — [Expo native intent](https://docs.expo.dev/router/advanced/native-intent/)
- Shared routes: the same URL in several groups renders per group. Cold links (deep links, reloads) have no current group, so Router renders the first alphabetical match. The docs warn against using shared routes for role-based screens and say to use `Stack.Protected`. — [Expo shared routes](https://docs.expo.dev/router/advanced/shared-routes/)

### Inferences
- Hyperview's model fits Argo's catch-all: one document URL = one native stack entry. `push` maps to `router.push('/plugins/<id>/<path>')`. `new` maps to a `presentation: 'modal'` or `'formSheet'` route. `back` / `close` map to `router.back()` / `router.dismiss()`.
- Hyperview chooses sheet vs push at the navigation-document level (`modal="true"` on the route) and with a separate verb (`new`), not by inspecting the screen. An Argo action could carry `presentation: push | sheet`. The catch-all file would then need either two sibling routes (one `card`, one `formSheet`) or a per-call param. Expo options are declared per `Stack.Screen` in the layout, and runtime `Stack.Screen options` inside the route can set header options but I did not find a source that changes `presentation` at runtime. Treat that as unverified.
- Because plugin pages would reuse one route file, Expo's "changing a route param remounts the component" and the catch-all `string[]` shape matter. The plugin page tree should be keyed by `pluginId` plus the joined path, and `path` must be treated as an untrusted array of segments.
- Hyperview's rule that deep links must contain the full hierarchy suggests Argo should keep plugin page URLs self-sufficient (a plugin page's path should fully identify the page, with no hidden dependence on a prior push), since Expo cold links only reconstruct what the URL and anchor define.
- Header/title/toolbar from server data: the Hyperview docs I found only show `<header>` content, not title data. For Argo, a `<Stack.Screen options={{ title, headerRight }} />` rendered from the JSON tree's `screen` metadata is the Expo-documented route. The "alpha" composition API (`Stack.Toolbar`) is documented only as alpha, so prefer `options`.
- On Android, formSheet cannot show a native header, so plugin sheets need an in-content title row (documented limitation).

### Gaps
- Shopify full-page extension navigation APIs: the customer-account Navigation page returned 404, so I could not confirm navigate/history behavior. Not covered.
- Airbnb Ghost: only secondary-source details (InfoQ). No primary Airbnb page was fetched for action types (e.g. navigate vs open sheet), titles, or deep links.
- Hyperview: no page found on how titles, header buttons, or the stack header options are set from HXML beyond the `<header>` element. State restoration in Hyperview is not documented in what I read.
- LiveView Native: the only source is a search summary of v0.3.0 docs; I did not read the page, and it is older than the current client docs.
- Raycast: nothing on deep links or state restoration in what was fetched.
- Expo: I did not find a source on `unstable_settings` / `anchor` and how deep links build a back stack (not in the native-intent page). I also did not verify changing `presentation` at runtime. The Stack page oddly lists `presentation` under Android only, which looks like a doc table quirk and should be verified against the installed SDK.

## 2. Slots: contribution points and extension targets

### Takeaway
Mature hosts separate three things: (1) host-defined named locations with an ID; (2) a declarative or typed contract per location (context data in, size or placement rules); (3) a policy for several contributors (ordering via group/priority, merchant or user placement, hard caps, per-contributor isolation). VS Code uses static manifest contributions with `when` clauses and lazy activation. Shopify uses typed targets with merchant placement, a three-extension cap per block target, and web-worker sandboxes. Claude Code mods use middleware chains per render site and per-hook failure isolation.

### Cited Findings

#### VS Code
- Menus: the `group` property "defines sorting and grouping of menu items", sorted lexicographically by group name. The `navigation` group "will always be sorted to the top/beginning of a menu". Order within a group is set by `@<number>` appended to the group id (for example `myGroup@1`). — [VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)
- `when` clauses apply to menus; `enablement` clauses apply to commands. "The `enablement` applies to all menus and even keybindings while the `when` only applies to a single menu." — [VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)
- Views go in `explorer`, `scm`, `debug`, `test` or a custom container. A view needs an id and name, and visibility is controlled by a `when` context value. `viewsContainers` can add to the Activity Bar and Panel. Views are populated by a TreeView or WebviewView. — [VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)
- `viewsWelcome` "only applies to empty tree views", where empty means no children and no `TreeView.message`. When several items target one view, core content comes first, then built-in extensions, then other extensions. — [VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)
- When-clause operators: `!`, `&&`, `||`, `==`, `!=`, comparisons, `=~` regex, `in` / `not in`. Built-in keys include `view` and `viewItem` (the tree item's `contextValue`) for `view/item/context`. Extensions set custom keys via `setContext`. — [VS Code when-clause contexts](https://code.visualstudio.com/api/references/when-clause-contexts)
- Activation is lazy: extensions should "activate only when a user needs your extension". `onView` fires when a view is expanded. `onStartupFinished` fires after startup without slowing it. Since 1.74.0 contributed commands and views do not need explicit `onCommand` / `onView` entries. — [VS Code activation events](https://code.visualstudio.com/api/references/activation-events)
- Status bar UX: items go in two groups, Primary (left, workspace-wide) and Secondary (right, contextual). Guidance: keep additions minimal because "other extensions contribute to the same area"; use short text; avoid custom colours. The page does not cover priority ordering. — [VS Code status bar guidelines](https://code.visualstudio.com/api/ux-guidelines/status-bar)

#### Shopify extension targets
- Static targets render immediately before or after a core checkout feature, and are not rendered if that feature is not rendered. Block targets are not tied to one section, can be repositioned, and "always render" even when their section is hidden. — [Shopify checkout targets](https://shopify.dev/docs/api/checkout-ui-extensions/latest/targets)
- Merchants activate and position block extensions in the checkout editor. Developers can set `default_placement` in TOML. Extensions do not appear until a merchant adds them. Placement references (`DELIVERY1`, `PAYMENT1`-`PAYMENT4`, `ORDER_SUMMARY1`-`ORDER_SUMMARY4`) are fixed identifiers. — [Shopify checkout targets](https://shopify.dev/docs/api/checkout-ui-extensions/latest/targets); [Shopify block-target testing page](https://shopify.dev/docs/apps/build/checkout/test-checkout-ui-extensions)
- "Merchants can add up to three extensions to the same block target location using the checkout and accounts editor." — [Shopify checkout UI extensions overview](https://shopify.dev/docs/api/checkout-ui-extensions/latest)
- One extension can declare multiple targets. With more than one, "you must define a separate code module for each target". Each target's config determines "which APIs it receives". — [Shopify checkout targets](https://shopify.dev/docs/api/checkout-ui-extensions/latest/targets)
- Isolation: extensions "run in an isolated sandbox, separate from the checkout page and other UI extensions", inside a Web Worker without `window` or DOM. The compiled bundle can't exceed 64 KB (128 KB for full-page customer account extensions). The docs say nothing about rendered height. — [Shopify checkout UI extensions overview](https://shopify.dev/docs/api/checkout-ui-extensions/latest)
- Rate limiting (secondary, via search summary): after an extension is rate limited it cannot make further changes in the buyer's session. — [Shopify checkout UI extensions overview (search result)](https://shopify.dev/docs/api/checkout-ui-extensions/latest)

#### Claude Code mods (render sites)
- A render site is "an extension point in Claude Code's interface". The `ui.render` event fires each time a site is about to be drawn, and the mod's hook returns what to draw. A hook filters by site with a matcher, e.g. `{ component: 'Pane' }`. `e.component` names the site, `e.surface` the app, `e.props` the site's data, `e.requestId` the instance (a pane's id). — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md)
- Site contract (props per site): `AbovePrompt` gets `hasSurvey`, `isWorking`, `maxRows`, `bodyColumns`, `scroll`, `view`; `Pane` gets `title`, `isFocused`, `bodyColumns`, `placement`, `scroll`, `view`. The sites are tagged with which surfaces (terminal / desktop) render them. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md)
- Sharing the band: "The band is a strip directly above the prompt input. It's always there, and every mod shares it." A returned tree "replaces what the mods after yours draw there". To keep theirs, include `await next(e)` among the children. Panes are different: each mod opens its own with an id, and with several open, "each gets a tab that shows its title". — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Order: hooks on an event form one middleware chain. The first mod is outermost. Order is built-in guard + org `prependPlugins`, then user-installed mods, then org `appendPlugins`, then built-ins. A mod runs before the mods it lists under `dependencies`, and within a module hooks run in `register` order. — [Mods: events](https://code.claude.com/docs/en/plugins/mods/events.md)
- Empty state: the pane and band "are empty until a mod fills them". A hook returns `next(e)` to draw nothing and keep the host's default. — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Sizing: draw to `e.props.bodyColumns`. A docked pane exposes `scroll.bodyRows`. An inline pane grows with its tree up to a limit, and `$.ui.open({ rows, columns })` asks for a different size. "A tree taller than the pane scrolls as a whole." Text in one tree is cut after 100,000 characters. — [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md); [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Redraw and performance: the host re-runs `ui.render` when site props or terminal width change, not on a timer. Mods call `$.ui.invalidate('ui.render')`. Redraws are throttled to 10/s (30/s in the terminal for visible pane, expanded band, and hint line) and coalesced. A hook's execution time limit is 10 s (50 ms for `prompt.edit`). — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md); [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md)
- Error isolation and validation: a hook that throws, times out, or returns a wrong-shaped result is skipped (if before `next`), and "A hook that fails doesn't break the session". If a tree "uses an element the app doesn't have, a prop an element doesn't take, or a child where none goes, Claude Code draws its own version of the site", with a diagnostic transcript line (e.g. `ui.render (Pane) refused: ...`). A `Client` region that fails to load shows a dimmed error line and "the rest of your drawing still shows". — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md); [Mods: events](https://code.claude.com/docs/en/plugins/mods/events.md)
- Panes opened without a user action are not placed in narrow terminals (144 columns; 110 after the user opens one once). `$.ui.open` returns `{ isPlaced, reason }`. — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Not every UI is a site: "The permission prompt isn't a render site". `AskUserQuestion` is, but a tree for it must hold the host reference exactly once. — [Mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)

#### Wix slots
- A host widget has one or more slots, each with a unique ID. A slot is "a placeholder within a host widget in which users can add a plugin". Plugin and slot share a Plugin API contract. Slots expose context data such as the current `productId`. — [Wix: About slots](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/site-extensions/site-plugins/supported-wix-app-pages/about-slots) (via search summary)
- Placement: users place plugins manually or the app auto-places on install. With a prioritized slot list, the plugin goes in "the first available slot in the order you define". Dashboard slot IDs can be shared across pages, so a plugin built for one such ID appears on all of those pages. — [Wix: About slots](https://dev.wix.com/docs/build-apps/develop-your-app/extensions/site-extensions/site-plugins/supported-wix-app-pages/about-slots); [Wix: dashboard page slots](https://dev.wix.com/docs/build-apps/developer-tools/extensions/dashboard-extensions/dashboard-plugins/supported-wix-app-dashboard-pages/about-dashboard-page-slots) (via search summaries)

### Inferences
- Context: VS Code passes context via context keys evaluated in `when` clauses (a flat bag of scalars/arrays), Wix via a per-slot context API, Shopify via per-target APIs (typed). Argo's `context={...}` prop is in the same family. The common lesson is that each slot name defines one fixed context type, and plugins declare which slot they fill and what context they need, so the host can type-check.
- Visibility: a declarative `when` (VS Code) lets the host decide whether a contribution shows before running any plugin code; useful for Argo since a JSON tree plugin may have no code to run. Context keys such as `session.status` or `project.hasPR` would let the host filter without activating the plugin. (Reasoning from VS Code's design, not a documented Argo requirement.)
- Ordering: three observed models. Explicit `group@order` strings (VS Code), a fixed three-item cap with merchant drag placement (Shopify), and host-defined mod order with middleware (Claude Code). For Argo slots like `session.header.actions` and `composer.above`, an explicit `order` plus a per-slot cap is the lowest-surprise option. The sources don't show one clearly best approach.
- Sizing: Claude Code gives sites an explicit width/rows budget in props and scrolls overflow; Shopify's docs I read say nothing about height. For `composer.above`, which sits in a pinned layout, a host-set `maxHeight` in the slot context with internal scrolling is the analogous pattern. (Argo design decision, not directly sourced.)
- Empty state: Claude Code and VS Code both treat unfilled sites as empty or default; the slot should render nothing (no placeholder) unless a `viewsWelcome`-style default is wanted. Keep per-slot empty handling in the host.
- Error isolation: the Claude Code docs describe a fallback to the host's default drawing on invalid trees plus a diagnostic. Each `<PluginSlot>` should wrap each contribution in its own error boundary and validate trees against the allowed element/prop set, so one bad plugin shows nothing and does not blank the host screen. This follows Claude Code's pattern; it is not a documented Shopify behavior.
- Performance and lazy activation: VS Code activates on first need (`onView`, `onCommand`) and declared contributions need no activation event. For JSON-tree plugins the equivalent is fetching a slot's tree only when that slot mounts and is visible. Redraw throttling (Claude Code) suggests debouncing plugin-driven re-renders.
- Block vs static (Shopify) maps onto Argo: `composer.above` / `project.details` are position-bound "static-like" slots tied to host UI; a user-placeable section would be "block-like". Static targets disappear when their host feature is not rendered, which matches slots inside conditionally rendered core pages.
