# State, interactivity and wire protocol in server-driven / remote UI systems

Scope: how systems that separate "code that produces UI" from "client that draws it" handle state, interaction round-trips and updates. Researched 2026-10-14 from vendor docs (primary sources). Short quotes only.

## 1. Where state lives (server-held vs client-side behaviours vs sandboxed JS near the UI)

### Takeaway
Every mature system ends up as a hybrid: durable/business state stays with the producer, but ephemeral UI state (visibility, toggles, input text, pressed states) is handled on the client without a round trip. Systems differ in how that client-side part is expressed: a closed vocabulary of declarative local actions (Hyperview, LiveView JS commands, DivKit, json-render `$state`, rfw local state) or by running the producer's real code next to the UI (Raycast's Node worker, remote-dom worker).

### Cited Findings

**Server-held state, every interaction round-trips**
- Phoenix LiveView: "A LiveView is a process"; state lives on the server as Elixir data on the socket, with a persistent connection opened after the initial static HTTP render. After an event, LiveView re-renders and pushes diffs. — [LiveView welcome](https://phoenix-live-view.hexdocs.pm/welcome.html)
- LiveView still has a client-only escape hatch: `Phoenix.LiveView.JS` commands "execute directly on the client without reaching the server" and suit UI state like dropdowns and tabs (show/hide/toggle/add_class/remove_class with transitions). They can be chained with a `JS.push` to the server. — [LiveView bindings](https://phoenix-live-view.hexdocs.pm/bindings.html), [LiveView welcome](https://phoenix-live-view.hexdocs.pm/welcome.html)
- LiveView recommends reducing server-held state: put state in URL query params (tabs via `patch` + `handle_params`), store relevant state in a database, and rely on automatic form recovery; for complex state, persist to Redis/S3/DB. Server state "may still have state that will be lost" on reconnect/deploy. — [LiveView deployments guide](https://phoenix-live-view.hexdocs.pm/deployments.html)
- Claude Code mods (the interface mod docs): the mod's JS module holds state in module-level variables, `$.state` (session-lifetime, reactive) or `$.store` (persistent JSON). A `ui.render` hook returns an element tree (`Box`, `Text`, `Button`, `Input`, `Select`...) built from current state; closures like `onPress` run in the mod's module, mutate a variable, then call `$.ui.invalidate('ui.render')`. Quote: "a callback changes state, and the hook renders again from the new state." Claude Code "doesn't run the hook on a timer, and it can't tell when a variable in your module changes", so mods must invalidate explicitly. A value in `$.state` redraws automatically because the hook "subscribes" to it by reading it. Redraws are throttled and coalesced ("the latest value shows and the values in between don't"). — [Claude Code mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Mods: callbacks are closures in the producer, not serialisable action descriptions. The UI process only knows control `key`s; each press/input/select also fires `ui.press`/`ui.input`/`ui.select` events with the `key` in `e.element`. Tests press controls by `key`, so every control needs one. — [Claude Code mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Adaptive Cards Universal Actions: `Action.Execute` replaces `Action.Submit`/`Action.Http`; the host POSTs an `adaptiveCard/action` invoke to the bot (verb, `data` = input values, `trigger: automatic|manual`), and the bot can return a new card "to be immediately displayed in the client" (HTTP body `statusCode` 200 + type `application/vnd.microsoft.card.adaptive`). There is no client-side logic or local state; inputs are collected on submit. A card `refresh` property re-invokes the action when the card is displayed; auto-refresh is limited to listed `userIds` (max 60) because unconditional refresh "would not scale"; otherwise a manual refresh button appears. `Action.Submit` cannot return a new card. — [Universal Action Model (Microsoft Learn)](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Slack Block Kit: interactions are HTTP callbacks. The app must ack with HTTP 200 "within 3 seconds"; `trigger_id` (needed to open a modal) expires in three seconds and is single-use; `response_url` can replace/delete the original message. — [Slack: handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction.md)
- Block Kit modals: `views.update` replaces an open modal's contents; input values survive if the new view reuses identical `block_id`/`action_id`; `hash` from the `block_actions` payload should be passed so stale updates are rejected. `view_submission` carries a `state` object with the values of stateful blocks; components in `input` blocks do not generate `block_actions`. `response_action` values: `update`, `push`, `clear`, `errors` (keyed by `block_id`). — [Slack modals](https://docs.slack.dev/surfaces/modals)

**Client-side behaviours / local state in the tree**
- Hyperview: every interaction is a "behavior" with `trigger`, `action`, `href`, `target`. Update actions that operate only on the current screen include `show`, `hide`, `toggle`, `set-value`, `select-all`, `unselect-all`, `copy-to-clipboard`; others (`replace`, `replace-inner`, `append`, `prepend`) fetch Hyperview XML. A fragment `href` ("#id") loads from the same document, "form data will be ignored." `dispatch-event` plus `on-event` trigger lets behaviors talk to each other. Triggers include `press`, `load`, `visible`, `refresh`, `change` (with `debounce` ms on `<text-field>`), `select`, `submit`, `back`. — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- json-render: spec = JSON `root` + flat `elements` map (`type`, `props`, `children` as IDs) limited to a catalog of declared component types. Props bind with `$state` (`{ "$state": "/user/name" }`), `$item`, `$index`, `$computed`, `$template`; `$bindState`/`$bindItem` give two-way binding for input `value`, `checked`, `pressed`. State is an optional top-level `state` object, provided at runtime by a `StateProvider` (client-side); an external store can be the "single source of truth." Actions are declared in the catalog with Zod param schemas; handlers are implemented by the host: "Your application provides the implementation. This is a core guardrail." Handlers get `(params, setState, state)`. — [json-render docs](https://json-render.dev/docs), [data binding](https://json-render.dev/docs/data-binding), [actions](https://json-render.dev/docs/actions)
- DivKit: global and local variables; `div-action://set_variable?name=..&value=..` and `set_state` switch local variables/state elements; `download` loads a patch from a URL; `submit` sends container variables through a link (JSON POST by default); `custom` passes a payload to the host app. Triggers: `actions` (tap), `longtap_actions`, `doubletap_actions`, `press_start/end_actions`, `hover_*`, `visibility_actions` (with percentage and duration). Child actions take priority over container actions. — [DivKit interaction](https://divkit.tech/docs/en/concepts/interaction), [DivKit variables](https://divkit.tech/doc/en/concepts/variables)
- Remote Flutter Widgets (rfw): data in `DynamicContent` (JSON-like, registered by name, read as `data.greet.name`); remote libraries "can't contain executable closures," so events (`event "digit" { arguments: [7] }`) are the only callback mechanism, delivered to the host via `RemoteWidget.onEvent`. Widgets declare local state in their header (`widget Button { down: false }`) and mutate inline (`set state.down = true`), so buttons respond immediately: they "cannot wait for logic that's possibly running on a remote server." Servers are recommended to send the binary format. Scope: "best suited for interfaces made out of prebuilt components"; custom painters, drag-and-drop, page transitions out of scope. — [rfw README](https://github.com/flutter/packages/blob/main/packages/rfw/README.md)

**Sandboxed JS near the UI**
- Raycast: extensions run in their own Node worker thread (own JS engine instance and run loop, memory limits) inside a separate Node runtime process. React state lives in the extension's worker (my inference from the article: developers use React hooks; Swift holds view models). A custom React reconciler (not react-dom) maps React changes to a JSON representation of each component, composed into a "render tree". Transport is JSON-RPC over stdio; only registered messages (e.g. "render", "setClipboard") may cross. The article does not detail the event path back to the worker. — [How the Raycast API and extensions work](https://www.raycast.com/blog/how-raycast-api-extensions-work)
- Shopify remote-dom: a remote tree under a root container is observed by `RemoteMutationObserver` (extends `MutationObserver`), mutations are posted to the host and applied by `DOMRemoteReceiver.connection.mutate(data)`, creating real DOM elements. Sandbox options: hidden iframe, or Web Worker via `@remote-dom/polyfill` ("a non-DOM environment, like a Web Worker"). Function properties/methods need a separate serialisation layer (examples use `@quilted/threads`). The host controls what is allowed through an `elements` allowlist (attributes, events, methods); omitting it "leaves element names unrestricted". — [Shopify/remote-dom](https://github.com/Shopify/remote-dom)

### Inferences
- There are three archetypes: (A) producer-held state + closures/verbs (LiveView, mods, Raycast, Adaptive Cards, Block Kit), (B) declarative client-side behaviours/state in the payload (Hyperview, json-render, DivKit, rfw), (C) producer code isolated but co-located with UI (remote-dom worker). Argo's plugins running on a local Node Server are archetype A (closure-based, like mods/Raycast) with the Server as the "near" runtime; the phone then sits across a network from the producer, which is the situation LiveView/Block Kit/Adaptive Cards were designed for, not Raycast's stdio setting.
- Every system that serves remote or high-latency clients adds a closed, declarative local-effects vocabulary (show/hide/toggle/set-value/set-variable/class changes/local `state`) so pure UI feedback never waits for the producer. The producer-side closure model (mods) has no such vocabulary in the doc read; it assumes near-zero latency (same process machine).
- Because the client in rfw/json-render/Hyperview cannot run plugin closures, handlers must be named/declared (verbs, event names, catalog actions). Closure-based producers need a layer that registers callbacks and sends opaque handler ids/keys (mods uses element `key`s; Raycast uses registered messages) and keeps them valid across re-renders.

### Gaps
- Raycast's exact mechanism for sending UI events back to the worker (article is silent); Raycast's JSON Patch is confirmed, but callback registration/ID scheme is not described.
- LiveView Native's wire details: the GitHub page does not cover them, and the repo is archived (read-only since 2026-02-10 per the page), so it is an unreliable reference for "recommendations" ([live_view_native README](https://github.com/liveview-native/live_view_native)).
- Mods reference page (render-site props/limits table, `$.state` redraw throttle numbers) was not fetched; only the interface guide was read.
- DivKit `text_variable` binding for inputs, `array_insert_value` URL form, triggers for variables were not found in the pages fetched. Hyperview and DivKit "variables" page is only an overview.

## 2. Forms: controlled inputs without a round trip per keystroke, validation, submit

### Takeaway
The dominant pattern is "client owns the live input value; the producer sees changes debounced or only on submit; the server's render never overwrites a focused field; submit is a distinct event with pending UI." Per-keystroke round trips are avoided by debounce (LiveView, Hyperview), by sending form data only on submit (Adaptive Cards, Block Kit), or by two-way client-side state binding (json-render, DivKit).

### Cited Findings
- LiveView: "the JavaScript client is always the source of truth for current input values." A focused input is not overwritten by server renders (opt-in `phx-patch-focused`). `phx-change` sends the whole form's fields (or one input's value if on that input), with a `_target` param naming the changed input. In-flight `phx-change` does not disable the input; the form gets `phx-change-loading`. — [LiveView form bindings](https://phoenix-live-view.hexdocs.pm/form-bindings.html)
- LiveView `phx-debounce` accepts an integer ms or `"blur"` (default 300ms when no value); `phx-throttle` fires immediately then rate-limits; a `phx-submit` or `phx-change` on a different input resets pending timers. — [LiveView bindings](https://phoenix-live-view.hexdocs.pm/bindings.html)
- LiveView validation: `phx-change` -> `validate` callback builds a changeset, re-render shows errors; `used_input?/1` avoids showing errors for untouched fields (untouched params are sent as `_unused_`). — [LiveView form bindings](https://phoenix-live-view.hexdocs.pm/form-bindings.html)
- LiveView submit: while pending, inputs become `readonly`, submit buttons are disabled, form gets `phx-submit-loading`; afterwards the form is reactivated and the last focused input restored; `phx-disable-with` swaps button text. Forms with `phx-change` and an `id` recover automatically after reconnect by re-sending the change event; `phx-auto-recover` can name a different recovery event or `"ignore"`. — [LiveView form bindings](https://phoenix-live-view.hexdocs.pm/form-bindings.html)
- Claude Code mods `Input`: `onInput(value)` on every change, `onSubmit(value)` on Enter. The `value` prop is "the text the field holds when it's drawn, and the user's typing replaces it until your hook draws the field again"; the docs' notes example always draws `value: ''` to clear after submit. So typed text is held in the UI process; the producer sees each change only if it supplies `onInput`. — [Claude Code mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- Hyperview: `change` trigger on `<text-field>` can be paired with `debounce` (ms); forms are submitted via behaviors with `submit`/`press` triggers; fragment `href` ignores form data. — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- json-render: `$bindState` gives two-way binding of `value` to a client-side state path; actions receive `(params, setState, state)` and typical handlers (`submit_form`) do the fetch and `setState` the result. Params are declared with Zod in the catalog; the docs do not say whether they are validated at runtime. — [json-render data binding](https://json-render.dev/docs/data-binding), [actions](https://json-render.dev/docs/actions)
- Adaptive Cards: input values are collected into the action's `data` on `Action.Execute` (no per-keystroke traffic); the response can be a new card, a message, or an error object. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Block Kit: input values return in `view_submission.state`; `input` block components don't emit `block_actions`; validation errors go back as `response_action: "errors"` keyed by `block_id`; 3-second budget. — [Slack modals](https://docs.slack.dev/surfaces/modals), [Slack: handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction.md)

### Inferences
- For Argo: text inputs need an explicit contract: the App owns the live value (uncontrolled/draft semantics), and the plugin receives `change` (debounced, optionally `blur`-only) and `submit` events. A server `value` re-send should not clobber a focused/dirty field (LiveView's rule) and should be able to reset the field explicitly (mods' draw-`''`-to-clear pattern is fragile; an explicit "reset"/version token would be clearer).
- Server-side validation errors should be a separate keyed channel (`errors` by field id, as Block Kit does) or part of the re-rendered tree (LiveView), and "untouched field" suppression is worth copying.
- Pending UI for submit (disable button, readonly inputs) can be done by the App automatically from "event in flight" state, as LiveView does, rather than plugin-authored.

### Gaps
- LiveView Native `live_form` behaviour (SwiftUI) not verified.
- Hyperview's form-serialisation details (how all fields in a `<form>` are sent) not fetched; the guide pages for forms returned 404/not fetched.
- rfw has no documented text-input story in the README; unknown.

## 3. Optimistic updates, loading/pending states, error states, timeouts

### Takeaway
The best-documented pattern is LiveView's: per-element "event in flight" states plus client-side optimistic commands that persist across server patches. Declarative-payload systems (Hyperview, DivKit) put loading indicators in the tree; messaging platforms (Adaptive Cards, Block Kit) impose hard server-response deadlines and typed error responses.

### Cited Findings
- LiveView: "Whenever an HTML element pushes an event to the server, LiveView will attach a `-loading` class to it" (`phx-click-loading`, `phx-change-loading`, `phx-submit-loading`, plus keydown/keyup/focus/blur). Classes persist until the client receives an acknowledgement; "the loading state is removed only when all events are resolved." — [Syncing changes and optimistic UIs](https://phoenix-live-view.hexdocs.pm/syncing-changes.html)
- LiveView optimistic updates: `JS.push("delete", loading: "#post-row-13")` assigns the loading state to another element; `JS.hide` / `JS.add_class` act immediately and are "DOM-patch aware" so they persist across server patches; hooks give full control for complex cases. LiveView tracks in-flight events per input/button/form and "shows server updates only after those events resolve." — [Syncing changes and optimistic UIs](https://phoenix-live-view.hexdocs.pm/syncing-changes.html)
- Hyperview: `show-during-load` (for navigation actions takes one `<screen>` id as loading state; for update actions shows elements then hides after the fetch), `hide-during-load`, `delay` (ms before requesting `href`; indicators toggle during the delay), `once`. — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- DivKit: `download` action loads a patch from a URL and updates the current element; "additional loading" of new markup can be automatic or on button press, with fallbacks. — [DivKit interaction](https://divkit.tech/docs/en/concepts/interaction), [DivKit variables](https://divkit.tech/doc/en/concepts/variables)
- Adaptive Cards: the invoke response carries a `statusCode` sub-status (200-599) that clients MUST inspect even though HTTP is 200; defined types include a returned card, a message string, 400/500 error objects, and 401 login-request. — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)
- Slack: 3-second ack, 3-second single-use `trigger_id` with `trigger_expired` / `trigger_exchanged` errors, `hash` to reject stale `views.update`. — [Slack: handling user interaction](https://docs.slack.dev/interactivity/handling-user-interaction.md), [Slack modals](https://docs.slack.dev/surfaces/modals)
- Claude Code mods: unknown elements/props make the host "draw its own version of the site" with an error line in a debug session: "ui.render (Pane) refused: ... the engine drew its own" and a `ui.fault` event for a failing `Client` region. This is graceful degradation of an invalid tree; no pending/timeouts for button callbacks were described in the page read. — [Claude Code mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- json-render: `loading` flag exists on component context ("Whether the renderer is in a loading state"); action docs show no error handling. — [json-render actions](https://json-render.dev/docs/actions)

### Inferences
- A tRPC-style round trip over WebSocket makes "event in flight" tracking cheap to implement in the App: tag each event with an id, mark the source element pending until ack (like `-loading`), and clear when the matching ack or new tree arrives. Doing this in the App, not the plugin, means every plugin gets pending states.
- Optimistic updates should be limited to a small, App-implemented vocabulary of reversible local effects (hide, toggle, set local value, mark pending) which the plugin can declare per interaction (LiveView's `JS.push(..., loading:)` shape), with the server's next tree being authoritative. LiveView's "patch aware" guarantee (the optimistic change survives intervening patches until the event resolves) is the subtle part to copy.
- A time-budget convention (Slack/Adaptive Cards both require sub-few-second responses) suggests Argo should define a handler timeout and a visible error state (toast; matches the project's "errors as toasts" decision per memory), plus a stale-tree guard (Block Kit `hash`) so a late response doesn't overwrite newer UI.

### Gaps
- No primary source found for LiveView's own timeout configuration for events, or for Hyperview error-state handling (what the client shows when a fetch fails).
- No source on optimistic-update guidance from Raycast, mods, rfw, or json-render.

## 4. Wire protocol: full tree vs diffs, streaming, batching, subscriptions, reconnection

### Takeaway
Options in the wild: (1) full tree each time (Adaptive Cards, Block Kit, Hyperview fragments, mods tree in the doc read), (2) generic structural diff of a JSON render tree (Raycast: JSON Patch + gzip above a size threshold), (3) mutation records from a live reconciler/DOM (remote-dom), (4) template-aware diffs with a static/dynamic split and change tracking (LiveView), (5) streamed row/patch protocols (RSC Flight, json-render JSONL patches). Reconnection is addressed by re-mounting and re-sending state (LiveView) rather than replaying.

### Cited Findings
- Raycast: "The new tree is diffed against the previous one using JSON Patch. If no patches exist, native code does nothing." Payloads above a size threshold are gzip-compressed. On the native side patches are translated into bitset types so the app knows which parts changed; native components get lightweight Swift view models and update only what changed. Messages are ordered via serial queues; temporary session IDs route messages to the extension instance; race conditions between the two processes are handled with custom logic. — [How the Raycast API and extensions work](https://www.raycast.com/blog/how-raycast-api-extensions-work)
- LiveView rendering: a `Rendered` struct has `:static`, `:dynamic`, `:fingerprint`. With change tracking (`__changed__`), unchanged dynamic expressions appear as `nil`, so content isn't sent; nested `Rendered` structs are tracked recursively with fingerprints identifying templates ("When fingerprints match, only the changes need to be sent"); loops are `Comprehension` structs with static parts once plus per-item dynamic entries. — [Phoenix.LiveView.Engine](https://phoenix-live-view.hexdocs.pm/Phoenix.LiveView.Engine.html)
- LiveView welcome: "render updates to a page as diffs"; after an event it re-renders relevant template parts and pushes the diff over the persistent connection. — [LiveView welcome](https://phoenix-live-view.hexdocs.pm/welcome.html)
- LiveView reconnect: automatic reconnect with exponential back-off (immediately, then 2s, 5s...); state may be lost in the transition; forms auto-recover by resending change events. — [LiveView deployments guide](https://phoenix-live-view.hexdocs.pm/deployments.html), [LiveView form bindings](https://phoenix-live-view.hexdocs.pm/form-bindings.html)
- remote-dom: mutation observer on the remote tree sends mutation records to the host; the host applies them through `connection.mutate(data)`; transport is any `postMessage`-like channel. Properties/events/attributes are declared (`remoteAttributes`, `remoteEvents`) and permissioned separately on the host. — [Shopify/remote-dom](https://github.com/Shopify/remote-dom)
- json-render: specs "render progressively. Each JSONL patch adds to the spec and the UI updates in real time" (the patch format itself is not shown on the page read). Flat `elements` map keyed by id makes streaming/patching individual elements natural. — [json-render docs](https://json-render.dev/docs)
- Hyperview: updates are fragments inserted with `replace`, `replace-inner`, `append`, `prepend` into a `target` id on the current screen (HTML-over-the-wire-style partials). — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- Adaptive Cards: the whole replacement card is returned; `refresh` is a pull model re-invoked at display time. Block Kit: whole replacement view via `views.update` (input state preserved by matching `block_id`/`action_id`). — [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model), [Slack modals](https://docs.slack.dev/surfaces/modals)
- Claude Code mods: producer re-runs the whole `ui.render` hook and returns a full tree for the site; invalidations are throttled and "coalesced into one redraw." A separate `$.ui.blit` repaints one `Raster` element without re-running the hook (an out-of-band fast path for animation). The doc read does not describe the serialisation between the mod runtime and the terminal/Desktop UI. — [Claude Code mods: interface](https://code.claude.com/docs/en/plugins/mods/interface.md)
- rfw: binary format recommended for transport; library blobs (widget definitions) are distinct from data blobs (`DynamicContent`), allowing data-only updates. — [rfw README](https://github.com/flutter/packages/blob/main/packages/rfw/README.md)

### Inferences
- Splitting "structure" from "data" (LiveView static/dynamic, rfw library vs data, json-render spec vs `state`) is what makes small updates cheap without full tree diffing; the cheapest design for Argo might be a flat id-keyed element map (json-render shape) plus JSON Patch (RFC 6902-style, as Raycast) over it, rather than a nested tree whose paths shift. Raycast diffs JSON trees generically; keyed-by-id elements make patches stable under reordering.
- Coalescing (mods) and ordered delivery with session ids (Raycast) are the two operational properties to specify; add a monotonically increasing tree version so the App can drop stale patches or request a full resync after a gap (cf. Block Kit `hash`).
- Reconnection: LiveView's answer is to re-mount and re-send state, with explicit recovery for forms. With a WebSocket to the Server, the simplest reliable approach is "on reconnect, send the full current tree (snapshot) then patches", with the Server retaining the per-plugin view state.

### Gaps
- Exact remote-dom mutation record format and batching behaviour (fetches of the core README returned 503; only the top-level README summary was read).
- RSC Flight wire format details (row types, chunking) not fetched in this pass.
- No primary source found on batching/streaming specifics for LiveView Native or on Raycast's RPC batching beyond message ordering.
- tRPC-specific behaviour (WebSocket subscription reconnection, `tracked()` event ids) was not researched here; it is outside the sources assigned and would need the tRPC docs.

## 5. Latency handling over slow networks; what LiveView Native and Hyperview recommend

### Takeaway
LiveView's published guidance is mainly: do UI-only work on the client (JS commands), show per-event loading states, keep the client the source of truth for inputs, debounce change events, and keep recoverable state out of the process. No usable primary source was found for LiveView Native's or Hyperview's explicit latency recommendations; Hyperview's mechanisms (local update actions, indicators, `delay`, `debounce`) imply its approach.

### Cited Findings
- LiveView: JS commands "execute directly on the client without reaching the server"; loading classes; `phx-debounce` default 300 ms; the JS client is the source of truth for input values and in-flight events are tracked per element. — [bindings](https://phoenix-live-view.hexdocs.pm/bindings.html), [syncing changes](https://phoenix-live-view.hexdocs.pm/syncing-changes.html), [form bindings](https://phoenix-live-view.hexdocs.pm/form-bindings.html)
- LiveView welcome claims the persistent connection lets apps "react faster to user events as there is less work to be done"; it does not describe a specific latency mechanism. The syncing guide does not cover latency simulation. — [LiveView welcome](https://phoenix-live-view.hexdocs.pm/welcome.html), [syncing changes](https://phoenix-live-view.hexdocs.pm/syncing-changes.html)
- rfw explicitly justifies local state on latency grounds: buttons "cannot wait for logic that's possibly running on a remote server." — [rfw README](https://github.com/flutter/packages/blob/main/packages/rfw/README.md)
- Hyperview offers `show`/`hide`/`toggle`/`set-value` (screen-local), `show-during-load`/`hide-during-load` indicators, `delay`, `debounce`, `once`, and fragment hrefs that avoid HTTP. — [Hyperview behavior attributes](https://hyperview.org/docs/reference_behavior_attributes)
- LiveView Native: "allows a single LiveView to serve both web and non-web clients" (SwiftUI, Jetpack Compose, HTML clients); platform-specific templates are transformed into native UIs. The repository is a public archive, marked read-only on February 10, 2026. — [live_view_native](https://github.com/liveview-native/live_view_native)

### Inferences
- If phones pair over a network, anything that must feel instant (toggle, expand/collapse, selected row, text echo, button press feedback) should be handled by the App without a round trip; only commits to plugin logic should wait. Latency-sensitive systems (rfw, LiveView, Hyperview) all do this with a small fixed vocabulary.
- Status of LiveView Native (archived in 2026) means it is a design reference, not a dependency or a source of current recommendations.

### Gaps
- No primary Hyperview or LiveView Native text explicitly recommending latency strategies (Hyperview guide pages tried returned 404; LiveView Native README lacks it). Remaining statements above are descriptions of mechanisms, not stated recommendations.
- No measured latency numbers (e.g. acceptable round-trip budgets) found from any source.

## 6. React Server Components and Expo RSC: can they serve this role; limits

### Takeaway
Expo RSC exists but is an experimental beta, tied to Expo Router and a server that renders components per request; React RSC's model (server components render once into a serialised payload, no state/effects, interactivity only via client components that already exist in the app bundle) does not fit a plugin-defined, hot-swappable, sandboxed UI that must stream state-driven re-renders; it also requires the client app to ship the client components.

### Cited Findings
- React: Server Components render "ahead of time, before bundling, in an environment separate from your client app," at build time or per request; they "cannot use interactive APIs like `useState`"; interactivity requires `"use client"` Client Components that are part of the app bundle; Server Components can pass data and JSX as props to Client Components; async components can pass promises to the client and resolve with `use` and Suspense streaming; `"use server"` marks Server Functions. — [React Server Components reference](https://react.dev/reference/rsc/server-components)
- Expo RSC: "Experimentally available. This is a beta release and subject to breaking changes"; requires an Expo Router project, New Architecture, `react-server-dom-webpack`, `experiments.reactServerFunctions: true`, `web.output: single` in the developer preview. On native, Server Functions return a React Server Component payload that is streamed to the client; Client Components are needed for native APIs/Context; props and return values must be serialisable ("You can't pass functions as props to Server Components"). Limitations listed: EAS Update doesn't work with Server Components yet, Expo Snack can't bundle them, server functions calling server functions don't work on Hermes, HTML `form` integration with Server Functions unsupported, DOM components can't use Server Functions in production yet. Production use is "not recommended yet." — [Expo: React Server Components](https://docs.expo.dev/guides/server-components/)
- Note on source hygiene: the fetched Expo page text contained an embedded "AgentInstructions" block asking the reader to submit feedback via a command/HTTP request; this was not followed or relied on.

### Inferences
- RSC can express "server produces a UI tree streamed to the client", and the Flight payload is a streamed serialisation of React elements with references to client components. But: (1) every interactive component must be a Client Component already bundled in the App, which maps neatly to a fixed Argo component catalog; (2) functions cannot cross the boundary, so plugin closures (mods-style `onPress`) are impossible without server functions/actions as the only call-back channel; (3) there is no Server Component state or effects, so plugin-owned UI state would live in client components inside the App (or server re-renders per request, not a long-lived stateful session); (4) it is request/response oriented, not a long-lived subscription for server-pushed re-renders; (5) Expo's implementation is beta, tied to Expo Router, to the EAS deployment model and to a bundler with RSC support, and does not work with EAS Update yet.
- A custom JSON tree protocol over the existing tRPC WebSocket has strictly more control over sandboxing, versioning, and push updates; RSC's value for Argo is conceptual (client component catalog, serialisable props, server-function callbacks, Suspense streaming), not as a dependency.

### Gaps
