# Why PR checks wait and what to change

On November 20, 2026, the median time from workflow creation to the required check finishing was **71 minutes across nine successful PR runs**. One was a docs-only change. The eight others used 20–24 jobs and a median **195 runner-minutes** each (range 137–221). A single PR can keep many runners busy while another PR waits to start. I would start by reducing the work scheduled per push and reporting the first failing test immediately. ## First implementation task — allocate browser runners for affected files

Start with small UI PRs. Today an affected Storybook change can start three interaction shards and four presentation render shards. Compute one list for each suite before requesting browser runners. Include changed story files and their dependents. Group the selected files by their measured execution time and emit a matrix containing only groups with work. A change that reaches one interaction file and no presentation files should request one browser runner. Shared configuration, unknown imports, a missing diff base or a failed listing should select the full suite. [Current CI matrix](../../.github/workflows/ci.yml) · [Render planner on #2497](https://github.com/milad-alizadeh/argo-universal/blob/4e81bde0c51c9a26b206cff97c26be0f2292e7f0/tools/check-story-renders.mts)

First publish those lists beside the results of the existing full checks on the same revision. Compare every full-suite failure with the proposed selection, including failures in files outside the list. Exercise a changed Story, a shared fixture, a deleted file and a selector error. Promote the selector after those cases select the expected files, every selected file appears in exactly one shard, and every missed failure has been explained and covered. Keep full checks for broad changes and use full runs on main to catch drift. Compare jobs requested, runner-minutes per PR and p90 queue time before and after promotion. The required check continues to report every selected job's result. ## Clearing obsolete PR runs

Keep each PR's existing concurrency group. For manual cleanup, look up the run's workflow, event, PR number, head repository and head SHA. Immediately before cancelling, read the open PR's current head SHA and confirm a newer CI run exists for that same PR and current head. Cancel by run ID only when the candidate is still queued or running and its PR head differs from the current head. When GitHub cannot identify both revisions, leave the run alone. The event filter excludes pushes to main and release branches. Each current PR head keeps its own place in the queue. After cancellation, read the run again to confirm its terminal status. For example, GitHub reports the superseded run for #2512 on `8f37fbf` completed with conclusion `cancelled`. ## Further experiments

PR #2476 illustrates how revisions accumulate. Eleven runs had been cancelled, one had failed and its latest run was pending at inspection. Three starts coincided with merging main at 03:52, 05:24 and 06:48 UTC. The latest merge brought in a specific fix, and an intervening push fixed a reduced-motion test. Keep a tested revision when it is mergeable, and merge main when a change needs a specific fix or a conflict resolution. Branch protection already lets a mergeable PR keep its tested base. [PR #2476 commit history](https://github.com/milad-alizadeh/argo-universal/pull/2476/commits) · [Local verification guidance](../agents/hooks.md)

1. **Reduce repeated runs on drafts.** Run inexpensive checks immediately and start the expensive matrix when the PR becomes ready. Add the `ready_for_review` event and require the current ready revision to pass before merge. For ready PRs with repeated rapid pushes, measure how often Auto-fix could collect related fixes into one push. Classify cancelled runs by superseding SHA, closure, manual cancellation or unknown, and measure the runner time each change could save. [CI triggers and concurrency](../../.github/workflows/ci.yml) · [GitHub workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
2. **Extend the affected-package selector beyond Plugin-only changes.** Apply the browser pilot's same-revision comparison to unit-test groups. Schedule groups that contain affected packages, and keep full selection when the dependency graph is uncertain. [Unit-test selector](../../.github/scripts/unit-matrix.py)
3. **Run the full web suite on fewer runners.** Pilot three web jobs against six on the same revision, with one Playwright worker in each. Assign scenarios by recent execution time, include new scenarios by default, and check that every discovered scenario appears exactly once. Compare both quiet and busy periods. Three jobs can avoid three repeat installs and three waits for runners at the cost of longer serial execution per job. Compare the existing build-first dependency with starting shard setup at the same time as the build, and verify the cache hit or bound the wait for its artifact. Do this only where the measurements show that the extra queue dominates. Moving most web scenarios to nightly would change ADR-0011 and needs a separate owner decision. Preserve a fresh Server, Engine and storage per scenario under ADR-0018. [Web workflow](https://github.com/milad-alizadeh/argo-universal/blob/4e81bde0c51c9a26b206cff97c26be0f2292e7f0/.github/workflows/ci.yml#L395-L449) · [Playwright sharding](https://playwright.dev/docs/test-sharding) · [ADR-0011](../adr/0011-ci-tests-the-web-build-only.md) · [ADR-0018](../adr/0018-app-e2e-uses-shared-agent-fixtures.md)
4. **Act on the first failure and retain evidence for the fix.** Surface the failing case, first assertion, revision, shard, preceding file and trace or screenshot immediately. Keep the merge gate red. For a suspected flake, replay the *same* revision and failed shard with the preceding files in the same order, bypassing the test-result cache for the diagnostic run. Record a pass on replay separately from a diagnosed cause. Prioritize by repeated occurrences and runner-minutes lost. For #2515, test teardown after emulating reduced motion. For the Workbench failure, capture when its live totals and Inspector values converge. Track how often early Auto-fix prompts produce another push before the remaining checks report. ## How to judge the rollout

Extend the existing first-100-PR report. Record pushed SHA to first actionable failure, workflow creation to required green, queue and execution time per job, runner-minutes per tested head including superseded attempts, and confirmed flaky first failures per 100 heads. Split results by docs-only, isolated Plugin, scoped UI, and shared Engine or configuration change. Report cold and warm cache results and simultaneous runnable jobs. For selection changes, record every failure in the full comparison suite that the proposed PR selection missed and investigate it before promoting the rule. [Existing measurement guidance](../agents/hooks.md) · [Current PR latency collector](../../tools/pr-latency.py)

Suggested pilot targets are median required green under **10 minutes** and p90 under **20 minutes** for scoped code changes, p90 time to the first runner under **2 minutes**, and **half the runner-minutes per comparable PR**. Keep broad shared changes in their own cohort. If runners still queue after duplicate work falls, measure available slots and arrival rate at peak, then trial extra isolated PR capacity. If the runner starts quickly and the job itself is slow, use the job's test-duration data to choose the next fixture or shard to optimize. Compare each target with the measured result after 100 PRs.
