# Plugins own sign-in and Argo brokers their Accounts

This builds on [ADR-0025](0025-plugins-run-on-the-server-and-draw-argo-components.md) and [ADR-0035](0035-plugins-add-to-named-slots-and-never-edit-core-screens.md), and amends [ADR-0022](0022-server-device-and-paired-devices.md) and [ADR-0030](0030-plugins-get-only-the-capabilities-their-manifest-declares.md) (owner, 2026-10-20). A Plugin that reaches a service needs the user signed in to it, and two Plugins often need the same sign-in: a code host Plugin and a CI Plugin, or two Plugins reading the same Linear workspace. Signing in twice means two tokens, two sign-outs and no way to see what the machine holds. The trap on the other side is Argo learning each service's flow, which would make every new service an Argo release. Neither is acceptable, so the line runs between the flow, which is the Plugin's, and the inventory, which is Argo's. This is how VS Code splits it: the extension owns the credential flow, the host owns the account list, the per-extension access list and sign out.

## Decision

- **One Plugin per product, and no vendor adapters inside one.** A code host with its CI is one Plugin, its Issue tracker is another, and GitLab is a third; each owns its own pages, Slots, actions and data. This amends ADR-0025's "the Issue tracker is one Plugin with Trackers inside" and deletes the Tracker registry: an internal adapter interface forces the union of every vendor's concepts to be designed before the third vendor exists, and the concepts that do not survive the translation are exactly the ones a user notices. Bundling a Plugin with Argo changes nothing about how it loads or what it may do.
- **A Plugin signs in on its own page.** Argo draws no sign-in sheet and knows no service's flow. A Plugin asks Argo for an Account; when nothing comes back it draws its own sign-in screen with kit components, on its own page (ADR-0025), and runs its own flow. One code path in the Plugin, whether or not it is the first to sign in.
- **An Account is named by the API host its token opens,** such as `api.linear.app` or `api.github.com`, never by a name the Plugin invents. Two Plugins cannot disagree about a host, so they cannot fail to share an Account by spelling it differently. GitHub Enterprise is a different host and so a different Account; CircleCI is `circleci.com`, a different Account from GitHub though both sign in with GitHub.
- **A Plugin declares the hosts it offers to sign in to, and the page that does it.** `contributes.accounts` is a list of `{ host, page }`, where the page is one of the Plugin's own registered paths and is where "Add account" sends the user. Each host must be a concrete host — no wildcard, no `localhost` — and must appear verbatim among the Plugin's declared `fetch` Capabilities (ADR-0030); a wildcard Capability does not satisfy it, so a Plugin cannot offer to sign in to a host it never named. Argo builds the "Add account" list from manifests alone, so no Plugin code runs to draw it. Two Plugins may declare the same host; both are offered, and the Account belongs to whichever one the user actually signed in with, recorded as `providedBy`. The other borrows it like any borrower.
- **Brokering governs sharing, not access.** A Plugin that declared a `fetch` Capability for a host can always run its own sign-in and keep its own token in its own secrets, where Argo cannot see it. What an Account buys is that the sign-in is listed, revocable and reusable by another Plugin. Settings › Accounts is not a complete list of what the machine is signed in to, and must not be sold as one.
- **Argo catches the OAuth redirect and nothing else.** `argo.oauth.start()` returns the `redirectUri`, a `state`, a PKCE `codeChallenge` and its method, always `S256` — a vendor's default is often `plain`, which is PKCE in name only, so the author is not left to choose. The Plugin builds its own authorize URL from them and calls `argo.oauth.await(state, url)`; Argo opens the browser on the Server Device, catches the one matching request, serves a page telling the person to close the tab, and returns the code and verifier. The Plugin exchanges the code itself. Argo generates `state` and the PKCE pair, allows one pending exchange per Plugin, and returns nothing on the five-minute timeout, on a denial, on a `state` it did not issue and when the Plugin reloads — the same one failure a borrow has. It parses no vendor's response and holds no token. The listener runs only while an exchange is pending, so nothing is held open at Server launch. Argo opens the authorize URL by running the platform opener with the URL as a single argument and never through a shell, and only `http:` and `https:` ever reach it.
- **One redirect URI for every Plugin:** `http://127.0.0.1:51789/callback`, on a fixed port, routed to the waiting Plugin by `state`. A Plugin author registers that one URI with the service and chooses nothing. RFC 8252 asks services to accept any loopback port, but enough of them demand an exact redirect-URI match that the port is fixed (owner, 2026-10-20): one string for every author to register, against an outright failure when something else holds 51789, which is the rarer and the more explicable of the two. A sign-in fails with a clear message naming the port when it is taken. Loopback over HTTP is what RFC 8252 prescribes for native apps, and the HTTPS rule that governs a Plugin's own calls is unchanged, because the listener is Argo's and not a Plugin call. A Plugin that needs a client secret keeps it in a `secret` settings field; PKCE means a public client needs none.
- **Every URL a Plugin hands to a Device is `http:` or `https:`.** That is `openUrl`, `share` and the authorize URL. Both URL fields are narrowed in the wire schema itself, so a tree carrying any other scheme fails preparation like any other bad prop and never reaches an App — there is no Server code on the `openUrl` path to refuse it at the time of the tap, and on the web App a `javascript:` URL would be script execution in Argo's own origin. The Server logs one line naming the Plugin and the scheme, and the App checks again, so neither side alone is the gate.
- **Sign-in runs on the Server Device** (owner, 2026-10-20). The browser and the listener are the same machine, so a paired phone cannot complete a sign-in: its Plugin page says to continue on the Server Device, and the Account appears there when it is done. A Plugin page learns this from an explicit flag the Server stamps from the Connection, never from the platform or the window width, and the Server refuses an OAuth call from a Connection where it is false — hiding the button is drawing, not the check. This amends ADR-0022, whose list of Server-Device-only work did not include it, and matches setup, which is already desktop-only.
- **Argo stores four facts and no vendor knowledge.** An Account row is `(host, id, label, providedBy)`, four strings; the Plugin supplies the label after signing in, because only it knows whose Account the token is, and Argo mints the id so two Plugins cannot collide. The Accounts, the grants and each Project's chosen Account are stored beside the Plugins' own state, not held in memory: signing in again after every restart would defeat the whole thing. The token itself stays where secrets already live, keyed by Account id and hard-namespaced per Plugin, so no Plugin can read another's.
- **A Plugin's own calls are `argo.accounts.add(host, { label })` and `argo.accounts.get(host)`.** `add` returns the Account id the Plugin stores its token under; `get` resolves the Account for this Project or nothing, which is how a sign-in page decides whether to draw a sign-in screen or a signed-in one.
- **A borrow is a call into the provider, not a copy of a token.** The providing Plugin registers `argo.accounts.provide(host, { header, prefix }, handler)`. When any Plugin borrows, Argo checks the grant and calls that handler in the provider's worker, waking it if it is asleep; the provider refreshes the token when it needs to, because only it knows the vendor's token endpoint. Argo stores no token and learns no vendor. Handing a borrower a copied string instead would leave it holding an expired token an hour later with the refresh token in another Plugin's secrets, unreadable and unfixable.
- **The borrower never sees the token, and the token never leaves the Account's host.** The borrower calls `argo.fetch(url, { account: 'api.github.com' })`; Argo looks up the grant, calls the provider for a fresh token, sets the header the provider named and sends the request. The request's host must equal the Account's host or the call is refused before anything is sent, and the header is dropped on any hop that leaves that host, exactly as `Authorization` already is on a redirect — otherwise a Plugin granted one borrow could point it at a collector of its own, or follow a redirect offsite, and have Argo mint a fresh token for every attempt. `{ header, prefix }` is two strings, which covers `Authorization: Bearer`, `Authorization: token` and `X-Api-Key` with an empty prefix; it may not name a header the network layer already reserves, and any header of the borrower's with the same name is removed before the Account's is set. Headers only: query-parameter auth is not supported, because a token in a URL ends up in logs. This makes the grant enforceable rather than advisory, since a Plugin with no grant has nothing to send.
- **A borrow either works or it returns nothing.** Disabled, uninstalled, crashed, slow, signed out, looping: all of them are nothing. There are no new states, no new screens and no cycle rule, and a Plugin that gets nothing draws its own sign-in screen, which it already has for the first-time case.
- **A grant is `(host, account, plugin)` and is allowed, refused, or unset.** Unset asks the user the first time a Plugin borrows an Account, naming the borrowing Plugin, the host and the providing Plugin; the call waits for the answer and the answer is the grant. Nothing is asked at install, so a Plugin that never borrows never prompts, and a Plugin update's new Capabilities are likewise ungranted until first used rather than raising a modal at update time — this replaces ADR-0030's rule that an update asking for more turns the Plugin off until the user approves it. The answer is remembered per Account, so adding a second GitHub Account asks again for a Plugin that already holds the first. Revoking one Plugin leaves the Account signed in for the others. Until the consent screens exist, first-party Plugins are granted silently, as their Capabilities already are, and the table is written from the start, so adding the screen later is UI only.
- **A Project picks one Account per host.** The choice is the Project's, not the Plugin's, so installing a CI Plugin later uses the Account that repository already uses with no further picking. Argo asks once, the first time any Plugin needs that host on that Project, and skips the question when only one Account exists. Two identities against one host inside one Project means making it two Projects.
- **Sign out is Account-wide,** as it is in every system that shares a sign-in. It deletes the Account row, every grant naming it and the stored token itself, so the providing Plugin does not keep calling the service after everyone else has stopped. The confirmation names the providing Plugin first and then each Plugin that will lose access. Removing a Plugin removes its Accounts and their tokens with it, so no credential outlives the row it was listed under, and the Accounts list names the provider on every row.
- **No Plugin is privileged.** A bundled Plugin's Accounts are revocable exactly like a third party's; VS Code's `trustedExtensionAuthAccess`, which greys out its own extensions' rows, is not copied.
- **Four screens and one served page, each needing a Paper design before code.** Settings › Accounts lists the Accounts with their provider; an Accounts detail screen lists the Plugins using one Account and signs out, with the confirmation as a native Alert naming who loses access; a Project gains an Accounts section below Folder, which is Argo's own and not the `argo/project/details/v1` Slot, because Argo owns the mapping; the Plugin's sign-in screen is a page of its own under its route; and Argo serves one page on the callback telling the person to close the tab. Plugin settings gain nothing: Plugins never draw Settings (ADR-0025).

## Considered options

- **Argo draws one standard sign-in sheet per kind of flow** and the Plugin supplies only the mechanics. Rejected: it makes Argo learn each service's shape, so every new service becomes an Argo change, and it breaks on the first flow that is neither of the kinds Argo drew.
- **A generic code host Plugin with vendor adapters inside.** Rejected: the adapter is a second plugin API, written before anyone knows what the second vendor needs, and the translation loses exactly the concepts each vendor's users came for.
- **Hand the borrower a copied token string.** Rejected: it goes stale within the hour, the refresh token sits in the provider's namespaced secrets where the borrower cannot read it, and Argo cannot refresh it without learning each vendor's token endpoint, which is the thing this ADR exists to avoid.
- **A richer failure contract for a borrow,** distinguishing disabled from uninstalled from a provider that is itself waiting on a borrow. Rejected: every one of those ends with the user signing in again, which the Plugin already draws, so the states would cost screens and buy nothing.
- **Device flow only** (RFC 8628), which needs no listener and works from a paired phone. Rejected as the primary flow: too many services do not offer it, and the owner holds OAuth to be the mechanism that must work first. A Plugin may still run a device flow with its own calls; it needs nothing from core.
- **A custom `argo://` scheme registered by each App,** so the redirect returns to whichever Device the person is holding and the App forwards the code to the Server over its Connection. This is the only way a paired phone can sign in, and it is how the limit above is lifted later. Not now (owner, 2026-10-20): it needs the scheme registered on three platforms and a path for the App to hand a code back, and several services refuse a custom scheme for the client type a desktop Plugin registers, so it would not remove the loopback listener anyway.
- **A random loopback port per sign-in,** as RFC 8252 prescribes. Rejected: services that demand an exact redirect-URI match — GitHub's OAuth apps among them — cannot be signed in to at all, which trades a rare failure for a permanent one.
- **Let a Plugin open its own port** to catch the redirect. Rejected: a listening socket is a far larger grant than `fetch`, and every Plugin would then register its own redirect URI and get the security details wrong separately.
- **A per-Plugin Account preference,** as VS Code's "Account Preferences for this Workspace" does. Rejected: it asks again for every new Plugin on every repository, where the user's real intent is that this repository is work and that one is personal.
- **Free-string provider ids** chosen by each Plugin. Rejected: two Plugins would name one service differently, silently hold two sign-ins, and never share.
- **Plugins reading each other's Accounts directly.** Rejected and impossible: secrets are namespaced per Plugin, and every join between Plugins is an Argo entity.
