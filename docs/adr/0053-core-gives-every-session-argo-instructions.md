# Core gives every Session Argo instructions

This amends [ADR-0044](0044-argo-is-driven-through-one-operation-registry-and-the-argo-cli.md) (owner). ADR-0044 sends the MCP server's `instructions` as the discovery line, then each Plugin's prose. Only a Plugin can tell every Session's Agent how to work in Argo, so a behaviour that belongs to Argo itself, such as keeping a Plan the person can follow, has nowhere to go.

## Decision

- **Core has Argo instructions: prose it gives every Session's Agent, beside the Plugin instructions.** The MCP server's `instructions` are the discovery line, then each Argo instruction under its name, in the order core lists them, then each Plugin's prose under its name, ordered by Plugin id.
- **Argo instructions ship in `argo mcp`.** They are fixed text in the CLI, as the discovery line is, so they need no Server read and still arrive when the Server will not give Plugin instructions.
- **Each is at most 1,000 characters,** the Plugin instructions limit, and a test holds it.
- **They reach the same Sessions Plugin instructions do:** every Session with Agent access, unfiltered by Project, fixed for the life of the MCP connection.
- **The first is the Plan.** It asks the Agent to keep a Plan for work of three or more steps with its own checklist tool, so the Feed and the Sessions list show progress. It names each Agent's tool: Claude Code reports `TaskCreate`, `TaskUpdate` and `TodoWrite` as a Plan once its install seed turns them on, and Codex reports `update_plan`. Claude Code defers its task tools behind `ToolSearch`, and while the Plan named no tool, no Session loaded them, so it names the tools and says to load a deferred one first.
Owner amendment, 2026-11-14: Codex keeps MCP server instructions from its model, so a Codex Session never saw them and kept no Plan. Codex's install seed (ADR-0004) now carries the Argo instructions as `developer_instructions` in its `CODEX_CONFIG`, beside `update_plan`. Only the Codex seed does this: it is a seed, not a per-Session ACP field, so the person still edits or clears it in Settings, and it is fixed at install, as the rest of the seed is. A Codex installed earlier keeps its saved environment until the person sets it or installs Codex again. Drop it when Codex gives its model MCP server instructions.

Owner amendment, 2026-11-14 (#2075): the second Argo instruction is **Agents**. Most Agents' spawn tools cannot carry a role (Codex's `spawn_agent` is told to omit its `agent_type`), so every spawned Agent drew the General mark. The instruction asks the Agent to run `session.declareSubagentRole` with an Agent role before each spawn. The live Session queues the roles; each Agent its Agent spawns takes the next one, stored on its spawn row, where it outranks any role the Agent reports. Argo does not guess a role from an Agent's title: the owner rejected that, since an Agent may be called anything. An Agent that skips the call draws the role it reports, or General. The queue lives only in the open Session, so a role declared and never spent is dropped when the Session closes.

Owner amendment, 2026-11-14 (#2115): Agents treated the Plan as optional, because MCP server instructions rank below an Agent's own system prompt. ACP now has one `systemPrompt` field on `session/new`, `session/resume` and `session/load`, and an Agent that takes it advertises `sessionCapabilities.systemPrompt`. So the Engine also sends the Argo instructions there, as `{ mode: "append", content: [text] }`, when a Session with Agent access opens on such an Agent. `claude-agent-acp` and `codex-acp` both take it. An Agent that does not advertise it still gets the instructions through MCP alone, and configuration discovery and Sessions without Agent access get neither. This replaces the rejected per-Agent system-prompt fields below: the field is now ACP's, the same for every Agent. Plugin instructions stay in MCP. The Codex seed drops `developer_instructions`, as the system prompt now carries them; a Codex installed earlier keeps its saved environment, so it gets the instructions twice until the person clears them or installs Codex again.

Owner amendment, 2026-11-15: the Plan becomes the **Todo list**, and Argo owns the tool. The checklist rode each Agent's own tool, so it needed an install seed per Agent, an instruction that named vendor tools, and nothing at all for an Agent with no such tool; one such Agent kept its checklist with `session.savePlan`, which wrote `.argo/plans/plan.md` into the Checkout, where it was committed. "Plan" also meant plan mode, the Written plan and the Plan role.

- **Two Operations keep the Todo list.** `session.setTodos` sets it whole, and `session.setTodoStep` changes one step by its number, so a progress report costs one small call. Completing a step also completes every unfinished step before it, and starts the next pending one when none is in progress. Both answer with how many steps are done and how many there are. They reach the calling Session when `sessionId` is left out, as `session.declareSubagentRole` does.
- **No new MCP tool.** ADR-0044 keeps `argo mcp` at two tools. The Todo list instruction gives the Operation ids and their params, so the Agent calls `operation_run` with no `operation_list` first.
- **The same Feed row.** The Engine hands the list to the Feed as the ACP `plan` update an Agent would send, so it is one `plan_update` row revised in place, and the Feed, the Composer and the Sessions list draw it unchanged. The row and its wire types keep ACP's names (ADR-0006). The App draws no Tool call for either Operation.
- **A checklist an Agent reports through ACP itself is still a Todo list.** Argo no longer asks for one.
- **The install seeds go.** Claude Code's `CLAUDE_CODE_ENABLE_TODO_TOOLS` and Codex's `update_plan` config leave `vendor.ts`. An Agent installed earlier keeps its saved environment until the person clears it.
- **The person turns the Todo list on or off in Settings,** with `agent.getTodoList` and `agent.setTodoList`; it is on by default. Off, a new Session gets no Todo list instruction, both Operations refuse, and the Engine drops a checklist an Agent reports through ACP. This amends "fixed text in the CLI": the Engine reads the setting when it opens a Session, leaves the instruction out of the system prompt, and tells `argo mcp` to leave it out through `ARGO_TODO_LIST=0`. The instruction is fixed for the life of the Session; the Operations and the drop follow the setting at once.
- **`session.savePlan` is for a Written plan only.** It says so, and it moves to the `confirm` tier, so an Agent that calls it asks the person first.
- **A Session without Agent access keeps no Todo list** unless its Agent reports one through ACP.
- **One list per Session.** A Subagent that shares its parent's Argo MCP server sets its parent's Todo list; Argo cannot tell them apart by the call.

Rejected: a mode that keeps each Agent's own tool. It kept the seeds and the vendor names for a little more reliability on two Agents. Rejected: `plan_set` and `plan_step` as MCP tools of their own, which ADR-0044 rules out.

Owner amendment, 2026-11-15 (#2226 eval): Argo drove Claude Agent, Codex and pi Sessions on several models through the Todo list. Four findings changed it.

- **The instruction asks for a Todo list for any task that changes files or takes more than one command**, and says to skip it only for questions that change nothing. "Three or more steps" left the call to the model, and fast models judged real work too small. It also says how to reach `operation_run` when it is not declared: tool search, or `ALL_TOOLS` in a harness such as Codex that runs MCP tools only from a code script. And it says the server can take seconds to start, so the Agent looks again after its first command.
- **Completing a step completes the steps before it.** Agents often mark only the step they reached, which left a finished list at 1/4.
- **pi starts through an Argo launcher.** pi-acp keeps the MCP servers ACP gives it but never connects them, and it takes no ACP system prompt, so a pi Session had neither Argo's tools nor its instructions. For a Session with Agent access, the Engine sets pi-acp's `PI_ACP_PI_COMMAND` to `argo-pi`, written beside the `argo` launcher. It runs pi (or the pi command the person set) with an extension that registers `argo mcp` as a direct MCP server and appends the Argo instructions the person's settings leave. Nothing is written to the person's pi configuration. Drop it when pi-acp connects ACP's MCP servers and takes a system prompt.
- **A Session whose Agent never loaded Argo's tools says so.** `argo mcp` reads its instructions with the Session's token as it starts, so the Engine knows whether it ran. A Turn that ends, finished or failed, within 20 seconds of the token's issue checks nothing, since `argo mcp` may still be starting; the first Turn to end after that checks. If `argo mcp` never ran, the Feed shows one info notice: the Agent can't run Argo Operations, nor keep a Todo list when the checklist is on, and its ACP adapter may not support MCP servers. It is shown once per Session: a reopened Session finds the notice it stored and says nothing more.

`argo mcp` takes two to eight seconds to start, so an Agent that looks for its tools first thing can miss them; a faster CLI start is left to its own Issue.

Owner amendment, 2026-11-17: the fourth Argo instruction is **Pull requests**. An Agent opened a pull request with `gh pr create` and stopped, leaving it unattached to the Session; the GitHub Plugin's prose only said when `github.discover` was useful, and sits at its 1,000-character limit. The instruction asks the Agent to run `github.discover` in the turn it opens one, and `github.attach` for one opened from another branch.

## Considered options

- **A built-in Plugin that holds only instructions.** Rejected: a person could disable it, and it would make a core behaviour look optional.
- **Serve Argo instructions from the Server through the instructions read.** Rejected for now: the CLI and Server ship together, and the CLI already owns the discovery line.
- **Per-Agent ACP system-prompt fields.** Rejected again, as in ADR-0044: they differ from Agent to Agent. Superseded by the 2026-11-14 (#2115) amendment, now that ACP has one `systemPrompt` field.
- **Write them to the Project's `AGENTS.md`.** Rejected: ADR-0044 never touches the user's repositories.
