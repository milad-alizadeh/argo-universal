# The Server owns the Prompt queue

A Session owns its durable, ordered Queued Prompts so prepared work survives Apps disconnecting and the Server restarting. App submission queues while a Turn runs or the queue is paused; existing Agent and Plugin Prompt callers keep their busy behavior. Queue records go through the Writer, never persisted machine snapshots (ADR-0002, ADR-0003). [ADR-0055](0055-plugins-prompt-and-archive-sessions-from-a-watch.md) amends this: a Plugin Prompt to a busy or paused Session is appended behind the queued work with its Plugin sender, and a Plugin never edits, moves or resumes the queue.

Normal completion starts one Queued Prompt per Turn in current order. Stop, error and restart preserve remaining work and pause processing until Resume queue; adding work never resumes it. A Prompt that cannot start stays queued and pauses processing. Once its Turn starts it stays in the Feed on failure and is never automatically repeated. Dispatch respects the cancelled request boundary in ADR-0024, applies held configuration, runs prompt Hooks at execution time and preserves attachments and user provenance (ADR-0012).

Editing holds a Prompt at its queue position on the Server until Save or Cancel; stale Apps cannot edit a Prompt that has started. Amended by the owner on 2026-11-14: Edit loads the Queued Prompt into the Composer; Send saves that same item at its existing position. The prior Composer draft stays aside and returns after Save or Cancel. Steering is distinct from queuing: it requires an adapter’s real active-Turn guidance capability and acknowledgement before removing a Prompt. Cancel-and-resend is never steering; unsupported Agents show no steering control.


The Server negotiates `_meta.steering.supported` at ACP initialization and calls `_session/steering` with `idleBehavior: "promptRequired"`. Codex ACP 2.4.0 and Claude Agent ACP 0.97.0 are the minimum supported adapter versions: idle fallback belongs to the host, and output remains owned by the running Turn. Only an `injected` acknowledgement consumes the item. The Server reserves that item during the request, blocks queue advancement until it settles, and commits queue removal atomically with a distinct user message in the same Turn. A failed request releases the reservation and preserves the item. Normal queue processing resumes after the request settles.
