# The Server owns the Prompt queue

A Session owns its durable, ordered Queued Prompts so prepared work survives Apps disconnecting and the Server restarting. App submission queues while a Turn runs or the queue is paused; existing Agent and Plugin Prompt callers keep their busy behavior. Queue records go through the Writer, never persisted machine snapshots (ADR-0002, ADR-0003). [ADR-0055](0055-plugins-prompt-and-archive-sessions-from-a-watch.md) amends this: a Plugin Prompt to a busy or paused Session is appended behind the queued work with its Plugin sender, and a Plugin never edits, moves or resumes the queue. [ADR-0063](0063-a-voice-call-belongs-to-the-server-and-speaks-for-one-session.md) sends the Voice call's Prompts the same way, steering a running Turn when the Agent supports it, and the 2026-11-19 amendment below does the same for an Agent's.

Normal completion starts one Queued Prompt per Turn in current order. Stop, error and restart preserve remaining work and pause processing until the user resumes it (Send with an empty Composer); adding work never resumes it. A Prompt that cannot start stays queued and pauses processing. Once its Turn starts it stays in the Feed on failure and is never automatically repeated. Dispatch respects the cancelled request boundary in ADR-0024, applies held configuration, runs prompt Hooks at execution time and preserves attachments and user provenance (ADR-0012).

Editing holds a Prompt at its queue position on the Server until Save or Cancel; stale Apps cannot edit a Prompt that has started. Amended by the owner on 2026-11-14: Edit loads the Queued Prompt into the Composer; Send saves that same item at its existing position. The prior Composer draft stays aside and returns after Save or Cancel. Steering is distinct from queuing: it requires an adapter’s real active-Turn guidance capability and acknowledgement before removing a Prompt. Cancel-and-resend is never steering; unsupported Agents show no steering control.


The Server negotiates `_meta.steering.supported` at ACP initialization and calls `_session/steering` with `idleBehavior: "promptRequired"`. Codex ACP 2.4.0 and Claude Agent ACP 0.97.0 are the minimum supported adapter versions: idle fallback belongs to the host, and output remains owned by the running Turn. Only an `injected` acknowledgement consumes the item. The Server reserves that item during the request, blocks queue advancement until it settles, and commits queue removal atomically with a distinct user message in the same Turn. A failed request releases the reservation and preserves the item. Normal queue processing resumes after the request settles. In the desktop App and web, Cmd+Enter sends a Composer draft through that same acknowledged steering path during a Turn, without adding it to the queue. With no active Turn it submits normally. Failed delivery leaves the draft intact and never resumes a paused queue.

Amended by the owner on 2026-11-19: an Agent's Prompt to a busy Session no longer fails. Before, `session.prompt` from another Session refused while the target's Turn ran ("Session cannot accept session.prompt"), so Agents messaging each other lost their messages mid-Turn. Now it goes where a Plugin's (ADR-0055) and the Voice call's (ADR-0063) Prompts go, through the same code: an idle Session starts a Turn, and a busy or paused one takes the Prompt at the end of its queue with the calling Session as sender. When the target's Agent supports steering, the queued Prompt is steered into the running Turn at once through the acknowledged path above; a refused steer leaves it queued. A Session Prompt never resumes a paused queue. The result says where it landed: `started`, `steered` or `queued` (with `notSteered` saying why a Prompt that could have steered waits), each with the Feed row its Prompt takes; a Hook's drop is unchanged. The Prompt's id is allocated before it is sent, and a queued Prompt's Turn takes its queued id, so a caller that waits follows a queued Prompt until its own Turn ends and a steered one until the running Turn ends. The person's own `session.prompt`, through the App or a user token, keeps its busy behavior; the App submits through `session.submit`.
