# App E2E uses shared fixtures at external boundaries

App E2E uses shared fixtures at external Agent boundaries, preserving the real App, tRPC, Engine, Session, Feed, Writer and SQLite. The original Agent adapter fixture boundary (owner, 2026-10-08) superseded ADR-0011’s CLI-only E2E rule: maintaining another provider protocol implementation in each mock CLI made fast provider updates expensive. Spec 0009 moves shared replies to the generic ACP process port as recorded below.

Provider translation tests are simple unit tests: provider response fixtures satisfy the official SDK or generated protocol types, then pass through the real pure mapping function and are compared with independent expected Argo events or rejections. They launch no provider CLI or SDK process and use no network, filesystem, transport stubs, capture or replay machinery. Updating the SDK or generated protocol types exposes incompatible fixture shapes at compile time; type-compatible behavior changes still require updated response fixtures and reviewing the expected translations. App fixtures describe observable product behavior and stay shared across providers. The mock CLIs and their test helpers are removed (owner, 2026-10-08).

The E2E Engine bootstrap lives outside production source and supplies fixture adapters from the registered Agent identities and metadata. Both App targets use isolated real storage and shared fixtures, with zero retries; they invoke no provider CLI or SDK query. The desktop App connects to that Engine rather than exercising the production Supervisor startup path, which retains its own composition tests.

Spec 0009 adds public ACP/process-port lifecycle tests while keeping the real Engine, Session, Feed, Writer, SQLite and Git. Generic mock peers use the official Agent SDK and NDJSON, with official request/response fixtures; a separate generic Node stdio process proves direct process ownership. Both registered Agent identities exercise empty Sessions with shared fixtures. Graph enumeration checks structural opening/closing/failure transitions, while public wire/Engine schedules prove ownership and cleanup. These tests launch no authenticated upstream Agent and prove neither descendant isolation nor 1/4/8 resource savings (owner, 2026-10-09, #348).

Spec 0009 #349 moves shared App replies onto the official ACP Agent SDK and NDJSON at the generic process port. Discovery mocks retain registered metadata and availability; their native stream no longer produces App replies. Prompted creation, successive Turns and Blob image scenarios traverse real App/tRPC/Engine/Session/Feed/Writer/SQLite behavior for both registered identities (owner, 2026-10-09).

Spec 0009 #351 adds configuration, cancellation and attachment schedules through the official SDK stream for both registered Agent identities. Public Engine tests prove authoritative options, prompt ordering, sibling isolation, model-dependent rejection, full attachment payloads and failed-setting closure. Shared App scenarios open an empty Session before prompting, configure Fast mode and explicitly cancel creation. Graph enumeration includes configuration and cancellation transitions. These controlled peers retain the compatibility limitations above (owner, 2026-10-09).

The owner aligned this decision with [Testing seams](../agents/testing-seams.md) on 2026-10-09. Registry responses may likewise be fixture data delivered at the external Registry port; validation, catalog sync, SQL reads and Writer persistence run for real. Minimal shared boundary code delivers fixture data and external timing or failures. Setup starts and cleans up production composition instead of reproducing its business logic. Required context and real layout justify UI wrappers; feature-specific fixture forwarding alone does not.

This is a deliberate exception to TS4's requirement for an upstream contract test plus recorded interaction, recorded in ADR-0016. Fixture-driven App tests prove Argo behaviour under controlled external responses. Official SDK peers and typed fixtures do not establish compatibility with an actual upstream Agent or Registry, authentication, descendant isolation or resource savings. Those claims require separate evidence from the relevant real system. This decision neither requires capture/replay in provider mapping unit tests nor authorizes authenticated or paid upstream runs.
