# App E2E uses shared fixtures at external boundaries

App E2E uses shared fixtures at external Agent boundaries and keeps the App, tRPC, Engine, Session, Feed, Writer and SQLite real. The original Agent adapter fixture boundary (owner, 2026-10-08) superseded ADR-0011’s CLI-only E2E rule: another provider protocol implementation in each mock CLI made fast provider updates expensive. Spec 0009 moves shared replies to the generic ACP process port, below.

The native translation fixtures and their tests are removed by #359 (owner, 2026-10-13). Shared named scenarios describe replies, attachments, cancellation, permissions, Elicitations and configuration. The scripted Agent uses official SDK types and serves those scenarios over ACP. App E2E starts it as a real stdio process. It implements no provider-native CLI or protocol.

The E2E bootstrap seeds saved Agent definitions in isolated SQLite. The production launch resolver and process launcher run those commands. Both App targets retain real App/tRPC/Engine/Session/Feed/Writer/SQLite behavior. Browser-safe App fixture imports remain separate from Node process fixtures.

Spec 0009 adds public ACP/process-port lifecycle tests with the real Engine, Session, Feed, Writer, SQLite and Git. Generic mock peers use the official Agent SDK and NDJSON, with official request/response fixtures; a separate generic Node stdio process proves direct process ownership. Both required Agent identities exercise empty Sessions with shared fixtures. Graph enumeration checks structural opening/closing/failure transitions, while public wire/Engine schedules prove ownership and cleanup. These tests launch no authenticated upstream Agent and prove neither descendant isolation nor 1/4/8 resource savings (owner, 2026-10-09, #348).

Spec 0009 #349 moves shared App replies onto the official ACP Agent SDK and NDJSON at the generic process port. Saved fixture commands use the shared ACP process port for readiness and Session work. Prompted creation, successive Turns and Blob image scenarios traverse real App/tRPC/Engine/Session/Feed/Writer/SQLite behavior for both registered identities (owner, 2026-10-09).

Spec 0009 #351 adds configuration, cancellation and attachment schedules through the official SDK stream for both registered Agent identities. Public Engine tests prove authoritative options, prompt ordering, sibling isolation, model-dependent rejection, full attachment payloads and failed-setting closure. Shared App scenarios open an empty Session before prompting, configure Fast mode and explicitly cancel creation. Graph enumeration includes configuration and cancellation transitions (owner, 2026-10-09). The stdio fixture Agents append each `session/close` they receive to a request log in the test's Server directory, and steps read the Project's `argo/*` branches and worktrees, so App scenarios see what an empty Session left behind (2026-10-13).

Spec 0011 replaces these fake Agents with one scripted Agent, `createScriptedAgent(scenario)` on the official ACP SDK's `agent()` (owner, 2026-10-10). E2E and the process ownership test launch it as a real process through the production process launcher with the scenario name in argv; Engine tests run it over in-memory streams. App fixture options name a scenario instead of a peer, and the previous E2E peer and its fixture files are removed (#445).

The owner aligned this decision with [Testing seams](../agents/testing-seams.md) on 2026-10-09. Registry responses may likewise be fixture data delivered at the external Registry port; validation, catalog sync, SQL reads and Writer persistence run for real. Minimal shared boundary code delivers fixture data and external timing or failures. Setup starts and cleans up production composition rather than reproducing its business logic. Required context and real layout justify UI wrappers; feature-specific fixture forwarding alone does not.

This is a deliberate exception to TS4's requirement for an upstream contract test plus recorded interaction that ADR-0016 records. Fixture-driven App tests prove Argo behaviour under controlled external responses. Official SDK peers and typed fixtures do not establish compatibility with an actual upstream Agent or Registry, authentication, descendant isolation or resource savings; those claims need separate evidence from the relevant real system. This decision neither requires capture/replay in provider mapping unit tests nor authorizes authenticated or paid upstream runs.

Spec 0009 #363 adds shared fixtures at the external download and installer ports that the approved Agent setup amendment names. The App, tRPC, Engine, Writer, SQLite, managed files and installation checks stay real. Fixture package metadata and launch content come from the shared scripted Agent. No vendor mock CLI is introduced. Controlled installer timing proves loading, cancellation, failure and cleanup behavior. Separate process tests launch real children and observe POSIX descendant exit. These fixtures do not prove upstream package compatibility or Windows process cleanup.
