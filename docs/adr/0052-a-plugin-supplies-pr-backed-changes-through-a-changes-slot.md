# A Plugin supplies PR-backed Changes through a Changes Slot

This amends [ADR-0037](0037-plugins-declare-the-data-they-need.md) and builds on [ADR-0035](0035-plugins-add-to-named-slots-and-never-edit-core-screens.md), [ADR-0036](0036-plugins-own-sign-in-and-argo-brokers-their-accounts.md) and [ADR-0039](0039-the-workbench-summarises-sections-and-the-inspector-shows-them-in-full.md) (owner, 2026-11-13, #2025, spec #2024; amended for refresh and failure by #2028). ADR-0037 said the Session Slot context carries no PR or check and that `SessionInfo.pullRequest` stays null, so core models neither. That line held while nothing supplied pull requests. The Workbench and Inspector already draw several Changes, and a Session can produce several PRs over time, so the data now needs a typed way in that keeps GitHub out of core.

## Decision

- **A versioned add-only items Slot, `argo/session/changes/v1`,** takes a Session's Changes from Plugins. Its context is `{ sessionId, projectId }`, ids only, like the Session row, and one batched call is keyed by Session id. Core draws the Changes in its own Changes card and Inspector; a Plugin never gets a card, a layout or a style. Items from every Plugin show (a limit of 100 per Plugin), because the card previews three itself (ADR-0039).
- **`Change` is a shared Contract.** `{ id, stage, title, provider?, repository?, branch?, base?, head?, pullRequest?: { number, url }, draft?, conflict?, totals? }`. Working and Branch Changes need no number, repository or provider. A PR-backed Change always has a repository: **a PR is identified by repository plus number, never by number alone**, and `id` is stable and unique within its Plugin, such as `github:owner/name#12`. Draft and conflict are separate facts, so both can hold at once. Every field after `title` is optional and the item is strict, so Checks (#2028) and files (#2029) arrive as new optional fields without breaking a Plugin that already answers.
- **Core keeps no PR model.** `SessionInfo.pullRequest` stays null. The App reads the Slot and draws PR-backed Changes from it; Working and Branch Changes still come from the Checkout, so a line of work is never counted twice. Matching a local Change with its PR is explicit, by repository and branch, never by title (a later increment).
- **A first-party GitHub Plugin (`plugins/github`) owns GitHub.** It builds the requests, parses the replies and keeps the **PR association** (Session to repository plus number) in its own storage, in one table keyed `(project_id, session_id, repository, number)`. Attaching twice is the same row. A later increment adds columns, such as where an association came from, and a row per Change, without rewriting these. The repository is stored as GitHub reports it for the pull request, in lower case.
- **Associations are written by Operations only.** `github.attach` (`act`, caller Project and Session) refuses a Session outside the caller's Project, a reference it cannot parse and a PR GitHub does not show to the Project's Account, then stores the row. `github.list` (`read`) returns the Session's PRs with GitHub's data, or the reason one could not be read. Loaders and Queries only read. No Operation changes a PR on GitHub.
- **GitHub reads only borrow the Project's Account** through the broker (ADR-0036), as a named Query shared by the Slot and the Operations. The Account is the one the Issue tracker Plugin already provides for `api.github.com`; the GitHub Plugin adds no provider, no sign-in page and no token store, and never reads another Plugin's secrets. It declares `fetch` for `api.github.com` and `sessions:read`. With no Account, a read fails the way any borrow does (the Operation says to sign in to GitHub, and the Slot leaves the Plugin's Changes out), and the person signs in through the Issue tracker's existing flow. The tests load both Plugins in one host and sign in through the Issue tracker.
- **Discovery is an `act` Operation too (#2027).** `github.discover` reads the Session's branch (`sessions:read`) and the Project's origin, asks GitHub for the pull requests whose head is that branch of the origin (and of the repository the origin was forked from, where a fork's pull request lives), in any state, and stores each as an association under the repository it targets. It adds rows and never removes any, so repeating it, switching branches, or a failed look keep every earlier association. It answers `found`, `no-match`, `branchless`, `not-github` or `unavailable` (with whether signing in would help) as data, so an Agent never mistakes one for another. A same-named branch of another fork is not matched. It reads only: no GitHub write, no timer, no service.
- **A Session keeps several associations, and `github.detach` removes one.** `github.detach` (`act`, caller Project and Session) takes the same reference forms as `attach`, validates the Session's Project, deletes only that row and is idempotent. It does not ask GitHub, so an association whose PR can no longer be read can still be removed. Branch switches and restarts never delete an association, and Merged and Closed PRs stay until detached. Answers keep the order associations were made in.
- **The App selects a Change by its identity, never by its place.** The Inspector's Changes tab lists every Change, a row opens that Change alone and Back returns to the list. The selection is the Change's `id` (repository plus number), held by the Session, so a refresh or a reorder cannot move it. A Change that leaves while selected sends the Inspector back to the list, never to a neighbour, and this is the intended handling, not a placeholder: the selection is dropped at once, so the same Change coming back is not selected again. A phone's sheet draws the same list and detail. The list also holds a provisional reference field that attaches a PR through the same `github.attach` an Agent runs; a refusal shows through the App's failure toast. A selected Change is the handle later increments, such as the PR's files (#2029), hang off.
- **A failed read is not an empty answer, and one failed PR does not drop the others.** Each PR is read alone, through named reads that throw on failure, so Argo keeps the last good answer beside the failure (ADR-0037). The provider reads them with `argo.queries.readState`, which answers `{ data?, error?, stale }` where `argo.queries.read` hides the error. A PR whose latest read failed but was read before is answered with what was last known and `stale: 'signIn' | 'failed'`, never as Closed, never with its Checks dropped. A PR never read is left out of the answer and `github.list` names it with why; the provider throws, so Argo leaves the Plugin's Changes out, logs why and keeps local Changes, only when nothing at all could be read. A Session with nothing attached answers empty and `github.list` answers an empty list, so empty and failed differ in `list`, in `stale` and in the failure Argo logs. Showing a PR that was never read, and `stale`, in the App needs a design that does not exist yet (see Not decided).
- **Checks are optional data on the Change.** `checks?: { name, state: 'running' | 'passed' | 'failed' }[]` is the Check runs of the head commit, read by a second named read keyed by repository and head. A Check that has not completed is `running`; only success, neutral and skipped are `passed`; every other conclusion is `failed`. Absent `checks` means not known (the read failed and nothing was read before), an empty list means GitHub reports none; neither is ever drawn as passed. A commit with more Checks than one read returns is refused rather than drawn from part of the list. The App draws no Checks part for either case and counts passed only when every Check passed.
- **A visible Changes list refreshes on Argo's clock.** An items Slot entry can declare `refreshMs` (the Changes Slot: 30 seconds). While at least one App holds that Slot's list open through its subscription, Argo runs one timer per Plugin and interval, shared by every open list (the Workbench and the Inspector), that makes the Plugin's named reads due, the existing stale mark (ADR-0037), and asks its provider again; the reads are the Queries' entries, so the two lists make one read per PR. The timer is released when the last list closes, is not armed while the Plugin is not running, and a Plugin that is disabled or reloads drops its timer and kept answers, then resumes if a list is still open. A Plugin has no timer, no poll and no second cache; a refresh whose answer is unchanged is not sent. An Operation run or `argo.changed()` still makes everything due at once.
- **Retry is an Operation.** `github.refresh` (`read`, caller Project and Session) makes everything due, reads the Session's PRs again now and answers what `github.list` does. Attaching also makes everything due, so a PR attached while a list is open appears in it. The control that runs `refresh` in the App needs a design (see Not decided).
- **Draft and conflict reach the App together.** The Change carries both; the App keeps both on the PR it draws, while its stage control still draws one modifier until a design shows both.
- **A PR's files and diff are read by the Plugin from GitHub and drawn by core, and never come from the Checkout (#2029).** `github.files` and `github.diff` (`read`, caller Project and Session) take a PR `reference` like `attach`, and a page `cursor` or a file `path`. `files` answers one page of 50 files in the shape of a local comparison's page (`ChangeFilesPage`: the files, the PR's own totals, `nextCursor`, and the repository, base and head they were read against), through a named read of GitHub's list of the PR's files in the repository the PR targets, so a fork PR is read where it lives. `diff` answers a `SessionDiffOutput`: one file's patch as GitHub gives it, with a git header, in one page; a file GitHub gives no patch for, such as a binary one, has none to draw. Both refuse a PR that is not attached to the calling Session, so an Operation never reads another Session's or an unattached PR through the Project's Account. They only GET, so the Session's Checkout is never switched, fetched into or written, and core adds no `SessionComparison` member for a PR. A read that fails rejects with why (not signed in, not found, GitHub failed); it is never an empty list.
- **The App draws a PR's files through the same seam as local ones.** `ChangesSource` (the files, diffs and refresh the Changes list reads) gains a second implementation, `remoteChanges`, built from those two Operations; `useChanges` and the file list are the ones the Checkout's Changes use. The selection (above) names the Change, so the Inspector's Files segment lists the selected Change's files and never the Checkout's, and with no Change selected Files is the Checkout's own, as before. A Change keys its reads by its identity and head commit, so switching Changes shows each one's own files and a push reads again. A selected Change shows no comparison picker, since it is compared with its own base. An Operation run makes the Plugin's reads due (see the refresh clock), so opening a file also makes the PR reads due; accepted for now. The selected Change's files that cannot be read show a provisional limitation, built from existing primitives, that names the Change and its reason and offers Try again; it never substitutes other files (see Not decided).

## Reconciling #1300

Spec #1300 proposed a core Change module with a Forge port and a `gh` adapter, plus automated Reviews. Spec #2024 chose a different boundary for the first increment: the GitHub Plugin supplies PR data and core only draws it. This ADR is that boundary, so the ownership and production GitHub transport parts of #1300 point here: core has no GitHub client and no `gh pr` integration. The Review proposals in #1300 stay future work, and this change does not close it.

## Considered options

- **A separate Pull Requests card or a Plugin-drawn Workbench card.** Rejected: it duplicates the Changes card and gives a Plugin control of core layout, against ADR-0035.
- **A core GitHub client and a Forge port (#1300).** Rejected for now: it puts one vendor's transport in core and designs a port before a second vendor exists.
- **A tree Slot for the Changes.** Rejected: ADR-0046 already removed tree Slots in favour of data Argo draws.
- **A Plugin-owned poll, or a second cache for PR data.** Rejected: ADR-0037 keeps one cache and its stale marks, and the Issue tracker's private view cache is the pattern not to copy.
- **A failure placeholder Change for a PR never read.** Rejected for now: it would need a stage and title Argo cannot know, and it is a new visible state.
- **Putting pull requests into the Issue tracker Plugin.** Rejected: ADR-0036 makes a code host and an Issue tracker separate Plugins.
- **A new core `SessionComparison` for a PR, read by core's own git.** Rejected: it needs the PR's head in the Checkout (a fetch or a switch), which inspecting a PR must never do, and a remote credential core does not hold.
- **Files and patches inside the Slot's Change items.** Rejected: every refresh of every PR would carry every patch, and the Slot is for what is drawn in a list.
- **Storing only a PR number.** Rejected: two repositories share numbers, and a fork PR belongs to its target repository.

## Not decided here

- Multiple Changes and detach (#2026) are drawn; their look, the Inspector list, the Change detail and the attach field, stays provisional until the owner reviews it in Storybook.
- Matching a local Branch Change with its PR by repository and branch. The App draws no local Change as a row today, so nothing is shown twice; the matching rule waits for the increment that draws one.
- A visible state for a failed or sign-in-needed read, for a PR that was never read, for `stale`, for a retry control and for draft and conflict together, which need a Paper design before code. The data is in the Slot, the App's PR model and `github.refresh`.
- The look of the unavailable-files state and of the Files segment of a selected Change, which are provisional until the owner reviews them in Storybook. A file's diff in more than one page, and a Files list that survives a Change's head moving while it is open.
- Legacy commit statuses (as opposed to Check runs), and more than one read's worth of Checks.
