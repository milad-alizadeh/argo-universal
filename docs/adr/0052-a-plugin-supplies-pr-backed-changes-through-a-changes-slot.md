# A Plugin supplies PR-backed Changes through a Changes Slot

This amends [ADR-0037](0037-plugins-declare-the-data-they-need.md) and builds on [ADR-0035](0035-plugins-add-to-named-slots-and-never-edit-core-screens.md), [ADR-0036](0036-plugins-own-sign-in-and-argo-brokers-their-accounts.md) and [ADR-0039](0039-the-workbench-summarises-sections-and-the-inspector-shows-them-in-full.md) (owner, 2026-11-13, #2025, spec #2024; amended for refresh and failure by #2028; amended by the owner on 2026-11-13, see "The Inspector holds no pull requests" and "Discovery runs at Turn end"; amended by the owner on 2026-11-14, see "PR automation and the row menu" and "The Plugin stores each pull request's last read"). ADR-0037 said the Session Slot context carries no PR or check and that `SessionInfo.pullRequest` stays null, so core models neither. That line held while nothing supplied pull requests. The Workbench and Inspector already draw several Changes, and a Session can produce several PRs over time, so the data now needs a typed way in that keeps GitHub out of core.

## Decision

- **A versioned add-only items Slot, `argo/session/changes/v1`,** takes a Session's Changes from Plugins. Its context is `{ sessionId, projectId }`, ids only, like the Session row, and one batched call is keyed by Session id. Core draws the Changes in its own Changes card; a Plugin never gets a card, a layout or a style. Items from every Plugin show (a limit of 100 per Plugin), because the card previews three itself (ADR-0039).
- **`Change` is a shared Contract.** `{ id, stage, title, provider?, repository?, branch?, base?, head?, pullRequest?: { number, url }, draft?, conflict?, totals? }`. Working and Branch Changes need no number, repository or provider. A PR-backed Change always has a repository: **a PR is identified by repository plus number, never by number alone**, and `id` is stable and unique within its Plugin, such as `github:owner/name#12`. Draft and conflict are separate facts, so both can hold at once. Every field after `title` is optional and the item is strict, so Checks (#2028) and files (#2029) arrive as new optional fields without breaking a Plugin that already answers.
- **Core keeps no PR model.** `SessionInfo.pullRequest` stays null. The App reads the Slot and draws PR-backed Changes from it; Working and Branch Changes still come from the Checkout, so a line of work is never counted twice.
- **A PR is matched with the Checkout's line of work by identity, never by title.** A PR-backed Change carries `headRepository` (the repository its branch is in, a fork's for a fork PR) beside `branch`. The Plugin, which alone knows the Project's origin and the Session's branch, sets `onCheckout: true` on a Change whose `headRepository` and `branch` equal the Checkout's repository and branch, so that Change is the same line of work as the local Branch Change. Another fork's same-named branch, a same-titled PR and a PR whose head repository GitHub no longer names are not matched. The App never adds the Checkout's totals to a PR's, and never shows them as a PR's. The `onCheckout` mark stays as data; the App draws no line for the Checkout beside the PRs. The Operations `github.list` carry the same mark; `github.attach`'s answer does not.
- **A first-party GitHub Plugin (`plugins/github`) owns GitHub.** It builds the requests, parses the replies and keeps the **PR association** (Session to repository plus number) in its own storage, in one table keyed `(project_id, session_id, repository, number)`. Attaching twice is the same row. A later increment adds columns, such as where an association came from, and a row per Change, without rewriting these. The repository is stored as GitHub reports it for the pull request, in lower case.
- **Associations are written by Operations only.** `github.attach` (`act`, caller Project and Session) refuses a Session outside the caller's Project, a reference it cannot parse and a PR GitHub does not show to the Project's Account, then stores the row. `github.list` (`read`) returns the Session's PRs with GitHub's data, or the reason one could not be read. Loaders and Queries only read. No Operation changes a PR on GitHub.
- **GitHub reads only borrow the Project's Account** through the broker (ADR-0036), as a named Query shared by the Slot and the Operations. The Account is the one the Issue tracker Plugin already provides for `api.github.com`; the GitHub Plugin adds no provider, no sign-in page and no token store, and never reads another Plugin's secrets. It declares `fetch` for `api.github.com` and `sessions:read`. With no Account, a read fails the way any borrow does (the Operation says to sign in to GitHub, and the Slot leaves the Plugin's Changes out), and the person signs in through the Issue tracker's existing flow. The tests load both Plugins in one host and sign in through the Issue tracker.
- **Discovery is an `act` Operation too (#2027).** `github.discover` reads the Session's branch (`sessions:read`) and the Project's origin, asks GitHub for the pull requests whose head is that branch of the origin (and of the repository the origin was forked from, where a fork's pull request lives), in any state, and stores each as an association under the repository it targets. It adds rows and never removes any, so repeating it, switching branches, or a failed look keep every earlier association. It answers `found`, `no-match`, `branchless`, `not-github` or `unavailable` (with whether signing in would help) as data, so an Agent never mistakes one for another. A same-named branch of another fork is not matched. It reads only: no GitHub write, no timer, no service.
- **A Session keeps several associations, and `github.detach` removes one.** `github.detach` (`act`, caller Project and Session) takes the same reference forms as `attach`, validates the Session's Project, deletes only that row and is idempotent. It does not ask GitHub, so an association whose PR can no longer be read can still be removed. Branch switches and restarts never delete an association, and Merged and Closed PRs stay until detached. Answers keep the order associations were made in.
- **A failed read is not an empty answer, and one failed PR does not drop the others.** Each PR is read alone, through named reads that throw on failure, so Argo keeps the last good answer beside the failure (ADR-0037). The provider reads them with `argo.queries.readState`, which answers `{ data?, error?, stale }` where `argo.queries.read` hides the error. A PR whose latest read failed but was read before is answered with what was last known and `stale: 'signIn' | 'failed'`, never as Closed, never with its Checks dropped. A PR never read is left out of the answer and `github.list` names it with why; the provider throws, so Argo leaves the Plugin's Changes out, logs why and keeps local Changes, only when nothing at all could be read. A Session with nothing attached answers empty and `github.list` answers an empty list, so empty and failed differ in `list`, in `stale` and in the failure Argo logs. The App draws none of this: `stale` and the never-read notice are data for Agents and for a later design.
- **Checks are optional data on the Change.** `checks?: { name, state: 'running' | 'passed' | 'failed' }[]` is the Check runs of the head commit, read by a second named read keyed by repository and head. A Check that has not completed is `running`; only success, neutral and skipped are `passed`; every other conclusion is `failed`. Absent `checks` means not known (the read failed and nothing was read before), an empty list means GitHub reports none; neither is ever drawn as passed. A commit with more Checks than one read returns is refused rather than drawn from part of the list. The App draws no Checks part for either case and counts passed only when every Check passed.
- **A visible Changes list refreshes on Argo's clock.** An items Slot entry can declare `refreshMs` (the Changes Slot: 30 seconds). While at least one App holds that Slot's list open through its subscription, Argo runs one timer per Plugin and interval, shared by every open list (the Workbench and the Inspector), that makes the Plugin's named reads due, the existing stale mark (ADR-0037), and asks its provider again; the reads are the Queries' entries, so the two lists make one read per PR. The timer is released when the last list closes (the list's generator ending, by abort or by the App stopping reading it, is what releases it) and while the person has the Plugin turned off; it is set again when they turn it back on, or the Plugin starts again, while a list is still open. A Plugin that is on but crashed or stopped keeps the timer: a tick reads nothing of it, but starts it once and asks again, so a list that stays open notices it come back. A Plugin that is disabled or reloads drops its kept answers. A Plugin has no timer, no poll and no second cache; a refresh whose answer is unchanged is not sent. An Operation run or `argo.changed()` still makes everything due at once.
- **Retry is an Operation.** `github.refresh` (`read`, caller Project and Session) makes everything due, reads the Session's PRs again now and answers what `github.list` does. Attaching also makes everything due, so a PR attached while a list is open appears in it. The App has no control that runs it.
- **Draft and conflict reach the App together.** The Change carries both and the App's `modifiers` keep both, while its stage control still draws one mark.
- **A PR's files and diff are read by the Plugin from GitHub and drawn by core, and never come from the Checkout (#2029).** `github.files` and `github.diff` (`read`, caller Project and Session) take a PR `reference` like `attach`, and a page `cursor` or a file `path`. `files` answers one page of 50 files in the shape of a local comparison's page (`ChangeFilesPage`: the files, the PR's own totals, `nextCursor`, and the repository, base and head they were read against), through a named read of GitHub's list of the PR's files in the repository the PR targets, so a fork PR is read where it lives. `diff` answers a `SessionDiffOutput`: one file's patch as GitHub gives it, with a git header, in one page; a file GitHub gives no patch for, such as a binary one, has none to draw. Both refuse a PR that is not attached to the calling Session, so an Operation never reads another Session's or an unattached PR through the Project's Account. They only GET, so the Session's Checkout is never switched, fetched into or written, and core adds no `SessionComparison` member for a PR. A read that fails rejects with why (not signed in, not found, GitHub failed); it is never an empty list.
- **`attach`, `detach`, `files` and `diff` accept a person's call,** so they declare `caller: ["project"]` and take the Session from an optional `sessionId` param, or from an Agent's own run; each still checks that the Session belongs to the Project, and `files` and `diff` that the PR is attached to it. The App no longer calls them, so `files` and `diff` are for Agents only.

## The Inspector holds no pull requests

Decided by the owner on 2026-11-13, replacing the provisional Changes UI that #2026 to #2029 built. Where this section conflicts with the decisions above or with those tickets, this section holds.

- **The Inspector holds no PRs for now.** Its Changes tab is the Session's Checkout alone: the changed files, as before this spec. It has no Change list, no Change detail, no attach field, no discovery, no Refresh, no sign-in or stale notices, no per-PR files or diff, and no Change/Files segment. The tab stays one call from outside (`panels.select('changes')`), so a later control can open it.
- **Workbench rows open GitHub.** The Changes card keeps its PR rows (stage, number, title, totals, Draft/Conflict, Checks). Pressing a row opens the PR's `url` through the App's external-link opener. The row has no menu. The card shows up to three PRs, then Show more for all of them and Show less to go back to three.
- **The PR Operations stay for Agents:** `attach`, `detach`, `discover`, `list`, `refresh`, `files` and `diff`, with `files` and `diff` Agent-only. The Plugin, the Slot, the refresh lifecycle, the Checks data, and the `stale` and `onCheckout` data stay. The client's `remoteChanges`, change selection, association, discovery and unread hooks and outcome parsers are removed.
- **The Checkout's totals are never added to a PR's and never shown as a PR's.**
- **The Composer's Changes pill is the entry to the Inspector Changes tab.** It shows the Checkout's files and line totals above the Composer, never a PR's, and is hidden while the Checkout has no changes. Pressing it opens the Changes tab in the Inspector, or the Changes sheet on a phone.

## PR automation and the row menu

Decided by the owner on 2026-11-14, for spec #2093, after a grilling and the Paper board "PR automation menu" (Option A). Where this section conflicts with the sections above, this section holds.

- **A PR row has a menu.** "The row has no menu" no longer holds. Each PR-backed Change row has a "…" that opens a menu, and a long-press opens the same menu on phones. Pressing the row still opens the PR on GitHub. The menu holds, in three groups: Open on GitHub and Copy link; Auto-fix, Auto-merge and Auto-archive as checkmark items; and Detach from Session, which runs `github.detach`. Core draws the menu and its words; the Plugin supplies only data.
- **Phones list PRs.** The phone Changes sheet shows the Session's PR rows, with the same menu, above the Checkout's files. The wide Inspector's Changes tab still holds no PRs.
- **The Change carries its automation as typed data.** An optional `automation` field holds `fix`, `merge` and `archive`, each `{ on, available, reason? }`. `reason` explains an unavailable item or a stopped Auto-fix, and the App draws it as the item's subtitle. An absent field means the Plugin offers no automation and the menu shows none of the three.
- **Toggles run one Operation.** `github.automation.set({ reference, kind, on })` (`act`, caller Project and Session) sets one toggle on one attached PR. A person's tap applies at once. An Agent may call it at the `confirm` tier.
- **Auto-fix and Auto-archive are the Plugin's own data.** They are rows in the Plugin's own tables beside the PR association, off by default, and they act from the Plugin's Watch through `sessions:prompt` and `sessions:archive` ([ADR-0055](0055-plugins-prompt-and-archive-sessions-from-a-watch.md)).
  - **Auto-fix** prompts the Session once per new failed Check, review comment or merge conflict, naming the PR and what failed. After three Prompts on one head commit with no new push, it turns itself off and gives the reason "Stopped after 3 tries on `<sha>`".
    - It is available only on a PR the signed-in GitHub account opened (owner, 2026-11-16, #2182). On any other PR the item is unavailable with the reason "Only pull requests you opened", and turning it on is refused. Push access is not checked: a PR the account opened is one it can push to, except from a fork it has lost access to.
    - It prompts only review comments from the repository's owner, members and collaborators, and from GitHub Apps. The signed-in account's own comments count, by the owner's choice. A comment from anyone else is not an event, so it is never prompted and never noted as seen.
    - A comment's Prompt quotes it as the reviewer's words, which carry no authority over the Agent's instructions. It tells the Agent to push a clear change and to ask the person about an ambiguous comment or a large design change.
  - **Auto-archive** archives the Session once its PR is Merged or Closed and the Session has no other Open Change and no uncommitted files.
- **Auto-merge is GitHub's own and is the one GitHub write.** "No Operation changes a PR on GitHub" no longer holds for Auto-merge alone. `github.automation.set` with `kind: 'merge'` enables or disables GitHub's auto-merge through `api.github.com/graphql`, choosing the first method the repository allows in the order squash, merge, rebase. The Plugin keeps no choice of its own: `on` is read back from GitHub through the pull request record, so auto-merge turned on in GitHub shows as on. It is unavailable, with a reason, when the repository does not allow auto-merge, the PR is a draft, or the PR is not Open. Every other GitHub write stays out of scope.
- **New reads.** The Plugin reads each attached PR's review comments, its auto-merge state and the repository's merge settings, through named reads as above, which `sync` keeps in the pull request record while the pull request is Open.

## Discovery runs at Turn end

Proposed for owner approval, 2026-11-14, spec #2107. Where this section conflicts with "Discovery is an `act` Operation too" above, this section holds.

- **The Engine runs `github.discover` when a Turn ends, for a Session with no attached PR.** Until now only an Agent ran it, so a PR opened from a Session stayed unattached until someone asked. The run passes `unlessAttached: true`, so a Session with any attached PR answers `attached` without asking GitHub, and the run happens once per Turn end until a PR is found. `attached` is a sixth answer, given only to that call.
- **It stays a read.** It adds associations and never removes any. `no-match`, `branchless`, `not-github` and `unavailable` are data, not errors, and draw nothing.
- **Still no timer, watcher or service.** The trigger is the Turn's end, which the Engine already knows. A PR opened in a Turn is attached by the end of that Turn, or the next at the latest. An Agent may still run `github.discover` itself.

Considered and rejected: running it on a branch push or `gh pr create`, which needs a watcher on the Checkout or on shell commands.

## The Plugin stores each pull request's last read

Decided by the owner on 2026-11-14. The Session row and the Changes read the same pull request through two paths, each with its own in-memory last answer and its own rule for a slow or failed read, so the row could say Open while the Workbench drew nothing. Where this section conflicts with the decisions above, this section holds.

- **One record per pull request.** The Plugin's storage gains `pull_records`, keyed `(project_id, repository, number)`: the last good read of the pull request, of its Checks and, while it is Open, of its auto-merge and its repository's merge settings, and why the latest read failed. Every Session associated with the pull request shares the row, and it survives a restart. This replaces "a Plugin has no second cache" for pull requests: the record is the one place they are read from, and the named Queries stay only as how `sync` reaches GitHub.
- **One writer, `sync`.** It is the only code that asks GitHub for a pull request or its Checks and the only code that writes a record. It calls `argo.changed()` only when what is kept changed. `github.attach` and `github.discover` run it before they answer; `github.list` and `github.refresh` run it and then read the record. `argo.changed()` asks every Slot again and makes every named read due; a Slot asked again for that reason answers from the record and does not read GitHub a second time, so one change costs one read.
- **A Slot answers from the record and never waits on GitHub.** The row Slot and the Changes Slot answer what is kept at once and run `sync` behind the answer, so neither can run late. The one-second wait, the per-Slot last answers and the two "drawn" comparisons are gone, and so is the row that falls back to a bare number after a restart.
- **A failed read keeps the record.** The last good read stays beside the failure and is answered `stale`, now across a restart too: a pull request read once is never again left out or listed as only an `error`. That is left for one whose first read failed. Checks kept for one head commit are never answered for a later one.
- **A settled pull request is not read again by a Slot.** A merged pull request whose Checks have all reported cannot change, so the sync behind a Slot skips it. `github.list` and `github.refresh` still read every one.
- **Detaching the last association of a pull request in a Project drops its record.**

Considered and rejected: a core table in the Server's database, which gives core a PR model and one vendor's fields (see "Core keeps no PR model"); and columns on `pull_associations`, which would keep one copy per Session of what is one pull request.

## A link's mark comes from the Plugins' records

Decided by the owner on 2026-11-14. The mark beside a link to a pull request or an Issue was read by core through the Server's `gh` sign-in, once when the link drew, so it could say other than the Session row and never moved while it was on screen.

- **A versioned add-only items Slot, `argo/link/mark/v1`.** Its context is `{ href, projectId }`, keyed by `href`: the link, and the Project it is drawn in, whose Account a Plugin reads it with. An item is `{ kind: 'pullRequest' | 'issue', state: 'open' | 'closed' | 'merged' | 'draft' }`, one per Plugin. Argo draws the mark; a Plugin sends no icon. The Slot refreshes on Argo's clock, every 30 seconds while a Session that shows the link is open.
- **The GitHub Plugin answers pull request links, attached to a Session or not,** from the pull request record, through the same `sync`. A link nobody attached gets a record with no association.
- **The Issue tracker answers links to Issues of the Project's own repository,** from the summary the Session row and the Session bar read. A link to another repository's Issue has no mark, because the Tracker reads one repository.
- **The App subscribes per Session page** with the links that page has drawn, so a mark changes when the record does. Core no longer reads GitHub for a mark. The hover card still does, through the Server's `gh` sign-in, for the author and avatar the records do not hold.
- **A link drawn outside a Session has no mark,** since there is no Project to read it for.

Considered and rejected: keeping the `gh` read for links no Plugin holds a record for, which keeps a second path that can disagree with the first.

Not decided here: dropping the record of a pull request once no feed shows its link, and the hover card reading the record too.

## Reconciling #1300

Spec #1300 proposed a core Change module with a Forge port and a `gh` adapter, plus automated Reviews. Spec #2024 chose a different boundary for the first increment: the GitHub Plugin supplies PR data and core only draws it. This ADR is that boundary, so the ownership and production GitHub transport parts of #1300 point here: core has no GitHub client and no `gh pr` integration. The Review proposals in #1300 stay future work, and this change does not close it.

## Considered options

- **A separate Pull Requests card or a Plugin-drawn Workbench card.** Rejected: it duplicates the Changes card and gives a Plugin control of core layout, against ADR-0035.
- **A core GitHub client and a Forge port (#1300).** Rejected for now: it puts one vendor's transport in core and designs a port before a second vendor exists.
- **A tree Slot for the Changes.** Rejected: ADR-0046 already removed tree Slots in favour of data Argo draws.
- **A Plugin-owned poll.** Rejected: the clock is Argo's. A second cache for PR data was rejected here too, until the two Slots' separate memories disagreed; see "The Plugin stores each pull request's last read".
- **A failure placeholder Change for a PR never read.** Rejected for now: it would need a stage and title Argo cannot know, and it is a new visible state.
- **Putting pull requests into the Issue tracker Plugin.** Rejected: ADR-0036 makes a code host and an Issue tracker separate Plugins.
- **A new core `SessionComparison` for a PR, read by core's own git.** Rejected: it needs the PR's head in the Checkout (a fetch or a switch), which inspecting a PR must never do, and a remote credential core does not hold.
- **Files and patches inside the Slot's Change items.** Rejected: every refresh of every PR would carry every patch, and the Slot is for what is drawn in a list.
- **Storing only a PR number.** Rejected: two repositories share numbers, and a fork PR belongs to its target repository.

## Not decided here

- Where PRs return to the Inspector, if they do, and how a person sees what an Agent attached, detached or refreshed.
- Legacy commit statuses (as opposed to Check runs), and more than one read's worth of Checks.
