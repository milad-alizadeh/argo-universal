# Three hook events that fail open

This amends [ADR-0027](0027-plugins-act-through-one-api-hook-core-and-replace-named-components.md) (owner, 2026-10-20), which named five hook events and said a hook missing its time budget is skipped without saying what the budget is. Five events was a guess at what Plugins would want. Two of them have no use: core fires `session.start` and `turn.complete` today, but there is nothing a Plugin can do at `session.start` that it cannot do when its own tree mounts, and nothing at `turn.complete` that is not already a Slot. A hook event is permanent surface — core must fire it, document its payload and keep its shape — so the set should start at what is actually used.

## Decision

- **The core-behaviour hook set is exactly three:** `process.spawn`, `prompt.submit` and `tool.check`. Each has a fixed payload and each can be refused by the chain. `session.start` and `turn.complete` are withdrawn. `ui.render` is not one of the three and is untouched: it is how a Replaceable Slot is drawn (ADR-0027, ADR-0035), not a core event a Plugin listens to. A fourth core event needs its own ADR.
- **`prompt.submit` and `tool.check` carry `projectId`.** Both are `{ sessionId, projectId, … }`. The withdrawn `session.start` was the only event carrying a Project, and without it the obvious Hook — expanding `#123` to the Project's repository — cannot be written. This is the one addition that pays for the withdrawal.
- **Argo sets the timeout, per event, and a Plugin cannot change it:** two seconds for `prompt.submit`, ten for `tool.check`, `process.spawn` and `ui.render`. The table is total over the event names, so a new event cannot be added without a number.
- **A hook's budget is wall clock.** It stops only while the hook waits on `next`, because that is the time of the hooks beneath it; a call the hook makes to `argo` is the hook's own time and counts against it. A two-second budget therefore does not reach a network service, deliberately: a `prompt.submit` hook reads what a declared query already fetched, or its own storage, or it answers.
- **A hook that runs over stops being waited on.** The chain answers without it and its return value is dropped; nothing stops its code in the worker. `next` is the commit point — a hook given up on before it called `next` is skipped and the chain runs on the event as it came; after `next` the rest of the chain has already answered and that answer stands.
- **Hooks on one event stay the chain ADR-0027 describes,** in worker order with first-party Plugins first. Each hook has its own budget for its own time, so a slow Plugin beneath it never spends it.
- **There is no Plugin-set `timeout` field, no `onFailure: "block"` and no `guard`.** Claude Code has the first two, and they are right there, because its hooks are scripts the user wrote for themselves. Argo's are third-party code: a Plugin that could declare its own timeout could stall every prompt, and a Plugin that could turn its own crash into a denial could block work by failing. `guard` is that second thing under another name, and it ships today — a guarded hook's crash, timeout or malformed answer becomes the event's refusal, and a stopped worker's guards keep refusing after the Plugin is gone. It is withdrawn with the two events. A Plugin refuses by answering: `tool.check` with a denial, `prompt.submit` by dropping the prompt, `process.spawn` by blocking the command.

## Considered options

- **Keep all five events** and fill them in later. Rejected: an event with no caller still has to be fired and kept, and removing one after a Plugin uses it is a breaking change, so the cheap direction is to add.
- **Keep `guard`,** so a Plugin can refuse by failing. Rejected: it makes fail-open false, and the orphan rule means a Plugin that is no longer running can still block work. A Plugin that wants to refuse has an answer for every event.
- **Copy Claude Code's numbers.** Its defaults are 600s for a command hook and 30s for a prompt hook, tightened to 10s on message display. Those suit a script on the user's own machine; two seconds in front of every prompt is the most a third party should be able to cost someone typing.
- **Keep the budget stopped for `argo` calls,** as it is today. Rejected: every call a hook makes has its own 30-second deadline, so the stated two seconds in front of a prompt is unbounded in practice, and the number means nothing.
- **Fail closed on timeout,** refusing the action when a hook does not answer. Rejected: a crashed or slow Plugin would stop the user working, and Claude Code's own guidance is not to count on a stalled hook to act as a gate.
