# A local Server owns all machine work, and Apps connect to it directly

The phone, the web app, and the desktop app must have the same abilities ([ADR-0022](0022-server-device-and-paired-devices.md), proposed, amends this: a short list of actions works only on the Server Device, owner, 2026-10-12). So the local Server owns Sessions, Agents, git, worktrees, and storage. Its deployable Supervisor and process startup live in `apps/server`; the reusable Engine implementation and domain work live in `packages/engine` (owner, 2026-10-09). Electron's main process does none of this work.

Every App connects to the Server over one WebSocket carrying every tRPC call (`wsLink`, `ws` with `applyWSSHandler`, Zod, no superjson). The one exception is file upload: tRPC accepts a file only over HTTP, so a client's `splitLink` sends a call whose input is a file through `httpLink` to the same router, served by tRPC's `createHTTPHandler` on the same `node:http` server. A one-shot upload has no reconnect path. Plain HTTP serves only `GET /blobs/:id`, because an image needs a URL that returns its bytes. There is no HTTP framework (owner, 2026-10-03; this replaces Hono). The Electron renderer connects like the phone, with no tRPC over Electron IPC; the preload script gives it only the Server address and window controls.

The Server owns the only database: SQLite at `~/.argo/argo.db`, through Drizzle on `node:sqlite`, following Argo ADR-0043 (SQLite owns per-machine state). Apps keep no local database; the TanStack Query cache is enough.

The Engine machine composes its child actors and owns their lifecycles, starting and stopping a sync supervisor beside the open Sessions actor and the shared database Writer. Catalog validation, fetching defaults and read projection belong to Agents, not the Engine machine or HTTP context. tRPC sends sync requests directly to the supervisor, which schedules work and invokes a supplied promise actor. The catalog actor fetches and validates the complete Registry; the supervisor submits the accepted result to the Writer. Source-specific fetching and record replacement stay concrete, with no shared pagination framework (Spec 0009 #361 review amendment, owner, 2026-10-09).

SQLite stores one sync job per source and scope, with current status and latest outcome. An Agents page visit or explicit Refresh requests the catalog job; repeated requests share pending or running work. The mutation acknowledges durable admission without waiting for the fetch. On startup the supervisor resumes pending or running catalog work and otherwise does not fetch the catalog. Queries read catalog rows and job status from SQLite; Writer commit notifications invalidate them, and the App keeps cached results visible and derives refresh progress from the saved job status. Search uses the Agents rows locally and treats search text as a literal substring.

The existing Writer performs every live catalog, Session, Feed and Blob metadata write. A successful catalog replacement and its job completion commit in one transaction; fetching holds no SQL transaction. Catalog sync owns Registry identity, accepted metadata, presence, search text and sync time. Removed entries stay as absent rows with their local identity and last accepted metadata. Transient fetch failures get bounded retries; invalid Registry data fails immediately. A failed fetch preserves the last good catalog and records an error. Sync writes wait through the Writer’s existing retry cycle, and a rolled-back write is not reported as completed. Disconnecting an App does not cancel admitted work. Shutdown stops supervisor admission, aborts fetching and drains the Writer before closing SQLite; unfinished durable jobs resume on the next startup. Blob bytes remain files, and metadata is acknowledged only after its Writer receipt. Browsing does not launch Agents or create Sessions.

`agents` is the durable read model for catalog and local Agent facts. Registration (#362) extends the same rows with local definitions, non-secret configuration and installation observations; catalog sync does not implement those. Credentials stay upstream, and a stored installation observation is not permanent readiness. The direct Agents creation migration uses the existing database connection and migration transaction, leaving existing main migrations and Session/Turn/Feed history intact.

For now the Server binds to `127.0.0.1` only, without authentication. It checks `Host` on every request, and `Origin` on the WebSocket and on tRPC over HTTP, so a website in a browser on the same machine cannot call it (owner, 2026-10-03). Pairing a real phone and authentication come later, with their own ADR.

## Considered Options

- Run the Server inside the Electron main process. Rejected: the phone cannot use it when desktop is closed, and Argo's current tRPC-over-IPC bridge is the code we want to remove.
- A custom JSON protocol over WebSocket, as Paseo does. Rejected: tRPC gives typed procedures and TanStack Query hooks for free.
- HTTP for queries and WebSocket only for subscriptions. Rejected: two transports means two reconnect paths.
- Uploads as base64 over the WebSocket. Rejected: a third larger, and a big image holds up the socket that streams the Feed.
- Hono for the plain HTTP routes. Replaced on 2026-10-03: once `/health` became a tRPC query, one blob route needed no framework.
