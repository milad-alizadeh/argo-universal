# One shape for a story

Storybook had no contract for what a story is. Three authoring models grew side by side — a hand-built gallery behind one story, one story per state, and hybrids that drew states twice — and each new file was a fresh guess. Spec 0021 (#1193) gives a story one shape, derived from where the component lives and from what the component branches on, so an agent can write one without inventing a value and a reviewer can deep-link to any single state. It builds on [ADR-0021](0021-storybook-renders-views-from-props.md), which owns Storybook's data boundary and is unchanged.

The shape is shown in [`docs/agents/storybook-template.md`](../agents/storybook-template.md) and written by `pnpm new:story <component-path>`.

## Decision

1. **A title is derived from the path, never written freehand.** The folder gives the root and the category, the file gives the name. The title stays a literal in the file, checked against the path. A test file's title is `Tests/` followed by its subject's whole title, with a segment the subject already says said once, so a component's tests hang off the component instead of a flat shadow tree.
2. **One title per file.** No two files share a sidebar node, so a story id is never decided by which file Storybook loaded first.
3. **One depth per root.** Every kit primitive is `Design System/Primitives/<Category>/<Name>`, four segments, with no primitive skipping its category, and every primitive has its own folder under its category so the path gives those four. The kit's other root is `Design System/Foundations/<Topic>`, three segments, for a token scale no component owns — the tone ramp, the spacing scale — written as `foundations/<topic>/`. The kit has no third root. Beside them, `packages/client/src/lib/product/` is `Design System/Patterns/<Name>`: a reader is told what a thing is, not which package draws it.
4. **A prop value earns a story when the component branches on it; otherwise it is an arg.** A story is one state the component can be in, not one value a prop can take. A component branches on a value when the value is a key in its `cva` or `tailwind-variants` map, a case in a conditional, or a platform fork. Everything else is an arg, and Controls covers it. The Docs page, which renders every story of a component above its props table, is the overview; there is no hand-built gallery.
   - **One story per branch, not per combination.** `disabled` is a story and `loading` is a story; `disabled` with `loading` is not, unless the component has a rule for the pair. Button has one such rule — a destructive button is transparent whatever its variant — and that pair earns its story. Nothing else does.
   - **If you would name it after the prop, it is an arg.** `WithIcon`, `SizeSm`, `VariantSecondary` and `FullWidthTrue` are not states. `Destructive`, `Loading`, `Compact` and `TooManyFiles` are. A name that happens to match a branch prop is not itself the fault: `Selected`, `Expanded` and `Disabled` name what the component looks like, and the prop that causes the look is named the same because the look is what the prop is for. It is the prop-shaped wrapper — `With`, `Without`, `True`, `False` — that never names a state.
   - **It barely shrinks a primitive.** Button has about thirteen branches and keeps about thirteen stories; what it gains is thirteen story ids and thirteen diffable snapshots in place of one untyped array. The shrinking happens at parents, which have few branches of their own.
5. **A child's states are exported fixtures, and a parent imports them.** A child exports each of its states as a named props fixture beside its story file. A parent story passes `args: { check: failingCheck }`, imported from the child, and never re-specifies inline what "failing" means. A parent earns a story for a child's state only when that state changes the parent's own composition — a row wraps, a column overflows, the empty state swaps, the layout reflows. If the parent is identical everywhere except inside the child's own box, the state belongs to the child.
6. **`argTypes`, or args typed by a literal union, wherever `component:` is set.** A kit component takes `kitArgTypes('<Name>')` from its Contracts schema; any other component lists the values its props can take. This is the enumerated prop domain an author picks values from.
7. **A story file varies only props its own component declares.** A parent that wants a child in another state passes the child's fixture through its own prop; it does not reach into the child. This is the whole of what the repo takes from atomic design.
8. **The sidebar has a fixed order,** set once in Storybook's preview, so the tree does not reshuffle when a file lands.
9. **If the Server needs to know it, it is a Contract; if it is only how it looks, it is the kit.** A kit component's props have one definition, its schema in `packages/contracts/src/plugins/`, which also names its `group`, and its drawing is the folder of the same name in `@repo/kit`, in that group. A `variant` union is a Contract, because `prepareSlotTree` validates what a Plugin sends against it; "a destructive button is transparent" is the kit's. The two halves pair by name and by that group, so an author handed `primitives/actions/button/` finds the `Button` definition with `group: 'actions'`, and `tools/check-kit-pairing.mts` fails when either exists without the other. Compound names (`List.Section`) pair through their parent. A folder with no schema is exempt only by a named entry with a reason in `tools/kit-pairing-rules.mts`.
10. **A fixture lives beside the component whose state it names.** A component exports its states from `<component>-fixtures.ts` in its own folder — under `packages/kit/src/primitives/**` for a kit primitive, beside the component in `packages/client/src/**` otherwise — one export per story, named for the story in the words of `GLOSSARY.md`: `neutralPill`, `runningSession`. Each holds the complete props of that state, so the component's own story is `args: neutralPill` and a parent passes the same object through its own prop. Callback spies stay in the story file, which keeps a fixture plain data. A fixtures file is story material, so the kit's import boundary exempts it as it exempts a story, and a fixture may draw on the shared mocks a story draws on. `@repo/kit/mocks` and `@repo/client/mocks` keep only a fixture two unrelated features both need; this narrows the rule in [`docs/agents/storybook.md`](../agents/storybook.md) rather than replacing it. Feed props keep the route the data boundary already gives them: a recording through the real converter, whose output is the fixture ([ADR-0021](0021-storybook-renders-views-from-props.md)).

## Considered options

- **Storybook autotitle,** deriving the title at build time and deleting it from the file. Rejected: autotitle moves a story's id on every file move, and `@repo/client/mocks` and the Vitest runner resolve stories by id. A literal title checked against the path keeps ids stable and still cannot drift.
- **"One story per meaningful state."** Rejected: "meaningful" is a judgement word, and judgement is how the three models grew. Branching on a value is decidable from the component's own source; `pnpm new:story` reads it.
- **Keep one hoisted gallery story as a narrow exception.** Rejected: that exception is what grew the hybrid files, which draw a state once in the grid and again on its own. Autodocs gives the same whole-component reading with an id, a snapshot and an args table per state.
- **Let a parent enumerate a child's states when it is convenient.** Rejected: a screen with `ChecksRunning`, `ChecksFailing` and `ChecksPassed` re-draws one child's enum three times, and its definition of each state drifts from the child's. An imported fixture has one definition.
- **Atom, molecule and organism folders.** Rejected: Brad Frost calls the split a mental model and its labels optional, and Primer, Carbon and Chakra stay flat under a few fixed roots. The dependency rule (7) is the part worth keeping.
- **Order the sidebar by glob.** Rejected: glob order changes whenever a file lands, so a reader's place in the tree moves under them.

## Consequences

- `pnpm new:story` writes a story file from the component's folder: the derived title, `component:`, `argTypes`, required args as placeholders, and one story per value in its variants maps, named for the value. Props with no branch stay meta args. It does not invent combinations: a pair story is the author's call, and so is a branch it cannot see, such as a conditional or a lookup table keyed by a prop.
- A state has one definition: the fixture the child exports. A parent that draws a child's state imports it, so the two cannot drift, and an author handed a component has its states to pick from instead of a shape to invent.
- Galleries are replaced by per-state stories, and checks enforce the rest. `pnpm quality:lint` runs the ones that read a file: `tools/check-story-titles.mts` for (1), (2) and (3); `tools/check-story-gates.mts` for (4), (5), (6) and (7); `tools/check-kit-pairing.mts` for (9). `pnpm verify` runs none of them — [`docs/agents/hooks.md`](../agents/hooks.md) says what it does run.
- The two checks that need a drawing run in their own CI job, because they draw every story and hold the browser-suite lock: a duplicate drawing inside one file, and a parent story that is a child's state in disguise, which masks the child's box and compares what is left. Both compare drawings for equality, so a story that moves on its own — a live clock, a running progress ring — can only hide a finding, never invent one.
- The gates read what a file says, not what its author meant, so each stops short of one thing. The `argTypes` gate is satisfied by a props table with no drivable Control, which is all a view whose whole state is one loaded-union object can offer. The gate on (7) finds almost nothing, because `satisfies Meta<typeof X>` already refuses an args key the component does not declare; it guards the file that drops `satisfies`. And a state fixture spread into a meta's args reaches every story in the file without any gate seeing it, because a spread names no key.
