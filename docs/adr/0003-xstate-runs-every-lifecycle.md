# XState runs every lifecycle, and the Server address lives in a file

XState machines own business lifecycle state, waiting and cancellation: the Server (the Supervisor, the Engine, Sessions, and the Feed writer) and the Electron main process (owner, 2026-10-03). The client runs no machines: an App's Connection and New Session are plain hooks and stores (#709). Each Session owns its Turn lifecycle and one ACP session lease. Engine owns the shared ACP process and connection; there is no separate Agent business lifecycle machine (owner, 2026-10-09, Spec 0009 and ADR-0015). The connection module manages SDK startup, identity routing and callback drains inside finite operations these machines invoke. Everything else stays outside machines: pure functions transform data, Zod holds shapes, and TanStack Query holds an App's copy of Server data.

Session waits for ACP close before Feed flush or an unstored Checkout discard. It closes and records its Shells first, outside the ACP deadline, because an Agent waiting on a Shell may not answer `session/close` (owner, 2026-10-16). Optional protocol close and callback drain share one five-second deadline. On error or timeout, the Server logs the failure and releases the Session. Close does not kill the Agent process or retain the Session until process exit (owner, 2026-10-15, #717). App disconnection changes no ownership.

Machines are small and run as actors that send each other events, so `xstate/graph` can walk every transition of each one. Machine state is never saved; the database is the only record (ADR 0005), so after an Engine restart each Session starts as `idle`, and a running Turn ends with the stop reason `error`.

The Supervisor is an XState machine in `apps/server`, beside the Engine process bootstrap; the Engine lives in `packages/engine` (owner, 2026-10-09). Its states are `starting`, `running`, `backingOff`, `failed`, `blocked`, and `stopping`. It restarts the Engine after a missed heartbeat, with capped exponential backoff. The Engine leads its own POSIX process group, and is replaced only after the Supervisor has killed that group and observed that no member remains, because an abruptly dead Engine cannot clean up its Agent processes (Spec 0009 #355). When release cannot be verified, including on platforms without process groups, the Supervisor enters `blocked` and exits non-zero rather than start a second Engine beside a possible survivor. A descendant that leaves the group, for example with `setsid`, is not contained. The Engine is a machine too: it opens the database, serves, sends the heartbeat, and stops on a signal, with an exit code as its output. Electron only ensures a Supervisor runs: it reuses a running one, starts one when none runs, and on quit stops only one it started (owner, 2026-10-03). When that Supervisor runs Sessions with a running Turn, Electron first asks whether to keep them going, and Keep quits without stopping it (owner, 2026-10-03). Only the Supervisor watches and repairs the Engine. Electron reuses a Supervisor of any version until release packaging adds a version check, and a setting may later keep the Supervisor running after every quit.

Shells use separate POSIX process groups (owner, 2026-10-16, #89). A wrapper remains the group leader after the command exits, so reparented descendants remain reachable. Before a command starts, the Engine records the wrapper pid and a unique token in its runtime directory. Command exit, Stop, Session close and archive kill the group and verify that no live member remains. Loss of the Engine IPC connection also kills the group. Before it reports the Engine released, the Supervisor also releases recorded Shell groups. Before a replacement Engine serves, recovery repeats this check and verifies group removal. A changed ownership identity or unresolved group prevents startup; recovery never signals an unrelated group. A descendant that leaves its Shell group is not contained; once the group is gone, it holds the Shell's output open for at most one second, so Shell close stays bounded (owner, 2026-10-16). This extends the Engine-group rule above for general Shells; sign-in terminals retain their separate ownership path.

The Supervisor atomically writes `~/.argo/server.json` with `{pid, port, version, startedAt}`. PID and port are runtime facts, so they stay out of SQLite: Electron finds the Server without the database package, and a crash leaves no stale row. Finding the Server never needs the database; only a quit with no live answer reads the keep-running setting from `argo.db`, read-only, and a failed read stops the Supervisor.

## Considered Options

- No Supervisor, Electron starts the Server directly. Rejected by the owner: the lifecycle must be an explicit machine from the start.
- PIDs in SQLite. Rejected for the reasons above.
- Machines on the Server only, with React state in Apps. Replaced by the owner on 2026-10-03: the Connection and Electron's Server lifecycle had the same waiting, timers, and retries as the Server's lifecycles.
- Saving machine snapshots across restarts. Rejected: a second record of a Session that can disagree with the database.
