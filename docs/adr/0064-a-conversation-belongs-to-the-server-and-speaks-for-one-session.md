# A Conversation belongs to the Server and speaks for one Session

Owner-approved decision, 2026-11-18, reached in a grilling Session after two spikes against the live service. The pipeline evidence is in [`docs/research/voice-mode.md`](../research/voice-mode.md), section 13.

Renamed by the owner, 2026-11-20: the feature was called a "Voice call" and is now a **Conversation**, and a **Voice** is only one voice a Conversation speaks with. The words changed; no decision did. The file was `0064-a-voice-call-belongs-to-the-server-and-speaks-for-one-session.md`. The Operations of the exchange are now `conversation.*`; those of one voice, such as `voice.setVoice` and `voice.preview`, keep `voice.*`.

A person can talk to a Session instead of typing. A Conversation is attached to one Session on any Agent. A voice model hears the person and speaks back; when the person asks for work, the Server sends it to the Session's Agent as a Prompt and tells the voice what the Agent answered. The Server owns the Conversation and the App only carries sound, so one design serves every Agent and every Conversation provider.

## Decision

- **The Engine owns the Conversation.** Its lifecycle is one XState machine in the Engine (ADR-0003). The Engine holds the Conversation provider's control link, receives what the person asked for, and sends replies back. A Conversation ends when the person ends it, when the Agent ends it, after an idle stretch, when its Session closes or is archived, when the App quits, when the Engine restarts, and when the control link is lost for more than a few seconds.
- **The App carries only sound.** It captures the microphone, plays the voice, and draws the Conversation. Audio travels straight between the App and the Conversation provider; the Engine relays only the connection offer and answer. The Engine receives raw audio on the control link as a side effect and discards it. Audio is never written anywhere.
- **A Conversation is attached to one Session.** It stays with that Session when the person looks at another one. One Conversation runs per App. The Session's Agent already has Argo's Operations, so it can start, prompt and watch other Sessions with no voice-specific work.
- **Conversation providers sit behind one interface.** A provider starts a Conversation from an offer, reports what the person and the voice said, reports each request for work, accepts text to speak or to keep as background, and ends the Conversation. The interface names no vendor; only the provider module does.
- **A request for work is a Prompt sent by the Conversation.** The Conversation is a Prompt sender (ADR-0012). The Prompt goes through the Server's prompt queue (ADR-0054) like any other: it steers a running Turn when the Agent supports that, and otherwise waits its turn. Because Argo sent the Prompt, the Turn has a start, a user side and a stop reason like every other Turn.
- **The Feed is the transcript of the person and the voice, plus the Agent's work.** What the person said and what the voice said in its own words are stored as Feed rows; the voice's Read-out of an Agent's result is not (amended below). The Agent's Turn is drawn as usual. The text passed between the voice and the Agent is stored and never drawn.
- **The Session is the Conversation's memory.** A Conversation keeps nothing between Conversations. A new Conversation is briefed from the Session's title, working folder and recent Feed, which includes the earlier Conversation's transcript.
- **Every Agent is told how to answer a voice.** The first Prompt of each Conversation carries an instruction to mark each message as progress, as a result, or as silent analysis. The Feed strips the marks, and drops silent analysis whole (amended below). An unmarked message counts as progress until the Turn ends.
- **Spoken consent is the person's own.** The voice announces a Permission request in plain words from the request's title, kind and target. The person's spoken allow-once or reject is applied through the same path a click uses (ADR-0044), and only when a spoken turn of the person's arrived after the announcement. Always-allow stays a click. Saying "stop" cancels the Turn.
- **GPT-Live is the first Conversation provider and runs on the ChatGPT subscription.** The Engine asks the installed Codex for a ChatGPT token, holds it in memory for the length of a Conversation, never stores it and never refreshes it (ADR-0004). The provider is usable only when Codex is installed and signed in. It uses a private ChatGPT endpoint, so Settings labels it experimental.
- **Desktop first.** The first version runs in the desktop App only. Mobile needs a native audio module and its own drawing of the Conversation.

## Considered options

- **Let Codex's app-server run the Conversation, on a socket shared with the Codex adapter.** Spiked and working, but it serves Codex Sessions only, and a Turn the voice starts reaches ACP with no start, no stop reason and no user side. Rejected for the direct route, which costs about the same and serves every Agent.
- **A hidden Codex Session that coordinates other Sessions through Operations.** Works with what was already proven, but every request takes two hops, spends Codex tokens on relaying, and the voice never talks to the Session on screen. Kept only as the fallback if the private endpoint closes.
- **The public OpenAI Realtime API.** Documented and stable, but it bills an API key, against ADR-0004's subscription rule. It stays available as a later Conversation provider.
- **An app-wide voice assistant attached to no Session.** Rejected for the first version: the Composer button implies the Session in front of the person, and a second kind of target can be added later without changing the provider interface.
- **An Operation that answers a Permission request.** Rejected: any Agent, and anything holding the control token, could then approve an Agent's own request. ADR-0044's exception for consent stands.
- **Argo's own OAuth sign-in to ChatGPT.** Rejected: OpenAI registers no third-party client, so Argo would present Codex's client id, and two refreshers of one rotating token sign each other out.

## Consequences

- The private endpoint can change without notice, and its use from a client other than OpenAI's may be against OpenAI's terms. The owner accepted this. A breakage shows as GPT-Live being unavailable, never as a broken Session.
- The voice hands over work only while the Engine holds the control link. If the link drops and the Conversation continues, the voice keeps saying it is working while nothing happens. Ending the Conversation on a lost link is therefore a rule, not a nicety.
- A person with a Claude Session and GPT-Live spends two subscriptions: voice on ChatGPT, work on Claude.
- The Engine handles the person's voice in passing even though it stores none of it.

## The Agent's answer is the record, so the Read-out is not stored

Owner amendment, 2026-11-19. On live Conversations the Agent's answer showed twice: once as the Agent's message, and again as the voice saying it in its own words, first as live words at the Feed's tail and then as a stored row. Silent analysis also showed in the Agent's message, and the voice was told it.

- **A Read-out is never a Feed row.** When the Engine hands the voice an Agent's result to speak, what the voice says next, until the person speaks again, is a Read-out: it is neither stored nor drawn as live words. The Agent's message is the record and the Read-out only repeats it. The person's words, the voice's own replies, and the voice turn already under way at the hand-over, such as its filler line, stay rows.
- **Silent analysis is dropped whole.** A section marked as analysis, up to the next mark, is left out of the Agent's message wherever it is read, and the voice is never told it. The instruction already says analysis must stay silent; telling the voice in the background broke that.
- **Hanging up keeps what was said.** Words the voice or the person had said when the Conversation ended are stored like any others, unless they are a Read-out.

## Custom voices and instructions, open to Agents and the CLI

Owner amendment, 2026-11-19 (#2469). The Conversation's Operations stay App-only, with these exceptions beside `conversation.hangUp`: `conversation.getSettings`, `voice.listVoices`, `voice.setVoice`, `voice.saveCustomVoice`, `voice.deleteCustomVoice`, `conversation.setInstructions`, `conversation.setOptions`, `conversation.listDevices` and `conversation.chooseDevices`. Agents and the CLI run them like any other settings change: reading is `read`, changing is `confirm`. They grant nothing, and change only what the next Conversation speaks with and is told, except volume and microphone gain (below). Starting, ending and previewing a Conversation, reading its status, turning Conversations on or off and choosing the Conversation provider stay the App's.

- **A custom voice is a built-in voice plus a description.** GPT-Live cannot make a voice from a description; it has a fixed set of voices. A custom voice is therefore a name, one of the provider's built-in voices, and a description of how it speaks, which is sent with the Conversation's instructions.
- **Argo's own instructions always come first.** A Conversation is told Argo's fixed instructions, then the custom voice's description, then the person's custom instructions, then the Session's briefing. Nothing the person writes comes before Argo's words.
- **Settings are kept on the Server.** Custom voices, custom instructions and the chosen voice live in the Server's settings, so every Device reads the same values.
- **A change applies from the next Conversation.** GPT-Live refuses new instructions on a running Conversation: a `session.update` sent on the control link is answered with `immutable_field_update`, "Instructions cannot be updated after initialization" (live probe, 2026-11-19, #2469). Codex never sends one on a WebRTC Conversation either. So the voice, a custom voice and the instructions are read when a Conversation is created.
- **Conversation options are Argo's, unless the service honours them.** `conversation.setOptions` keeps the filler words, an opening note, the idle timeout, the volume and the microphone gain. Only two go to GPT-Live: the filler words (`delegation.ack_filler`) and the opening note (a developer item in `initial_items`), both proven on the live service. Other session fields we probed, such as noise reduction, turn detection and text output, break the Conversation, so Argo does not offer them.
- **Volume and microphone gain reach a running Conversation at once.** The App applies them to its own sound, so they travel in the Conversation status every App already watches, and a change from an Agent or the CLI is heard without a new Conversation. Everything else in the Conversation options applies from the next Conversation.
- **Microphone and speaker stay each Device's own.** A Device keeps its own choice, since another Device has other microphones and speakers. Each App that can carry a Conversation reports its microphones, speakers and choice to the Server over its own Connection (the `conversation.devices` stream, App plumbing like `navigation.requests`), and subscribes again when they change. `conversation.listDevices` and `conversation.chooseDevices` act on one App: the one carrying the running Conversation, else the one that started the last Conversation, else the one that connected last. The Server pushes the choice to that App, which keeps it as if chosen in Settings › Conversation; a running Conversation moves to it at once.

## A voice's greeting is recorded once and replayed

Owner amendment, 2026-11-19. A preview opens a provider call, so each tap in Settings › Conversation took several seconds, and a second tap while one loaded missed. The provider seam is unchanged: the Engine still relays only the offer and the answer, and still never hears a Conversation.

- **Preview clips are the one case where the App hands audio to the Server.** The first preview of a voice plays live as before. The App records the voice's side of that Conversation once the greeting has been said whole, and uploads it with `voice.storePreviewClip`. The Server stores it, for replay only. No Conversation, no microphone and no speech of the person is ever recorded or sent.
- **The App replays it, the Server does not play it.** Before a preview the App asks `voice.getPreviewClip`. A stored clip plays on the App's own speaker with no provider call; with none stored, the preview plays live and is recorded.
- **A clip is kept by what changes how it sounds.** The key is the Conversation provider's id, the built-in voice, the custom voice's description and the name it greets with. Editing a custom voice's name or description, or choosing another provider, asks for a new clip. Old clips are not deleted; they are only unused.
- **A clip is whole or not kept.** A preview let go of early, a recording that fails and an upload that fails keep nothing, so the next tap records again.
- **Stored in the Server's home.** One file per clip under `voice-previews`, written whole or not at all. The Operations are App-only.
- **Phones.** Only a browser or Electron page carries Conversation audio today, so only it records. A native App has no Conversation connection, and so no preview.

## Argo reads a Spoken answer; the voice sends no reply form

Owner amendment, 2026-11-20 (#2412), after the third spike against the live service (#2406, [`docs/research/voice-mode.md`](../research/voice-mode.md) section 14). The design asked the voice to send a fixed reply form bound to one Permission request. It cannot: in 19 hand-overs the voice never sent a form. Each hand-over was the person's turn transcript, word for word, naming that turn in `user_bidi_turn_id`, and GPT-Live offers no tool channel. Spoken consent stays the person's own, and Argo now reads the answer instead of the voice.

- **The voice is told the request in plain words.** The Agent's name, what kind of thing it asks to do, its title and what it acts on (a command, a file, or an Argo Operation's id), then: ask the person "allow once, or reject?" and hand over their answer in their own words. The request itself, its options and its ids never reach the voice.
- **A hand-over answers the request only when all of these hold.** Its words read as an answer. It names a turn of the person's whose words first arrived after the announcement. That turn's final words arrive within about a second, since they land 41 to 434 ms after the hand-over, and they read as an answer too. The announced request still waits. Anything else applies nothing, the request stays open, and the voice is told so and asks again.
- **Argo owns the words.** An answer is an utterance made only of answer words: allow words such as "allow", "yes" and "go ahead"; reject words such as "reject", "deny" and "no"; and filler such as "it", "that", "once" and "please". Any negation ("no", "don't", "not") makes it a reject, never an allow, so "Don't allow it" rejects. "Always" asks for always-allow, which is still only a click; the voice is told so and nothing is applied. Words that are not an answer are a request for work, as before.
- **Applied as a click is.** The Engine picks the waiting request's option of that kind and applies it through the same hand-written procedure as `session.answerPermission`. It is not an Operation, so ADR-0044's consent exception and the Operation mutation gate are unchanged. An Agent that offers no allow-once or reject option leaves the request to the screen.
- **The voice repeats Argo's outcome.** The reply says what was applied ("Allowed once: …", "Rejected: …") or that nothing was. A request settled by a click before the spoken answer lands is answered "Nothing was applied". A settled request can be named this way for five seconds only; after that, or once its Turn ends, a "yes" is a request for work again. A spoken answer still waiting for the person's final words when the call ends applies nothing.
- **"Stop" is unchanged.** A hand-over that only asks to stop cancels the running Turn and any request it waits on, and the call goes on. A lone "Stop." is often not handed over at all, because the voice takes it as an interruption; the Composer's Stop button covers that case.

## Screen sight (#2473)

Owner spec, 2026-11-19. An Agent and the voice can see the person's whole screen as one still picture. Owner amendment, 2026-11-20: no permission prompt. Nothing asks the person before a capture, not a Permission request, not a spoken ask and not the system's display picker; the safeguards are the Device switch, which is off until the person turns it on, the one Notice shown for each attempt, and that the picture is never kept.

- **The Voice provider interface gains one optional capability: send an image.** A call that can carries `look`, which gives the voice one still frame as background it may look at, never as something to say. The call tells the Engine when it answers whether it has `look`. A call without it changes nothing else: the Engine takes no picture for it, and Agents still see the screen through the Operation.
- **The voice asks for a frame through the request-for-work path.** A `frame.requested` event reaches the call's relay as a `work.requested` does, and the call's relay answers it. The Engine asks the App, then hands the image to the provider.
- **The Operation `app.screenshot` is `act`.** An Agent calls it with no Permission request, as does the person. It answers `captured` with the image, `refused` (`off`), `not_opened` or `not_available`, and never claims a picture it did not take.
- **The Server asks the one desktop App on the Server Device.** The App tells the desktop main process each change of its Device preference, off by default and reported again at startup, and main answers `refused` with `off` to every capture until it is told yes, so no caller of the preload can skip the switch and turning it on or off needs no new subscription. The desktop App takes the picture of the main display itself, through its preload, with no picker, and owns the words about system permission; it answers each capture request over its own Connection; only the Connection that was asked can answer. With no such App the answer is `not_opened`. A browser share-prompt fallback was removed: the web has no capture path, because the Server asks only the desktop App.
- **The picture is never stored and never drawn in the Feed.** An Agent's Tool call settles as `captured` without the image; the image reaches the Agent as an image through its MCP result, and reaches the voice through `look`. The Feed gets one Notice that a capture was taken, and by whom.
- **GPT-Live reports that it cannot send an image** until a still frame is sent on a live call and the voice describes it (`docs/research/voice-mode.md`, section 15). Until then this ships as the Operation alone for Agents.
