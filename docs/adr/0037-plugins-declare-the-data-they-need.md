# Plugins declare the data they need

This amends [ADR-0025](0025-plugins-run-on-the-server-and-draw-argo-components.md), [ADR-0027](0027-plugins-act-through-one-api-hook-core-and-replace-named-components.md) and [ADR-0035](0035-plugins-add-to-named-slots-and-never-edit-core-screens.md), and builds on [ADR-0036](0036-plugins-own-sign-in-and-argo-brokers-their-accounts.md) (owner, 2026-10-20). Everything a Plugin contributes is declared: its nav items, its Settings schema, its Slots, its Hooks, its Capabilities and its Accounts. Fetching was the one thing left imperative, and it is the first thing every Plugin author touches. Left alone, each of them writes their own timer, their own cleanup and their own cache, twenty Session rows make twenty requests, and nothing connects the data a background pass warmed to the widget that wants to draw it. The bar is that anyone can extend Argo with a few simple prompts, so the easy path has to be the correct one.

## Decision

- **A Query is a described call, not a written one.** `useData(query, { every })` takes a value, and Argo performs it, so Argo owns the clock, the in-flight call and the result. Nothing is HTTP-only: the first GitHub Plugin reaches the forge through `gh`, and a GraphQL service reads with a POST, so there is no rule about methods — Argo cannot tell a read from a write by verb.
- **A Query is a read, and only a read.** It is its own union in Contracts beside the Plugin API's own calls, built from the same member schemas so a call's fields have one definition: a fetch, a process `run`, and a storage read. Writes are not describable, because a declared Query is a read Argo may repeat on a timer — files, secrets, settings, Projects, assets, spawning or killing a process and running arbitrary SQL are not members. A new call does not become describable until someone adds it here, and the member itself is one line; answering for it is not. Adding an api means saying what it answers with (`QueryResults`), how it reaches its normal form, how it reads its reply, whether it can time out, and how it reaches the Server — around a dozen sites across Contracts, the Engine and the kit. Each one is a type error until it is answered, so the cost is visible rather than silent.
- **The Query is the key.** Argo hashes the normalised Query; there is no key field to get wrong. The entry is keyed by the Plugin, the Project and that hash, because the Account a borrow resolves to is a property of the Project (ADR-0036) and a process runs in the Project's folder — two Projects describing the same call are two entries. Two Slots in one Project that describe the same call share one call, and a background pass that describes it fills the same entry. Raycast's `useFetch` hashes a request the same way.
- **The hook returns `{ data, error, stale, refresh }`.** `data` is the call's own answer and keeps its last successful value; `error` is set only when the call could not be made at all — a refused Capability, a borrow that resolved to nothing, a transport failure, Argo's own timeout — and a 401 on a borrowed Account is a result the Plugin reads, not an error. `stale` is true while a refresh runs over data already on screen. No ladder of loading flags. `refresh()` marks the entry due now and runs it, joining a call already in flight; it exists because a Plugin that writes knows its own list is wrong before Argo does, and without it the first author folds a counter into the Query and breaks both dedup and the warm path.
- **Mounted is live, background is warm.** While a Plugin's tree is on screen its Queries refresh on `every`; when the last viewer leaves, Argo stops. A registration belongs to the view that made it, not to the worker, so a crashed, reloaded or disabled Plugin releases every one of them and no timer outlives the page. There is no lifecycle API, because a Plugin page is a React component and leaving unmounts it.
- **A background pass is a headless mount, one per Project.** `contributes.background: { path, interval }` (Raycast's `no-view` plus `interval`) names one of the Plugin's own page paths. Argo activates the Plugin as opening a page does, mounts that path with no App and no viewer and with one registered Project's `projectId` in the view's context, discards the tree and unmounts it — so a background Query and a mounted one are the same entry by construction, with no second query API. There is no global, Project-less pass: the Account a borrow resolves to is a property of the Project (ADR-0036) and a `process.run` Query runs in the Project's folder, so a pass with no Project could neither borrow, authenticate nor run a process, and would have nothing to do. Every `(Plugin, Project)` pair owns its own timer, and the five-minute floor is per pass; a Project registered later gets a pass, a Project removed releases its pass and its entries, and there is no recency or active-Project filter. It may set `argo.nav.badge(id, count)` on its own nav item. A nav item is one rail item for the whole Plugin and the call carries no Project, so the count a pass sets replaces the one before it: a Plugin that counts per Project keeps its own per-Project numbers (its SQLite is the natural place) and sets the total it wants shown. It never raises a Notification, because a Plugin that can wake the device at 3am for a changed label is not repairable by a per-Plugin setting. This is the one contribution that starts a Plugin without the user reaching for it, which is why its floor is the higher one.
- **Argo clamps the interval:** ten seconds for a mounted page, five minutes for a background pass, clamped silently with a line in the log rather than refused. The pass's `interval` is the pass's only clock and a Query's `every` is the page's; neither reads the other. A Plugin can still write its own timer around a direct call — the declared path is the easy path, not a cage.
- **The cache is in memory in the Engine.** A map per Plugin, written and read on the one thread that already owns every SQLite handle, so there is no second writer and no lock question. Restarting the Server refills it on the next pass. Accounts and Grants are not in it — those are stored, because signing in again after every restart defeats ADR-0036. The Plugin's own `plugin.db` keeps the Plugin's records and Argo never writes there (ADR-0025).
- **An ungranted Capability behaves the same as it does anywhere else.** Mounted, the first run waits and Argo asks, naming the Plugin and the host, exactly as a first borrow does (ADR-0036). In the background it is refused silently, `error` is set and Argo stops that Query's clock until the Plugin is next opened. A background pass can never raise a consent dialog the person did not go looking for.
- **A Session Slot's context is `{ sessionId, projectId, branch }`.** Not a pull request, not a check status: core does not know those exist, and the Plugin maps a branch to whatever its service calls one. What comes back is a wire tree of kit components, as from every other Slot, and that tree is the typing — there is no separate contribution shape to design — because Argo draws that row, not the Plugin (ADR-0035). The allowed children are exactly the ones `ListItem`'s `meta` slot already declares, `Label` and `Pill`, and Argo refuses the rest; a `Pill` is the kit's `{ text, tone, color? }`, with `tone` the `tones` enum Contracts already has. So a pull request number crosses as a `Label` and a CI state as a `Pill` with a tone, and core still models neither: `SessionInfo.pullRequest` stays `z.null()`. Slot ids are versioned, so a fourth fact that is genuinely core's would come with a new id rather than break the Plugins already drawing.
- **A Plugin that throws fails that view and nothing else.** The Slot draws nothing, as it already draws nothing before a tree arrives, and the App shows one toast per Plugin. Its other pages, Slots, Hooks and background pass keep running. Error logs and a debugging surface are out of scope for now.

## Considered options

- **Describe a call with the Plugin API's whole request union.** Rejected: that union nests every call under a `call` field and contains writes, so the examples would not parse and `useData` would be able to describe deleting a secret on a ten-second timer.
- **Re-export TanStack Query from the kit.** Rejected: it is a large third-party API that Argo would version and support forever, its focus and online managers read `window` and `navigator`, which a Plugin worker does not have, and dedup falls out of Argo doing the fetching anyway. If one helper is ever wanted, Raycast's `useCachedPromise` is the size to copy.
- **Leave authors to write `useEffect` and a timer.** Rejected: it is the one imperative hole in an otherwise declared system, and it breaks the warm path, because a hand-written effect and a background pass have no way to name the same data.
- **Give the cache its own SQLite file.** Rejected as premature. It buys only the first second after a Server restart, and costs a schema, migrations, a version check, eviction and an uninstall path. VS Code opens `state.vscdb` from one process with neither WAL nor a busy timeout and survives on that; when it let a second process share the file it began crashing on `SQLITE_BUSY`.
- **Receive webhooks instead of polling.** Rejected because no supported path exists to a machine with no public address. `gh webhook forward` is documented as not for production and allows one forwarder per repository at a time, so two Argo users on one repository collide; smee.io's public channels are unauthenticated; tunnels all want a daemon and an account. There is no pull-based alternative either: GitHub's GraphQL has no subscriptions and its Events API disclaims realtime at 30s to 6h. Polling is also what Codex and Claude Code do, which is why neither updates a pull request's status until you open the session.
- **Cache eviction, expiry and conditional requests now.** Rejected as optimisation ahead of an architecture. A conditional request returning 304 does not count against GitHub's primary rate limit and the limit is 5,000 an hour, so there is nothing yet to save.
